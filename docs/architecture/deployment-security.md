# Deployment Security

> Network exposure, owner authentication, deployment readiness, transport guidance, and request-volume controls. Last updated: 2026-10-26

## Security model

Huabu is a single-owner application. A Huabu-owned `IdentityService` resolves the caller before routes execute. It distinguishes owners, members (Bubble identity only), and unauthenticated callers. Under Bubble identity it also decides, per Workspace and Space, what each member may read and write; see [Workspace and Space access](#workspace-and-space-access). Conversations and agent execution remain Agenetes-owned. An explicit no-login deployment treats all callers as the owner; its operator must restrict access through a trusted network or an authenticated proxy.

The default `local` provider needs no directory or identity server. It supplies a stable synthetic `local-owner` principal. The owner may perform Settings, OAuth, credential, External Agent Profile and harness-discovery operations when any condition holds:

- Basic Auth is unconfigured and the credential-free request's direct TCP peer is loopback;
- the request passed Huabu's configured HTTP Basic Auth gate.
- login was explicitly disabled for this deployment.

The connection token is a separate high-privilege machine credential shared by the complete read/write RFS surface and the embedded or remote Agentlet control and relay transports. Its generation and injection are independent of browser owner authentication; possession grants both Agentlet attachment and Space data access. It resolves to the `huabu-agentlet` bot. In local mode it keeps the owner rule that applies to every local caller, owner over loopback or with login disabled; under Bubble identity it never has owner authority. The existing machine reachback surface remains available in both identity modes; public credential-free root Skill bootstrap and CORS preflights remain exempt from authentication.

There is no connection-token Settings API or hot-switch. Before attachment the Server fixes its token from non-empty `HUABU_CONNECTION_TOKEN` or an automatically generated SecretStore-backed managed token that survives restarts, ignoring but retaining historical Settings overrides. Owner-only `POST /api/acp/connection-command` is the deliberate reveal boundary: it validates the requested shell/format and derives the public origin from the effective canonical deployment origin, using the validated browser origin only as an unconfigured loopback-development fallback. It returns a source `pnpm start:daemon` command or private connection dotenv data with no-store headers for direct clipboard use. Copying makes the token available to the clipboard and later shell history/private env file, never Agentlet argv. HTTP derives insecure WS inside the launcher and is appropriate only on a trusted network; loopback commands remain available for same-host, Windows/WSL, container, virtual-machine, or forwarded setups and carry a warning. Explicitly resetting the managed token via setup requires restart and fresh commands; ordinary restart does not. Embedded attachment receives the active token automatically.

The global Agent Change Review configuration follows the same owner boundary. `GET` and `PUT /api/agent-change-review/config` are available only to requests resolved as owners by the selected identity provider; possession of the RFS connection token does not authorize reading or changing the automatic-acceptance policy.

The Utility Agent (external Profile or explicit Built-In Pi) and external functional-model preference follow the owner boundary through `GET` and `PUT /api/agent/defaults`. The recent conversational Agent is browser-local UI state, not a Server credential or authorization setting. Neither preference grants new tool permissions or changes native harness approval policy.

The optional personal Canary helper follows the same owner boundary for status, branch configuration, remote checks, and redeployment. Its persisted branch is a bounded Git ref name, not an executable input surface: the Server checks only the exact `refs/heads/<branch>` on fixed remote `origin`, launches one repository-owned runner without a shell, and supplies only the validated branch in a fixed argument position. Invalid, unavailable, stale, and concurrently changed values fail explicitly without falling back to `alpha`; see [Alpha Canary deployment](./canary-deployment.md).

Optional submission-time Ink OCR is an explicit outbound data boundary. Configuring an Azure AI Vision endpoint and key through Settings > Services or `VISION_ENDPOINT` / `VISION_KEY` opts the Server into sending a transient raster containing only the selected Ink strokes to that resource when the owner submits an Ink Query. Settings sends newly entered keys to the owner-authorized Server for secure storage; reads never return a plaintext key, and the browser never calls Azure directly. Both reads and writes at `/api/integrations/ink-ocr/config` require owner authorization. Only Azure AI Vision's Image Analysis Read protocol is supported. Successful OCR evidence persists both in the structured envelope at `AgentSubmission.content.focus.selection.inkRecognition` and in the canonical inputs at `AgentSubmission.rendered`. Normal provider diagnostics record only outcome, duration, HTTP status, raster dimensions, node count, and line count; they exclude credentials, endpoint values, image bytes, and recognized text.

Prompt debugging is a separate local retention surface: when enabled, it writes the assembled prompt, including OCR evidence subject to the diagnostic's text truncation. When `HUABU_DEBUG_PROMPT` is unset, it defaults to enabled outside production and disabled in production; an explicit value overrides that default. Set `HUABU_DEBUG_PROMPT=off` to disable these additional prompt logs. This does not disable normal conversation persistence or remove previously written data. Operators are responsible for the persisted conversation, local debug artifacts, and the configured Azure resource's data-processing and retention policy.

OCR settings validate HTTPS resource-root endpoints against the Azure public-cloud `cognitiveservices.azure.com` and regional `api.cognitive.microsoft.com` host forms, excluding arbitrary gateways, IP literals, non-default ports, and sovereign-cloud endpoints. The adapter applies the same validation to effective stored/environment configuration before sending a key and rejects redirects. The endpoint and key overrides are persisted as one encrypted SecretStore record with serialized updates, avoiding the partial-write state where a replacement key could be sent to a previous endpoint. All settings mutations require writable secure storage; read-only deployments may still use environment configuration. See [credential storage](./credential-storage.md) for migration and fallback semantics.

Owner-only `POST /api/acp/connection-credentials` is a second deliberate reveal boundary for the optional remote desktop local-Agent connection. It validates an empty JSON object and returns the same existing shared token plus the configured process limit with `Cache-Control: no-store` and `Pragma: no-cache`; it does not mint credentials or expand their privileges. Electron main requests it only for its configured Server through the authenticated network session, without redirects, after native local-execution consent. The renderer receives only connection state. Remote mode's separate device vault does not expose the local Server credential bridge or native filesystem picker. Explicit no-login deployments retain their existing trusted-network owner boundary; HTTPS alone does not add owner authentication.

## Bind and authentication policy

### Automatic initialization and setup

`pnpm start:web`, `pnpm dev`, and `pnpm dev:desktop` never prompt. A new local instance needs no `.env`: startup initializes credential storage, resolves saved deployment settings into a process-lifetime environment snapshot, validates deployment prerequisites, initializes the stable connection token, and only then composes/listens with the HTTP application. `deployment.json` in the private instance directory contains version 1 and `remoteAccess.enabled`, plus the optional `authentication` mode (`basic` or `none`), login `username`, canonical `publicOrigin`, and confirmed disk `workspacePath` when enabled. Missing `authentication` retains the legacy Basic Auth requirement. Passwords remain in SecretStore, not the JSON configuration or `.env`.

`pnpm run setup` is a terminal wizard on the hosting machine, including SSH-managed servers. It asks whether to enable network access, suggests non-internal IPv4 addresses with the actual configured Server port, requests an explicitly confirmed address, and collects a masked, non-empty password without control characters, with confirmation and no readline history. Setup imposes no password-length minimum beyond non-empty and no maximum, for either interactive or redirected input. The login username is customizable: Enter reuses the saved username or defaults to `owner`. Usernames are trimmed, must be non-empty, and cannot contain colons or control characters; one shared schema validates interactive input, automation, and persisted settings. Existing version-1 configurations without `username` continue to use `owner`. This is still one owner's Basic Auth credential pair, not a multi-user account system. HTTPS must already be provided externally. Interactive HTTP setup shows an unencrypted-transport warning without an additional trusted-network confirmation; automation still requires `--allow-http`. No unauthenticated HTTP setup route exists.

The root setup launcher silently builds the existing client-runtime prerequisite and reports captured build diagnostics on failure without starting the wizard. It preserves terminal and redirected-password input for the setup process and suppresses dotenv informational logs. The interactive wizard uses `@clack/prompts` for a compact connected flow: an introduction and stop-services reminder, keyboard-selectable confirmations, text inputs with defaults, masked password inputs, and a final effective-configuration summary with the next startup command. Completed answers collapse into short rows, validation errors stay at the current input, and cancelling any prompt exits without saving configuration. Remote access defaults to the saved mode, or No for a new instance, unless `HUABU_BIND_HOST` controls the mode; `--help` documents the full operating prerequisites. Styling supports terminals without color; non-interactive flags and `--password-stdin` retain plain output.

On subsequent runs, the saved address, Home, and username are prefilled as editable text, rather than displayed only as placeholders; Enter retains them. New instances prefill the corresponding suggested values. A saved password is never prefilled or revealed. When a password is already stored, `Change login password?` defaults to No and retains it without rewriting credentials; choosing Yes requests and confirms a replacement. First-time login still requires a password unless the environment manages the credential pair. Unreadable saved credentials fail explicitly rather than being treated as missing.

Remote setup asks `Require login?`, defaulting to the saved choice or Yes for a new instance. Choosing No skips username/password collection only after a separate default-No risk confirmation; declining or cancelling saves nothing. This option is available for private-network access and externally authenticated reverse proxies or tunnels, but Huabu does not verify those protections. `--no-login` is the explicit automation opt-out and cannot be combined with `--username` or `--password-stdin`. `HUABU_AUTH_MODE=none` manages the same choice through the environment; `basic` restores the login requirement. Invalid modes or `none` combined with any Basic Auth override fail explicitly. Complete environment credentials enable Basic Auth even when saved setup opted out, unless a conflicting explicit `none` is present. Setup retains inactive saved credentials rather than deleting them, and re-enabling login can reuse the retained password. CLI summaries, startup logs, Vite logs, and deployment readiness clearly report disabled login. The Agentlet connection token and Bearer-only RFS protection remain enabled.

Setup displays environment-managed fields at their corresponding steps and skips their inputs. The source is labelled `environment` because values may come from `.env`, the shell, or a deployment platform. `HUABU_BIND_HOST` fixes the access mode, `HUABU_PUBLIC_ORIGIN` fixes the address, `HUABU_WORKSPACE` fixes the disk Home, and a complete `HUABU_BASIC_AUTH_USER` / `HUABU_BASIC_AUTH_PASS` pair skips both credential prompts. An absent Home override falls back to the saved path; an explicitly empty, whitespace-only, or relative override fails validation instead. Absolute path bytes, including trailing spaces, are preserved. Passwords are shown only as configured, never printed or copied into the encrypted store from environment overrides. Existing saved credentials and environment-shadowed origin/Home choices are retained; first-time remote setup still records the required non-secret origin. Server-port and additional-host overrides are also displayed. The final summary derives effective bind, port, address, Home, and authentication from the same deployment resolver as startup, marking environment-owned values instead of presenting ignored saved choices.

The `Server address` prompt shows the saved origin or first detected LAN address as its default. A single LAN candidate is not listed separately; multiple candidates are listed so the operator can choose another interface. HTTPS prerequisites remain in `--help`. An effective HTTP address, whether prompted, saved, or environment-managed, displays one transport warning and continues without another confirmation. This does not affect the separate risk confirmation for disabling login or the `--allow-http` requirement in automation.

Before any setup operation, including `--local`, remote password changes, and `--reset-connection-token`, the operator must stop all Huabu servers and Vite development servers sharing the instance's credential storage. Run setup only while those services are stopped, then start them to load the new configuration. Setup does not detect running services or coordinate cross-process credential writes. The standalone SecretStore retains an in-memory snapshot and replaces the complete encrypted file on writes, so a still-running server's API-key save or OAuth refresh can overwrite setup changes. Concurrent setup and service operation is unsupported; this is an operator-enforced prerequisite, not a runtime guard.

For disk storage, the wizard confirms a Home directory, suggesting the previous setup selection or `<dataDir>/workspace`. An explicit `HUABU_WORKSPACE` stays deployment-owned and skips that prompt; SQL backends have no folder prompt. Automation may use `pnpm run setup --local`, or redirect a private password file/Secret into `pnpm run setup --remote --origin <origin> --password-stdin`, optionally adding `--username <name>`, `--workspace <absolute-path>` for disk storage, and `--allow-http` only on a trusted private network. `--origin` can be omitted when `HUABU_PUBLIC_ORIGIN` is configured; omitting `--password-stdin` reuses an existing stored password or a complete environment-owned login pair. With no saved or environment password, setup fails and requests interactive setup or redirected password input. Explicit empty or invalid replacement input never falls back to an old password. Omitting `--username` reuses the saved username or `owner`; it requires `--remote` when provided. Without a Home override, automation reuses the saved Home or the default. Setup checks directory accessibility, writes a newly entered password before atomically publishing non-secret configuration, and reports success only after acknowledged writes. Home preparation/migrations run through existing managed-mode startup; remote clients retain their restriction against arbitrary filesystem selection. Local mode removes the saved remote Home binding, never its contents. Changes take effect when the services are started after setup.

Explicit deployment environment values override setup choices, including values loaded from existing `.env` files; setup never rewrites those files. Invalid bind hosts, origins, Home paths, aliases, ports, and empty or partial Basic Auth overrides fail explicitly rather than falling back to prompted or saved values. Environment usernames follow the same username rules without silently trimming them; environment passwords must be non-empty and cannot contain control characters. A partial Basic Auth override is never mixed with a stored password. An explicit `--local` or `--remote` conflicting with `HUABU_BIND_HOST` is rejected; otherwise `--local` clears saved remote mode but leaves independent environment overrides intact. Saved remote mode derives `0.0.0.0`, the chosen public origin, and Basic Auth from its encrypted password. Bind resolution, guards, authentication, readiness, and generated connection commands consume the same effective startup snapshot. Vite development loads the same saved password without bundling it into browser assets; production browser builds do not initialize deployment storage.

`HUABU_BIND_HOST` defaults to `127.0.0.1`. A non-loopback bind requires `HUABU_PUBLIC_ORIGIN` and either both Basic Auth values or an explicit no-login choice; the server fails before listening when any requirement is missing. `HUABU_PUBLIC_ORIGIN` is the single root HTTP(S) origin used to derive remote Canvas RFS and Agentlet WebSocket endpoints. It accepts public DNS names, IP literals, and non-default ports, normalizes a trailing slash, and rejects credentials, query strings, fragments, path prefixes, unsupported schemes, and loopback origins for network binds. Its hostname automatically joins the effective Host, CORS, and Origin allowlist. A partial Basic Auth pair also fails on loopback because silently disabling authentication is more dangerous than rejecting an invalid deployment. No-login mode does not bypass Host, Origin, CORS, or rate-limit guards.

`HUABU_ALLOWED_HOSTS` is an optional list of additional browser aliases beyond the canonical public origin. It contains only hostnames or IP addresses, without scheme, port, or path. Loopback aliases remain built in. The merged set of loopback aliases, the public-origin hostname, and additional aliases drives the Host guard, CORS, and the Origin fallback.

`SERVER_PORT` is the only Server-listen-port configuration. `pnpm start:web` treats it as fixed, defaults it to `3001` when absent, rejects invalid values, and fails on bind conflicts instead of silently advancing. Development launchers may still search forward from their preferred ports for intentional parallel instances.

`pnpm dev` keeps zero-configuration access for loopback clients. Vite listens on all interfaces for development flexibility, but a non-loopback client must pass complete Basic Auth before receiving assets or reaching the API proxy unless login was explicitly disabled. The Authorization header reaches Fastify, so owner authorization does not depend on Vite's loopback backend connection. Vite resolves the same saved and environment-managed login mode as the Server.

`pnpm start:web` serves the compiled SPA and API from Fastify. On a non-loopback bind, startup validation requires Basic Auth or Bubble identity unless the operator explicitly disables login.

## Bubble identity

`HUABU_IDENTITY_PROVIDER=bubble` runs Bubble (`@octostaff/bubble@0.7.6`) inside the Huabu Server; there is no separately deployed Bubble to configure. Bubble is loaded and started only when a service needs it, which today is this provider; local mode never loads it. Do not set the Basic Auth pair in this mode. A network bind still needs `HUABU_PUBLIC_ORIGIN`. Selecting Bubble never falls back to local identity, including for loopback requests.

Bubble keeps its principals, grants, and local tokens only in Postgres, so this provider requires `HUABU_POSTGRES_URL` and stops startup without it. Huabu's own records may use any structured backend; Bubble reaches Huabu's Workspaces and Spaces only through the storage abstraction. Bubble's records are installation-level, not Workspace data, and live in the `bubble` schema of that database over connections Bubble opens and closes. On shutdown Huabu stops Bubble's workers before closing Bubble's store.

Bubble owns credential validation, its durable principal directory, issuer/subject mapping, and account status. Huabu resolves each request through the runtime's verifier and identity registration, the path Bubble's own routes use, so a credential resolves to the same principal through `/api/identity` and Bubble's API. The verifier sees the request's headers as it would on a Bubble route. Huabu preserves the principal ID and projects only kind, display name, email, and avatar. No second directory, credential cache, or cross-provider account merge is created. Every request is resolved afresh; a verifier or store failure returns a redacted 503.

`HUABU_BUBBLE_AUTH` is Bubble's ordered authenticator list as JSON, passed to Bubble unchanged; Bubble validates it at startup and a rejected list stops the Server. Every driver Bubble ships is therefore available: `local-token`, `master-key`, `auth0`, `entra`, and `default`. When unset, it is `[{"driver":"local-token"}]`. `master-key` must come last because it claims every Bearer token. Its key is a system-owner credential, and the embedded Agentlet and its agents inherit every environment variable outside the `HUABU_` namespace, so Huabu refuses to start when `BUBBLE_MASTER_KEY` is set or a `master-key` entry would read it: give the entry `"masterKeyEnvVar": "HUABU_BUBBLE_MASTER_KEY"` (any `HUABU_` variable) or an inline `masterKey`. `default` treats the Bearer text as the principal ID without verifying anything; Huabu refuses it when `HUABU_BIND_HOST` is not loopback.

Huabu authorizes its own routes with two system permissions, which it adds to Bubble's core roles through the `coreRoleCapabilities` of Bubble's host `authz` model and checks on Bubble's `system` target with Bubble's policy. `huabu.use` admits a principal to Huabu and is carried by the `member` and `owner` roles. `huabu.admin` is the owner authority for Settings, OAuth, credential, External Agent Profile, folder Workspace and similar routes, and is carried by `owner` only. So a system `member` grant makes a Huabu member, a system `owner` grant a Huabu owner; no other role, and no grant on a thread or principal, confers either. A principal with neither can inspect only `GET /api/identity`; other routes return 403 `ACCESS_REQUIRED`. A member reaches every route that does not itself require an owner. The local provider's principal always holds both. In Bubble a system grant also carries that role's Bubble authority over every thread. Bubble's first-user owner auto-grant is always off. `HUABU_BUBBLE_OWNER` names one principal that startup provisions as system owner, creating it when missing without an external identity. That suits a master-key caller: set the `master-key` entry's `defaultPrincipalId` to the same ID. Provisioning only adds; removing the variable does not revoke a stored grant. Owners authenticated by Auth0 or Entra receive their principal at first login, so an existing owner grants them `owner` on `system` through Bubble afterwards.

Bubble issues local tokens to bot principals only. An owner creates the bot and its token through Bubble's API, and the bot reaches Huabu's routes once it also holds the system-owner grant:

```bash
B=https://huabu.example/bubble/v1
curl -X POST -H "Authorization: Bearer $HUABU_BUBBLE_MASTER_KEY" -H 'Content-Type: application/json' -d '{"principalId":"ci-bot","kind":"bot"}' $B/principals
curl -X POST -H "Authorization: Bearer $HUABU_BUBBLE_MASTER_KEY" -H 'Content-Type: application/json' -d '{}' $B/principals/ci-bot/tokens
curl -X POST -H "Authorization: Bearer $HUABU_BUBBLE_MASTER_KEY" -H 'Content-Type: application/json' -d '{"target":{"type":"system"},"principalId":"ci-bot","role":"owner"}' $B/grants
```

Bubble's HTTP and WebSocket API is served under `/bubble` on the same listener, so SDK clients use `<origin>/bubble` as their base URL. Bubble authenticates and authorizes each of its routes itself with the same verifier, so bots and non-owners can use Bubble, and its credential-free discovery routes (`/bubble/v1/auth/authenticators`, `/bubble/v1/info`) stay reachable before login. Huabu's admission therefore skips exactly the routes Bubble registered, matched by route and not by URL. The Agentlet connection token is not a Bubble credential. Host, Origin, CORS, and rate-limit guards apply to `/bubble` as to every route. Only upgrades addressed to `/bubble` reach Bubble's WebSocket server; the Agentlet gateway keeps its own upgrade path.

`GET /api/identity` works before Workspace activation and returns `{ provider, principal, member, owner }` with `Cache-Control: no-store`. No token, external subject, issuer, or grant list is returned. Readiness reports `owner.policy: "bubble-system-owner"` in Bubble mode and retains `"loopback-or-basic-auth"` in local mode.

Long-lived Bubble-authenticated HTTP responses, including existing SSE streams, revalidate every 30 seconds. Revocation, lost membership, a change in owner authority, changed principal, a revoked grant on any Space the request was admitted to, or provider failure closes the response. Stream revalidation is released when the response ends, and outstanding responses are closed during server shutdown. This does not cancel an already-running agent job.

### Workspace and Space access

Huabu declares its own permission model to Bubble as host targets and roles, so grants live in Bubble's table and Bubble's policy answers every check. There are two target kinds: `huabu.workspace`, named by Workspace id, and `huabu.space`, named `<workspaceId>:<canvasId>` so that a grant never reaches a Space of the same id in another Workspace. A Space's parent is its parent Space or, for a root Space, its own Workspace. Three capabilities apply on both kinds and flow down that chain, never up or sideways:

| Capability     | Allows                                                                        |
| -------------- | ----------------------------------------------------------------------------- |
| `huabu.read`   | Seeing and opening the Workspace or Space, every `GET`, search, live streams. |
| `huabu.write`  | Editing Spaces and creating them.                                             |
| `huabu.manage` | Renaming and deleting it, and granting roles on it.                           |

| Role                     | Granted on  | Gives                                              |
| ------------------------ | ----------- | -------------------------------------------------- |
| `huabu.workspace.owner`  | a Workspace | read, write, manage                                |
| `huabu.workspace.editor` | a Workspace | read, write                                        |
| `huabu.workspace.viewer` | a Workspace | read                                               |
| `huabu.space.owner`      | a Space     | read, write, manage on it and the Spaces inside it |

A system `owner` holds every Huabu capability everywhere, which is Bubble's root rule. Every role on a Workspace or Space is granted with `huabu.manage` there, so whoever owns a Workspace or Space may share it, for example `{"target":{"type":"huabu.workspace","id":"<workspaceId>"},"principalId":"dave","role":"huabu.workspace.viewer"}` posted to `/bubble/v1/grants`; system roles stay with system owners. A Workspace or Space grant alone does not admit anyone: admission still needs `huabu.use`. On startup, Space grants that name a Space by id alone, as the first Bubble release wrote them, are rewritten to name the Workspace holding that Space, and dropped when no Workspace does.

Creating a Space makes its creator its `huabu.space.owner`. A selection move into a new Space claims it right after creating it, before any content leaves the source, so a failed claim is compensated like any other move failure. A move also requires read access to every Space whose artifact a moved node cites before copying it into the destination. That covers `POST /api/canvas`, bundle import, moving a selection into a new Space, adding a child Space, and detaching a Space to the root, where it no longer inherits from a parent. A Space created by an agent through the machine credential is claimed by nobody and is reachable through its Workspace or system ownership.

One `preHandler` authorizes every request that names a Space before its route runs. The Space is the `canvasId` route parameter, query field or body field, in the Workspace the request runs in; when more than one is given they must agree, and conflicting, repeated or non-string ids answer 400 `SPACE_ACCESS_AMBIGUOUS`, so a handler never reads a different Space from the one authorized. A request that also names another Space is checked against both: the destination of a selection move, the new parent of a re-parent, the target of a conversation fork (write), and the source of an artifact clone (read). Safe methods need read and other methods need write; the few `POST` routes that only read declare it, and renaming or deleting a Space declares manage. A Space the caller may not read answers 404, exactly like a missing one, and one it may read but not change answers 403 `SPACE_ACCESS_REQUIRED`. A member runs the Built-In agent and its conversations through `/api/agent`, in a Space they may use; a request naming a conversation must name its Space too (400 otherwise). External agents stay with administrators: a member gets 403 `AGENT_ACCESS_REQUIRED` from every `/api/acp`, `/api/agent-change-review` and `/api/rfs` route except `GET /api/acp/profiles`, which lists Built-In alone for them, from any route that declares `invokesAgent` (Interactive View actions), and from a run bound to an external agent. External agents act through the shared machine credential, which reaches every Space, on the operator's machines and under the operator's own CLI logins. RFS is that credential's own surface — it launches agents and Task Runs and leases shared service credentials — and the web app never calls it. The Built-In agent runs in-process, in the request's Workspace and caller scope, and its tools check the person who started it: a World conversation reads another Space only if they may read it, Workspace memory and Skills change only with `huabu.manage` on the Workspace, and the Task Run tools are refused. A member's edits still never count towards the memory worker, which runs an agent over Workspace-wide memory and Skills, and a member's node preprocessing runs without LLM enrichment. That preprocessing also fetches only from public addresses: inside its run every outbound request, each redirect hop included, refuses at connect time any loopback, private, link-local, carrier-grade NAT or other non-public address (`modules/security/outbound.ts`), and the desktop fetch fallback is skipped. The Space list and Space cards omit or report as missing what the caller may not read. World is an ordinary Space under its Workspace, so only those who may read the Workspace reach it.

The local provider's owner and the Agentlet machine credential pass every Space check. An external agent therefore acts with the machine credential's full RFS reach, which is why only administrators may run one. Workspace-level state such as `setting/user.md` memory and user Skills is shared by everyone in a Workspace. Each request authenticates once and answers all its checks from one Bubble policy scope, one grant load and one ancestry walk per Space.

### Workspaces per person

In Bubble mode each request runs in its caller's own current Workspace, so several people work in different Workspaces of one Server at once; local mode keeps one process-active Workspace for everyone. Admission chooses it after authentication: the caller's stored current Workspace while they may still enter it, else the first Workspace they may enter, which becomes current. The current Workspace is a per-principal row in the `huabu_identity.current_workspaces` table of `HUABU_POSTGRES_URL`, referencing Bubble's principal ID. A member who may enter no Workspace gets a personal one, "<name>'s Workspace", owned by them, on their first admitted request; concurrent first requests in one process create one. A caller may enter a Workspace they hold a Workspace role on, or one holding a Space they hold a role on; a system owner may enter any, and lands first on the process-active one. The choice is carried through the request and everything it starts in an `AsyncLocalStorage` scope (`modules/workspace/context.ts`), which the Workspace getters, the storage backends' per-call namespace and the identity checks read; see [Multi-backend storage](./canvas-storage.md).

`/api/workspaces` then acts for the caller alone. It lists the Workspaces they may enter, `active` marking their current one. `POST` with a `name` creates a Workspace they own, wherever the backend keeps one: a row on SQL backends, a folder under the data directory on Disk. Activating sets only their current Workspace. Renaming and unregistering need `huabu.manage` on that Workspace, and unregistering refuses a Workspace with work in flight or the process-active one; a person whose current Workspace was unregistered moves on at their next request. Folder Workspaces stay with system owners, from localhost, as do `/api/workspace` folder picking and path validation, because they name places on the Server's filesystem; members never receive a Workspace path. `GET /api/workspace` reports `capabilities.namedWorkspaces`, and the web app then switches and creates Workspaces by name.

An agent run keeps the Workspace it started in: its reachback URL is `/api/rfs/w/<workspaceId>/<canvasId>`, and the RFS routes under that prefix run in that Workspace whatever its starter or the process does later.

### Personal settings

In Bubble mode a member's calls run in their own settings namespace (`modules/identity/personal-settings.ts`), carried through the request and the agent runs it starts. The secret store keeps their model keys, OAuth credentials and connected-service keys under ids of their own, and gives them no fallback to the deployment's environment variables, which are the operator's. Their model settings and agent defaults live under `<data>/people/<key>/`, and their default agent is always the Built-In one. So `/api/llm`, `/api/agent/defaults`, `/api/integrations`, `/api/services` and Ink OCR settings change the caller's own settings for a member and the deployment's for an administrator; the deployment's connection token and access password are never anyone's personal ones. A member with no model configured is told to add one in Settings.

### People

`/api/people` lets a system owner administer people without Bubble's API: list every principal Bubble knows with their system and Workspace roles, admit or revoke `member` (`PUT /api/people/:principalId/member`), and give or remove a Workspace role (`PUT /api/people/:principalId/workspaces/:workspaceId`). A principal appears after their first sign-in. An administrator cannot revoke their own access there. Settings shows it as the People tab.

### Browser sign-in

The SPA asks `GET /api/identity` before mounting. A local deployment answers at once and the app renders as before; a Basic Auth challenge remains the browser's. In Bubble mode a caller without a session sees a sign-in screen with one choice per interactive authenticator in Bubble's credential-free `/bubble/v1/auth/authenticators` discovery (the `entra` and `auth0` drivers). The SPA runs an OAuth authorization-code flow with PKCE against that provider: it reads the provider's endpoints from `<issuer>/.well-known/openid-configuration`, redirects back to `<origin>/auth/callback`, and exchanges the code without a client secret. Register `<origin>/auth/callback` as a single-page-application redirect URI, and `<origin>` as an allowed web origin for the token request, and the `scopes` Bubble publishes as the API the app requests. An authenticated principal without `huabu.use` sees a no-access screen instead of the app.

The SPA then hands the access token to `POST /api/identity/session`. The Server accepts only a credential Bubble validates, never the machine token, and stores it in an `HttpOnly; SameSite=Strict` cookie, `Secure` over HTTPS. Admission reads that cookie in place of a missing `Authorization` header, so images, frames, downloads and streams authenticate as well; an explicit header always wins. The cookie is a carrier, not a server session: Bubble validates the token on every request, so expiry and revocation behave as for any Bearer caller. When the token expires, the next refused request returns the SPA to its sign-in screen. `DELETE /api/identity/session` clears the cookie without needing a valid credential, and the App menu's Sign out item calls it. Signing out of Huabu does not end the identity provider's own session. Stored documents (artifacts, extracted MHTML snapshots, Interactive View files) are served under Bubble identity with `Content-Security-Policy: sandbox allow-scripts allow-forms allow-popups`, so a member's HTML or SVG opened as a page runs in an opaque origin and cannot use another viewer's session; the web app already embeds them without `allow-same-origin`. Local mode sends no such header. `POST` and `DELETE /api/identity/session` stay reachable before a Workspace is configured, so an owner can sign in to set one up. Behind a TLS-terminating proxy the listener sees plain HTTP, so an `https:` `HUABU_PUBLIC_ORIGIN` also marks the cookie `Secure`. When the Server serves the built web app (`WEB_DIST_PATH`), Bubble mode serves its static files and `index.html` fallback without a credential so a fresh browser can load the sign-in screen and `/auth/callback`; they contain no data, and every `/api` route is still admitted. Local mode keeps them behind Basic Auth. Desktop and Vite's remote Basic Auth gate remain local-mode tooling.

API clients can still send the Bearer token themselves:

```sh
curl -H "Authorization: Bearer $BUBBLE_TOKEN" https://huabu.example/api/identity
```

Sign-in asks for `offline_access`, and the page keeps the refresh token in memory only, never in storage. It renews the session a minute before the access token expires and on any `401`; when it cannot, the sign-in screen opens over the still-running app and signs in through a popup, whose code returns to the page by `postMessage` and is redeemed with a verifier only that page held, and the saves the lapse refused are sent again. With `HUABU_SIGN_OUT_PROVIDER=true`, `GET /api/identity` reports `providerSignOut`, and signing out also sends the browser to the provider's `end_session_endpoint`; register `<origin>/` as a post-logout redirect URI.

Changing providers does not migrate or link `local-owner` to a Bubble principal. Existing conversation records remain untouched.

`pnpm start:desktop --server <URL>` is a native client for the same remote deployment boundary. It accepts a root HTTP or HTTPS origin but does not weaken the Server's Host, Origin, CORS, or Basic Auth policy and does not inject allowed hosts. A `401` challenge from the selected exact origin opens a sandboxed Electron credential prompt; credentials remain in Chromium's current network session and are not placed in the command line, exposed to the renderer, or persisted by Huabu Desktop.

## Deployment readiness

`GET /api/deployment/readiness` is available before workspace activation. It returns the resolved bind scope, whether remote-access prerequisites are configured, whether the current request is recognized as the owner, credential-store writability, transport status, and structured warning codes.

The response is deliberately redacted: it never contains usernames, passwords, connection tokens, secret keys, credential values, or the configured allowed-host entries. No-login mode reports owner policy `unauthenticated` and, on network binds, a `REMOTE_LOGIN_DISABLED` warning rendered in Settings.

Settings loads readiness when it opens. It does not render a permanent notice solely for operator-unverified transport; readiness errors, read-only credential storage, and disabled-login warnings remain visible. Device-connection pages and copy-result toasts omit insecure-transport notices; native desktop connection confirmation retains the exact Server and permission consequences without an additional HTTP warning. Transport status and copy-response warning codes, startup/setup guidance, TLS validation, and authentication checks are unchanged. Removing presentation does not encrypt HTTP or WebSocket traffic. A read-only credential store disables API-key and OAuth mutations while leaving non-secret model configuration available. Standalone deployments automatically initialize encrypted credential writes or use the explicit `HUABU_SECRET_KEY` override; see [`credential-storage.md`](./credential-storage.md).

## Application-wide rate limiting

Every production HTTP route inherits one in-memory `@fastify/rate-limit` policy: 1,000 admitted requests per 60-second window, keyed by the normalized direct TCP peer IP. Authentication and authorization are independent of admission control, so loopback clients, Basic-authenticated browser traffic, and RFS bearer traffic receive neither a bypass nor credential-specific buckets.

Huabu does not enable Fastify `trustProxy` and does not derive rate-limit identity from `Forwarded`, `X-Forwarded-For`, or similar caller-controlled headers. A supported external TLS terminator therefore shares one bucket for all clients that reach Huabu through that proxy. Per-client identity behind trusted proxies requires a future explicit proxy trust contract; operators must not enable arbitrary forwarded-header trust as a workaround.

`OPTIONS` preflights and `GET /api/deployment/readiness` are exempt so browsers can negotiate access and deployment monitoring remains available. There is no separate health endpoint. Static assets, ordinary APIs, RFS—including the public root Skill bootstrap—and uploads are limited. Upload admission runs before body parsing and remains additionally bounded by the 500 MB upload-size ceiling.

An SSE connection attempt consumes one request when the stream opens; events and heartbeats on the established connection consume no further requests. Reconnect attempts are ordinary requests. A rejected request returns HTTP 429 with the canonical `ApiErrorBody`, `code: "RATE_LIMITED"`, retry details, limit/remaining/reset headers, and `Retry-After`. The web client shows one deduplicated warning and Canvas Sync waits at least the advertised retry interval before reconnecting. The server records a structured warning containing the direct-peer key, method, and route template, never credentials.

## Transport

Huabu's Node server currently speaks HTTP. A non-loopback bind logs and reports `operator-unverified` transport because the process cannot prove whether a private network or external TLS terminator protects the client-facing connection.

Production HTTPS termination belongs to deployment infrastructure such as Caddy, Nginx, Tailscale Serve, or a cloud load balancer. Trusted-proxy identity and verified forwarded transport are intentionally separate from the current direct/Vite deployment boundary and must not be implemented by accepting arbitrary forwarding headers.

The Desktop remote-client path uses the operating system's normal certificate validation and does not bypass invalid or self-signed certificate errors. Its startup readiness probe follows no redirects, so an unexpected redirect, TLS failure, unreachable host, rejected Host header, or incompatible readiness response produces an actionable startup failure instead of silently starting a local Server.
