# Canvas Storage Architecture

> Last updated: 2026-10-20

## 1. Overview

Every Space remains fully self-contained on Disk by default, but storage no longer presents one all-purpose `CanvasStore` as its backend contract. `apps/server/src/modules/storage/` separates backend-neutral blob and structured ports, Disk adapters, process-wide composition, and a shrinking Disk compatibility facade. Opaque artifact bytes flow through `BlobStore`; `StructuredStore` exposes one `spaces()` repository for the Space collection — membership, World identity, and create/delete/rename — while `SpaceHandle` exposes the Space's own async record read and ordered write plus the parts it holds: `nodes`, `changes`, `tasks`, and `events`. `SpaceNodes` reads one node by id, a named selection through `readMany()`, and the whole Space through `list()` / `stream()`; all four return the same records and the same opaque revisions. The application reaches all of it through one `space(canvasId)` handle on the composition root, which joins the structured handle with the Space's blob areas and, on Disk, its `diskTree`. Space creation and deletion, standalone node writes, executor and revert batches, preprocessing persistence, and event/change mutations enter these ports. Every production structured read now enters these ports too; `CanvasStore` lives inside the Disk adapter and its own suites, and no production module outside `storage/` imports it or a Disk layout symbol. What is left outside the ports are Disk-shaped _capabilities_ rather than reads: bundle export and import, reveal-in-file-manager, the built-in file tools, external-note observation and claim, RFS upload/delete, and boot migrations. Each mutates or names physical files, so they keep non-Disk profiles unselectable until they are declared as unavailable there rather than merely undesigned.

Runtime Home-folder activation reserves the namespace switch before preparing and migrating the selected directory in a disposable child process. An in-flight Workspace operation therefore refuses the switch before the target is touched, and no new operation can enter the old Workspace while preparation is pending. This isolation is required because synchronous filesystem calls against cloud, network, or virtual drives can block indefinitely; a stuck preparation is terminated after 70 seconds with `WORKSPACE_ACTIVATION_TIMEOUT`, while the Server event loop and previously active workspace remain available. Concurrent activation attempts return `WORKSPACE_ACTIVATION_IN_PROGRESS`. Managed-mode startup still prepares synchronously before the Server accepts requests.

Standalone remote setup confirms and persists an absolute disk Home directory, suggesting an existing setup selection or `<dataDir>/workspace`. Startup resolves that saved path through the same effective deployment snapshot as authentication and origin configuration; explicit `HUABU_WORKSPACE` wins. This uses existing managed-mode preparation and disables runtime folder changes, so a first remote browser can use its prepared Home without being granted arbitrary server filesystem selection. SQL backends do not save or request a Home folder. Returning setup to local mode removes the saved binding without deleting the Home; local users can select it again through the existing picker.

Conversation persistence binds captured Agenetes namespaces to the immutable Workspace identity and stable Space ID, not to the mutable `.history` directory. Every named conversation-store operation acquires the existing Workspace-operation lease and resolves the Space's current history location before touching thread metadata, Tier-1 events, or Tier-2 turns. A reused live logging wrapper therefore follows a Space rename without recreating the old directory, while a namespace captured in a different Workspace is rejected. Rebinding preserves whether the captured namespace has a `storage.root`: explicit file-backed history follows a renamed Space, while a rootless namespace never acquires a Disk path merely because the active backend changed. Restored Disk namespaces are admitted only from the active Workspace's containing directory before receiving their process-local identity binding. Recent-conversation reads and acceptance additionally retain a workspace-bound Space handle and hold the lease across Canvas-mutex queueing, pending-acceptance recovery, reservation, canonical append, and finalization; activation cannot split those phases across Workspaces that happen to contain the same Space ID.

Default legacy Agent lifecycle transitions, activity projection and viewed acknowledgement retain the existing Workspace lease from Canvas-mutex queueing through asynchronous reads and persistence. This is coordinator-level Workspace pinning: it preserves existing state/token rules, releases on no-op/failure, and does not certify the full turn, binding preparation or all historical raw capabilities.

`AgentNodeBindingCoordinator.confirm()` also holds one existing Workspace lease across the canonical execution-record read, optional history read, validation and Bound promotion, including mutex queueing and the already-locked promotion path. Nested lifecycle leases cannot release the outer confirmation lease. Null/already-Bound results and exceptions release it, with no automatic retry or rollback of execution records. Upstream owner resolution, supplied-record capture and external realization remain outside this interval.

The recent-conversation GET includes its Space existence check inside that same leased, mutex-protected read and uses the captured Space handle for both validation and index access. Resolving a pending acceptance repairs the index once, removing the marker for either a proven accepted turn or a rejected append; later reads no longer scan that thread's history. Repair-write failure is logged while ordinary reads return the already verified pointer and leave the pending index retryable. Rehome cleanup requires successful repair before deleting canonical history, so the only durable proof of acceptance cannot disappear while the pointer is still pending.

## 2. Disk Layout

### Authored node properties and PDF notes

Node data optionally carries `properties: Record<string, string | number | boolean | string[]>` and `propertyDisplayKeys: string[]`. These are authored fields, initially exposed on Note and PDF, without a property schema registry. Human content PUTs and agent `MERGE_NODE_DATA` patches share keywise property merging: `{"year": 2026}` changes only `year`, `{"year": null}` deletes it, and `{}` changes nothing. The patch is applied to the record as stored at the moment of the write and no revision protects it: different keys never conflict, the same key is last-writer-wins, and a list value is one value (the format has no per-item add or remove). Display keys replace the whole ordered priority list, shared by property rows and PDF cards; unlisted existing keys follow in object-key order, duplicates and missing keys are ignored, and `[]` uses object-key order rather than hiding properties. Reordering saves the complete resolved key list; renaming retains its position and adding appends.

The existing SpaceNodes port persists these fields in Disk YAML frontmatter and in the complete node JSON record on SQLite/PostgreSQL; no SQL migration or separate property table is needed. Hydration, content GET/PUT, executor writes, the stripping of content fields from the structural record, and the browser content queue use the same fields. A page saves them through the per-node content PUT only — they are content keys (`NODE_CONTENT_KEYS`), stripped from the commands the send queue sends — and they reach other open pages as a node-scoped fetch; see [Properties and PDF notes between pages](./canvas-realtime-sync.md#properties-and-pdf-notes-between-pages). The queue sends the keys a store change touched, a removed key as a `null` tombstone, including edits made while an earlier save is in flight; it never sends a key nobody changed on that page. Preprocessing preserves authored metadata while replacing derived content; it never infers custom properties.

PDF-owned notes are real `note` nodes with their own ID, canonical `content`, revision, provenance, sidecar or SQL record. The PDF stores `data.noteNodeId` in structural state; it does not store a second copy of the Note body. Opening Add notes creates the Note and its ownership link in one undoable command batch; later opens reuse that Note. One Note can belong to only one PDF and has no Frame parent. Linked Notes are hidden and unselected on the canvas and omitted from Layers, but remain addressable by ordinary Note operations. Inspection exposes `noteNodeId`; Agent reads and edits target the linked Note's own identity.

UI, Agent, and API writers initialize notes with `INITIALIZE_PDF_NOTE`. An Agent or API caller provides only the PDF ID; the command creates and links a fresh empty Note or returns the existing Note without mutation, and server results include the Note ID for ordinary follow-up reads and edits. A browser page runs the same shared handler locally first and sends the command through its send queue with the Note id it chose (`noteId`, `ui` only: refused for an agent batch and for an id that already exists), so the Note the page shows at once is the node the Server creates. Lower-level ownership writes (copy, and the `RESTORE_NODES` of an undo) may link only to a Note created or restored in the same command batch. Claiming a pre-existing independent Note is rejected, even if it is hidden or deleted and recreated with the same ID in that batch. Existing links remain valid; copied pairs use fresh IDs, and undo/redo may restore an absent pair.

Explicitly deleting an owned Note clears its link, so a subsequent `INITIALIZE_PDF_NOTE` may create a fresh empty Note, including in the same command batch. This accepted destructive sequence does not permit claiming another existing Note or replacing a still-live link. Snapshot-based review reversion of such a same-batch replacement remains subject to the no-replacement ownership guard.

Copy and cross-Space move include the owned Note and remap the PDF's link. Its images follow the existing Note artifact path. Deleting a PDF (including through Frame deletion) deletes its Note; deleting the Note directly clears the owner's link. Undo/redo are sent as commands like every other undo ([Browser structure edits](./canvas-realtime-sync.md#browser-structure-edits)): undoing a deletion restores the pair with one `RESTORE_NODES` batch that carries both nodes, the Note's body and the link; undoing the creation is `DELETE_NODES` for the Note plus an `unset` of `noteNodeId`, and redoing it is `RESTORE_NODES` for the Note followed by the link. Agent change review groups ownership changes with the associated Note delta so Keep, preview, and Revert operate on the pair, with freshness checks for every member. Owned Notes cannot be converted to Text or independently reparented or moved to another Space. Bundle import remaps `noteNodeId` as an explicit node reference. Command execution and server delta replay validate ownership against both the state before the batch and the proposed state: replacing an existing link is forbidden, and clearing a link (a `noteNodeId` patch, or a page's `unset` of it) or deleting its PDF requires removing the old Note too; a `RESTORE_NODES` that carries a `noteNodeId` is held to the same rule, so an undo cannot hand a PDF a Note that exists on its own. Both derive hidden state. There is no whole-Space save to validate. This development-branch replacement has no migration or compatibility layer for the removed inline-notes representation.

The content revision covers the body only: `content` and `src` (`nodeRevisionOf`, `CONTENT_REVISION_KEYS`). The property bag and display keys are **not** part of it — setting, changing, removing or reordering a property leaves a node's revision as it is — and neither are title, summary or keywords; see [what is versioned and what is not](./canvas-realtime-sync.md#what-is-versioned-and-what-is-not). The revision is computed from the stored record on every read and is never persisted with a node, so no stored data changes with this rule; only a short-lived copy can still hold a revision computed with properties (an execute result record kept for request replay, an agent run's read-set, an `ETag` a client kept), and each is corrected by the next read. PDF and owned Note bodies have independent content revisions. Property PUTs and property-only agent patches are never checked against a revision, on any node type, and a supplied one is ignored; a stale **body** write conflicts rather than overwriting another writer. Both whole-Space and single-node GETs hash the canonical stored record, even when Office presentation strips a legacy parser preamble. Built-in `inspect_nodes` exposes authored properties on every storage backend, with `rev` (the body's revision) for a node that has a body or source. Property patches need neither inspection nor `read`; body writes require `read`, and inspection does not stand in for it. A node `read` projects frontmatter, body and revision from one canonical record and records the body's freshness. Native callers use the returned `rev` as `expectRev` for body writes; built-in agents receive injected revisions. Non-sidecar `spacePreview` nodes reject authored property commands instead of reporting a non-durable write as successful.

`fileReference` nodes retain only device/path/display metadata in structural state and use a frontmatter-only `.md` sidecar for labels. External bytes are never stored as node content or artifacts; copy and bundle export preserve only the reference. Source/body mutations are rejected for this type. See [connected-device files](./device-files.md).

Space ownership is logical metadata, not directory nesting. Ordinary Space records optionally store `parentSpaceId` and `parentEntryNodeId`; missing/null fields mean top-level. SQLite and PostgreSQL add `parent_space_id` / `parent_entry_node_id` and a Workspace/parent index in migration v2. The collection's trusted `setParent` primitive persists both fields, while the canvas hierarchy service owns existence, cycle, and canonical-entry checks under its Workspace-leased process lock. Ordinary structural writes preserve stored hierarchy instead of accepting it from clients. Disk summaries capture hierarchy in the existing directory-index scan without extra record reads or write-back. Imported single-Space bundles clear ownership and remain top-level; they do not recursively import children. See [Space ownership and lifecycle](./space-preview.md#space-ownership-and-lifecycle) for API, navigation, deletion, and concurrency guarantees.

Single-Space bundle import allocates fresh node, edge, and conversation thread IDs before publication. Mappings update topology, Frame parents, edge endpoints, node frontmatter, known structured history references, and SQLite Tier-2 conversation payloads. Source-scoped node deep links and artifact URLs follow the imported Space; prose and labels are not treated as identifiers. Turn ordering, sequence fences, and cursor generations remain unchanged. Invalid/duplicate identities or unreadable structured records fail the staged import instead of publishing a partially remapped Space. Existing Spaces are not rewritten.

History remapping uses explicit per-contract field plans for ChatEnvelope, attachments, Ink resources/grounding, Canvas commands, and recent actions. Envelope and attachment plans cover every shared type field, including fields deliberately kept opaque; command and action plans cover every discriminant, so adding a contract member requires an import decision at compile time. Singular/plural attachment origins, selection references, grounding operands, command geometry/layout/order/edge references, action endpoints/Frames, and excerpt provenance all follow the imported identity map in JSONL and SQLite. Attachment content rebases source-scoped artifact URLs and node deep links, including when history must be rendered again from the envelope; ordinary prose, labels, filenames, and links to other Spaces remain unchanged. Import also remaps current and pending pointers in `.ext/huabu.recentconversation/target.json`, preserving acceptance markers; unrelated extension documents remain opaque and unchanged.

Canonical Huabu `request.rendered` inputs are migrated as captured inputs, not rebuilt from live Space contents. Text, multipart, and command-context inputs retain images and command text; host node/edge/attachment XML, source-scoped URLs, and embedded Ink/Interactive View reference records are rebased. Captured `<ink_ocr>` origins use their space-separated ID format, distinct from comma-separated attachment origins; the identity mapping leaves transcription text and unknown origin IDs unchanged. User requests, quoted comments, skill bodies, and application event inputs remain unchanged, including when an adapter flattened text parts. Interactive View event content and its rendered event use the same node identity. This preserves historical screenshots and point-in-time neighbourhoods without a live storage read.

Change-review fingerprints are recalculated from the remapped historical applied snapshot (`DELETE_NODE.node` or `REPLACE_NODE.prev` in the inverse deltas), never from the current node. The original fingerprint must match that original snapshot; inconsistent records fail import. A later human edit therefore remains stale after import, while a source-link rewrite alone does not disable Undo.

Legacy node sidecars without a nonempty string `id` use the filename stem, matching Disk indexing, and receive the mapped ID in frontmatter. Recognized JSON-string tool response envelopes and bare snapshot arrays in `rawOutput` are decoded, remapped, and re-encoded in JSONL and SQLite history; ordinary text and unrecognized JSON receive only the existing source-link rewriting, not identifier remapping.

Thread discovery covers Question nodes, durable workload records, per-thread log/change filenames, and SQLite thread keys, including history without a live node. Import rekeys `threads.json`, Tier-1 and legacy Tier-2 filenames, change-review filenames, and all three SQLite tables (`turns`, `turn_generations`, `jsonl_imports`), plus known thread references in node data, interactive-view ownership, Task runs, and history. References to threads not owned by the imported bundle are preserved. Imported conversations therefore cannot reuse the original Space's thread-keyed runtime handle or browser state.

External workload imports retain configuration and visible history but start a fresh native session: copied session IDs and launch snapshots are discarded, and the existing reachback environment builder targets the new Space and thread. Internal workload host context targets the new Space. Supported legacy v3 ACP records pass through the existing migration before this reset; unsupported or malformed legacy records fail import rather than restoring a source session. This does not copy a CLI's private native conversation state.

Canonical contracts dispatch before the bounded legacy-history/host-extension walker. Node/edge `id` and edge `source`/`target` fields are mapped only in their structural contexts. Interactive-view schemas and values, provenance `source`, task/change/tool-call IDs, driver settings, unknown nested application objects, and unrelated JSON files remain opaque. Folded tool arguments and JSON-string results without a live `internalToolName` marker are interpreted as host records only when the owning workload is internal and the tool is recognized; external tool arguments are not Canvas commands.

Key points:

- Sketch `data.strokes` may carry one optional `resourceBinding` on the first of four source strokes. It persists inline with geometry through normal Canvas commands, undo, and sync; no new sidecar or migration is required. Canvas PUT and shared create/data-merge commands reject malformed incoming binding metadata. Legacy malformed bindings are reported and excluded from projection without deleting the underlying Ink. Target identity is scoped to the containing Space. Source-invalid records remain stored but are not projected as live references, so Undo can restore them; missing targets project as broken references. Clipboard copies and cross-Space moves strip the record. See [Sketch Sigils](./sketch-node.md#42-handwritten--resource-references) for the complete lifecycle.
- Recent conversation routing state uses the existing `SpaceHandle.extension('huabu.recentconversation')` substrate and shared document helper on Disk, SQLite, and PostgreSQL. It stores only the accepted `{ nodeId, threadId }` pointer plus an optional pending acceptance UUID and target; no conversation history, summaries, context, or memory are copied. The conversation event-store adapter serializes anchored chat acceptance with the Space mutex: persist a pending candidate retaining the previous target, append the canonical `turn_start` with that UUID in server-owned submission metadata, then finalize the pointer. Reservation failure rejects before acceptance; finalization failure is logged but cannot turn an already accepted request into a rejection. A pending pointer resolves against the durable turn-start identity on the next read or submission, with strict file/document reads that distinguish corruption and I/O failure from absence. Canonical history deletion during rehome first resolves any matching pending pointer, preserving the source Space's unavailable-target identity. Node deletion does not clear routing state; Space deletion removes the extension. Ordering follows actual serialized durable acceptance rather than timestamps or asynchronous completion callbacks, and ordinary editable Canvas writes cannot overwrite the extension. These are the existing single-server admission guarantees, not cross-process transactions.
- `storage/disk/workspaces.json` is the Disk backend's discovery index and stores only `schemaVersion` plus `{ workspaceId, workspacePath, lastOpenedAt }` entries. Array order is stable and carries no meaning: successful adoption or activation stamps that entry's `lastOpenedAt`, and listings sort by it, so recency survives a hand-edited or re-serialized file. It is the single in-process representation of membership and the welcome screen's source: it is re-read from disk on every access and each member's display metadata is read back from its own `.workspace.json` on demand, so nothing here can go stale against the files it describes. The Server process is its only writer — the isolated preparation child adopts the manifest but never registers membership.
- Electron's former `<userData>/workspace.json` path/recents store is deprecated. `start:desktop` passes its location to the Server as a read-only upgrade source; the first plural Workspace request imports its active path and recents only when `workspaces.json` does not yet exist. An existing registry always wins and the old file is never written again.
- Opening an externally moved Workspace reads that manifest and replaces the indexed path for the same id. If it is active, the process-local active path moves with that registration before the API publishes the new location. Two physically distinct live paths carrying the same id are rejected as a copied-identity conflict; symlink aliases of one directory are the same materialization, not copies. A path whose folder was deleted and recreated is re-adopted under the identity now on disk, which is what keeps the legacy Home-folder selection flow working after the user rearranges folders outside Huabu.
- A registered Workspace that cannot answer for itself — folder deleted, volume unmounted, path taken over by another Workspace — reads as "not a member right now" rather than an error, so one unreachable entry cannot take down the whole collection, and it returns when its volume does. A _malformed_ manifest or registry still throws: that is damage the operator has to see. Unregistering removes only the index entry, works while the Workspace is unreachable, and never deletes the Workspace directory or manifest.
- Workspace identity is a precondition of storage rather than a product of it, so the composition root resolves the async Workspace repository (`getWorkspaceRepository()`) on its own axis, separate from `StructuredStore`. The configured backend connections are process-wide: selecting another Workspace changes the active namespace inside those existing connections and does not drop or reconnect them. A SQL adapter therefore holds all Workspace membership and data behind one live connection/pool, with Workspace ids scoping repository and handle operations. Managed-mode Disk adoption still happens while `app.ts` is evaluating; a connection-backed adapter wires its repository during the awaited storage startup.
- `WorkspaceHandle` carries identity and display name only. _Where_ a Workspace is is a materialization fact, not an identity one, so a backend that keeps Workspaces in a database is never asked to invent a path. The locator is the Workspace-level twin of the Space handle's `diskTree` member and resolves in composition — `adoptWorkspaceDirectory()`, `workspaceAtDirectory()`, `workspaceDirectory()` — where a non-materializing profile refuses outright. `workspace.ts` therefore holds the active identity and the active path as two separate facts. Operation leases expose a `workspaceKey` (a Disk path or `workspace:<id>`); a refused SQLite activation preserves both the active identity and the connection scope.
- The manifest schema is the single definition of a valid manifest and guards the write as well as the read, so a caller cannot persist a name that would fail validation on the next read.
- Managed deployments expose exactly one Workspace — the active one. Other registrations in the same data directory are unaddressable there, so listing them would leak host folder names through the API that redacts host paths.
- `space(canvasId)` is the one entry point to a Space. It is a composition-layer facade, not a port type: `StructuredStore` and `BlobStore` never import each other, and they are joined only where the cross-store rules already live — the blob-put precondition and the blob-first delete saga. It composes from its receiver, so substituting one axis on a `Storage` object yields Spaces built on the substitute.
- A capability only one backend has hangs off that same handle, named for the backend and typed by its absence rather than stubbed to throw: `diskTree` is the Disk Space directory and is `null` on every other backend. It is not a port and does not live in `ports/`. `module-boundaries.test.ts` holds its exact production consumer census — a list that may shrink and must not grow — and asserts the barrel exposes nothing that reads as a portable path API.
- A Space's bytes are reached the same way as its records: `BlobStore.space(id)` returns one member per user-visible area — `artifacts`, `guide`, `memory`, `uploads` — so the Disk paths a user sees are unchanged and retention can diverge later without moving bytes. The `guide` area is bounded by its member names rather than by a directory, because its area is the Space root: a directory scope there would let `list()` claim `space.json` and `deleteAll()` remove the Space. Rename and per-key delete remain unsupported.
- `space(canvasId).extension(namespace)` hands an owner an isolated place to keep its own per-Space state — a reserved directory on Disk, a shared connection plus a Space-owned parent row on SQLite — and nothing else. Storage validates the namespace, creates it on demand, and destroys it with the Space, which is the one operation an owner cannot perform itself; it guarantees nothing about the contents, and cannot, because it never sees them. `extension()` returns `null` for a Space that is gone, which is where the per-owner `existsSync` resurrection guards went. Memory-worker bookkeeping, the debug prompt log, and the Agenetes conversation stores are its owners; ACP session state is assigned here but moves with the Agenetes `Namespace` change. SQLite event-log and turn-log replacement pre-encodes every record, then uses a savepoint to make deletion and insertion atomic, preserving the old log if replacement fails. Agenetes awaits asynchronous persistence. SQLite retains `sqliteTree` internally for its synchronous store implementation; Postgres resolves the async extension substrate. Both keep conversation data in owner tables with a Space-owned cascade parent.
- Features that are _about_ a filesystem are declared, not emulated. `capabilities.ts` lists Workspace folder selection, bundle export and import, reveal-in-file-manager, the built-in file tools, RFS's file plane, external-note discovery, the Workspace memory document, and user-authored skills as Disk-only; startup logs the ones the selected profile does not offer and each refusal reuses that same wording. An unavailable feature is a stated limitation and startup continues, while a profile naming an unimplemented backend stays a misconfiguration that fails fast. Fewer features is therefore not a reason to make a backend unselectable — an _undeclared_ gap is. Windows directory-handle coordination applies only when a directory operation invokes it; it is not a declared capability or a limitation of SQLite.
- `closeStorage()` closes both connections on graceful Server shutdown and forgets the holder. On Disk it releases nothing a process exit would not, and it exists for the backend that will hold a pool.
- `SpaceRepository.ensureWorld()` is the backend-neutral World bootstrap: it returns the established World or mints exactly one version-0 World when the namespace holds none. An _established_ World that is missing or malformed stays the integrity error `worldId()` reports, because regenerating identity there would orphan every reference to it. Disk delegates to the same idempotent primitive Workspace preparation calls, so one file keeps one writer.
- An ordinary Space **directory name** is derived from its title via `toSafeFilename(title)`, not from `canvasId`. The stable `canvasId` only lives inside `space.json`; the World is the reserved `.world` exception.
- `SpaceRepository.list()` rescans on every call, returns ordinary Spaces only, skips ordinary directories without `space.json`, rejects malformed records (including a corrupt established World), and leaves ordering to the caller. `worldId()` resolves the hidden World from the same rescan and rejects missing or malformed state; it is the single World resolution point the collection's own create/delete/rename refusals also go through.
- The `canvasId -> directory name` index in `canvas-dirs.ts` is invalidated **lazily**, never by a live filesystem watcher. Catalogue reads and the World resolvers re-scan unconditionally, server-owned create/rename register the new directory directly, and `CanvasStore.read()` re-scans and retries when `space.json` is missing — which is also how a Finder-side Space rename is adopted as the new title. A stale index therefore self-heals on the next read of the affected Space.
- External-note observation exists for one feature: surfacing user-authored `.md` files dropped into `<Space>/nodes/` from outside the app. There is **no workspace-level watcher**. In steady state there is at most one native `fs.watch` handle per **active Space session**; concurrent SSE subscribers to the same Space share that session, watcher, and scan, so watcher count follows distinct active Spaces rather than open streams. Unknown Space ids remain inert: the Disk tree's `existingDirectory()` checks the directory index before any watcher, scan, or Windows probe is armed. Opening a known Space's stream arms its native watcher _before_ the one lazy scan begins (closing the scan-then-watch gap), limits that scan to eight concurrent file reads plus one asynchronous topology read for filtering known note ids, and returns a single merged snapshot; live events read the latest topology synchronously and always win over an older scan observation of the same path. When `nodes/` does not exist, non-Windows sessions watch the Space root and promote themselves to the child directory as soon as it appears. Windows sessions use one periodic existence probe instead, avoiding a root handle that would block external Space rename/delete. If an active `nodes/` directory is deleted or replaced, the session verifies its filesystem identity before emitting an empty snapshot, re-resolves a Finder-renamed Space by `canvasId`, then waits for the path and resumes child watching instead of remaining attached to the stale inode. The final `close()` releases the watcher, clears pending timers, and drops the Space's discovery state. A failed scan is not cached, so a later subscription retries. Workspace and session generations reject scans and events that resolve after a workspace switch or a close/reopen. Inactive Spaces hold no watcher and no in-memory state; their eventual state is rebuilt by the first lazy scan when they are next opened.
- Because a live `fs.watch` handle inside a Space subtree makes `renameSync` / `rmSync` fail with EPERM on Windows, `space-dir-handles.ts` arbitrates between handle owners and directory mutations. Each active external-note session registers itself against its `canvasId`; server-owned Space rename and delete bracket the mutation with `withSpaceDirHandlesReleased(canvasId, fn)`, which releases that Space's handles and lets the owner re-acquire afterwards — re-resolving the directory, so a rename re-arms at the new path and a delete collapses the session to an empty snapshot. A Space with no open stream has no registered owner, so the bracket is a plain passthrough. Neither side knows about the other.
- Workspace preparation creates exactly one hidden `.world/space.json` after migrations. Its generated `canvasId` remains stable, resolves through the normal `CanvasStore`, and is exposed separately as `WorkspaceInfo.worldCanvasId`; ordinary Canvas lists continue to omit it.
- An established `.world` directory with a missing or malformed `space.json` is an integrity error. World identity is never silently regenerated, and the World cannot be deleted or directory-renamed through ordinary Space lifecycle operations.
- The World Canvas GET calls `reconcileWorldPreviews()` to ensure one canonical `spacePreview` for every live ordinary Space. Reconciliation creates missing previews with fresh IDs in deterministic open-grid slots, removes previews whose target was deleted, preserves existing preview identity and user geometry, and rejects duplicate or malformed managed identities. It does not migrate legacy Portal IDs or geometry.
- Canonical World preview identity is server-owned: non-system commands cannot create or repoint managed previews, change their type, or delete them while their target is live. Missing-target previews remain removable. Users may move and resize previews or parent them under ordinary Frames. Ordinary Spaces may create and delete their own `spacePreview` nodes through normal UI commands.
- Legacy `canvasRef`, `frameRef`, `nodeRef`, `SET_PORTAL_NODE_PINS`, and `GET /api/canvas/:canvasId/references` are retired rather than supported compatibility surfaces. The current model is specified in [space-preview.md](./space-preview.md).
- Node filenames are `safe(label).md`; the node's stable id lives in the `id:` frontmatter field.
- The Disk `BlobStore` maps each Space scope to `.artifacts/`, with blobs named `<artifactId><ext>` and no manifest file — the filename is the URL key. Artifacts are one of four blob areas a Space has, resolved as `space(canvasId).artifacts`: `put()` requires an existing Space record, while reads and `deleteAll()` remain available for recovery after a record goes missing. `CanvasStore` owns no artifact methods. Blob adapters keep bytes in local files (`disk`) or objects (`azure`), never in structured records. Both are selectable; the Azure adapter is described in §2c.
- Remote PDF preprocessing writes the already-fetched source bytes into the Space BlobStore as `artifact-<id>.pdf` before structured persistence and replaces the node's remote `src` with that key. As with other artifact imports, this blob write precedes the node write operation; a later structured persistence failure may therefore leave an unreferenced blob until Space deletion, while a blob-write failure degrades to retaining the remote URL.
- Events are append-only JSONL (`events.jsonl`); each line is `{ ts: number, payload: RecentAction }`.
- The memory analyzer reads Space existence and at most 100 recent action events through one `SpaceHandle`. A missing Space skips the pass before reading memory files or calling the model; corrupt part data still fails the pass. Memory body/state files remain materialized workspace paths, while Agenetes-owned chat history is not part of the curator bundle.
- **Chat history is Chat-V2, owned by Agenetes L2 — not `CanvasStore`.** Which store owns it depends on where the Space lives: a namespace carrying a `storage.root` (Disk) keeps Tier-1 `<threadId>.events.jsonl` files and one live Tier-2 `chat_v2/turns.sqlite`; a Space that is rows reuses its own backend's `agenetes_*` tables, in SQLite or in Postgres; an unnamed namespace stays in memory. The Disk database stores all thread turns by `(thread_id, ordinal)` plus per-thread replacement generations, so newest and older display pages issue bounded ordinal queries rather than parsing complete histories; the SQL adapters keep the same ordinal and generation arrangement, so a stale history cursor is refused the same way on every backend. Its connection participates in Space-directory handle arbitration: rename and deletion close the database and WAL handles, while subsequent access reopens the resolved path lazily. Existing per-thread Tier-2 JSONL is a migration source only: first access imports valid records in order inside a savepoint, records idempotent completion, and renames the source to `.bak`; malformed and trailing partial lines are ignored, while failure keeps the source retryable. `CanvasStore` never touches either tier. Do **not** confuse `chat_v2/<threadId>.events.jsonl` with the sibling `events.jsonl` canvas action log.
- Durable Agenetes workload records live in `.history/threads.json` (`agenetes-v2` schema, one record per thread; written by `FileThreadStore`). The host-local `namespace.storage.root` is never persisted: reads bind each record to the current Space namespace, so a Home synchronized across computers cannot redirect storage back to another machine's absolute path.
- Conversation names have one authority selected by current ownership. Unbound Chat stores the current `{ title, source }` in `ThreadRecord.hostMetadata.huabuConversationTitle`; a Question uses its canonical node `label` and server-owned structural `conversationTitleSource` provenance instead. The shared title service resolves the Question first, so old thread metadata is not a second title after conversion. Its node adapter uses the Canvas mutex, canonical delta persistence, and Canvas Sync to keep the label/sidecar rename and structural provenance together without changing prompt content or lifecycle. Ordinary snapshots, commands, and undo cannot overwrite that provenance. Conversion transfers the effective title at creation, and eligible late generation/ACP updates continue through the same node writer. See [shared conversation naming](./agent-architecture.md#panel-conversation-titles).
- Canonical Task and Run records live in `.history/tasks.json`, owned by Huabu Server through the async `SpaceTasks` ledger (`read`, `create`, and `runs.create`/`runs.update`/`runs.complete`). The Disk adapter validates the versioned snapshot and referential integrity on every read, rejects duplicate identifiers and Runs whose Task is absent, serializes read-modify-write operations with an independent per-Canvas process-local mutex, and atomically replaces the file. This mutex is intentionally separate from the Canvas topology write coordinator, so Task metadata does not participate in `space.json` version CAS.
- Legacy chat files are migrated in stages: workspace activation converts the oldest pi-ai `Context` `chat/<threadId>.json` through `migrate-chat-threads.ts`, then writes compatible `chat_v2/<threadId>.turns.jsonl` staging logs through `migrate-chat-turns.ts`; the live Disk Tier-2 adapter performs the lazy final import into `turns.sqlite`. Each successful stage retires its source to `.bak`, and failures preserve a retryable source without replacing already durable history. The obsolete `CanvasStore` chat methods and `chatPath()` helper remain removed; `chatDir()` remains because change-review and agent-owned files still use that directory.

### Retired Portal/Pin topology on load

The composition-layer `space(canvasId).read()` applies the shared [`stripLegacyPortalTopology()`](../../packages/shared/src/utils/strip-legacy-portal-topology.ts) helper to the returned topology for every backend. It ignores only nodes whose top-level type is exactly `canvasRef`, `frameRef`, or `nodeRef`, plus edges incident to their IDs. It does not follow reference targets, remove ordinary descendants, or discard unrelated dangling edges or unknown node types.

A surviving node whose direct parent was ignored becomes a root: its position is rebased through the original ancestor chain and its parent-relative `extent` is removed. Children of surviving Frames retain their hierarchy. Missing ancestor positions contribute zero, and missing ancestors or cycles stop the coordinate walk. The helper does not mutate its inputs and preserves unaffected object identities and array order.

This filtering performs no writes, deletes no node sidecars or other local files, and does not change the stored version. The underlying structured handle and node repository remain unchanged. Web Canvas load, clipboard preparation and resolution, and undo/redo restore reuse the same helper rather than migrating old nodes into previews. Ordinary later saves, including a World reconciliation batch that actually adds or removes previews, may persist topology without the ignored entries; there is no dedicated disk cleanup or migration pass. Current command and full-state write boundaries reject attempts to reintroduce the retired types.

## 2b. SQLite layout — records in a database, bytes in files

`HUABU_STRUCTURED_BACKEND=sqlite` selects the second implemented structured backend. The blob axis is chosen separately, because bytes are always files — `disk` here, and §2c for the Azure pairing. It needs **no Workspace folder and no Space directories**: every record is a row, and the only directories are the ones a Space's bytes sit in.

SQLite uses Node's built-in `node:sqlite`, which requires the `node:` prefix. The server and worker bundles preserve that prefix with tsup's `removeNodeProtocol: false`; stripping it makes desktop startup try to load an npm package named `sqlite` and fail before the server can listen.

```
<HUABU_DATA_DIR>/storage/
  sqlite/                         # the SQLite backend's area
    huabu.sqlite                  # every record; override with HUABU_SQLITE_PATH
    huabu.sqlite-wal              # WAL sidecars, managed by SQLite
    huabu.sqlite-shm
  disk/                           # the Disk backend's area
    workspaces.json               # Disk *structured* store: Workspace registry (unused here)
    blobs/                        # Disk *blob* store; override with HUABU_BLOB_ROOT
      <workspaceId>/
        <canvasId>/
          skill.md                # retired guide blob retained only for cleanup compatibility
          .artifacts/             # blob area `artifacts`
          .memory/space.md        # blob area `memory`
          .upload/                # blob area `uploads`
```

Each directory under `storage/` is named for the backend that owns it, and one file per backend decides its layout: `backends/disk/data-dir.ts` and `backends/sqlite/database.ts`. The composition root asks them and builds no path of its own (`module-boundaries.test.ts` enforces that).

`storage/disk/` has two owners, so they get separate subtrees. `workspaces.json` is the Disk _structured_ store's Workspace registry — present only on a Disk-structured deployment, and never inside `blobs/`, because the blob store deletes whole directories and the registry is not its to delete. `blobs/` is the Disk _blob_ store's, reached only when the structured backend gives a Space no folder; `HUABU_BLOB_ROOT` moves that subtree alone.

The byte root is Server-owned, not a Workspace folder: nothing in it is a Space record, and the Disk-only capabilities below stay unavailable because they need a real Space tree, not merely a directory.

The layout beneath `<canvasId>/` is byte-for-byte the one the Disk profile uses inside a Space folder, because it is the same adapter. `blobs=disk` names a _medium_ — bytes are local files — and composition names the place, under one rule: **a Space's bytes live with the Space.** On a Disk-structured profile the Space _is_ a folder, so its bytes stay inside it, which is what keeps a Space folder self-contained for bundle export, reveal-in-file-manager, RFS, and the file tools. On a database-structured profile the Space has no folder to be inside, so the adapter gets the root above. One rule, two outcomes — the Space has two possible homes.

| Table              | Holds                                                                                                                                    |
| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `workspaces`       | Workspace identity and display name; `forgotten_at` is how `remove()` forgets a member without destroying what it owns                   |
| `spaces`           | One row per Space, scoped by `workspace_id`; `is_world` marks the hidden World, and a partial unique index keeps it to one per Workspace |
| `nodes`            | Complete node JSON plus its opaque revision token and de-duplicated label key                                                            |
| `events`           | The Canvas action log, ordered by an autoincrement id                                                                                    |
| `changes`          | One coalesced change-review snapshot per `(Space, thread)`                                                                               |
| `tasks`            | The versioned Task/Run snapshot                                                                                                          |
| `delta_log`        | The executor's private journal, keyed by committed Space version                                                                         |
| `space_extensions` | One row per extension namespace — the parent an owner's own tables cascade from                                                          |

Owner-created tables hanging off `space_extensions`: `extension_documents` (memory bookkeeping and the debug prompt log) and `agenetes_threads` / `agenetes_events` / `agenetes_turns` (the conversation stores). Storage never reads them; deleting a Space removes them by cascade.

Canvas action-event reads validate the complete chronological log before applying a tail limit, matching Disk strict-read behavior; a malformed older row remains an error even when the requested limit would exclude it.

Notes an operator needs:

- **A Workspace is a row.** There is no folder to pick, so the Server creates and activates one on first start and reports `path: null` with `canChangeWorkspace: false`; the client shows no picker. Switching Workspaces re-scopes the one connection and reopens nothing.
- **The connection is shared.** The structured store and the Workspace repository use one `node:sqlite` connection, opened in WAL with `synchronous = NORMAL`, a bounded `busy_timeout`, and foreign keys enforced. One process, one connection: nothing here promises a multi-process fence.
- **Bytes are outside the database.** The blob axis is a file system on every profile, so a Space's uploads, artifacts, guide and memory body are ordinary files under the byte root and the database stays the size of its records. Deletion order is the composition layer's saga — sweep every blob area, then drop the record — and, where the record is a row, composition also removes the `<workspaceId>/<canvasId>/` directory it placed those areas under, because nothing else would.
- **What this profile does not serve** is declared in `capabilities.ts`, logged at startup, and refused in the same words at each call site: choosing/creating/revealing a Workspace folder, `.huabu.zip` export and import, reveal-in-file-manager, the built-in agent file tools, RFS's file plane, external-note discovery, the Workspace `setting/user.md` memory document, and user-authored skills under `setting/skills/`. A Space's _own_ memory body is unaffected — it is a blob. Bundled skills are unaffected; retired Agent Team folders remain data, not a runtime skill source.

  These are keyed on the **profile**, both axes. Most need a Space or Workspace to be a real directory (a structured-backend property); bundle export, bundle import, the file tools, and RFS additionally need the Space's _bytes_ to be in that directory, which is the blob backend's. Each row states a requirement with one clause per axis: every clause present must hold (`and` across axes), any listed backend satisfies its own clause (`or` within one), and an absent clause requires nothing — so a blob-agnostic row never needs editing when a blob backend is added. On the hybrid profile the answer is unchanged: a file system for the bytes hands nothing back, because every row still needs the record and node documents to be files. Refusals ask `storageServes(id)`; `module-boundaries.test.ts` checks that every declared row is refused somewhere.

## 2c. Postgres and Azure profiles

All six structured/blob pairings are selectable: `validateStorageProfile()` admits `postgres` and `azure` beside `disk` and `sqlite`. `HUABU_STRUCTURED_BACKEND=postgres` with `HUABU_POSTGRES_URL` puts Workspaces, Spaces, nodes, logs, Tasks, extension parents, and agent conversations in one Huabu database or schema; `HUABU_BLOB_BACKEND=azure` with `HUABU_AZURE_BLOB_CONTAINER` and either an account URL or a connection string puts bytes in an existing private container. Both connect before first use, so `requiresExplicitInit()` keeps either profile off the lazy path and a deployment that names one must reach storage through an awaited `initStorage()`. Filesystem capabilities keep their existing declarations, including the features that require both Disk axes, and local runtime state still needs a writable data directory. This remains a single-Server topology: SQL locking is not distributed admission, and a Space deletion that spans rows and bytes is not a distributed transaction.

### Postgres lifecycle, records, and coordination

`backends/postgres/database.ts` owns a `pg.Pool` per context, shared by `PostgresStructuredStore` and `PostgresWorkspaceRepository`. Defaults are four connections, a five-second connection timeout, and a thirty-second idle timeout; callers may supply `PoolConfig` overrides. Initialization applies contiguous versioned migrations in a transaction under a database advisory lock, recording the version in `huabu_schema_version`. A future schema fails without modification, and migration failure rolls back so initialization can be retried. Health runs a liveness query. Closing drains the context's queued transactions and ends its pool; operations on a closed or uninitialized context fail. A structured store closes a context it constructed, while an injected context remains its caller's responsibility.

The v1 schema has the same record families shown in the SQLite table above, using PostgreSQL identity columns, foreign-key cascades, uniqueness constraints, and JSON-validating text columns. Shared `backends/sql/` codecs and rules own JSON serialization, identity/name validation, collision allocation, and Task/Run transitions; SQL dialect and migration history stay adapter-owned. Parameter values are bound. Workspace activation changes the context's active identity without reopening its pool; retained Space handles and queued operations reject an inactive Workspace. A call running in a Workspace scope (`modules/workspace/context.ts`, used in Bubble mode) reads that Workspace instead, per call, so concurrent calls in different Workspaces share the pool without sharing a namespace; transactions bind it when they open, and the one database-wide write order still applies. Forgetting a Workspace marks its membership row without deleting data. `ensureDefault()` reuses a registered Workspace or creates one if no registered Workspace remains, including after the last one was forgotten.

Structured mutations run in native transactions with a five-second lock timeout and a database-wide transaction advisory lock. This conservative write order makes CAS, label allocation, Task/Run mutation, and node → Space record → delta batches atomic across independent pools. SQL failures roll back; failed rollback discards the connection, and a failed operation does not poison the next queued writer. Reads use the pool directly; bulk node reads use bounded batches, and streaming supports cancellation.

The existing process-local Space lifecycle gate and keyed transaction queue are shared by contexts whose resolved database name and `huabu_schema_version` table schema match. Resolution queries PostgreSQL instead of comparing connection strings, so credentials, pool settings, and connection aliases cannot split coordination. Matching names on different servers conservatively share the same queue and per-Space gate too; distinct schema names remain independent. Deletion closes mutation admission and drains already-admitted transactions across peer contexts before returning a deletion session for blob cleanup. New node, Task, event/change, and other guarded Space mutations reject while deletion is pending. No SQL transaction stays open across blob I/O. `finish()` deletes the Space and cascades its owned rows; both finish and abort release admission. The per-context tail remains only to drain that pool on close. This gate is not a distributed deletion fence, and blob cleanup plus row deletion is not a distributed transaction.

A Postgres extension substrate exposes its pool and a Space-owned namespace row. Existing namespaces are read before insertion so repeated resolution does not consume identity values. Agent-owned asynchronous document/log helpers lazily create `extension_documents`, keyed by extension id and document name, with cascade deletion and atomic SQL log append. The substrate is a raw owner extension point; direct owner SQL does not enter the structured adapter's transaction queue or deletion gate.

### Agenetes conversation persistence

The three Agenetes storage ports accept a value or a promise, and the mounted stores are dispatchers: a namespace with a `storage.root` gets the file stores, a named namespace without one gets the store for the active structured backend, and an unnamed namespace stays in memory. `agent/agenetes/postgres-stores.ts` owns `agenetes_threads`, `agenetes_events`, `agenetes_turns`, and `agenetes_turn_generations`, each hanging off the Space's `space_extensions` row with `ON DELETE CASCADE`, so deleting a Space takes its conversations with it. Writes run in a transaction under a per-thread advisory lock with a five-second lock timeout; a wholesale replacement bumps the thread's generation, which is what refuses a history cursor issued against the previous arrangement. A missing Space is each adapter's own case: reads answer empty and writes refuse.

The application awaits that persistence throughout. A thread snapshot persists before its notification, an event persists before it is published live, a turn boundary is durable before the first frame of the turn, and `close` drains a thread's queued state writes; a failed state write surfaces on the next `record`, `run`, or `close`. Conversation rehome awaits every write and every compensating undo. Memory bookkeeping and debug prompt logs go through the same asynchronous extension helpers.

### Azure lifecycle, keys, and byte publication

`backends/azure/blob-store.ts` receives an operator-owned container and a Workspace-key provider. Its environment factory requires `HUABU_AZURE_BLOB_CONTAINER` and exactly one of `HUABU_AZURE_STORAGE_ACCOUNT_URL` or `HUABU_AZURE_STORAGE_CONNECTION_STRING`; optional `HUABU_AZURE_BLOB_PREFIX` defaults to `huabu`. An account URL must be an HTTPS service root without embedded credentials, a query, or a fragment. It uses `DefaultAzureCredential`, which supports Azure managed identity and local developer credentials such as Azure CLI login. The Azure SDK owns token caching and refresh. To require managed identity in Azure, set `AZURE_TOKEN_CREDENTIALS=ManagedIdentityCredential`; for a user-assigned identity, also set `AZURE_CLIENT_ID` to its client ID. Grant that identity Storage Blob Data Contributor on the existing container. Connection strings remain available for Azurite and existing deployments; setting both authentication sources is an error, and identity failures never fall back to a connection string. Initialization and health check container properties; the adapter never creates or deletes the container. Closing invalidates operations, and retained scopes reject a changed Workspace key.

Browser uploads and downloads stream through Huabu's existing artifact API. The server accesses Azure with its selected credentials; it neither generates Blob SAS URLs nor redirects the browser to Blob Storage. Managed-identity deployments can keep Shared Key authorization disabled and do not require browser-to-Blob CORS. See [Azure Blob authorization with JavaScript](https://learn.microsoft.com/en-us/azure/storage/blobs/storage-blob-javascript-get-started?tabs=javascript%2Cazure-ad) for identity and role setup.

The identity belongs to the Server host, not to Huabu. Agent environment isolation strips only the `HUABU_` namespace (see [agent reachback](./agent-reachback.md#environment-injection-and-isolation)). With the local identity provider, the embedded Agentlet and its agents run on the Server host as the same OS user, so they can obtain the same storage token: through the platform identity endpoint (`IDENTITY_ENDPOINT`/`IDENTITY_HEADER`), IMDS, a workload-identity token file, or `AZURE_CLIENT_SECRET` when `EnvironmentCredential` is used. Such an agent can read, write, and delete objects in the container outside Huabu's Workspace keying. Connection-string deployments have the same agent reach, because those agents can read the secret from `.env` or the Server's process environment; identity mode makes the access ambient instead of removing it. Grant the role on Huabu's container only, never on the account, and give the host identity no privileges that agents should not hold. Bubble deployments do not run the embedded Agentlet; their agents run on users' own devices and cannot reach the Server's identity.

Keys have the shape `<prefix>/<encoded-workspace-key>/<canvasId>/<area>/<encoded-name>`, where area is `artifacts`, `guide`, `memory`, or `uploads`. The prefix is one validated segment. Workspace keys use URI component encoding with trailing dots escaped. Blob names use the shared flat-name normalization, then escape percent signs, control characters, and trailing dots so Azure's trimming cannot collapse distinct names. Listing decodes only canonical adapter keys; guide membership remains restricted to the port's allowed names. `deleteAll()` sweeps the area's prefix, including uncommitted uploads and snapshots, without touching neighboring Spaces or the container.

Uploads stage four-MiB blocks with unique per-upload block ids and publish only through `commitBlockList`; an interrupted stream preserves the previously committed object and Azure expires leftover uncommitted blocks. The adapter rejects uploads exceeding 50,000 blocks. A process-wide keyed mutex serializes staging and commit for each container URL (without SAS query data) and object key, because a competing commit can discard another upload's uncommitted blocks. This is not distributed writer ownership across Server processes.

`open()` supports inclusive byte ranges and obtains metadata and bytes from one download response; missing blobs return `null`. `read()` buffers the whole object, while `hasMany()` bounds concurrent metadata requests. `materialize()` streams into a private temporary file, makes it read-only, and returns a disposable lease that removes its directory; failures clean up the partial file. There is no cross-store atomic commit and no remote directory emulation; operators provision the container, and deleting a Space only sweeps its own scopes.

### Profile verification

`pnpm run test:storage-backends` provisions disposable PostgreSQL 18 and Azurite services through Vitest global setup and Testcontainers, exactly as CI does. Each case owns an isolated schema or container, and teardown handles partial startup failures. Contracts and integration cases cover fresh/existing schemas, rollback, constraints, CAS and name allocation across pools, Workspace isolation, peer deletion admission and draining, extension persistence/cascades, byte ranges, key mapping, failed staged uploads, and same-key upload serialization. Conversation and product cases run over every selectable profile, so a Space's records, bytes, and conversation are exercised together on each pairing. Docker is required; unavailable infrastructure fails the suite. Co-located unit tests run in the normal server suite without Docker. Verification against a live Azure account, and coordination between several Servers on one database, remain separate work.

## 3. Storage composition and ownership

`apps/server/src/modules/storage/` has three layers plus its composition root:

| Path                                            | Responsibility                                                                                                                                                                                                      |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ports/blob.ts`                                 | Backend-neutral `BlobStore` connection/scope contract for opaque bytes and bounded materialization leases.                                                                                                          |
| `ports/workspace.ts`                            | Backend-neutral Workspace identity, membership, and locator repository.                                                                                                                                             |
| `ports/structured.ts`                           | Backend-neutral `StructuredStore`, the `SpaceRepository` collection — including the `ensureWorld()` bootstrap hook — and the `SpaceHandle` composite: record read/ordered write, nodes, changes, Tasks, and events. |
| `ports/contracts/`                              | Reusable Space-collection, node, Space-write, log, blob, extension-substrate, and store suites; guarantees are the minimum every adapter implements.                                                                |
| `capabilities.ts`                               | The Disk-only capability matrix `validateStorageProfile()` consults, plus the shared wording for a startup declaration and a runtime refusal.                                                                       |
| `testing.ts`                                    | Product harness: opens a real profile on a temporary Workspace through the production lifecycle, once per entry in `PRODUCT_STORAGE_PROFILES`.                                                                      |
| `backends/disk/`                                | Disk implementations: before-image rollback for rejected ordered batches, plus the write-ahead intent and recovery of §4.2.                                                                                         |
| `backends/disk/legacy/`                         | The legacy `CanvasStore` and its synchronous adapter primitives, bounded Workspace-qualified cache, and process-local node tombstones.                                                                              |
| `compatibility/canvas.ts`                       | Residual Disk reads plus direct-module create/delete test fixtures; lifecycle writers are not exported from the public storage barrel.                                                                              |
| `space-lifecycle-admission.ts`                  | Backend-neutral, writer-preferring single-process coordinator shared by structured mutations and blob puts during a delete session.                                                                                 |
| `profile.ts` and `storage.ts`                   | Two-axis backend selection, validation, adapter construction, process-wide lifecycle, blob scopes, and the blob-first deletion saga.                                                                                |
| `index.ts`                                      | Public exports only; application code imports here rather than reaching into an adapter.                                                                                                                            |
| `canvas-store.ts`, `paths.ts`, `canvas-dirs.ts` | Deprecated forwarding shims with no logic, retained only for high-fanout compatibility imports.                                                                                                                     |

The Disk structured adapter and compatibility facade resolve the same cached legacy object, so migration does not create two in-memory authorities. The SQLite adapter instead owns one explicit database filename and connection; retained handles stay bound to that connection, and its `init`, `health`, and `close` lifecycle is exercised by adapter and mounted product tests. Postgres owns an async connection pool with the same Workspace binding. All portable repository methods are async. `SpaceRepository` owns membership reads, structured create/rename, and an exclusive `beginDelete()` session; composition holds that session across the existing blob-first delete saga and then calls `finish()` or `abort()`. Every Space-record write goes through `SpaceHandle.write`, which is the version-checked replacement with the node and delta batch attached; `SpaceHandle.read` reads only. `SpaceNodes` returns complete records plus revision tokens without exposing filenames. `write` preserves the old node mutations → Space record → optional delta order. When a normal in-process node → record → delta batch rejects, the adapter must restore that batch's prestate before returning the rejection. An explicit title rename remains the preceding ordered, best-effort boundary and is not rolled back with the batch. The port does not promise process-crash or power-loss recovery, a determinate result after an unknown remote outcome, multi-process serialization, idempotent retry, or publication. Disk meets the in-process restoration requirement with its existing before-image rollback; SQLite uses a native transaction.

Canvas persistence DTOs and the write coordinator live under `modules/canvas/`; Workspace identity, durable membership, and Disk locators live under `modules/storage/`, while active-Workspace lifecycle and boot migrations remain under `modules/workspace/`; generic filesystem and Markdown codecs live under `utils/`. `canvasRoot()` validates the identifier and then verifies that the resolved Space directory remains a strict descendant of the active Workspace before any downstream Disk operation receives it. `module-boundaries.test.ts` enforces the storage dependency direction, prevents new consumers of the forwarding shims, and holds the neutrality guard: no production file outside `storage/` may import a Disk layout symbol or a legacy `CanvasStore` symbol. The check is import-level and symbol-level — a local variable that happens to be called `artifactPath` is not a violation, while importing `canvasRoot`, or reaching `getCanvasStore` through the barrel, is. Migrations are exempt because they rewrite frozen historical on-disk shapes; tests are exempt for the same reason they may name an adapter.

Disk Space directory rename resolves both basenames through the shared `resolveDirectChildPath()` boundary before calling `renameSync`. The helper uses the CodeQL-recognized normalized-root containment pattern and then requires a separator-free direct child on both POSIX and Windows. This defense-in-depth check applies even though user-facing titles are already converted with `toSafeFilename`, so no upstream caller can turn a nested or absolute path into a rename target.

Space deletion is serialized against composed blob puts by a writer-preferring admission coordinator and holds an active-Workspace lease across blob cleanup and structured destruction. `beginDelete()` acquires the exclusive session before blob I/O; `finish()` removes structured state, while `abort()` releases the fence without doing so. Blobs are swept before structure so a failed sweep can be retried while the Space record still names them. Puts already admitted may finish; a put queued behind a successful deletion rechecks existence and fails without recreating blobs, while a failed blob sweep leaves the record available for retry. Mutations through existing Space handles and repositories reject while deletion is active or queued; reads remain available for cleanup. Residual direct-filesystem capabilities such as ZIP import, RFS upload/delete, and external-note claim are outside this repository fence; each is a declared Disk-only capability rather than an undesigned gap, so a non-Disk profile refuses the feature instead of being unselectable because of it.

Cross-Space Move is an application-level compensated operation, not a new storage transaction. It holds an active-Workspace lease and both Canvas write mutexes, optionally creates a named destination Space, copies every referenced Blob to a fresh destination key before structural mutation, commits the destination Space, closes and rehomes eligible dormant Agent conversations under their turn leases, then deletes the source selection and optionally creates a `spacePreview` breadcrumb in one source executor batch. A determinate later failure rehomes completed conversations back before applying inverse source and destination deltas; after successful compensation, a request-created destination and its blobs are removed. Unknown Agenetes outcomes or compensation failures retain both Spaces for reconciliation and never trigger automatic destination deletion. Failure to remove a new destination after a determinate failure is surfaced explicitly rather than reported as an ordinary rejected move. BlobScope intentionally has no per-key deletion, so a failed move into an existing Space may leave freshly copied unreferenced blobs until that Space is deleted; referenced source blobs are retained because the source Space may still contain other references. The guarantee remains all-or-compensated while the Server continues running and receives determinate backend outcomes, matching the existing `SpaceHandle.write()` boundary.

Retained Disk Space repository and handle instances, blob scopes, and legacy `CanvasStore` instances reject use after the active Workspace changes. Every Workspace getter answers for the Workspace the call runs in: its scope where one is open, else the process-active one. The Disk directory index is kept per Workspace folder and the SQL World id per Workspace, so several Workspaces are served side by side; operation leases count per Workspace. Each `spaces()` call returns a fresh Workspace-bound handle and each read rescans current Disk state. The Workspace-qualified LRU is cleared and rebuilt on the next lookup after a switch. The delete-session contract covers overlapping operations through one configured backend instance. Disk realizes it with the shared process-local coordinator; it is not a multi-process transaction or distributed lock, and a SQL adapter must supply an equivalent backend-instance fence using its own mechanisms.

The `chat_v2/` two-tier log and `threads.json` remain owned by Agenetes L2 (`FileEventLogStore`, SQLite-backed `FileTurnStore`, and `FileThreadStore`), wired in [agenetes/drivers.ts](../../apps/server/src/modules/agent/agenetes/drivers.ts); see [agent-architecture.md](./agent-architecture.md) §5. Workspace activation is coordinated by `apps/server/src/modules/workspace-activation.ts`; the isolated child entry is `workspace-prepare.worker.ts`, and the ordered migration sequence is centralized in `workspace-prepare.ts` with migration implementations under `modules/workspace/migrations/`.

Space hierarchy serialization also lives in `modules/canvas/write-coordinator.ts`. Its process-local queue covers ownership validation and mutation, collection/move, subtree deletion, and composed Space creation/deletion. It acquires a Workspace operation lease before queueing and holds it through completion, permits nested calls for creation and compensation, and invalidates inherited ownership once the outer operation ends. Acquire the hierarchy lock before any Canvas mutexes. The storage composition root uses this application coordinator for lifecycle entry points; adapters retain their own per-Space deletion admission. Neither coordinator provides distributed locking or crash-atomic transactions.

Standalone `deleteSpace()` lists membership to reject non-leaf deletion. Confirmed subtree deletion lists membership once under the hierarchy lock, validates the confirmation token, and uses `deleteSpaceFromValidatedTreeAlreadyLocked()` for its descendant-first plan instead of repeating that listing for every member. This internal path asserts active hierarchy-lock ownership and reuses the same per-Space deletion session and blob-first cleanup. The caller stops on the first failure and reports completed and remaining members; Canvas mutexes, Agent turn leases, and the Workspace lease remain held across the operation.

Node-sidecar DELETE removes the record of a node that is no longer in the Space; for a node that is in the Space it answers success and removes nothing (the batch that deletes a node deletes its record, see [canvas-realtime-sync.md](./canvas-realtime-sync.md#browser-structure-edits)). It validates its shared Canvas/node identifier contract, acquires a Workspace operation lease, and captures the Workspace-bound Space handle before waiting on the Canvas mutex. Workspace activation is refused throughout queueing and deletion; the lease is released on every success or failure path.

### 3.1 Task creation across persistence domains

`TaskService.create()` validates its shared request contract, target Canvas, and selectable default root Profile before mutation. It then creates a static ordinary Task Note through the authoritative Canvas executor and persists the canonical Task record through `SpaceTasks.create`.

The Task Note and Task record deliberately remain separate persistence domains rather than introducing a cross-store transaction. If Note creation is rejected, no Task record is written; if Task persistence fails after the Note is committed, `TaskCreationError` reports the created anchor node id so the visible orphan is explicit and recoverable.

### 3.2 Task Run launch sequence

`RunLauncher.start()` validates the shared request, resolves the Canvas-scoped Task, and verifies the effective selectable root Profile before mutation. It persists a `pending` Run snapshot first, then derives a root-level Agent position to the right of the Task Note with a stable vertical offset for each Run of that Task.

The launcher creates the fixed root Agent Node through `AgentNodeService`, records its node and thread ids, and prepares the first turn through `AgentThreadService`. Because the invocation stream is lazy, the launcher persists `running` and `startedAt` before it begins background draining; a failure to persist that transition disposes the prepared invocation so Agent execution does not start.

The launch path deliberately has no compensation transaction. A launch failure leaves the Run `pending`, while any root node or thread ids already created are retained in the Run record when available and returned on `RunLaunchError` for explicit recovery.

### 3.3 Task Run completion

`RunCompletionService.complete()` validates the shared request and delegates the guarded transition to `SpaceTaskRuns.complete()`. All structured adapters perform lookup, `running → completed`, and persistence inside one Task-snapshot mutation boundary: Disk uses the per-Canvas Task mutex and atomic file replacement, while SQLite and Postgres use native transactions and share Task/Run transition rules. HTTP and built-in-tool callers therefore share one atomic transition rather than performing a read-then-update race.

A completed Run stores immutable `completion.completedAt` and an optional trimmed caller-owned `completion.message`. The platform treats the message as untrusted text and does not interpret issue, pull-request, or URL semantics. A retry with the same normalized message is idempotent and preserves the original timestamp; a different message conflicts. A `pending` Run cannot complete, and Agent turn termination never implies Run completion.

## 4. Portable write seam and application ordering

Agent Node FSM metadata (`bindingState`, `invocationToken`, `status`, `errorMessage`, `viewed`) and association (`threadId`) live in the Space node record, separate from authored Markdown content. On Disk these are node data in `space.json`; SQLite persists them through its existing structured record adapter. `AgentNodeBindingCoordinator` confirms the canonical workload with `agenetes.record()` through the existing Disk/SQLite conversation-store dispatch; application FSM modules use the portable `space(canvasId)` facade and never name `.history/threads.json` or a database table.

Canonical create persists a ThreadRecord before the Canvas projection acknowledges Bound. These are ordered writes, not a cross-store transaction. If the second write fails, the next guarded edit or interaction recognizes the record and completes promotion; no background recovery scan or automatic invocation replay is added. Bound remains monotonic even when the record later goes missing. Existing in-process persistence restoration and crash limitations below are unchanged.

Web undo/redo resurrection writes the restored topology and its sidecar together: a tombstoned, structurally absent node correctly suppresses late content writes with a benign response, so the web sends one `RESTORE_NODES` batch that carries the node's content and the executor writes the sidecar in the same commit. The batch waits for actual in-flight DELETE completion instead of treating fetch abort as cancellation, and content saves for the node wait until the batch is answered. A returning Agent Node is re-associated through its own endpoint and keeps the content queue's hold: its body is written only after the association is confirmed, starting from the absent-sidecar content revision baseline; normal content CAS remains unchanged. See [Undo interaction](./canvas-realtime-sync.md#undo-interaction).

Preprocessing for a returning node is blocked until the restoring batch is answered (for an Agent Node: until its held content has been written). The preprocessing queue owns whether interrupted or newly requested work is pending; storage does not decide this or automatically reprocess completed nodes. See the authoritative [client responsibility boundary](./node-preprocessing.md#client-responsibility-boundary).

For optimistic Question creation, the canonical create command writes the initial sidecar and the web content queue suppresses its generic new-node PUT. A genuine edit made before acknowledgement waits for the tracked create command rather than assuming the sidecar is absent. Question content requests may contain only the locally dirty sidecar fields; the route preserves omitted fields from the existing record, while authored-content CAS remains based only on `nodeRevisionOf({ content, src })`. The web fences PUT results with its authoritative-baseline generation: if Canvas Sync seeds a newer revision while a request is in flight, the older success cannot regress the baseline or label and an older conflict is retried instead of surfacing a false `NODE_CONTENT_CONFLICT`.

Standalone content PUT and preprocessing persist call `updateNode(SpaceNodes, ...)`. The coordinator acquires the existing Workspace-operation lease before Canvas-mutex queueing and retains it through the asynchronous read, caller projection, CAS put and any conflict readback. A Workspace activation cannot strand a queued or executing standalone write; refused lease admission does not read storage or invoke the projection. Every terminal outcome and thrown error releases the lease, without retrying the caller's mutation or treating an unknown persistence result as success. The Canvas-domain promise-chain mutex remains per Space. The caller still owns field-merging policy; authored-content revisions remain `nodeRevisionOf({ content, src })`, and a genuinely stale baseline still maps to the same `NODE_CONTENT_CONFLICT` response. This process-local protection does not give these writes a request id or result record (§4.2), or revoke retained raw storage capabilities.

Ordinary content PUT's pure body/label/metadata resolution lives in `node-content-update.ts`; it owns CAS, label protection and empty-body protection for that route. Preprocessing retains its existing owner-specific merge callback.

### 4.1 Executor persistence restoration

For a node/delta batch, Disk's ordered writer changes multiple files: affected node sidecars, `space.json`, and the append-only delta log. Its existing `runCanvasPersistenceTransaction()` helper now lives inside the Disk adapter. It captures raw bytes for `space.json` and affected sidecars, plus the delta log's existence and byte length. If a normal in-process write throws, rollback restores the sidecars and record bytes and truncates or removes the delta log back to its captured state before the rejection returns. A rejected node → record → delta batch therefore does not expose a completed prefix.

`CanvasStore.withValidatedNodeMutationTransaction()` validates `space.json` once, snapshots adapter-local tombstones for affected node ids, and grants the authoritative inserted-id set a tombstone bypass until the full commit succeeds. Rollback restores `space.json` through `writeNodeMutationRollback()` without inferring another tombstone transition, then restores the captured in-memory tombstones. The normal rejection path returns only after the persisted and in-memory prestate has been restored.

An explicit title rename is resolved before the protected node → record → delta batch and retains the old ordered, best-effort behavior; a later batch rejection does not promise to undo that rename. Artifact import happens before the Canvas mutex and is also outside this restoration boundary. Change-review records of an executor batch are part of the write (§4.2). Process termination, power loss, an unknown remote outcome, and uncoordinated multi-process access can still leave an unknown or partial result for a write without a request id: this restoration boundary itself has no filesystem WAL, startup recovery, durable tombstone or outbox. SQLite/Postgres satisfy the in-process batch guarantee with a native transaction. What a request id adds on each backend is described in §4.2.

### 4.2 Reliable save in the write

`executeOnServer` accepts two optional inputs: a request id (`operationId`, a UUID) and a read version (`basis`, the opaque string `b1.<lineage>.<version>`). Without them it behaves exactly as described above. Both are served by the ordinary `SpaceHandle.write` and its companion `SpaceHandle.save` member ([ports/save.ts](../../apps/server/src/modules/storage/ports/save.ts)); there is no second write path, no caller-visible session and no per-Space switch.

**Result records.** With a request id, the executor looks up the result record for (authenticated principal, request id) before ID allocation, foreign-source import or the engine run. The record holds a SHA-256 digest of the canonical request (`canvasId`, commands, basis, runs when stated, source, thread; not `runId`) and the complete response. The same digest returns the stored response verbatim, including generated node/edge ids and versions, marked `replayed: true`, and publishes nothing. A different digest is refused. Otherwise the batch runs and `write({ ..., result })` stores the record in the same commit as the node mutations, the Space record and the delta; no-op and all-rejected batches store theirs through `save.record()` without a version bump. Thrown domain errors are not recorded. A retry that arrives while the original is still running waits for it through a process-local single-flight map, the lookup is repeated under the Canvas mutex, and the write's own check is the final arbiter (`result-exists`). Records are kept per Space for 14 days; each write that stores one prunes at most 64 expired ones. A response larger than 4 MiB is not stored: the request is then served as if it had no request id, and a warning is logged. The stored response includes `nodeContentRevisions` as computed from the node records handed to that write, since the record is committed before anything can be read back; see [content revisions of a batch](./canvas-realtime-sync.md#content-revisions-of-a-batch).

**Node version stamps and the lazy baseline.** Each Space may have a save head: a `lineage` UUID, the `floor` version at which it was created, and sparse per-node stamps `{ created, membership, createdBy?, membershipBy? }`; a node without a stamp counts as `{ floor, floor }`, changed by nobody. The head does not exist until the first `save.stamps()` call — a read that returns a basis, which now includes the page load `GET /api/canvas/:id`, or an execute that supplies one — which creates it at the current version. Until then a write does no stamp work beyond one lookup. Afterwards every `SpaceHandle.write` advances the stamps itself from the previous and next record: a new id gets `{ to, to }`, a changed `parentId` sets `membership = to`, a removed id is dropped. Callers never maintain stamps, so `applyDeltasOnServer`, the node content PUT and Space-card rename keep them current as well. The pure rule is `advanceNodeStamps` in the shared engine ([readVersion.ts](../../packages/shared/src/canvas-engine/readVersion.ts)).

**Who made a change.** A write may name an `author` (`SpaceWriteInput.author`: `{ by, except? }`). The stamps it sets then record `by` — `createdBy` and `membershipBy` on a node it creates, `membershipBy` on one it re-parents (not for the ids in `except`); a write without an author records nobody and so forgets who moved the node before. `by` is an opaque key of at most 64 characters; the executor passes `pageKeyOf(principalId, pageId)` ([read-version.ts](../../apps/server/src/modules/canvas/read-version.ts)), the first 22 base64url characters of a SHA-256 over the transport's principal and the page's `originator.tabId`, so a stamp holds no principal id and a page id alone names nobody. Only an execute from a browser page whose every command was checked against a read version names an author; every other writer (agents, the content PUT, rename, revert, a page's batch without `runs`) is nobody. The keys live inside the stamp map, so no column or table was added: SQLite and PostgreSQL keep them in `space_save_heads.stamps_json`, Disk in `head.json`, and the schema upgrade from v2 is unchanged.

**Read-version check.** One check for every writer, only when a read version is supplied, and always over the nodes a command names (`commandReadTargets`); never "the version must equal head". A target that is missing, or was created after the quoted version and not earlier in the same batch, is `stale-target`. A target the command depends on the parent of — a `SET_NODE_GEOMETRY` item that carries a position, the nodes of `SET_NODE_PARENT`, `REORDER_NODES` (and its anchor), `ALIGN_NODES` and `DISTRIBUTE_NODES`, and the `cells` / `placements` nodes of `SET_FRAME_LAYOUT` — whose parent changed after the quoted version is `stale-parent`. `CREATE_NODES` and `CONNECT_NODES` are never checked, `expectRev` content CAS is unchanged, and same-field edits remain last-writer-wins. The check is an `admit` hook on the shared engine executor, built by `createReadVersionAdmission` ([readVersion.ts](../../packages/shared/src/canvas-engine/readVersion.ts)); [read-version.ts](../../apps/server/src/modules/canvas/read-version.ts) decodes what the caller sent against the Space's stamps.

The version is quoted in one of two ways. An agent quotes one `basis` for the batch: each command is judged on its own against the state it would run against, one stale target rejects that command, and the other commands keep the existing in-order, accepted-subset-commits-once semantics. A browser page quotes one basis per edit (`runs`): a run is judged once, over all its commands, against the state its first command would run against, and is taken or refused as a whole; a run may name earlier, unconfirmed edits of the same page it was made on top of (`after`) and is refused with `stale-parent` when one of them was (see [read versions of a page](./canvas-realtime-sync.md#read-versions-of-a-page)).

**A page's own change.** A stamp newer than the quoted version does not make a target stale when the same page made that change (`createdBy` / `membershipBy` equals the request's page key). This is what lets a page send a second edit of a node before its first is confirmed. It is sound because a stamp names a page only for a change that page was entitled to make: the write that set it was checked against a read version for every command, and the node was either a target that passed the check or — when the batch moved it as a consequence, such as the children a dissolved Frame releases — had its previous stamp at or below the oldest version the batch quoted, or already named the page (`unseenMoves` lists the others, which are stamped as nobody's). So when the last change to a node is the page's own, every change by anyone else before it was one the page had read, and there is none after it; a change by anyone else after it replaces the stamp and counts. "The same page" is the principal _and_ the page id: the same person's other device has another page id, and another person cannot use a page id to pass for it. A reloaded document has a new page id, so what the old document's last request committed is foreign to the new one unless the load already returned it.

**Review records.** The Review records of an agent batch travel in the same write (`reviews: [{ threadId, records }]`), are coalesced with the thread's stored list exactly as `changes.append` does, and are returned in the write result for the broadcast. They land with the record or not at all; a replayed request appends nothing.

**Rejections.** Three outcomes reject the request as a whole, before or instead of a domain result: `operation-id-reused` (the request id is already stored with a different digest), `basis-unknown` (the basis, or the basis of a run, has another lineage, a version above head or one below the baseline's floor) and `operation-outcome-unknown` (the write failed and the follow-up lookup failed too, so the caller must retry under the same request id). A write that fails while the lookup succeeds and finds nothing surfaces the original error.

**Backends.** SQLite and PostgreSQL keep `space_save_heads` and `space_save_results` (schema v3), both cascading from the Space row; the result check, the ordered write, the stamp advance, the Review upsert and the result insert share the transaction that already wraps state and `delta_log`. Shared SQL text, row codecs and pure rules live in `backends/sql/save-rules.ts`. Schema v3 and v4 created tables for an earlier, separate operation path that was removed before use; v6 drops them. Disk has no transaction, so a write that carries a result record is bracketed by a write-ahead intent under `<space>/.history/save/`: `pending.json` is flushed first, the existing writer runs with `head.json` inside its rollback scope, then `results/<hash>.json` is written and the intent removed. `space.json` is the commit point; recovery runs before every write, `save` call and Review read/write, and either completes the missing delta row, stamps, Review lists and result or drops the intent. A Disk write without a result record updates stamps and Review lists inside the existing in-process rollback scope only. A head whose version disagrees with the record is replaced by a fresh lineage, which refuses every basis issued before. An open page then gets `basis-unknown` for its next edit, is told once and loads the Space, which carries the new lineage. Importing a Space discards the bundle's `save/` directory.

**Cost of a baseline.** Pages always quote a read version, so every Space that has been opened has a head. Storage is one row (`space_save_heads`) or one file (`.history/save/head.json`) per Space, holding one entry per node created or re-parented since the baseline (about 60 to 150 bytes each, the two page keys included); entries of deleted nodes are dropped, and nothing prunes the others, so the map grows towards the number of live nodes that were created or moved after the baseline. Per write, on SQLite and PostgreSQL: one indexed read of the head row and a parse of the map inside the transaction that already replaces the whole `state_json`, and one `UPDATE` of `stamps_json` only when the write creates, deletes or re-parents a node. On Disk: one read and one atomic rewrite of `head.json` on every write (it carries the version), beside the rewrite of `space.json`. Computing the next stamps walks the previous and next node lists once in memory. None of this is a new order of cost — every write already serializes the whole Space record — but it is proportional to the stamped nodes, not constant. The load adds one `save.stamps()` call (a read; a write the first time).

**Not covered.** The node content PUT does not accept a request id or a basis; it advances stamps but a lost reply is not replayable. (There is no whole-Space `PUT /api/canvas/:id`; see [No whole-Space save](./canvas-realtime-sync.md#browser-structure-edits).) On Disk, sidecar writes that landed before a crash that preceded `space.json` are not undone; for a write with a request id the version, delta log, Review lists and result record are all-or-nothing, the sidecars are not. Every machine-token caller is one principal, so result records of different external agents share a key space and thread attribution proves only that the thread belongs to the Space. Single-flight is process-local. Tests terminate a separate SQLite writer before and after COMMIT and a Disk writer at each stage; this is process-termination evidence, not power-loss certification.

Blob materialization uses one shared disposable-copy implementation on Disk and Azure. Path-only consumers receive a read-only temporary copy; even a retained string or consumer changing its permissions cannot mutate authoritative bytes. Release removes that copy and invalidates the lease getter. This does not revoke raw Disk paths, extension connections or handles retained earlier, and process termination can still leave temporary files for host cleanup.

`executeOnServer` captures a Workspace lease before the result lookup, ID allocation or foreign-source preparation, and public inverse replay leases the Workspace before mutex queueing. RFS staged-upload creation/deletion likewise acquire the Workspace lease before Canvas-mutex queueing; the upload namespace is bounded with `safeJoin`, and exclusive creation prevents replacing a raced filename. This is not complete Space-deletion coordination, durable staging publication or revocation of a raw path previously handed to another caller.

### 4.3 Which nodes were written since a position

`SpaceNodes.changes(since?)` answers, without reading any node record, which nodes of a Space were written after a position, and returns the position the sequence stands at. It exists so a page that was not listening when node content was saved can be told what to fetch ([Content saved before the stream was open](./canvas-realtime-sync.md#content-saved-before-the-stream-was-open)); a content save does not change the Space version, so nothing else records it. Every node write counts — the standalone `put` behind the content PUT and preprocessing, and a `put` inside `SpaceHandle.write` — whatever field it changed, so a title or summary is covered as well as a body. A deleted node is not named. The answer is complete, not minimal: it may name a node written at the position itself, so a caller treats a name as "read it again". A position is `{ epoch, seq }`: `epoch` names the sequence, and a position of another epoch (or ahead of the sequence) is answered with `nodeIds: null`, "cannot compare".

What each backend persists per node, and what `changes` reads:

| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |

Both are written in the transaction that writes the node. `epoch` is `sqlite:<Space created_at>`, so a Space deleted and created again under the same id is another sequence                                 | Two indexed statements; rows returned only for nodes written since                                                                                                                                     |
| PostgreSQL | The same columns                                                                                                                                          | The same two columns (`BIGINT`), schema v3. The Disk position is `min(latest sidecar modification time, now)` and a node is named when its time is **at or after** the position asked from. "At or after" makes a file system with coarse timestamps safe: a write in the same tick as the position is named again instead of missed. Taking the position from the files rather than from the clock keeps it in the file system's own time, so a workspace on a volume whose clock differs from the server's is unaffected; the bound by `now` keeps a sidecar dated in the future from carrying the position past later writes, and lets the position follow a clock that was set back. The costs: the nodes written in the same millisecond as the Space's most recent write are named on every question until a later write moves the position (one or a few redundant fetches), and a future-dated sidecar is named until the clock passes it. What the Disk marker cannot see is a write dated before the position: a clock set back past the Space's most recent write and not yet caught up, or a sidecar put in place with an older modification time preserved (`cp -p`, a sync client restoring a file). SQL backends have neither limit.

Rows that existed before schema v3 share position 0, and the migration reads no record. The contract is in `space-nodes.contract.ts` (run for Disk, SQLite and PostgreSQL), including a position read before the store is reopened and a node put by a Space write.

Executor and revert batches already hold that mutex for their whole command
batch, so they make one `SpaceHandle.write(...)` call instead of
re-entering the standalone coordinator per node. That call receives complete
node puts/deletes, the next Space record, and its optional delta row. HTTP
response schemas/statuses, version increments, no-op handling, and SSE
publication remain in the Canvas application layer. Conflict responses now
report the existing logical title/label instead of a Disk filename or directory
locator.

Phase 4 changes no shared schema or web/client source. HTTP statuses and schemas
and the SSE shape remain stable, subject to the logical conflict-value correction
above. Publication remains an application action after persistence rather than
a storage-port responsibility.

The mutex is single-process application policy. It is not advertised as a
backend transaction or distributed lock; an adapter supplies its own CAS and
may be stronger than the common contract.

Ordinary structure edits (`POST …/execute`) compose supported editable fields with current Agent metadata under this same Canvas mutex. Trusted projections and editable inverse replay use already-locked writer entries to avoid recursive acquisition; draft acceptance holds a nonblocking turn lease through its actual Canvas write. Space Move retains sorted multi-Canvas locking and nonblocking turn acquisition rather than waiting for an invocation while holding a Canvas lock.
