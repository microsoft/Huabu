# Canvas Real-Time Sync

## Overview

Out-of-band and in-process canvas mutations propagate to **every open tab** of
the same canvas over a Server-Sent Events (SSE) stream, without a manual
reload. This is the **multi-agent** substrate: any mix of the built-in chat
agent, question-node agents, ACP agents, and headless `/execute` callers can
write concurrently and all live tabs converge.

Two channels cooperate:

- **Structure** — server-authoritative. Every persisted batch produces a
  `Delta[]` diff that names, per node, only the fields that changed; it is
  broadcast and merged id-keyed into each client's state.
- **Change review** — per-conversation records (label + inverse deltas +
  staleness fingerprint) attributed to a `threadId`, rendered as a Keep/Revert
  card above the chat input.

Space Shortcut does not open a target Canvas sync stream or fetch preview scenes. It shares workspace Space metadata for titles, target availability, node counts, and update timestamps, refreshed on entry and focus; local moves and renames also invalidate/refetch affected summaries. Inactive target content mutations appear on the next metadata refresh, not through live target subscriptions; see [space-preview.md](./space-preview.md).

World preview reconciliation is a system-originated command batch against World and publishes through World's existing delta stream when topology changes. Portal Pin routing, batched source-reference refreshes, and World `nodeRef` conversation presentation are retired. Opening an Agent conversation from a Space card subscribes to its dedicated owner-state SSE transport without loading or applying the source Canvas document; the server derives these snapshots from the existing Canvas publisher, and passive Space cards still do not subscribe.

`version` (monotonic per canvas) is the concurrency primitive. What a page has changed and not had confirmed — a structure edit still on its way, a body or title not saved yet — is **held**: an incoming change never overwrites it, and everything else of that change is applied. There is one such mechanism, see [What a page holds against incoming changes](#what-a-page-holds-against-incoming-changes).

Canvas loading co-delivers `nodeContentRevisions`, computed from the same canonical node records used for hydration. The browser seeds its content-save queue from those server revisions, not from the rendered node projection: PDF extracted bodies are omitted from Canvas responses, and Office bodies may be normalized. Hashing those incomplete or normalized projections would falsely reject the first property save. Successful writes advance the queue to the returned revision; genuine stale writes remain conflicts. Because every structure edit — the page's own included — comes back through `applyServerDeltas`, an applied batch moves a node's revision only when it changed that node's saved content, and then to the revision the server sends with the batch (`nodeContentRevisions`, read from the same node records); the page never hashes a node to obtain a baseline on that path. See [Where a baseline comes from](#where-a-baseline-comes-from). These revisions use the structured node repository and are independent of Disk, SQLite, or Postgres serialization.

> Request ids and read versions on `execute` are shipped; see [reliable save](./canvas-storage.md#42-reliable-save-in-the-write). The browser sends its own structure edits through `execute` too, so they reach every other open page; see [Browser structure edits](#browser-structure-edits). Node content (body, title, properties and the other sidecar fields) is saved per node and reaches the other pages as described under [Node content between pages](#node-content-between-pages). Two pages typing in the same body at once is not supported; the remaining proposal is [canvas-realtime-sync-plan.md](../proposals/canvas-realtime-sync-plan.md), and multi-server fan-out is outside that scope. Which other pages have the Space open, and what they point at, select, drag or edit, is [Space presence](#space-presence).

## Data flow

```
writer (agent / ACP / headless /execute / a browser page's send queue)
  │
  ▼
executeOnServer  ── per-canvas mutex ──► persist .md + space.json
  │                                      append delta-log, bump version
  │                                      (optional) computeChanges → sidecar
  ▼
publishCanvasUpdate(canvasId, { type:'update', fromVersion, toVersion,
                                deltas, pendingEffects, orderEvents?,
                                nodeContentRevisions?, threadId?, changes?,
                                operationId?, source })
  │  in-memory pub/sub (listenersByCanvas)
  ▼
GET /:canvasId/sync/stream  (SSE, one per tab)
  │
  ▼
canvasSyncStore  ── fromVersion === local? ──► applyServerDeltas (field-level, held units kept back)
  │                │                            └ then orderEvents → sibling paint order
  │                └ gap (toVersion > local) ─► loadCanvas  (in place; held until the send queue is empty,
  │                                             no body is unsaved and nothing is being typed)
  ▼
canvasStore state  +  acpThreadChangesStore.replaceFromBroadcast(threadId, changes)
```

## Broadcast contract

The wire event is defined once in
[canvas-sync.ts](../../packages/shared/src/types/api/canvas-sync.ts) (zod
schema + `z.infer`, web imports as `import type` only):

| Event        | When                                                              | Payload                                                                                                                                                                                                                                                                                            |
| ------------ | ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `snapshot`   | once, on SSE connect                                              | `{ version }` — lets a tab that connected _after_ a mutation detect the gap and `loadCanvas`. It says nothing about node content, which does not change `version`; the page asks for that separately ([Content saved before the stream was open](#content-saved-before-the-stream-was-open)).      |
| `update`     | after every persisted batch                                       | `{ fromVersion, toVersion, deltas, pendingEffects, orderEvents?, nodeContentRevisions?, threadId?, changes?, agentNodeProjection?, operationId?, source? }` — `deltas` name per node only what changed, `pendingEffects` names nodes by id; see [what an update carries](#what-an-update-carries). |
| `invalidate` | node-content save, orphan-sidecar deletion or Space-tree deletion | `{ nodeIds?, originPageId? }` — refresh observed read models for those nodes, or every observed owner in that Space when omitted; not editable Canvas deltas. With `nodeIds`, a Canvas page fetches those nodes' content unless `originPageId` is its own id.                                      |

`canvasSyncSubscription` manages the per-Space Canvas transport, preserving the 45-second inactivity timeout, heartbeat handling, rate-limit-aware 500ms-to-10s reconnect backoff, and version baselines for late subscribers. The final subscriber aborts the transport. Conversation views instead share one dedicated owner-state subscription per conversation address per page: the server listens to this same Canvas publisher, reads canonical ownership, and pushes complete versioned metadata snapshots. The browser applies those snapshots without querying ownership for each change or loading the source Canvas document. Reconnect, focus and visibility restoration obtain a fresh baseline. Canvas rendering never treats `invalidate` as a document replacement or as a reason to reload. An `invalidate` that names nodes makes the page fetch those nodes' content, see [Node content between pages](#node-content-between-pages); one without node ids is ignored by the Canvas page. See [conversation observation](./preview-workspace.md#3-opening-and-target-conversion).

- `deltas` are `unknown` on the wire (they mirror the loosely-typed
  `PostCanvasExecuteResponse`; the engine `Delta` shape lives in the
  canvas-engine module, not the API layer). The client casts.
- `threadId` + `changes` are present **only** for thread-attributed batches; they
  feed the originating conversation's review card.
- `orderEvents` is present only when an `executeOnServer` batch changed a parent's direct-child list; see [Sibling paint order](#sibling-paint-order).
- `nodeContentRevisions` (`{ [nodeId]: rev }`) is present when the batch created a sidecar-backed node or changed a sidecar field of one; see [Content revisions of a batch](#content-revisions-of-a-batch).
- `agentNodeProjection` identifies trusted server binding/lifecycle/association effects for browser undo handling; it is output metadata, not client authorization to submit those writes.
- `operationId` is the request id the writer supplied, when it supplied one; a page uses it to recognise the update for its own batch. `source` is who the Server took the batch to be from (`ui`, `agent` or `system`; it follows the credential and is never read from the request), set on every `executeOnServer` batch and absent on `applyDeltasOnServer` replays; a page uses it to tell another person's edit from an agent's.

### What an update carries

An update, the `POST /execute` response, a delta log row and a result record are all proportional to what the batch changed, never to the size of the nodes it touched.

**Node rows name only what changed** ([delta.ts](../../packages/shared/src/canvas-engine/delta.ts)). A `REPLACE_NODE` is `{ type, nodeType?, hidden?, prev, next }` where `prev` and `next` hold the node's `id` and just the fields that differ — top-level fields whole (`position`, `style`, `parentId`, …), `data` key by key — with their previous and new values. A field on one side only was added or removed. `nodeType` is the node's type after the change and `hidden` says it stayed hidden; both are on the row because an unchanged field is in neither side and a reader has no node to ask. Moving a PDF whose extracted text is a megabyte is a row of about 150 bytes; the text is not in it. A changed body is in it once, with its previous value: that is what reverting an Agent's edit needs.

**One applier.** A row is applied by merging it into the node as it is now — `mergeNodeFields(current, prev, next)`: every field either side names takes `next`'s value or is removed, everything else stays. `applyDeltas`, the server's delta replay (`applyDeltasOnServer`: Review revert, Agent Node projection and association, titles, cross-Space move compensation) and the Review card's preview all go through it, and the page merges a row into its live node with the same function before its field-level rewrite (`expandNodeRows`, see [Applying](#browser-structure-edits)). A row in the format used before — whole `prev` and `next` nodes, as in Review records and history stored or exported earlier — is valid input of the same applier and is reduced to the fields that differ by `slimDelta`; `applyDeltasOnServer` does that to every row it is given, so a revert puts back what its change touched and leaves later edits of other fields alone, for every node type.

**Inserts and deletes.** An `INSERT_NODE` carries the node: there is nothing to merge into. A `DELETE_NODE` travels as `{ type, node: { id, type, hidden? } }` (`toWireDeltas`, applied where an update is published and where a response or a log row is built): applying a deletion needs the id. Bringing a deleted node back needs its content, and after the deletion the server no longer has it — the batch removed the record. That content is therefore kept in exactly one place, where a revert is possible at all: the **Review record** of the batch, whose revert row is the `INSERT_NODE` with the whole node. It is written in the same commit as the deletion, read by the revert route on the server, and is sent to pages with the thread's `changes` (for the card's press-and-hold preview). It is not fetched, because there is nothing left to fetch, and it is not in the `deltas`, because no page needs a megabyte of text to remove a node. A deletion that is not attributed to a conversation has no Review record and is not revertible by the server; the deleting page's own undo restores it from its history (`RESTORE_NODES`). Edges are small and travel whole.

**Pending effects name nodes by id.** `pendingEffects` is `{ mutatedNodeIds, deletedNodeIds, contentEditedNodeIds, deferredFitFrameIds }`. A page that applies the batch reads a mutated node from its own state afterwards (preprocessing of an agent's batch, the unclaimed-history check), and the conversation owner stream only needs to know whether its node is among them.

**No echo.** The response does not repeat the commands it was sent, neither as a list nor per result. What a caller cannot know itself — the ids the server assigned — is in the per-command result (`nodes[].nodeId`, `edges[].edgeId`).

Measured on Disk for a PDF node with 1.05 MB of extracted text being moved (`execute-payload-size.test.ts`): response 514 bytes, `update` event 378, delta log row 316, result record 542 (each about 2.1 MB before). For an Agent rewriting a 102 kB note body: the deltas are 306 kB (old body, new body, and the block provenance derived for the new one), the event 613 kB because the thread's Review record carries the revert row beside them, the result record 553 bytes (1.02 MB before), and the log row is journalled without its deltas because it exceeds a row ([delta log](./canvas-storage.md#41-executor-persistence-restoration)).

Not reduced: an Agent-attributed batch still carries what it changed twice in the event — in `deltas` and in the Review record's revert rows (`changes`); a created node is in `deltas` (the insert) and in the revert row of its creation, which the staleness check and coalescing read. `orderEvents` keep two complete child lists per changed parent.

## Sibling paint order

Entity `deltas` are keyed by id and cannot express stacking order: a pure `REORDER_NODES` batch commits with `deltas: []`. `executeOnServer` therefore calls `diffSiblingOrderEvents(prestateNodes, finalNodes, toVersion)` for every committed batch and attaches the result as `orderEvents` (`SetSiblingOrderEvent[]`, [contract](./canvas-command-architecture.md#sibling-paint-order-and-isolated-replay)) to the `update` event, to `publishCanvasExecution`, and to the `POST /execute` response. Each event lists one changed parent's complete direct-child ids before and after the commit, so a batch that creates, deletes or reparents nodes carries one too. The field is omitted when no list changed, and when the strict forest check rejects a legacy topology (the batch still commits and broadcasts entity-only). The schema validates each entry with `isSetSiblingOrderEvent`. A consumer that ignores the field behaves as it did before the field existed.

`applyServerDeltas` takes the events as an optional argument. After the entity deltas are replayed and tree-normalized it calls `replaySiblingOrder` ([siblingOrderReplay.ts](../../apps/web/src/store/canvasStore/siblingOrderReplay.ts)), which runs `applySiblingOrderEvents` against the pre-batch local nodes — minus local optimistic copies of nodes the batch inserts — and installs the returned forest. An order-only batch no longer returns early; it takes one undo snapshot like any other editable batch.

If the events do not fit the local forest (`SiblingOrderReplayError`: stale `before` list, membership mismatch, invalid local topology) the store keeps the entity-only result and still adopts `toVersion`; nothing is partially reordered. It then compares each listed parent's local child order with the event's `after` list. Only when one differs, no content value or deletion was kept back for this page's unsaved text, and `hasUnsavedCanvasEdits()` is false does it call the caller's `onDiverged`: `canvasSyncStore` runs the same `loadCanvas(…, { resetHistory: true })` as a version gap, and the Question-creation HTTP path in `executeCommands` reloads the Space. With unsaved local edits the local order stays; the update for the page's own queued batch carries the order the server ended with.

Limits: `applyDeltasOnServer` batches (review revert, Agent Node projections, title updates) send no `orderEvents`, so a reverted deletion is still appended by entity replay. The delta log and Review records stay entity-only; the stored outcome of a request with an `operationId` does include `orderEvents`, so a replay returns what the first call returned (unless the outcome had to be stored without its optional parts). Each event carries two complete id lists, so its size grows with the changed parent's child count — ids only, about 45 bytes per child and list. The format was left as it is: making it proportional to the change (a move within a list instead of two lists) would need a new replay rule on every consumer. The behaviour is covered by server and store tests, not by a two-browser run.

## Content revisions of a batch

A page keeps, per node, the content revision its next content save quotes as `expectRev` (the baseline). A batch that changes a node's content changes that revision, so the batch says what it is now: `nodeContentRevisions` names the **stored** revision of every node whose saved content the batch created or changed, on the `update` event, in the executor's output and in the `POST /execute` response a page applies.

- _Which nodes._ `contentChangedNodeIds(deltas)` in [canvas-executor.ts](../../apps/server/src/modules/canvas/canvas-executor.ts): every `INSERT_NODE` of a sidecar-backed type, and every `REPLACE_NODE` of one (by the row's `nodeType`) whose `prev` and `next` name a sidecar field (`NODE_CONTENT_KEYS`, compared by value). A node the batch only moved, resized or restyled is not named, and the field is omitted when no node is. A title, summary or custom-property change is named too, although it does not change the revision (see [what is versioned](#what-is-versioned-and-what-is-not)), so that a page that sees a content change always finds a revision for it.
- _Where the value comes from._ After the commit, and still under the Space's write mutex, the executor reads exactly those node records (`SpaceNodes.readMany`) and hashes each with `nodeRevisionOf`, the way `GET /api/canvas/:id` hashes the records for its own `nodeContentRevisions`. It is not a hash of the node in `deltas`. A node that has no record is given the revision of empty content, as a load gives it.
- _Cost._ One `readMany` per batch that changed node content, of the changed nodes only; a structure-only batch reads nothing. Disk: one sidecar file read per named node, located through the store's cached name index, which the store revalidates on each read. SQLite and PostgreSQL: one `SELECT` by id list per 500 named nodes; PostgreSQL also checks the Space row first. The read runs after the write transaction, not in it.
- _Publishers._ `executeOnServer` (agents, headless `/execute`, a page's own batches) and `publishCanvasExecution` (Space moves, hierarchy changes, and other callers that defer publication) take it from the executor's output. `applyDeltasOnServer` returns it and each of its publishers forwards it: the Review revert route, Agent Node projection, Agent Node association, and conversation titles. The rename update carries no deltas and no revisions. A node-content PUT publishes an `invalidate`, not an `update`; the page fetches the node and its `rev`.
- _Repeated requests._ The result record of a request with an `operationId` (its outcome) is written in the same commit as the batch, before anything can be read back. It therefore carries the revisions of the records that commit handed to storage (the record put for a node, or the one read before the batch for a node it did not put). The backends store the revision-covered fields as given, so this is the revision read back afterwards (the replay tests compare the two on Disk and SQLite); the executor compares them on every such batch and logs a warning if they ever differ, in which case the live response and event carry the stored revision and a replay the other. A replay returns the stored field, also when the node has been saved again since: it is the revision of that commit. (A replay carries no deltas; a page takes the baseline with the `update` it applies.)
- _A failed read-back._ The batch is committed and is not failed for it. A request with an `operationId` then answers and publishes the revisions computed before the commit; a call without one (and an `applyDeltasOnServer` batch) omits the field, and pages take the [fallback](#where-a-baseline-comes-from).

Covered by `canvas-update-revisions.test.ts` on Disk and SQLite (a note, a PDF with extracted text, an Office body, a created node, a structure-only batch, a replay after the node was saved again, a delta replay, and `POST /execute` against a load), and by `conversation-title.conversion.test.ts` for a title projection.

## One write path, one broadcast

`executeOnServer` normally broadcasts after persisting a non-empty batch. Trusted coordinated lifecycle callers can defer publication with the internal `publish: false` option and publish after their orchestration reaches its declared boundary. `applyDeltasOnServer` persists and returns its result; its caller owns publication. These exceptions do not expose a client-controlled broadcast policy.

- The built-in chat and question-node agents mutate the canvas in-process via
  `executeOnServer`. Their chat SSE tool result is now **UI-only** (tool card +
  the annotated command list); it does **not** apply canvas state. The
  initiating tab is a plain receiver that applies its own change once, from the
  broadcast.
- ACP / headless writers hit `POST /:canvasId/execute`, which calls the same
  `executeOnServer`.
- A browser page's own structure edits are a writer of the same kind: they go through `POST /:canvasId/execute` with a request id. The page is not filtered out of the broadcast; it recognises its own batch by `operationId` and applies it through the same path, see below.

## Browser structure edits

A `ui` command batch (`executeCommands` with the default source: create, delete, move, resize, reparent, reorder, style, connect, …) runs on the page first and is then sent to the server by a send queue. Code is under [canvasStore/sync/](../../apps/web/src/store/canvasStore/sync).

**Sending** ([sendQueue.ts](../../apps/web/src/store/canvasStore/sync/sendQueue.ts)). One serial lane per open Space. Each entry is one `POST /execute` with `originator: { tabId }` and a fresh `operationId`, and it holds **edits**: every batch handed to the queue is one edit — the commands of one gesture — with the read version it was made on (`basis`) and the earlier, still unconfirmed edits of this page it was made on top of (`after`), see [Read versions of a page](#read-versions-of-a-page). The request's `edits` are the entry's edits, in order; nothing is addressed by command index. The server checks an edit against the nodes it names only, so edits to unrelated nodes from two pages never reject each other. A transport failure, a 5xx (including `operation-outcome-unknown`), 401, 408 or 429 repeats the same request with the same id after a backoff (500 ms doubling to 10 s); any other 4xx fails the entry. Edits made while a request is on the wire are folded into the next entry (up to 200 commands), so a slider drag is not one round trip per tick. **An entry is frozen when it is first sent**: its request is built once and repeated byte for byte, and later edits start a new entry, so "request id + position in `edits`" names the same edit for good. `CREATE_NODES` and `CONNECT_NODES` are given explicit node, thread and edge ids before the local run (`withClientIds`), and `INITIALIZE_PDF_NOTE` the id of the Note it creates (`noteId`), so the server creates the entities the page already shows.

**What is sent** ([serverCommands.ts](../../apps/web/src/store/canvasStore/sync/serverCommands.ts)). `SET_NODE_SELECTION` is not sent, and a created node is sent with `selectOnCreate: false`; selection is a page's own view state and is not in the saved record. A data key a patch clears with `undefined` — which JSON would drop — is named in the patch's `unset` list (a Question ignores `undefined`, so there the key is only left out). Content fields of existing nodes (`NODE_CONTENT_KEYS`: body, label, summary, …) are stripped from `MERGE_NODE_DATA`; they keep their own writer, the per-node content PUT, and reach other pages through it ([Node content between pages](#node-content-between-pages)). A created node is sent whole and the content queue does not write its first sidecar (`prepareServerCreatedNodes`). A batch that leaves nothing to send is not queued.

**A Space that is not loaded.** Nothing is sent for the open Space while it is loading (`isLoading`), or after the store was switched to it and no load of it has succeeded yet (`spaceAcceptsEdits`): no command batch, no gesture prelude, no undo/redo restore, no `patchNodeSilent` commands and no measurement report. An edit made in that state changes this page only and is dropped, not queued — the load that ends the state replaces what the page shows with the server's Space. This is what the whole-Space autosave did (it skipped while loading); `apps/web/e2e/question-compact.spec.ts` drags a node of such a fixture and asserts that no write request leaves the page.

**Pointer gestures.** Live drag ticks and resize preview ticks (`executeCommands(…, { localOnly: true })`) change the store without sending. `beginGesture` records the nodes at gesture start; the batch that closes the gesture is sent with a prelude of `SET_NODE_GEOMETRY` / `MERGE_NODE_DATA` commands for what changed since then ([localDiffCommands.ts](../../apps/web/src/store/canvasStore/sync/localDiffCommands.ts)). A free drag whose resolver emits no command is sent as that prelude alone from `onNodeDragStop`. The server therefore runs the engine on a geometry command the page applied tick by tick; what the engine adds (a structured Frame named by the command is re-flowed, a hug Frame refits) reaches the page with the update. While the gesture is open, what its ticks have changed so far is held against incoming updates like a queued batch's changes, and the recorded start state is kept in step with every update, so the closing batch sends only what the gesture changed and a cancelled drag returns to where another page has put the node meanwhile. A batch sent while the pointer is still down (a modifier key interrupting a resize) restarts the recorded state from what that batch left; the resize end handlers call `closePointerGesture` so ticks after it are sent too.

**In-flight set** ([inFlight.ts](../../apps/web/src/store/canvasStore/sync/inFlight.ts)). Every queued batch holds the (entity, property unit) pairs it changed, derived from the difference between the state before the batch (before the gesture, for a closing batch) and the state after it — not from the command list, so engine consequences such as a Frame refit are held too. Property units ([propertyUnits.ts](../../apps/web/src/store/canvasStore/sync/propertyUnits.ts)): `position`; `size` (`width`, `height`, top-level `style`); `parent` (`parentId`, `extent`, `expandParent`) — a change to either `position` or `parent` holds both, see [Read versions of a page](#read-versions-of-a-page); each `data.style` leaf; every other `data` key; each custom property (`data.properties.<key>`); every other top-level node key; node existence; each edge as a whole; and each parent's direct-child order. The send queue holds structure units only: content `data` keys are held by the content queue, through the same predicate ([What a page holds against incoming changes](#what-a-page-holds-against-incoming-changes)), and the read-model keys that are never sent (`isUnsentUnit`) are held by nobody. React Flow runtime fields (`selected`, `dragging`, `measured`, `resizing`) belong to no unit.

**Applying** ([fieldLevelDeltas.ts](../../apps/web/src/store/canvasStore/sync/fieldLevelDeltas.ts)). A row names the fields the batch changed. `applyServerDeltas` first merges each row into the live local node with the shared applier (`expandNodeRows`: `prev` becomes that node with the fields' previous values, `next` that node with their new values, so the two differ in exactly what the batch changed and nothing the row does not name is touched), and then rewrites every incoming batch — a person's or an agent's — before replaying it: a `REPLACE_NODE` becomes a replace of the live local node with only the units `prev → next` changed, minus the held ones (held by an unanswered batch, the open gesture, unsaved content, see [What a page holds against incoming changes](#what-a-page-holds-against-incoming-changes)); an `INSERT_NODE` for a node the page already has (its own optimistic creation) is merged the same way; selection is never taken from another page, and an edge the page has keeps its own `selected` flag when the server's edge is installed (the saved edge has none, so the update for the page's own restyle of a selected edge would otherwise deselect it and close its toolbar). So when page A has moved X and page B recolours X, A applies the colour and keeps its position, and B applies A's move when it arrives. A held unit keeps the local value and the remote value is kept back as the unit's last confirmed value. A `DELETE_NODE` for a node whose existence is held (it is being edited, or a later batch of this page brought it back) is kept back the same way. A row for a node the page does not have is not applied.

**Own update.** The update for the page's own batch is recognised by `operationId` and applied through the same path, except that only holds of _later_ queued batches withhold a unit: two moves of one node in a row keep the second position when the first update arrives, and the version still advances. When the update is applied the batch's holds are released. A unit the update did not change is set to its last confirmed value — the remote value kept back meanwhile, or else the value before the batch — because the server did not take that part of the change. The same release happens when the response reports nothing written (`toVersion === fromVersion`). The HTTP response of the request is used as the update when it is the next contiguous version (`fromVersion === local version`) and carries `deltas`; the stream copy that follows is then stale and ignored, and vice versa. Otherwise the page waits for the stream, and reloads if the update has not arrived 8 s after the response. A **replayed** response (`replayed: true`, the answer to a repeated request id) has no `deltas` and is never applied as an update: the page reads the per-edit outcomes from it and gets what the request changed from the stream, or by that reload.

**Refused edits.** The response says, per edit, whether it took effect (`edits[i].applied`), why not (`reason`) and which command caused it (`failedAt`). The server takes an edit whole or not at all: a stale read version (`stale-target`, `stale-parent`, see [Read versions of a page](#read-versions-of-a-page)), an edit made on top of one that did not take effect, or one command that fails for any reason other than `no-op` refuses the edit and nothing of it is applied. A refused edit, or a request refused with a 4xx, shows one warning toast per request, releases the entry's holds as above (kept-back remote values are installed) and requests a reload of the Space, in place. Other edits of the request, and other queued entries, are still sent and applied. A creation the server did not take removes its optimistic nodes before the next entry is sent. The page's own local run is the same edit: it runs a gesture's commands through the engine as one edit before sending them ([the engine rule](./canvas-command-architecture.md#edits)), so a gesture one of whose commands the engine refuses changes nothing on the page and is not sent; the person is told by a warning toast that dismisses itself, worded by the reason, and a refused drag puts its nodes back where the drag began ([what the person sees](./canvas-command-architecture.md#edits)). What is left for the server to refuse is what the page could not know — a read version, another page's change — and the gesture prelude, which the page applied tick by tick and not through the engine.

**Reloads.** `requestCanvasResync` is the only way the sync subscriber reloads (version gap, reconnect snapshot mismatch, paint order that could not be installed, missing update, rejected command). It runs `loadCanvas(…, { resetHistory: true, inPlace: true })` at once when the send queue is empty and otherwise as soon as it has drained; a page with unsent changes is never replaced. Nor is what the user is doing (`reloadBlockedBy`): the reload is **held, not dropped** (`holdReload`) while any node has unsaved content, while the user is typing into a control of the Space (`pageIsEditing`: a node's body, title or property field as reported by the presence editing tracker — a title being renamed or a property field keeps its draft in the control until it is committed, so the content queue knows nothing of it yet — or another text control of the canvas such as an edge label), and while a drag or resize is under the pointer. It runs by itself when none of that is left — normally a moment later, when the debounced save is acknowledged (`onContentPersisted`) or the control loses focus (the text it then commits is saved first); a one-second check also catches what ends another way, such as a conflict answered with the server's version, the node being deleted, or the editing tracker giving an idle control up after two minutes.

**A reload is a refresh in place.** A sync-triggered reload is of the Space the page already shows, so it does not enter `isLoading` and `CanvasPage` keeps the canvas mounted (the loading surface is for a first load and for a switch to another Space). The page stays usable while the request is under way; when the answer arrives the nodes and edges are replaced, the undo history is reset, the viewport is left where it is, and nodes and edges that still exist stay selected. If the page did something meanwhile — sent or queued an edit, typed, started a drag, or applied a newer version from the stream — the answer is not used (`stale`) and the reload is asked for again through the same gates. `canvasSyncStore` sees the end of such a load through `loadGeneration` (for the content catch-up and the behind-the-stream check that otherwise follow `isLoading`). If the text is still unsaved after 5 s — a save that keeps failing, a conflict the user has not answered — a warning toast (`canvasSync.reloadWaiting`) names the notes the newer changes are waiting for; the failed-save or conflict toast of each note is where the user acts. Leaving the Space drops the held reload, since the next visit loads it. A reload whose load fails (the request did not get through, a 5xx) is not given up either: `loadCanvas` reports how it ended (`LoadCanvasResult`; `getCanvas` returns `null` only for a 404 and throws otherwise), the page keeps showing what it showed, and `browserSync` asks again after a backoff (`RELOAD_RETRY`: 500 ms doubling to 10 s) until a load succeeds or the user leaves the Space — after a refused command the version is in step, so no later event would ask. One reload runs per Space at a time; one that becomes wanted meanwhile runs after it. What follows a reload (`requestCanvasResync`'s callback, the notice after **Reload and discard unsent changes**) runs only after a load that succeeded. A paint-order divergence is ignored while the page holds an unconfirmed change to the same parent's children, since the update for that change carries the order the server ended with.

**When a request cannot be sent.** The queue's status for the open Space is mirrored in `useCanvasSyncStatusStore` ([syncStatus.ts](../../apps/web/src/store/canvasStore/sync/syncStatus.ts)) as `synced`, `syncing`, `unsynced` or `error`. After the first failed attempt the page shows a persistent warning toast (`canvasSync.unsynced`) and keeps retrying; the edits stay on screen and nothing is persisted locally, so closing the page loses them. The `online` event retries at once. After 8 consecutive failed attempts, or 60 s since the first of them, the lane stalls: nothing is sent, and a danger toast (`canvasSync.sendFailed`) offers **Keep trying** (`queue.resume`) and **Reload and discard unsent changes** (`discardUnsentCanvasEdits`, below). The page never reloads over unsent changes on its own; while stalled a wanted reload stays held and `drainPendingSaves` rejects, so leaving the Space goes through the existing unsaved-changes dialog (whose discard also drops the lane). Renewing a lapsed session resumes the lane.

**Reload and discard unsent changes.** What could not be sent is structure; note text has its own request and may well get through. The action therefore always ends in something the user sees:

1. If any node has unsaved content, failed saves are retried and pending ones flushed, under an info toast (`canvasSync.savingTextBeforeReload`), for at most 5 s. (The bound matters for a node whose creation is itself among the unsent edits: its content save waits for that creation.)
2. If no content is unsaved after that, the lane is dropped, the Space is loaded (`resetHistory`) and an info toast says it was reloaded and the unsent changes discarded.
3. Otherwise nothing is dropped yet. A danger toast (`canvasSync.unsavedTextConfirm`) names the notes whose text could not be saved — up to three titles, then a count — and offers **Cancel** and **Discard this text and reload**. Cancel leaves the page exactly as it was (the text is there to copy out, the unsent edits are still queued) and shows the error toast with its two choices again. Discard drops the lane, suspends the Space's content writes, lets requests already issued settle (at most 5 s), forgets the Space's content queue and failures (`discardCanvas`, as the navigation boundary's discard does), loads the Space and says so.

Typed text is never discarded without that second confirmation, and text typed between the check and the reload sends the action back to step 1.

**Derived reports.** `APPLY_MEASURED_HEIGHT` and `APPLY_MEASURED_SIZE` batches report what the page computed, not what the user did, and are queued as `derived` entries (an entry that also folds in a user's edit is the user's). They are sent, retried and flushed like any other entry, but they are not unsent work: `syncStateOf` reports `synced` while only derived entries wait, so neither the unsynced nor the error toast is shown for them; `hasUnsavedCanvasEdits` and the page-close confirmation ignore them; and `drainPendingSaves` waits for a derived entry only while it is not failing. A lane that reaches the retry limit holding only derived entries gives them up instead of stalling (the page keeps what it measured, values withheld for them are installed, and the height or box is no longer marked as reported, so the next measurement of that content is sent). A user's edit queued behind a failing report is unsent work as usual.

**Page close.** With unanswered batches the `beforeunload` handler ([unloadFlush.ts](../../apps/web/src/store/canvasStore/save/unloadFlush.ts)) sends each of them with `keepalive` — the one on the wire with the request id it already has, so it cannot run twice — and, when at least one of them is a user's edit, asks the browser for its leave confirmation. Derived reports alone are flushed without asking. The desktop app does not ask; it closes through its own save boundary, which drains the queue via `drainPendingSaves`. A keepalive request is best effort and limited in size by the browser. A queued edit that was made on top of an edit still on the wire names it (`after: [{ operationId, edit }]`); should the flushed requests reach the server out of order, that edit is refused rather than applied to a state it was not made on. A request is fixed when it is first sent, by the flush or by the lane: if the page stays open, later edits start a new entry and the entry is repeated exactly as flushed, so its request id and the positions in it still name the same edits.

**Writers that do not start from a command.** These read their result back as commands ([localDiffCommands.ts](../../apps/web/src/store/canvasStore/sync/localDiffCommands.ts)) and send them through the same queue.

- `patchNodeSilent`: structure fields are sent as `MERGE_NODE_DATA` (the proposal is run through the engine first, `commandsReproducing`, and sent only if it reproduces the patch); during a pointer gesture the patch is left to the batch that closes it — also when the gesture moves nothing: a click, or a drag that is cancelled (`cancelActiveNodeDrag`), sends what else reached the store during it, without any placement. A patch of content fields only is saved by the content queue. The read-model hints the server derives when it reads a node (`contentMissing`, `contentDuplicate`, `duplicateFiles`) and the stored renderer box (`measuredSize`) are shown, never sent. One predicate, `isUnsentUnit` (content keys and those read-model keys), decides this everywhere: command batches, the gesture prelude and tick submission, `patchNodeSilent`, undo/redo plans and the in-flight holds.
- Undo and redo (`restoreFromHistory`, planned by [restorePlan.ts](../../apps/web/src/store/canvasStore/sync/restorePlan.ts)). Each undo entry records the in-flight keys its edit changed. While no other page's edit has been applied since the entry was taken, the snapshot is restored whole. Once one has (`markRemoteChange`), only the recorded keys are restored ([historyRestore.ts](../../apps/web/src/store/canvasStore/sync/historyRestore.ts)), so the other page's edit stays; a later edit by another page to the very property being undone is still overwritten. The resulting state is sent as:
  1. per-property commands where they exist: moves, resizes, data keys set or removed (`MERGE_NODE_DATA` with `unset`), reparenting, deletions, removed edges;
  2. `RESTORE_NODES` for a node that comes back — with its id, its place in the tree and its content, which the server writes to the sidecar in the same batch (`prepareServerCreatedNodes` keeps the content queue from creating it a second time) — and for an edge that comes back, handles included;
  3. after the engine has run that proposal, `RESTORE_NODES` with `replace` for a surviving node that still differs (a type change, a lock, another top-level field), keeping its content fields (`keepDataKeys`), then `REORDER_NODES` and edge repairs.

  The whole list is then run once more as the one batch the server will execute. If it reproduces the snapshot, the page shows the snapshot. If it does not — the engine fits a Frame or routes an edge its own way at the end of a batch — the page shows what the commands give instead, so page and server hold the same state; no whole-Space write is used to force the snapshot. A deleted node's record is removed by the batch that deletes it (`DELETE_NODES`, or the deleting half of an undo): no page sends a request of its own for it, neither the page that deleted nor a page that received the deletion, so nothing can arrive after a restore and unlink the body it wrote. The restoring batch is behind the deleting one in the page's serial send lane; a returning Agent Node's association waits for the deleting batch to be answered (`nodeRemovals`). `DELETE /api/canvas/:id/nodes/:nodeId` remains only for a record left without a node and answers success without touching the record of a node that is in the Space (`apps/web/e2e/delete-undo-body.spec.ts`). Content saves and preprocessing for the node wait until the restore is answered, and a refused restore (the id exists again, the parent is gone) is handled like any rejected command: one notice, then the server's Space.

  A returning Agent Node is not part of that batch. Its identity is re-established by the association endpoint once the batch is answered, its content is held by the content queue until the association is confirmed, and its edges and place in the sibling order follow in a second batch gated on the association.

- Cut (`cutSelectedNodes`, Mod+X) and select all (Mod+A). Select all only changes this page's selection, which is never sent. Cut is a copy followed by a deletion, with no write path of its own: once the selection is on the clipboard — bodies included, PDF↔Note pairs and the children of selected Frames with it — and neither the cut nodes nor their edges changed during the clipboard write (another page's or an agent's update to one of them stops the cut as a plain copy), it dispatches the `DELETE_NODES` intent, so the removal is one command batch in the send queue, the records are removed by that batch, and other pages drop the nodes on its `update`. A selection that owns a child Space, or an Agent Node with a conversation, is refused before the clipboard is touched. Pasting is `CREATE_NODES` (+ `CONNECT_NODES`) with fresh client ids and the clipboard's content, sent whole, so other pages receive the pasted nodes with their bodies in the `update`. Undoing a cut is the undo of a deletion: one `RESTORE_NODES` batch with the original ids, content and edges. Covered with two browser contexts by `apps/web/e2e/multi-page-clipboard.spec.ts`.
- Measured heights (`applyMeasuredHeights`): a measurement of an auto-height note is applied on the page at once, as `system`. It is reported to the server as a `ui` `APPLY_MEASURED_HEIGHT` batch when the stored hint is current, the node's content save is not pending (the report then waits for it, because the server checks the measurement key against its own copy of the body), and no non-provisional measurement under the same key is known to be on the server — from another page's update, from this page's own confirmed report, or from the load. Two pages that render one body a pixel apart therefore do not keep rewriting each other's size; the later one shows its own measurement locally. The report's holds do not put back the previous height when the server refuses it. Load-time warm-up measurements are reported the same way.
- Renderer-measured boxes (`reportMeasuredSizes`): `text`, `question` and `spacePreview` nodes have no authored height. When React Flow reports a changed box for one, the page lays its own Frames out around it at once (`onNodesChange`, and the deferred relayout after a batch) without sending that layout, and reports the box as `APPLY_MEASURED_SIZE`. The server stores it (`data.measuredSize`, mirrored to `measured`) and lays the same Frames out with the same engine pass; the update brings the result to every page. The key (`measuredSizeKey`: content revision and authored width) lets the server ignore a box measured before the content changed, so a report waits for the node's content save. A page does not report when the server already holds the same box (within a pixel) for the key, and does not answer another page's report for the same key with its own slightly different rendering — it reports a different box under an unchanged key only when its own earlier measurement of that content changed (a font size, say). Reports are therefore triggered by local measurement changes only, never by an incoming update. A batch that changes what a box is measured against (a width resize) is followed by one check after the renderer has reflowed. Pages without write access report nothing.
- The legacy Frame-header migration on load: the coordinate change is sent as `SET_NODE_GEOMETRY` commands before the Space is shown, and the Space is then loaded again; one attempt per load, and a Space whose migration is refused (no write access, a failed request) is shown as stored.
- The Space title (`tryRename('canvas')`): sent to `PATCH /api/canvas/:id/title` with the title the page last saw. The rename publishes the `update` from the previous version to the new one with no deltas and the new `title`, so every open page — including the renaming one — advances its version and shows the title without loading the Space again.

**No whole-Space save.** The browser no longer sends `PUT /api/canvas/:id` in the editing lifecycle: there is no structure autosave, no dirty detector, no version-conflict state and no page-close PUT. A store write that is not a command batch (or one of the writers above) changes this page only. The page-close flush is the queue's keepalive flush. `drainPendingSaves` — leaving the Space, submitting a prompt, signing out — waits for the queue, then for pending Agent Node associations, then for content saves; a request that was failing is retried at once (`queue.retryNow`, which cuts the backoff short but keeps the failure count and the time of the first failure) and one more failure rejects the drain instead of sitting out the retry schedule, while a stalled queue rejects immediately. An attempt made by a drain therefore counts towards the retry limit, and repeated drains end in the stalled state. Only **Keep trying**, the `online` event and a renewed session start the count again (`queue.resume`). The action-log event buffer is flushed whenever the queue drains. The web API client has no whole-Space save (`putCanvas` is removed). The server has no such route either: `PUT /api/canvas/:id` is removed and answers 404, so structure reaches storage only through `POST …/execute`, the title through `PATCH …/title`, and node content through the content PUT. `apps/web/e2e/no-whole-space-save.spec.ts` exercises every former PUT path with two browser contexts and asserts the other page never loads the Space again and keeps its undo history; its second test does the same for a body and a move arriving together, and for the receiving page's undo afterwards.

### Read versions of a page

A position is relative to the node's parent, a cell belongs to one Frame, and an edit of a node that has been deleted has nothing to apply to. So every edit a page sends says which version of the Space it was made on, and the server refuses an edit whose node somebody else deleted or moved into or out of a container after that version, rather than reinterpreting it. The rule between two pages is: the edit committed first stands; a later edit is applied when nobody else has deleted its nodes or changed their parents since the version it quotes, and refused as a whole when somebody has. The server converts no coordinates. It is the same check an agent's `basis` gets ([reliable save](./canvas-storage.md#42-reliable-save-in-the-write), [api-design.md](./api-design.md#request-id-and-read-version-on-execute)); there is no second precondition.

- _Where the page gets a basis._ `GET /api/canvas/:id` returns `basis` (`b1.<lineage>.<version>`). The page keeps the lineage and combines it with the version it has applied — the load's, advanced by each contiguous `update` — using `encodeBasis`. Loading a Space is therefore what creates its stamp baseline.
- _Which version an edit quotes._ The version the page had applied when the edit was made: `submit` reads it in the same task as the edit (for a drag, at the drop), and it is never replaced by a newer one while the batch waits in the queue, however many updates the page applies meanwhile. One correction makes it honest. For a node whose placement the page was holding — an unanswered batch or the open pointer gesture had changed it — the page was not showing what that version says: an update that changed its position or parent was kept back (rule 2: an unconfirmed local change keeps the local value; rule 7: no rubber-banding). `browserSync` remembers, per node, the version before the first update it kept back (`keptBackSince`), and an edit that names such a node quotes that version instead. So a drag during which another page re-parented the dragged note quotes the Space from before that change, although the page has applied the rest of that update, and the server sees the change as one the page has not read. A node the page was not holding is read as of the drop, so a Frame another page created during the drag can be dropped into.
- _What is checked._ `commandReadTargets`, the one list for pages and agents: every named node must exist and not have been created since; the nodes a command depends on the parent of — `SET_NODE_GEOMETRY` items that carry a position, `SET_NODE_PARENT` node ids (the parent they are moved _from_), `REORDER_NODES` ids and anchor, `ALIGN_NODES` / `DISTRIBUTE_NODES` ids, and the `cells` / `placements` nodes of `SET_FRAME_LAYOUT` — must not have changed parent since. A size alone, a data key, a lock or a deletion depend on no parent. Content fields are not sent through `execute` and are not part of this.
- _An edit is an edit of the request._ Each queued batch is one entry of the request's `edits` (`{ basis, after?, commands }`); a folded request has one edit per batch, each with its own basis. The server judges an edit once, before its first command, and applies it whole or not at all: a drag's parent change, its positions, its data patches and its layout command are taken or refused together, also for the other nodes of a multi-node drag — whether the reason is a stale read version or one of its commands failing. Other edits of the same request are judged on their own.
- _A page's own changes._ A second edit of a node made before the first is confirmed quotes a version from before the first, and the first has changed the node's parent on the server by the time the second arrives. That change is the page's own, and a page's own committed change is not held against it: the server records which page made the last creation and the last parent change of each node, and "the same page" is the authenticated principal together with the page id (`originator.tabId`). The same person's other tab or device is another page, and a reloaded document has a new page id (`CANVAS_PAGE_ID` is minted per document), so the exemption never reaches across a reload: what the old document's last request committed is either in the Space the new document loaded, or foreign to it.
- _An edit made on top of an unconfirmed one._ The page's own earlier edit may also be refused, and then a later edit made on its result must not be applied either — even when nobody else touched its node (a note moved "inside the Frame" the refused edit would have put it into). `browserSync` keeps, per unanswered batch, the nodes it placed (those its commands depend on the parent of, and those whose position, parent or existence it changed here); a new batch that depends on the parent of one of them names that batch in `after`, as `{ edit }` for an edit of the same request or `{ operationId, edit }` for one of an earlier request. The server does not run an edit whose named edit did not take effect; for an earlier request it looks at that request's stored outcome. A named batch that is known to have taken effect by the time the request is sent is no longer named, so in the ordinary case nothing is looked up. Measurement reports are not named: they are not edits.
- _While the request is unanswered._ `deriveHeldKeys` holds `position` and `parent` together: a change to either holds both. An update that changes the parent of a node whose placement this page holds is therefore kept back whole — parent and position — and the page keeps showing its own complete edit, never its own coordinates under the other page's parent. The same holds for a node under the pointer: a drag goes on in the container the page shows, and a cancelled drag adopts the server's parent together with its position. A paint-order event that does not fit because of a parent kept back is not treated as a divergence.
- _After a refusal._ The page follows the rejected-command path above (rule 4, rule 6): one warning toast (`canvasSync.changeRejected`), the kept-back parent and position are installed, and the Space is loaded once the queue is empty, which also brings the server's sibling order and clears the undo history, so the refused edit cannot be replayed. Undo restores `position` and `parent` together as well (they are recorded together), so undoing a move after another page reparented the node puts it back where it was, in the container it was in.
- _A basis the server does not know._ When the Space's stamps were given a new lineage behind the page's back, the request is refused as a whole (`409 basis-unknown`). The page tells the user once, drops what is queued behind that request — it was made on the same history — and loads the Space, whose `basis` carries the new lineage. A lineage the page had just loaded and is still refused for does not trigger another load, so there is no reload loop.

What this gives that comparing parents could not: a node another page moved out of its Frame and back in is in the same container as before, yet an edit made before that is refused, because the node is not there as the page read it.

### Known gaps of browser structure edits

- An undo whose snapshot the engine would not reproduce exactly is shown as the commands leave it, not as the snapshot (see above). The cases are Frame fits and edge routes that differ from what the snapshot recorded, typically around children whose rendered box changed since.
- The sibling order of a returning Agent Node and its edges are sent in a follow-up batch; until it is answered other pages show the node without them.
- A refused edit (see [Read versions of a page](#read-versions-of-a-page)) converges by loading the whole Space, in place, which resets the page's undo history (the selection is kept for nodes that still exist); the affected nodes are not patched in place, because the server's sibling order is not known from the refusal. While the refused page's request is unanswered it shows the other page's Frame already fitted around a note it still shows elsewhere.
- The read-version check covers the nodes a command names. A node carried along implicitly (the children of a moved Frame) or touched only by the engine (a Frame refit) is not checked, and a size-only resize depends on no parent.
- One version is quoted per edit. When an edit names several nodes and one of them had an update kept back, the whole edit quotes the version before that update, so a change another page made to one of the _other_ named nodes after it — and that this page did show — can refuse the edit although the page had read it.
- An edit names at most 64 earlier batches it was made on top of (the newest are kept).
- The page-close flush sends queued batches before the batch on the wire is answered. A batch made on top of that one is refused if the server has not stored its answer by then (the requests overtook each other), so such an edit can be lost on page close.
- A page whose load carried no `basis` (the Space could not take a baseline just then) sends its edits without a read version, unchecked, until it loads the Space again. The legacy Frame-header migration on load and the conversation-owner patch are sent without one as well.
- A preview tick committed outside a pointer gesture (`localOnly` with no gesture baseline) is not sent by anything; no caller does this today.
- A renderer box is reported for the content the server holds. While a body edit is unsaved the page lays out around its own measurement and the stored box lags; with two pages that render one body differently by more than a pixel, the stored box is the first page's and each page keeps its own local Frame layout until its next measurement change.
- Body, label and other content fields are not sent through the queue; they reach other pages by a fetch after the save ([Node content between pages](#node-content-between-pages)), so for a moment a page measures and lays out against the body it had.
- The unsynced and error states are toasts; there is no separate indicator, and unsent edits are held in memory only.
- Restricted undo relies on the keys recorded for the entry; changes that reached the store without a command batch between two snapshots (a deferred relayout, a locally shown measurement) are not in them and are not undone once another page's edit has been applied.
- Covered by unit tests with a simulated second page and by `apps/web/e2e/multi-page-sync-baseline.spec.ts` with two real browser contexts (moves, create, delete, style, layer order, two writers, one page offline, undo after the other page's edit, a height measured on load); the error state, **Keep trying** and the page-close flush are covered by unit tests only. `apps/web/e2e/sync-convergence.spec.ts` checks in a real browser the page-close confirmation for a derived report versus a user's edit, and **Reload and discard unsent changes** with one note whose text can be saved and one whose text cannot (saved first, asked by name, Cancel, then discard and reload). A reload held for unsaved text, its automatic run and its notice are covered by unit tests; a reload held while a text node is typed into, and its in-place run afterwards (same canvas element, viewport kept), by `apps/web/e2e/sync-reload-while-editing.spec.ts`. `apps/web/e2e/multi-page-frames.spec.ts` covers Frames with two browser contexts and real input: a note dragged into and out of a Frame, a Frame moved with its children, a Grid cell swap, a Column and a Row reorder, grouping and dissolving, a Frame deleted and restored by undo, a Frame resized and switched between layout modes, and two pages editing one note at once in both arrival orders (a drag into a Frame against a recolour and against a move on the canvas, a drag out of a Frame against a move inside it, two drags of one note into different Frames, and a deletion against a move; the refused page is told once and loads the Space once), a move against a drag out of the Frame and back in (refused), and one page dragging a note three times before its first request is answered (all taken). Not covered: edges in a two-browser run, nested and locked Frames, two pages laying out the same structured Frame at once, the SQLite backend, and a run across two devices.

## Node content between pages

A node's sidecar fields (`NODE_CONTENT_KEYS`: `content`, `label`, `labelSource`, `src`, `summary`, `keywords`, `provenance`, `properties`, `propertyDisplayKeys`) are saved by `PUT /api/canvas/:id/nodes/:nodeId/content` from the per-node content queue ([nodeContentQueue.ts](../../apps/web/src/store/canvasStore/save/nodeContentQueue.ts)). That request does not change the Space `version` and produces no `update`. This covers note and text bodies, the Question prompt, and the label of every node type that has a sidecar, including labels and summaries that preprocessing derived on the saving page.

```
page A edits a body / title           page B (not editing that node)
   │ content queue (debounced)
   ▼
PUT …/nodes/:id/content { …, expectRev, pageId: A }
   │ server: rev check, write sidecar
   ▼
invalidate { nodeIds: [id], originPageId: A } ──► canvasSyncStore
                                                    │ originPageId ≠ B
                                                    ▼
                                    GET …/nodes/:id/content → { content, label, …, rev }
                                                    ▼
                                    adoptRemoteContent: the fetched fields as an update's row,
                                    through the same partition by holds; + baseline rev
```

### What is versioned and what is not

One rule, for pages and agents alike:

| Part of a node                                                | Protection against concurrent writes                                                                                                                                                                    |
| ------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Body**: `content` and `src`                                 | The **content revision** (`nodeRevisionOf`, `CONTENT_REVISION_KEYS`). A writer quotes the revision it last saw (`expectRev`); a stale one is refused (`NODE_CONTENT_CONFLICT` / an execute `conflict`). |
| **Custom properties**: `properties`, `propertyDisplayKeys`    | None. Each write is a per-key patch applied to the stored record as it is at that moment: different keys never conflict, the same key is last-writer-wins. No revision is needed, quoted or checked.    |
| **Title** a person or an agent gave: `label`, `labelSource`   | None. A rename is applied to the stored record as it is at that moment: it never conflicts with a body edit or a property edit, and two renames of one node are last-writer-wins. No revision.          |
| Summary, keywords, provenance, an automatic title (`auto`)    | The body's content revision: they are derived from one particular body, so a save of them quotes that body's revision and is refused when the body has changed since.                                   |
| Structure: position, size, parent, colour, font, order, edges | The read-version check per command ([Browser structure edits](#browser-structure-edits)); same-field edits are last-writer-wins.                                                                        |

Consequences. A custom-property change or a rename, by anyone, never changes a node's content revision, so it never refuses a body save and never asks a person to choose. A body change never refuses a property write or a rename: somebody renaming a note while somebody else types in it both keep what they did, and nobody is asked. Position, colour, properties and title are all independent small items in this sense; only the body has a version. The revision is computed from the stored record on demand and is not stored with the node, so existing Spaces need no migration: a node that has properties simply reports the revision of its body from now on.

**Sending.** The queue adds this page's id (`CANVAS_PAGE_ID`) to the request as `pageId`. The server copies it to the event as `originPageId` and does not store it. It is routing information, not a credential: the event carries `originPageId` only on streams of the principal that made the save (`eventForSubscriber`), so a page cannot be made to skip another principal's save by that principal quoting its page id — every other principal's pages receive the event without it and fetch. One schema, `canvasPageIdSchema` (1–64 characters of `[A-Za-z0-9_-]`), is the shape of a page id everywhere: `originator.tabId`, the content PUT's `pageId`, presence and the stream's `pageId`.

**Receiving** (`canvasSyncStore` → `adoptRemoteNodeContent` → `NodeContentQueue.adoptRemoteContent`). A page ignores an event whose `originPageId` is its own, so it does not fetch what it just wrote; an event without `originPageId` (another client) is fetched. For each named node that the page has and that has a sidecar, the page fetches `GET …/nodes/:nodeId/content` and:

- turns the fields that differ into the row an `update` would carry (`remoteContentRow`: the node as shown, and that node with the fetched fields) and applies it by the rule every remote change is applied by — `BrowserSync.prepareRemote`, i.e. `toFieldLevelDeltas` with this page's holds — through `_setStateRaw`, replacing only that node's object. A field the response does not carry is left alone, a body is given only to a node type that has one, and a response reporting a missing sidecar is not adopted (the deletion arrives as a structure update);
- sets the node's baseline revision to the returned `rev` in the same step — when the page then shows the server's body — so the page's next save of that node sends the fetched revision as `expectRev` and is not refused;
- puts the same fields into every undo and redo entry of the Space (`rebaseRemoteContent`), so undoing an earlier local edit cannot restore the previous body and save it over the other page's.

One fetch runs per node at a time; saves that arrive during it are read by one further fetch. A fetch is dropped only when the node was forgotten or brought back by an undo meanwhile; this page's own save of the node during the fetch — a rename, say — does not drop it. An event that arrives while the Space is loading is fetched when the load ends. The response carries `provenance` for this purpose.

**What it does not do on the receiving page.** No content save, structure save or preprocessing request is sent, the Space is not marked as having unsaved changes, no undo entry is added, and selection, viewport and focus are not touched. An open preview of that node shows the new body and title through the editor's existing external-content path; a text node that is not being edited re-syncs its draft.

**A node with something unsaved on this page** — a queued or in-flight save, a failed save, a conflict, or a body held for an undo restore — keeps exactly the fields this page changed (`NodeContentQueue.holdsUnit`). Everything else the other save changed is shown at once: with a body being typed here, the other page's title, summary and custom properties appear; with a rename being saved here, the other page's body appears. A custom property is held per key. The baseline follows the body: when the fetched body was kept back the baseline stays, so this page's save is refused with `NODE_CONTENT_CONFLICT` and the existing **Keep mine / Load latest** toast decides; when the fetched body is now the one shown, its revision is the baseline. If the other save changed only fields the revision does not cover, this page's body save is accepted, because the revision did not move. Once this page's save has been acknowledged the node is fetched once more. Text typed while a fetch is under way is kept the same way.

**A conflict stays the user's to answer.** A node frozen by `NODE_CONTENT_CONFLICT` counts as having unsaved content for as long as the choice is open (`hasUnsaved`), and its body fields are held, so no `update` replaces its text, re-seeds its baseline or reloads the Space under it: an update to another node, a move of the node itself and a wanted reload all leave it frozen with its toast. An `update` that carries a new server body for the frozen node (an agent's write, say) has that body kept back like any body being edited, and the user is told their version was kept, but it does not resolve the conflict: `rebaseConflict` only moves the revision **Keep mine** will overwrite on to the one the update names (`nodeContentRevisions`); when the update names none, the node is compared with what the server holds, as for another page's save below. Only **Keep mine**, **Load latest**, deleting the node, a confirmed discard — or the server turning out to hold the same content, below — ends the freeze.

**Identical content is not a conflict.** When the server holds exactly what this page was saving, there is nothing to choose between, so nothing is asked. "Exactly" means the fields the content revision covers (`content` and `src`; custom properties are not compared, they cannot conflict) compared as a save sends them: the same revision (`nodeRevisionOf`), or, for a node whose stored body the page does not hold (a PDF's extracted text), equality of each of those fields the page would send. One character of difference is a conflict as before. In every case below the page's text and caret are not touched (the store is not written), the server's revision becomes the baseline, and no toast is shown; fields the revision does not cover that are still unsaved (a title, a summary, a property) go out with the next save.

- _At the refusal._ `performSave` compares the revision the `409` names with the revision of what it sent; when they differ it fetches the node once and compares fields (`serverHoldsSameContent`). If identical, the save is sent once more on the server's revision and the node is never frozen, so the conflict toast never appears. A second refusal is reported as usual. The page-close keepalive save does not do this.
- _While frozen, from an update._ `applyServerDeltas` asks the queue for every row that names a frozen node (`settleConflictIfIdentical`): the revision of the node as the page shows it is compared with the stored revision the update names for it. If they are the same, the freeze and its toast are dismissed before the holds are read; the row then applies like any other and nothing is reported as kept back. An update that names no revision for the node settles nothing by itself; the fetch described next does.
- _While frozen, from another page's save._ An `invalidate` for a frozen node fetches it (`checkFrozenAgainstServer`) instead of ignoring it. Identical content ends the freeze the same way; anything else leaves the node frozen and moves the revision **Keep mine** will overwrite on to the fetched one.

**Measured height and box.** The receiving page re-measures the node against the new body and shows the result at once: the height of an auto-height note, the rendered box of a `text` or `question` node (and its own Frames around it). Whether it reports the measurement is decided by the existing rules for `APPLY_MEASURED_HEIGHT` and `APPLY_MEASURED_SIZE` ([Browser structure edits](#browser-structure-edits)): at most once per page and measurement key, and not at all when another page's report under the same key has already arrived. The receiving page has no content save pending for the node, so its report does not wait; when it and the saving page both report before either has seen the other's update, the server receives two reports under one key and neither page answers the other's. A report changes the Space through `execute`, never through a content save, so it cannot cause another content event.

### Content saved before the stream was open

A content save does not change the Space version and reaches other pages only as an event, so a page that was not subscribed when it was made — because its stream was down, or because it had loaded the Space and not yet opened the stream — cannot learn of it from the `snapshot`. The page therefore tracks a **content position** and asks.

- `GET /api/canvas/:id` returns `contentPosition: { epoch, seq }`, read by the server **before** it reads any node: every content save up to that position is in the response, and a save that lands while the response is being put together is after it. The page keeps it as `canvasStore.contentPosition`.
- `GET /api/canvas/:id/content/changes?epoch=&seq=` answers `{ position, changedNodeIds? }`: the nodes whose content was saved after the position given, and where the sequence stands now.
- `canvasSyncStore` asks (`catchUpContent`) whenever it could have missed a save: on every `snapshot` — the first connection and every reconnection — and whenever a load ends while the stream is open. It asks from `contentPosition`, hands the named nodes to `adoptRemoteNodeContent` (the same path as a live `invalidate`: one fetch per node, nothing for a node with unsaved content on this page, no Space load, no undo entry), and then moves `contentPosition` on to the answer's. A snapshot that arrives while the Space is loading does not ask; the end of that load does, from the position the load brought. The same holds for a snapshot whose version differs and starts a reload; when that reload is held back (unsent edits, unsaved text) the question is asked at once rather than waiting for it.

Why nothing is missed across load and subscribe, in either order. When the page asks, the stream has delivered its snapshot, so the server subscribed this page before the question was answered: a save after the subscription arrives as an `invalidate` (possibly as well as in the answer), a save between the position and the subscription is in the answer, and a save before the position is in the load. Fetching a node twice is harmless: the fetch only changes fields that differ.

The position moves only when the request succeeded and every named node was fetched (or was left alone for its unsaved content, which is fetched after its own save). A failed request or fetch keeps the position, so the same question is asked again: after 1 s, 2 s and 4 s, and then at the next snapshot or load.

The position is storage's own persisted record of node writes ([`SpaceNodes.changes`](./canvas-storage.md#43-which-nodes-were-written-since-a-position)): a per-Space counter written with each node on SQLite and PostgreSQL, the sidecars' modification times on Disk. It is not kept in process memory, so it means the same after a server restart, and it covers every field of a node's record — a title or summary as well as a body — and every writer, including preprocessing and an agent's batch. Nothing is recorded when an event is published. A restart therefore changes nothing for a reconnecting page: it asks from the position it has and is told exactly which nodes to fetch.

When the server cannot compare the position with the Space's sequence it answers `reset: true` instead of a list. That is left for a Space that was deleted and created again under the same id, a deployment moved to another storage backend, and a page still holding a position from before this record existed. The page then fetches every node that has saved content, four at a time, whatever their number. Content never causes a whole-Space reload, so it never costs the page its undo history.

**Structure and presence across the same window.** A structure commit made before the subscription is seen through the version: a `snapshot` whose version differs from the page's makes it load the Space again. A snapshot that arrives while the Space is still loading is not compared (the load in flight is expected to bring that version), so the sync store remembers the highest version the stream has named and, when a load ends below it — its read predated a commit that predated the subscription — loads once more. A commit after the subscription arrives as an `update`. Presence has no such window: the server subscribes the stream to presence and writes the presence snapshot in the same tick, and presence is not part of what a load returns.

Covered by `sync.route.test.ts`, `canvas-content-cas.test.ts` (a load's position, then a body and a title saved, then the question), `content-position.restart.test.ts` (the same across a server restart, on Disk and SQLite), the storage contract, the web sync-store tests, and `apps/web/e2e/sync-convergence.spec.ts` in a real browser: content saved between a load and the first stream connection, a body and a move made after the server read the Space for a load still in flight, and a body and a title saved while a connected page's stream is cut.

### Properties and PDF notes between pages

Two features share this machinery: authored node properties (tags and other values, [storage](./canvas-storage.md#authored-node-properties-and-pdf-notes)) and the Note a PDF owns.

**Properties are node content without a revision.** `properties` and `propertyDisplayKeys` are content keys: they are stripped from the commands the send queue sends, never held as a structure unit, and saved through the content PUT. They are **not** covered by the content revision ([what is versioned](#what-is-versioned-and-what-is-not)): every write of them is a per-key patch, applied by the server to the properties it holds at that moment.

| Writer                                                                         | Path                                                                                                                                                                                                                                                                            | How another page gets it                                                                                             |
| ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| The properties region of a preview (`commitNodeProperties`)                    | `NodeContentQueue.commitProperties`: one content PUT at once that carries the changed keys (`null` deletes one), the display order when it changed, and `pageId` — no body, no title, no `expectRev`. The store is changed only when the server has answered (one undo entry).  | `invalidate { nodeIds, originPageId }`, then a fetch (`adoptRemoteContent`)                                          |
| Undo or redo of a property edit, any other store change of them                | The debounced content save. The queue records which keys the store change touched (`pendingPropertyKeys`) and sends those, a removed key as `null`. Properties alone: a request without `expectRev`. Beside a body changed at the same time: in the body's request (see below). | The same                                                                                                             |
| An agent's `MERGE_NODE_DATA` (`properties`, `propertyDisplayKeys`, `coverUrl`) | `execute`; the engine merges the keys into the node (`mergeNodeProperties`) and the server writes the sidecar in the batch. No `expectRev` and no prior read are needed, and one that is sent is not looked at, unless the patch also rewrites `content`.                       | The `update`. Its `nodeContentRevisions` names the node with the revision of its body, which the write did not move. |
| A PDF cover set or cleared on a page (`coverUrl`)                              | Structure: `MERGE_NODE_DATA` through the send queue (`unset` for a clear).                                                                                                                                                                                                      | The `update`, as the `data.coverUrl` unit                                                                            |

**The server rule** ([canvas.route.ts](../../apps/server/src/modules/canvas/canvas.route.ts), `updateNode` in [write-coordinator.ts](../../apps/server/src/modules/canvas/write-coordinator.ts)).

- _A request that carries only unversioned items_ — a property patch (`properties` and/or `propertyDisplayKeys`) and/or an authored title (`label` / `labelSource` other than `auto`), besides `nodeType`, `pageId` and `expectRev` — is applied without a revision check, for every node type (`isRevisionCheckedRequest` in [node-content-update.ts](../../apps/server/src/modules/canvas/node-content-update.ts)). An `expectRev` in it is ignored. Its answer names the revision of the body the server holds, which the request did not change.
- _A request that carries a body (or a summary, keywords, provenance, an automatic title) and unversioned items_ checks `expectRev` for the body, as before. When the body is refused, the authored title and the property patch are still applied (`applyNodeUnversionedPatch`) — in the same pass under the Space's write mutex (`applyUnversioned`) — the `invalidate` is published, and the `409` says so: `NODE_CONTENT_CONFLICT` with `titleApplied: true` and/or `propertiesApplied: true`. The body and what is derived from it are not written. The one exception keeps a rename's own rule: a title another node already uses (`labelSource: 'user'`, strict) answers `NODE_LABEL_CONFLICT` and writes nothing of the request, as it does when the body is not stale.
- _Agents._ `collectMergeConflicts` in [canvas-executor.ts](../../apps/server/src/modules/canvas/canvas-executor.ts) checks `expectRev` (and reports `not-read` without one) only for a patch entry that carries `content`. An entry that carries `content` **and** properties is refused as a whole when the body revision is stale; nothing of it is applied. Agents are told to send properties in their own entry.
- _A PDF._ Its extracted text is a derived body: content PUTs of a PDF are last-writer-wins and were only checked while properties shared the revision. With properties unversioned no PDF write is checked, and the acceptance of a "metadata-only revision" (`derivedBody`) that existed for that is gone.

**The page rule** ([nodeContentQueue.ts](../../apps/web/src/store/canvasStore/save/nodeContentQueue.ts)).

- A save carries only what this page changed, see [What a save carries](#what-a-save-carries). A body save quotes the body's baseline and carries no property that was not changed in the store on this page. It never carries another writer's keys, so it can neither overwrite nor remove them.
- A property save never moves the body's baseline: the revision its answer names is the server's body, which this page may not show. The same holds for a rename's answer: another page may have saved a body this page has not fetched yet, and a baseline moved to that body's revision would let this page's next body save overwrite it unseen instead of being refused.
- `commitProperties` has a lane of its own (`propertySaves`), separate from the body's (`inflight`). A property edit on the wire is not unsaved content of the node (`hasUnsaved` is false for it), so a body another page or an agent saves meanwhile is shown at once; and it is sent while the node's body is unsaved, in flight, or frozen by a conflict. Two property edits of one node from one page are sent in the order they were made.
- The one exception to "by itself": a node this page created and has not saved yet. Its first save (which carries its properties) goes out before a property edit, and the edit is not made when that fails.
- When a refused body save reports `propertiesApplied` or `titleApplied`, the page settles those fields of that request and keeps only the body for the user's choice; **Keep mine** then sends the body alone.
- A rename follows the same rule as a property save: it quotes no revision, its answer never moves the body's baseline, and a node frozen by a body conflict still sends a rename (and its properties) by itself while the body waits for the user's choice. The title the answer names is shown when it differs from the one sent (an agent's or an automatic title may be de-duplicated).

**Properties arriving while this page has something unsaved for the node.**

| This page holds for N                                    | An `invalidate` for N (another page's save)                                                                                                   | An `update` for N (an agent's write, a page's execute)                                                                                                                        |
| -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| An unsaved or in-flight body                             | Fetch; show the properties (and every other field this page has not changed), keep the text and its baseline. The next body save is accepted. | The property keys the batch changed are applied to the node as it is shown, text and baseline untouched. Also when the batch changed the body too and that part is kept back. |
| A property edit on the wire (`commitProperties`)         | Fetch and show the whole node (body and baseline included). One more fetch follows this page's answer.                                        | Applied as to any node. One fetch follows this page's answer.                                                                                                                 |
| A property key changed in the store and not saved (undo) | The other keys are shown; that key keeps its value here and its save, which follows, is the last writer.                                      | The same, per key.                                                                                                                                                            |
| A body frozen by a conflict                              | Fetch to compare bodies; the properties are shown whichever way it ends.                                                                      | The property keys are applied; the freeze is as described above.                                                                                                              |

The fetch after a property edit's answer exists because a fetch made while the edit was on the wire may have read the server before or after the edit was written. The page does not guess: it reads the node once more and shows what the server holds, which is what the last writer of each key left.

A fetched response always carries the node's whole property bag and display order, so their absence removes them on the receiving page.

**Failure of a property save.** A failed `commitProperties` leaves the store as it was (the edit is retracted) and shows a danger toast; a transport failure (network, `5xx`) offers **Retry**, which is refused once the Space, the permissions or the affected keys have changed; a `403` and other `4xx` offer none. The queue records nothing for it: no failure record, no freeze, and the node's body is unaffected. A property save cannot be refused by revision. (Against a server that predates this rule it can; the edit is then retracted with the toast and no retry.)

**Lists.** A property whose value is a list (tags) is one value: the patch format (`nodePropertiesPatchSchema`: a key maps to a string, number, boolean, string list, or `null`) can replace or remove a key, not add or remove an item of it. Two writers that each add a tag to the list they saw are therefore last-writer-wins on that key, and the first writer's tag is lost. `propertyDisplayKeys` is likewise replaced as a whole; this loses no property, because a key missing from the order is still shown, after the listed ones (`orderedPropertyKeys`), and a listed key that no longer exists is ignored.

**Editing properties of N is editing N.** The properties region is inside N's preview, so a focused property field reports N as being edited ([One editor at a time](#one-editor-at-a-time)), and while another page edits N — its body, its title or a property — this page shows N's properties read-only. This is unchanged and is no longer needed for correctness: a property save made while another page types does not refuse that page's body save. It still prevents two people from editing the same property (the later save would silently win). Menu actions that never focus a field (retype, delete, reorder by drag) take no lock themselves but are refused by one.

**Two pages, different properties of one node.** Each save patches only its own keys, so both stand whatever the order and timing of the two requests, with one request each and no fetch before it. `apps/web/e2e/multi-page-properties.spec.ts` holds one page's request back until the server has taken the other's and checks that it is applied as sent. **The same property:** the later request wins on the server; both pages end up showing it (the page whose value lost fetches the node after the other's `invalidate`, and the page whose value won reads the node once more after its own answer), and nobody is asked.

**A PDF's Note** is created by `INITIALIZE_PDF_NOTE` through the send queue with the id the page chose, so it is one edit with one read version like any other (target: the PDF). The other pages receive an `INSERT_NODE` for the hidden Note and the PDF's `noteNodeId` as an update; the Note's text then travels as node content. If two pages give the same PDF its Note at once, the second command is a `no-op` on the server, and that page removes its own optimistic Note and shows the first page's when the update arrives. Deleting the PDF is one `DELETE_NODES`; the engine takes the Note with it on the page and on the server. Undo and redo of the pair are command batches ([Browser structure edits](#browser-structure-edits)): `RESTORE_NODES` carries both nodes with the Note's body, which the server writes in the same batch. A copied pair is pasted as `CREATE_NODES` with remapped ids; images in the Note are cloned into the destination Space first.

**Releasing the edit lock does not save twice.** When a property field loses focus while its save is on the wire, the page waits for that save before reporting the release instead of sending the node again.

### Known gaps of node content between pages

- Only `content` and `src` are covered by `expectRev`. A summary, keywords, provenance or automatic-title save quotes the baseline all the same and is refused with the body's conflict choice when another writer changed the body since; when nobody did, two pages that change the same one of those fields are last-writer-wins without a notice.
- Two people renaming one node at the same moment get no notice: the later rename wins, on the server and on both pages (the page whose title lost fetches the node after the other's `invalidate`). A rename the server refuses for a name in use (`NODE_LABEL_CONFLICT`), or that fails in transit, is put back to the previous title on the renaming page, and that title stays this page's unsaved change until its next save, which writes it; a title another page gave the node in between is overwritten by it.
- The page's own title is shown to it again when a save that did not carry a title is answered and the page holds no unsaved title: the answer names the title the server holds.
- A list-valued property (tags) and the display order are replaced as a whole: two writers that each add an item to the same list are last-writer-wins on that key ([Lists](#properties-and-pdf-notes-between-pages)).
- Two people editing the **same** property at the same moment (possible only when both editors opened before either page heard of the other) get no notice: the later save wins.
- A remote save replaces the node's content fields in this page's undo entries as a whole (`rebaseRemoteContent`), properties included: after another page's property edit has arrived, undoing an earlier local property edit of that node no longer changes it.
- On the Disk backend the position is taken from file modification times: the node or nodes written in the same millisecond as the Space's latest write are fetched again at each reconnection, and a write dated before the position is not seen — a clock set back past the Space's most recent write, or a sidecar replaced from outside with an older modification time kept ([details](./canvas-storage.md#43-which-nodes-were-written-since-a-position)).
- After a `reset` (see above) a large Space costs one fetch per node with saved content.
- A fetch that fails after a live `invalidate` is not retried; the next save of that node by another page, or the next reconnection, fetches again. (A fetch that fails during a content check is asked for again, see above.)
- The page's content position moves only at a load and at a content check, not with each live `invalidate`, so a reconnection names — and fetches again — every node saved by any page since this page's previous connection, including its own saves.
- Each save costs one extra request per other open page. Bodies are not sent in the event.
- Covered by unit tests and by two real browser contexts in `apps/web/e2e/multi-page-sync-baseline.spec.ts` (case f) and `apps/web/e2e/content-sync.spec.ts` (title, open preview, measured height), and `apps/web/e2e/multi-page-properties.spec.ts` (a PDF's Note created, and deleted and restored by undo; tags and a PDF property set and cleared; the properties read-only while another page edits them; two pages editing different properties of one note, in sequence and at the same moment, neither refused; two pages editing the same property, the last writer winning on both; an agent's property write while a page types the body of that note; an agent's tag right after a page saved the body, without a revision and with a stale one, and its body rewrite still refused; an agent's `execute` write to a PDF's properties followed by another page's property save on it, and to a note body followed by another page's edit of it). Text nodes and Question prompts use the same path and are covered by the queue's unit tests only.

## What a page holds against incoming changes

Loading a Space may attempt to persist a legacy Hug Frame header adjustment before displaying the adjusted geometry. This optional layout write is not a prerequisite for reading the Space: if it fails (including version conflicts or Agent execution-record validation), loading completes with the original loaded geometry, content, edges, and snapshot version. The failure is logged without a blocking or persistent toast, and neither the rejected geometry nor its warmup hints are automatically resubmitted by the load path. Normal save validation and SSE reconciliation remain in force; this fallback does not repair missing execution records or force an overwrite.

**One mechanism.** A node is a set of property units ([propertyUnits.ts](../../apps/web/src/store/canvasStore/sync/propertyUnits.ts)): position, size, parent, each `data.style` leaf, each custom property, every other `data` key (body, title, summary, …), every other top-level key, and the node's existence. A unit this page has changed and not had confirmed is **held**. One function decides what a remote change may touch — `toFieldLevelDeltas` ([fieldLevelDeltas.ts](../../apps/web/src/store/canvasStore/sync/fieldLevelDeltas.ts)), reached through `BrowserSync.prepareRemote` — for structure and content alike, and for both ways a change arrives: the rows of an `update`, and content fetched after an `invalidate`, which is first turned into the row an update would carry ([remoteContent.ts](../../apps/web/src/store/canvasStore/sync/remoteContent.ts)). For every unit the change names: a held unit keeps its local value and the remote value is **kept back and buffered**; every other unit is written. Nothing is skipped as a whole node and no remote value is dropped.

| Holder                                                                                                | What it holds                                                                                                                                                                                                                                                                  | Until                                                                                   |
| ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| The send queue's in-flight set ([inFlight.ts](../../apps/web/src/store/canvasStore/sync/inFlight.ts)) | The structure units each unanswered batch changed                                                                                                                                                                                                                              | The batch is answered ([Browser structure edits](#browser-structure-edits))             |
| The open pointer gesture                                                                              | What its ticks have changed so far                                                                                                                                                                                                                                             | The gesture closes; its batch then holds the same units                                 |
| The content queue (`NodeContentQueue.holdsUnit`)                                                      | The content fields this page changed and has not saved: body, title (with its source), summary, keywords, provenance, the display order, each custom property by key; the body's fields of a node frozen by a conflict; every content field of a node an undo is bringing back | The save that carries the field is acknowledged, or the page takes the server's content |
| The node being edited (`localEditingNodeId`)                                                          | The node's existence                                                                                                                                                                                                                                                           | The editing ends                                                                        |

The buffer is the in-flight set's (`InFlightSet.withhold`). A holder the send queue does not know answers "is it held" through `prepareRemote`'s `alsoHeld` and says when its hold ends through `BrowserSync.localHoldsEnded`: a kept-back value is then shown, unless this page's own value replaced it on the server (a save that carried the field), in which case it is dropped. Structure holds are released as described under [Browser structure edits](#browser-structure-edits): a refused or no-op batch installs what was kept back.

`applyServerDeltas` ([canvasStore.ts](../../apps/web/src/store/canvasStore.ts)) is that rule plus what belongs to an `update`: it merges the rows into whole nodes and drops what must not come back (an optimistic Question removed here), settles a conflict the update itself resolves, partitions by holds, applies the rest, replays sibling order, moves content baselines (`settleContentBaselines`), runs post-effects and releases the page's own confirmed batch. `version` always advances to `toVersion`, so the next update is contiguous.

**What the person keeps, and is told.**

- _Unsaved body text is never overwritten._ The body's fields are held from the first keystroke until the save is acknowledged, through a failed save and through an unanswered conflict. This is so for every body a person types into: a Note's editor and a text node edited in place both write each change to the store, where the content queue sees it (`scheduleChanges`); neither keeps a draft of the body outside it. A text node's editing session is one undo entry: its first change is an ordinary edit (`updateNodeData`), the following ones are written without an entry (`patchNodeSilent`), and its control shows the store's text, so a value the control did not write — an undo, the server's body taken after a conflict — replaces what is in it.
- _An Agent's change that was kept back is reported._ `applyServerDeltas` returns the nodes of which a body, title or summary value — or the deletion — was kept back for the page's own content. `canvasSyncStore` shows the "your version was kept" warning at that moment and passes the ids to `acpThreadChangesStore` (`conflictedByThread`), so the conversation's review card marks the row (`· skipped`, revert disabled) and a `ConflictBadge` counts it on the Question's "done" badge; the Agent's value stays inspectable in that row. A custom property kept back is not reported: the later writer of a property wins without a notice, here as everywhere. Post-effects (preprocessing, fit) do not run for such a node.
- _A node is not deleted from under the caret._ A `DELETE_NODE` for the node this page is editing is kept back. The page says so (`canvasSync.deletedWhileEditing`), keeps the node with what is typed, and sends nothing more for it (`NodeContentQueue.setDeletedElsewhere`: the server has no node to write to). When the editing ends — the control loses focus, the editor closes, the tracker gives the node up — the node is removed, its bookkeeping is forgotten, and a notice (`canvasSync.deletedElsewhere`) offers text the server never received for copying. A node that is not being edited is removed at once, with the same notice when it had unsaved text. An `INSERT_NODE` for the node meanwhile (the deletion was reverted) cancels the removal.

**Baselines** ([Where a baseline comes from](#where-a-baseline-comes-from), [Baseline and save status](#baseline-and-save-status)). After a batch is applied, the content-CAS baseline moves for the nodes whose saved content the batch changed or created (the nodes `nodeContentRevisions` names, a `REPLACE_NODE` whose content keys differ, an `INSERT_NODE`), to the revision the server stored.

- _A node with nothing unsaved_ shows the server's content: the baseline moves and what was recorded about its saves is cleared.
- _A node with something unsaved, whose body the batch changed._ The baseline moves to the batch's revision whether the body was applied (only a title was unsaved here) or kept back. Kept back, this is the **local-first rebase**: the person's next save quotes the writer's revision and replaces the writer's body instead of being refused with `NODE_CONTENT_CONFLICT`; the warning and the review card are the record of the kept-back change. Only the baseline moves: a failed save stays recorded with its **Retry**. This applies to bodies that arrive in an `update` — an Agent's write; a page never writes a body through `execute`. Another person's save arrives by fetch, where a kept-back body leaves the baseline alone and the person chooses ([Node content between pages](#node-content-between-pages)).
- _A node with something unsaved, whose body the batch did not change_ (a title, a property, structure) keeps its baseline. So a body being typed while another page's (or this page's own) structure update arrives is saved normally, and a baseline that is behind another person's body is not silently moved past it.
- _A node frozen by a conflict_ stays frozen; only the revision **Keep mine** will overwrite moves.
- _A node whose stored body the page does not show_ — a PDF's extracted text is not sent with a load, an Office body is normalized — keeps the canonical revision the load brought unless the batch changed its content; a revision recomputed from what the page shows would not be the server's.

On a **version gap** (`toVersion > local`) the tab catches up with `loadCanvas`, held until nothing is unsaved and the send queue is empty ([Reloads](#browser-structure-edits)).

**Agent Nodes.** There is no Question-specific merge. A pending prompt holds the body, so an independent generated title lands; a pending manual title holds the title, so the server-seeded first prompt and lifecycle metadata land; same-field overlap keeps the local value and is reported as above. A lifecycle or title projection (`agentNodeProjection`) is replayed onto the live node first (`projectionRowsOntoLive`), so it carries its data effects only. The eventual content PUT carries only the fields that are pending.

### What a save carries

`PUT …/nodes/:nodeId/content` writes the fields a request carries and keeps every other field of the stored record. The page ([nodeContentQueue.ts](../../apps/web/src/store/canvasStore/save/nodeContentQueue.ts), `buildRequest`) sends only what it changed since its baseline — the fields the content queue holds:

| The page changed                                                       | The request carries                                                                                                           |
| ---------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| The body (`content`, or `src`)                                         | That field and `expectRev`                                                                                                    |
| The title                                                              | `label` and `labelSource` together (the server protects a person's title from an automatic one by the source); no `expectRev` |
| An automatic title (`labelSource: 'auto'`)                             | `label`, `labelSource` and `expectRev`: it is derived from the body                                                           |
| Summary, keywords, provenance                                          | Each one that changed, and `expectRev`                                                                                        |
| Custom properties, the display order                                   | The changed keys (`null` removes one), the order when it changed; no `expectRev`                                              |
| A title or properties, and the body or something derived from it       | All of them in one request with `expectRev`; the server writes the title and the properties whatever becomes of the rest      |
| Nothing                                                                | No request                                                                                                                    |
| A node this page creates and has not saved, or one an undo brings back | The whole node: its record does not exist yet                                                                                 |

This holds for every node type with a sidecar: a note, a text node, a Question (which was already saved this way), and a PDF, Office or web node, whose rename carries neither the file reference nor derived text. After a body conflict, **Keep mine** resends what is still unsaved on this page — the body, with the server's revision — so a title, summary or property another writer changed meanwhile is not written back from this page's copy; a title this page itself changed and has not saved goes with it, being its own change. Covered by `nodeContentQueue.changedFields.test.ts`, `canvasStore.remoteProtection.test.ts` and, with two browser contexts and a third writer, `apps/web/e2e/content-sync.spec.ts`.

### Where a baseline comes from

The baseline of a node is always a revision the server computed from the stored record. The page hashes a node (`revOfNode` in [nodeContentQueue.ts](../../apps/web/src/store/canvasStore/save/nodeContentQueue.ts)) only to compare its **own** content with a server revision, never to obtain the baseline of content the server sent.

| The page learns the revision from                                      | Source of the value                                                            |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| A load (`GET /api/canvas/:id`)                                         | `nodeContentRevisions` of the response                                         |
| Its own save of a body or of something derived from one                | `rev` of the PUT response                                                      |
| Another page's save (`invalidate`), a content check, **Load latest**   | `rev` of `GET …/nodes/:id/content`, installed with the fetched content         |
| An `update` that changed the node's content and was applied            | `nodeContentRevisions` of the update                                           |
| An `update` whose content change was withheld from a node being edited | `nodeContentRevisions` of the update; the text is not touched                  |
| An `update` for a node frozen by a conflict                            | `nodeContentRevisions` of the update, as the revision **Keep mine** overwrites |
| The HTTP response of the page's own `execute` (applied as its update)  | `nodeContentRevisions` of the response                                         |
| A refused save whose content the server already holds                  | `currentRev` of the `409`, or `rev` of the fetch that compared them            |

**A content change without a revision.** A server older than `nodeContentRevisions`, or a batch whose read-back failed, sends a content change with no revision for the node. The page does not compute one. It treats the update, for that node, as another page's save of it and calls `adoptRemoteContent` (the `invalidate` path):

- a node that shows the server's content (the change was applied) is fetched; the fetched `rev` becomes the baseline together with the fetched content, so its next save is accepted. If the fetch fails the baseline stays; the next body save is refused and settled by the identical-content rule or the user's choice;
- a node with an unsaved body keeps its baseline and its text (the fetch shows what the page does not hold). Its save is refused, and the refusal is settled as always: silently when the server holds exactly what was saved, otherwise by **Keep mine / Load latest**. With such a server the local-first rebase is therefore a choice put to the user instead of a silent one. Once the page's own save has been acknowledged the node is fetched;
- a frozen node is compared with what the server holds (`checkFrozenAgainstServer`): identical content ends the freeze, anything else moves the revision **Keep mine** will overwrite to the fetched one.

The fetch-and-install path is not used to move the baseline under unsaved text: a fetch returns whatever the server holds by then, which may include a later save by somebody else that the page has never shown, and a baseline moved to it would let the next save overwrite that silently.

Remaining uses of `revOfNode`, each of the page's own content: the comparison of a node the page shows with a fetched or named server revision (`showsServerContent`, `serverHoldsSameContent`, `settleConflictIfIdentical`); the baseline of a node this page itself creates and sends whole (`prepareServerCreatedNodes`), replaced by the server's revision when the update for the creation arrives; and `setBaselines` for a node a load did not name a revision for, which only happens with a server that sends no `nodeContentRevisions` on load.

### Baseline and save status

The content queue keeps two things per node, changed by two operations:

- `setBaselines(nodes, revisions)` moves the baseline — the body's revision, and the generation that tells a body save in flight that the baseline moved under it — and nothing else. Custom properties and the title have no baseline.
- `clearUnsavedStatus(nodeIds)` forgets what is recorded about the node's saves: the failure record and its toast, the once-per-node toast guards, and a conflict freeze.

| Event                                                                      | Baseline                                             | Failure record and toast         | Conflict freeze                    |
| -------------------------------------------------------------------------- | ---------------------------------------------------- | -------------------------------- | ---------------------------------- |
| Load                                                                       | moves                                                | cleared                          | cleared (the text was replaced)    |
| Own body save acknowledged                                                 | moves                                                | cleared                          | —                                  |
| Own property save acknowledged (`commitProperties`, or properties alone)   | stays                                                | kept                             | kept                               |
| Own rename acknowledged (a title alone, or with properties)                | stays                                                | kept while a conflict is open    | kept                               |
| Remote content adopted by fetch, node with nothing unsaved                 | moves                                                | none to clear                    | none to clear                      |
| Remote content fetched for a node with something unsaved                   | stays, unless the server's body is now the one shown | kept                             | kept (compared, see above)         |
| Update that changed the node's content, applied (node had nothing unsaved) | moves                                                | cleared                          | cleared                            |
| Update whose content change was withheld from a node being edited          | moves                                                | **kept**                         | **kept** (only its revision moves) |
| Update that did not change the node's content                              | stays                                                | kept                             | kept                               |
| **Keep mine** / **Load latest**                                            | moves                                                | cleared with the save / the load | cleared                            |
| Identical content (at the refusal, from an update, from a fetch)           | moves                                                | cleared                          | cleared                            |

So a baseline moves whenever the page learns the server's current revision of the node; a failure record and its toast go only when the node's save succeeded or the page no longer holds anything unsaved for it; and a freeze ends only by the user's choice, by the identical-content rule, or because the page's copy was replaced by the server's. The withheld-update row is the one caller that uses `setBaselines` alone, so it cannot clear either. Before the split it cleared the failure record and the **Retry** toast of a node whose save had failed while the text stayed unsaved.

The ids of nodes with a kept-back content value flow back through `canvasSyncStore` into `acpThreadChangesStore` (`conflictedByThread`) and surface as described under [What a page holds against incoming changes](#what-a-page-holds-against-incoming-changes).

## Change records & the review card

The Review records of an agent batch are saved in the same write as the batch (see [reliable save](./canvas-storage.md#42-reliable-save-in-the-write)); a request answered from a stored outcome appends none. The card, the accept/revert routes and the broadcast shape below are unchanged, and this does not make inverses safe for concurrent Revert.

Change records are derived **purely from a batch's `Delta[]`**, so revert is a
generic operation — no per-command inverse logic:

- [change.ts](../../packages/shared/src/canvas-engine/change.ts) —
  `extractCanvasChanges` builds one `CanvasChangeRecord` per node/edge delta,
  carrying the **inverse delta** (`applyDeltas(state, revertDeltas)` undoes it,
  content included). An update's revert row holds the previous value of
  exactly the fields the edit changed and is merged into the node as it is
  then; a deletion's revert row holds the whole deleted node (the only copy
  once its record is gone); a creation's revert row holds the created node,
  which the freshness check reads. `coalesceChanges` folds every record
  targeting the same entity into one **net** record: per field the value
  before the first edit that touched it and after the last one, a create
  followed by edits as a create of the edited node, an edit followed by a
  delete as a delete of the node before the edit (a create+delete, or an edit
  that is edited back, nets to nothing and drops out). Records stored before
  rows became partial hold whole nodes and are read, coalesced and reverted
  by the same code; an imported Space's history is accepted in both forms
  (`rewriteImportedChange`).
- **Staleness:** UPDATE / CREATE records carry a `fingerprintKeys` +
  `appliedFingerprint` over only the fields the edit actually changed. Before
  reverting, the client recomputes the current node's fingerprint over the same
  keys; a mismatch means a field this edit changed was modified again since, so
  revert is blocked. Later system rewrites of untouched fields (preprocessing
  regenerating `label` / `summary`, a re-measure) therefore never falsely block
  revert. Structural (create/delete/connect/…) records are existence-based.

Records are persisted per thread in a mutable sidecar (`<threadId>.changes.json`, coalesced on read) and reach the frontend two ways: `load()` on thread open, and `replaceFromBroadcast()` (the broadcast carries the thread's full coalesced list, so the client replaces rather than appends). The global Settings → General preference **Automatically accept Agent Space changes** suppresses computation and persistence of new records for successful Agent batches when enabled; existing records remain available, and Canvas delta broadcast and current-session undo snapshots are unchanged.

PDF ownership changes are an exception to one row per entity: the PDF change and its associated Note change share one row and all inverse deltas. Coalescing nets the constituent entities before regrouping them, preserving the pair through persistence and later edits. The shared freshness check examines every inverse delta, including the Note body for creation reverts. The revert endpoint repeats this check under the Canvas mutex and rejects stale rows with HTTP 409; server delta replay also rejects dangling links, replacement of existing Note links, and detachment of surviving owned Notes before writing.

Every reviewed update inverse replays only the recorded field changes onto the live node — the applier merges a row, and a stored whole-node row is reduced to the fields that differ first — so it is no longer a rule for PDFs alone. Reverting Note initialization or restoring a deleted Note therefore preserves later PDF properties, display order, title, and extracted text that the original operation did not modify, and reverting an Agent's recolour of a note keeps a move made since. Changes to fields touched by the reviewed operation are still caught by the freshness check. Question editable-data inverses keep their own replay (`replayAgentNodeEditableData`).

The [ChangeReviewCard](../../apps/web/src/components/Panels/ChatPanel/ChangeReviewCard.tsx)
above the chat input renders the thread's records with per-item and bulk
Keep / Revert, plus press-and-hold **preview** (temporarily applies the inverse
deltas without autosave). It renders for the built-in chat, question-node, and
ACP threads alike. The per-message
[CanvasCommandCard](../../apps/web/src/components/Messages/AIMessage/Tool/CanvasCommandCard.tsx)
is now **display-only**.

**Revert path:** `POST /:canvasId/threads/:threadId/changes/:changeId/revert`
applies the record's inverse deltas server-side via `applyDeltasOnServer`
(persist → delta-log → bump version → broadcast), then drops the record. So a
revert propagates to every tab through the same broadcast as any other write.
`Keep` (`DELETE …/changes/:changeId`) just discards the record.

## Thread attribution

To attach a canvas change to the right conversation's card, the initiating
`threadId` rides the write:

- **Built-in / question-node agent:** `agent.route.ts` passes `threadId` →
  `runAgent` → tool build context → `handleCanvasCommands` sets
  `originator.threadId` and `computeChanges: true`.
- **ACP agent:** the daemon injects `HUABU_THREAD_ID` into the external agent's
  env ([`reachback-env.ts`](../../apps/server/src/modules/agent/acp/reachback-env.ts)).
  The agent forwards it on the reachback `POST /api/rfs/:canvasId/execute` call
  via the `X-Huabu-Host-Thread-Id` header; the route
  ([`rfs.route.ts`](../../apps/server/src/modules/remote_fs/rfs.route.ts) →
  [`space-execute.ts`](../../apps/server/src/modules/remote_fs/space-execute.ts))
  reads it and sets `originator.threadId` + `computeChanges`. This is
  **best-effort**: a missing/malformed header applies the write unattributed. The
  header is distinct from the thread ID in `/agent/:threadId/prompt` (which continues an
  internal built-in-agent turn — a different thread space).

A browser page cannot attribute a batch: the page route's `originator` is `{ tabId? }` and a body that names a `threadId` is refused with 400, whatever credential it arrived with. A person's edit therefore never produces Review records.

`executeOnServer` computes review records only when `computeChanges` is set (i.e. thread-attributed batches) and the global Agent Change Review configuration does not auto-accept Agent writes, so untagged and auto-accepted writers pay no extraction cost. When a `threadId` is present and explicit review is enabled, the batch's records are folded into the thread's coalesced sidecar and that full list is broadcast as `changes`.

## Preprocessing cost dedup

When N tabs replay the same broadcast delta they each schedule an identical
`preprocess` request. [PreprocessDispatcher](../../apps/server/src/modules/preprocessing/dispatcher.ts)
**coalesces concurrent identical requests** via
[coalesceInFlight](../../apps/server/src/modules/preprocessing/coalesce.ts):
requests keyed the same (`dedupeKey` over canvasId / nodeId / type / trigger /
hashed snapshots / options) share one in-flight promise; the entry evicts on
settle. The expensive pipeline (extract + LLM enrich) therefore runs **once**
regardless of tab count. The remaining _ownership_ cleanup (receivers not
triggering at all, plus a server-owned trigger + enriched writeback broadcast)
is deferred — see the plan.

## Navigation save boundary

Each new drain retries retained non-conflict content failures once through the serialized content queue, only while the requested Space's nodes are fully loaded, and retries a failing send-queue request at once. Label-collision failures also retry the current node state: `tryRename` restores the previous label after a server rejection, and the retry saves that reverted label together with any pending body edits before navigation. Writes already scheduled or in flight are reused; failures created by that drain are reported rather than retried in a loop. Version/content conflicts and duplicate-sidecar failures still require explicit resolution. Direct `switchCanvas` keeps the outgoing Space loaded until the drain succeeds, so staying and switching again can recover without requiring another edit. Authoritative baseline updates retire both failure toasts and their notification guards, allowing a later failed save to surface its own error and Retry action.

`drainPendingSaves(canvasId)` is the shared save boundary for route navigation, `switchCanvas`, Space operations, and Agent submission. It waits for the send queue, content, and deletion work and rejects unresolved ordinary content failures, a send queue that cannot send, content conflicts, and held restored bodies. Submission wraps these failures as `CanvasSubmissionSaveError`. Offscreen submissions remain scoped to their captured Space; content-failure filtering uses live node membership only when that Space is not loading, so a returning Space cannot accidentally use the previous Space's nodes as evidence that failed edits were deleted.

The always-mounted `SpaceNavigationGuard` in the router root blocks pathname changes out of a Canvas route. Saving failure retains the current route and presents Common `Modal` with **Stay in this Space** (initial focus, also Escape/backdrop dismissal) and **Discard and leave**. Staying preserves the in-memory edits and failure records for retry. Explicit discard cancels unsent save/preprocess timers and suspends the Space's content-write admission before waiting for admitted writes/deletions to settle. Structure acknowledgements cannot release held restored bodies during this interval; queued content writes and rebase retries cannot issue a new PUT. Failure records and held bodies remain until settlement, then discard forgets that Space's content queue and save failures, clears its undo history, and releases its in-memory Canvas before allowing navigation. Returning therefore reloads server state rather than recovering discarded bodies. Discard never issues compensating deletes or reverses writes already accepted by the server, and it needs no successful reload/network request. A discard failure restores content-write admission and leaves navigation blocked with visible feedback.

A caller that must not act while the Space is still on screen leaves through the guard with `leaveSpace(navigate, to)` (`components/Space/spaceDeparture.ts`), which settles `true` once the route is off the Space (saved or discarded) and `false` when the person stays. Switching Workspace from inside the app uses it: with input frozen as for sign-out, `savedBeforeLeaving()` first settles everything the page owes the Server (`pageLifecycle.prepare()`, so recordings stop and are kept and imports and uploads finish, then the Canvas flush and the preprocess queue). The switch then leaves the Space for `/spaces` through the guard, and activates the new Workspace only after `leaveSpace` settles `true`. It goes on to `/` only once the new Workspace is current, because the `/` landing resolves against whichever Workspace is current and would otherwise open the old Workspace's World. Sign-out uses the same `savedBeforeLeaving()`.

On desktop, the same guard first diverts cross-Space/Home navigation through `DesktopTabs.open`, preserving the existing renderer and its edits without draining or discarding. Desktop close/reload/quit use the acknowledged [desktop lifecycle boundary](./desktop-tabs.md#3-saving-and-lifetime); browser reload/window close remain best-effort unload paths rather than this in-app confirmation flow.

An in-app navigation drain lasting over 150ms displays Common `Loading` with the brand animation and “Saving…” inside a full-viewport native modal dialog, outside the page's flex layout. It uses the same `md` indicator and centered text row as Space loading. The underlying Canvas and chat geometry stay unchanged; native modal inertness blocks pointer and keyboard interaction with the editor and its portals while saving. There is no cancel button, and Escape does not dismiss the saving state. Settlement closes the dialog before proceeding or showing the existing unsaved-changes decision.

The saving dialog explicitly carries `role="dialog"` for the shared Canvas interaction guard. This excludes its keyboard events from window-capture shortcuts such as Delete and Undo, which run before the dialog's bubbling handler.

## Undo interaction

Editable broadcast batches from an agent take **one** undo snapshot (via `applyServerDeltas`), including a batch that only changes sibling paint order. A batch written by a person (`source: 'ui'`) — the page's own or another page's — takes none: the page's own edit already has its entry, and another person's edit is not this page's to undo. Undo and redo themselves are described under [Browser structure edits](#browser-structure-edits). Trusted Agent Node projection batches and FSM-only replacements do not create ordinary undo entries. The server's first-submitted-content effect rebases matching empty Question content in existing snapshots, so undoing an earlier drag cannot erase that submitted intent.

**Restore persistence is ordered, not delay-dependent.** A node that an undo or redo brings back is restored by one `RESTORE_NODES` batch that carries its content, so its sidecar is written by the server with the topology rather than by a later content PUT. No page sends a request to delete a node's record: the batch that deletes the node removes it ([Browser structure edits](#browser-structure-edits)). The restoring batch is behind the deleting one in the page's serial send lane, so the two are executed in order, as is a later redo that removes the node again. Until the restoring batch is answered, content saves for the node wait (as they do for a creation), every content field of it is held, and preprocessing for it is blocked; all resume when it is. Deleted-node content bookkeeping is forgotten immediately, while the preprocessing queue remembers interrupted work for history resurrection. Ordinary content edits retain their independent debounce and revision baseline.

**Server-derived data of a returning PDF or video.** A PDF's extracted text and a video's cover are produced by the server and are not part of what a page is given (`SERVER_DERIVED_SIDECAR_NODE_TYPES`): a load leaves the PDF body out, and a node-scoped content fetch does not bring it into a page that holds none (`remoteContentPatch`; a page that does hold one, because it preprocessed the PDF itself, keeps it current and restores it). So the restoring batch normally cannot carry them: it writes the record back with the file reference (`src`), label and properties the page holds. A missing body is therefore not an incomplete snapshot for these types, and the node is not marked `contentMissing`. When the restoring batch is answered and the server took the node back (`sendRestore`, per `RESTORE_NODES` result), the page asks for preprocessing of that node at once — not debounced, because leaving the Space cancels debounced work and nothing else would ask again — and the server, which treats an empty body as a cache miss, extracts the text from the file again. A refused restore asks for nothing. Other pages receive the node with the restoring batch's `update`; they never held the extracted text either. Covered by `canvasStore.restorePersistence.test.ts` and, with a real server and file, `apps/web/e2e/select-all-cut.spec.ts`.

A returning Agent Node keeps the earlier barrier: the content queue holds its sidecar behind a generation token, and releases it only when the association endpoint has confirmed the node; a later undo/redo invalidates the token.

History reports node changes to the existing preprocessing queue rather than independently cancelling or resuming tasks. The queue owns selective input reconciliation, waiting demand, and client callback validity under the authoritative [client responsibility boundary](./node-preprocessing.md#client-responsibility-boundary). These client guarantees do not establish server-side freshness of derived-content writes.

A restore that cannot be sent keeps the page's edits and follows the send queue's unsynced and error states; a refused one converges the page to the server's Space. The exception is a returning node the user edited before the refusal: its unsaved content holds the reload back, its content save fails (it waits for the restore) and shows the failed-save toast. **Retry** on that toast, and the next `drainPendingSaves`, send the restore again (`retryFailedRestores`: a `RESTORE_NODES` batch for every node of the Space whose restoring batch failed, as the page shows them now, content included) and then the content save, which waits for it. A restore that is refused again shows the toast again. A content failure or content conflict stays dirty until saved or explicitly resolved. Route navigation, `switchCanvas`, and explicit Canvas loads drain the same queues and refuse to silently discard an unresolved body; Retry, explicitly removing the node, or the navigation boundary's confirmed discard lets the user continue. A snapshot with `contentMissing` or without a text-bearing node's string body never invents a body. Unload remains best-effort: the restoring batch is flushed with keepalive like any other.

Host-side refinements keep undo coherent with sync:

- **Transient-field parity.** `diff.ts` and the web snapshotter share one
  canonical `TRANSIENT_NODE_FIELDS` / `TRANSIENT_EDGE_FIELDS` list
  (`selected` / `dragging` / `measured` / `resizing`) so a pure selection flip
  never diffs into a phantom REPLACE, and undo/redo re-applies the live
  transient fields instead of clearing selection.
- **Question-node ownership preservation.** Undo/redo restores editable geometry/content/presentation while preserving live FSM fields and Bound preparation. Server change-card inverse replay applies only the editable data fields changed by that recorded effect, not an old complete Node. Undo reinsertion awaits deletion, and the batch that restores the rest of the same undo, then confirms the restored thread through the association endpoint; a failed confirmation removes the optimistic node and does not silently create a fresh binding.
- **Pending Question removal.** Undo/deletion removes optimistic Questions immediately, filters their late creation inserts (and incident inserted edges) from both HTTP and SSE reconciliation, and delays the tracked server DELETE until creation settles. Failed creation/fork/restore rolls back its optimistic Question and history references on this page only; the server never took the node, so nothing is sent for the rollback.

Question restoration preserves main's immediate local undo/redo behavior and content-queue restore barriers. The server association waits for the batch that restores the rest of the same undo and for the node's tracked DELETE; `drainPendingSaves` waits for pending associations before it flushes content.

- **Retired topology filtering.** Undo/redo applies the shared `stripLegacyPortalTopology()` helper before restoring a snapshot, so old Portal/Pin nodes and their incident edges cannot reappear and ordinary children retain rebased positions. The former Portal-specific history invalidation path is removed; this filtering does not migrate or clean up stored files.

The auto-accept preference still suppresses new Agent review records only. It does not suppress broadcasts or editable undo snapshots, and it does not weaken FSM ownership during manual revert or undo.

## Space presence

When a Space is open on several pages (tabs or devices), each page shows the others: a coloured cursor where the other page's mouse, pen or finger is, and an outline in the same colour around the nodes that page has selected, is dragging or is editing. A marker stands for a page: the server gives each page a colour and the page supplies a short device label such as `Chrome · Mac`. A page of another person is shown with that person's name, which comes from the identity provider and not from the page.

Presence is ephemeral. It is held in server memory and in a browser store of its own; it is not part of the Space record, its `version`, the delta log, change records, undo/redo or anything an Agent reads, and reporting it neither marks the Space dirty nor schedules a save. A drag is reported only as "these nodes are being dragged": positions are not streamed, and the moved node arrives on drop through [browser structure edits](#browser-structure-edits).

```
page A pointer / selection / drag / focus
   │  useReportCanvasPresence → presenceReporter (≤1 request / 80 ms)
   ▼
POST /api/canvas/:id/presence ──► canvas-presence hub (memory, per Space, by principal + page id)
                                        │  relay to every other subscriber
                                        ▼
GET /api/canvas/:id/sync/stream?pageId=B ──► event: presence
   ▼
canvasSyncSubscription → canvasPresenceStore → RemoteCursors / RemoteNodeOutlines
```

### Wire contract

Schemas and limits live in [canvas-presence.ts](../../packages/shared/src/types/api/canvas-presence.ts) and [canvas-presence-limits.ts](../../packages/shared/src/types/api/canvas-presence-limits.ts).

| Endpoint                                    | Body                                                                                                  | Result                                                                                                                                 |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/canvas/:canvasId/presence`       | `{ pageId, label?, pointer?: { x, y } \| null, selectedNodeIds?, draggingNodeIds?, editingNodeIds? }` | 204; 400 invalid; 413 over 128 KiB; 429 `PRESENCE_RATE_LIMITED` / `PRESENCE_SPACE_FULL` / `PRESENCE_TOO_MANY_PAGES` with `Retry-After` |
| `POST /api/canvas/:canvasId/presence/leave` | `{ pageId }`                                                                                          | 204; 400 invalid                                                                                                                       |
| `GET /api/canvas/:canvasId/sync/stream`     | query `pageId?`                                                                                       | adds `presence` events to the stream; 400 for a malformed `pageId`                                                                     |

The report body is strict (unknown fields are rejected). An absent field leaves that part of the page's presence unchanged, so a pointer tick does not resend the selection. `pageId` is the page's `originator.tabId` (`CANVAS_PAGE_ID`); `pointer` is in canvas (flow) coordinates so it lands on the same canvas point under any pan and zoom, and is `null` when the pointer is not over the canvas. There is no name field: a report that carries `displayName` is rejected like any unknown field.

A `presence` event's data is one of `{ op: 'snapshot', pages }` (sent once on connect: every other page present), `{ op: 'update', page }` (a page appeared or changed anything besides its pointer), `{ op: 'pointer', pageId, pointer }` and `{ op: 'leave', pageId }`. A page is `{ pageId, colorIndex, label, displayName?, pointer, selectedNodeIds, draggingNodeIds, editingNodeIds }`. A stream opened with `pageId` is never sent that page's own presence. What a page is shown as depends on who is looking: to a stream of the same principal (the person's other tabs and devices) `pageId` is the id the page reports with and there is no `displayName`; to a stream of another principal `pageId` is an id the server assigned for as long as the page is present, and `displayName` is the principal's name from the identity provider. Page ids therefore do not travel between principals, and `displayName` is preferred over `label` when present.

Both POST routes need only read access to the Space (`spaceAccess: 'read'`), the same as the stream, and go through the same host, origin, identity and Space-access guards as every Canvas route. The page id is chosen by the page and is not a credential, so it never acts alone: **an entry belongs to the authenticated principal together with the page id** (`callerPrincipalId`, [caller-principal.ts](../../apps/server/src/modules/canvas/caller-principal.ts)). A report, a `leave` and a closing stream reach only an entry of the caller's own principal; quoting another principal's page id creates or removes a separate entry of the caller's. A caller can therefore not overwrite another page's label, pointer or selection, evict it, or use up its rate window.

**The edit lock needs write access.** `editingNodeIds` is what makes the other pages show those nodes read-only ([One editor at a time](#one-editor-at-a-time)), so it is taken only from a caller who may write the Space; the route asks the identity provider whenever a report carries a non-empty list. From a read-only viewer the list is dropped — the rest of the report is accepted, so the viewer still shows a pointer and a selection — and a lock held by a caller whose write access was revoked ends with its next report.

| Limit                    | Value                                                                                                                               |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| Node ids per list        | 200, each at most 128 characters                                                                                                    |
| `label` / `displayName`  | 40 / 80 characters                                                                                                                  |
| Coordinates              | finite, magnitude at most 10,000,000                                                                                                |
| Pages per Space          | 32; a further page is refused with 429 `PRESENCE_SPACE_FULL`                                                                        |
| Pages per principal      | 16 per Space; a further page of that principal is refused with 429 `PRESENCE_TOO_MANY_PAGES`, so one caller cannot take every place |
| Reports per page         | 30 per second on the server; the browser sends at most one per 80 ms and one at a time                                              |
| Reports per principal    | 120 per second across its pages of one Space                                                                                        |
| Reports per network peer | 3,000 per minute, counted apart from the application-wide request budget                                                            |
| Colours                  | 6 colour indices; the lowest unused one, kept while the page stays present                                                          |
| Heartbeat / expiry       | the page repeats its whole state every 20 s; a page silent for 75 s is dropped                                                      |

### Server

[canvas-presence.ts](../../apps/server/src/modules/canvas/canvas-presence.ts) keeps a map of pages per Space (the Space keyed by Workspace id and Space id, a page by principal and page id) and its own subscriber list; it does not use `publishCanvasUpdate`, so conversation observers and other server-side listeners of Canvas Sync never see presence. A page is removed, and the others are sent `leave`, when it posts `leave`, when the last stream its principal opened with its `pageId` closes, or when it has not reported for the expiry time (a sweep runs while any page is present), so a crashed page or a dropped connection leaves no marker behind. The expiry is longer than a minute because a background tab's heartbeat timer may fire only once a minute. Pointer events are skipped for a stream whose unsent backlog exceeds 256 KiB.

### Browser

[canvasSyncSubscription.ts](../../apps/web/src/store/canvasSyncSubscription.ts) opens the Space's one stream with this page's id and hands `presence` events to presence listeners only; a listener that subscribes late is given the current set as a snapshot, and every listener is told when the stream drops. [canvasPresenceStore.ts](../../apps/web/src/store/canvasPresence/canvasPresenceStore.ts) holds the other pages in two maps, `pages` and `pointers`, and clears them when the stream drops. `pages` keeps its identity across pointer events, so only the cursor layer re-renders for a pointer tick; neither map is in `canvasStore`, and the React Flow node list is not touched.

[useReportCanvasPresence.ts](../../apps/web/src/components/Panels/Canvas/presence/useReportCanvasPresence.ts) reads this page's state without writing any: the pointer over the canvas (mouse, pen or finger as described under [Pointer](#pointer), converted to flow coordinates once per frame; `null` when it leaves, the window loses focus or the tab is hidden), `selected` / `dragging` flags of `canvasStore.nodes`, and the node being edited, which [editingTracker.ts](../../apps/web/src/store/canvasPresence/editingTracker.ts) derives from the focused text control, on the canvas or in the preview panel (see [One editor at a time](#one-editor-at-a-time)). [presenceReporter.ts](../../apps/web/src/store/canvasPresence/presenceReporter.ts) sends at most one request at a time and one per 80 ms, each carrying only the latest values of what changed; it sends the whole state on every stream (re)connect and as the heartbeat, waits out a 429, and posts `leave` (`keepalive`) when the canvas unmounts or the page is hidden for unload. Report failures are silent.

[CanvasPresenceLayer.tsx](../../apps/web/src/components/Panels/Canvas/presence/CanvasPresenceLayer.tsx), mounted inside `<ReactFlow>`, draws the cursors and outlines as a screen-space layer in the `.react-flow` container, like `SelectionOutlines`. A remote outline reuses `SelectionOutline` and the measured node geometry, drawn 3 px outside the node (a further 3 px per additional page) so it stays visible beside this page's own selection outline. Every node being edited or dragged carries the page's label with `· editing` / `· moving`; of a plain selection only the first node is labelled. A node this page does not have is not outlined.

### Colours

The server hands out a colour index; the browser maps it to the node accent palette in [presencePaint.ts](../../apps/web/src/components/Panels/Canvas/presence/presencePaint.ts) (`PRESENCE_COLOR_TOKENS`), so there are no presence-specific colour tokens. The six are teal, orange, purple, green, red and amber, in that order of index so that the first pages to arrive get unlike hues. White and grey are left out because they do not read as a colour, and blue because it is this page's own selection colour.

A marker is a thin outline, a 16 px arrow and a 10 px label whose text is `--fg-inverse` on the marker colour, so each entry uses the accent's existing foreground token rather than a tint: `--accent-<name>-text-fg`, except amber, which uses the darker `--accent-amber-fg` because `--accent-amber-text-fg` is too light under white label text in the light theme (3.6:1). In the dark theme the two tokens have the same value.

| Token                     | Light: label text / on canvas | Dark: label text / on canvas |
| ------------------------- | ----------------------------- | ---------------------------- |
| `--accent-teal-text-fg`   | 5.0 / 4.6                     | 11.0 / 12.4                  |
| `--accent-orange-text-fg` | 4.8 / 4.4                     | 12.4 / 14.0                  |
| `--accent-purple-text-fg` | 5.1 / 4.6                     | 10.2 / 11.5                  |
| `--accent-green-text-fg`  | 4.9 / 4.5                     | 11.2 / 12.6                  |
| `--accent-red-text-fg`    | 4.9 / 4.5                     | 11.4 / 12.8                  |
| `--accent-amber-fg`       | 7.1 / 6.5                     | 14.1 / 15.9                  |

The figures are WCAG contrast ratios computed from the token values: label text (`--fg-inverse`) against the marker colour, and the marker colour against the canvas background (`--bg-default`, `#f5f5f5` light and about `#0a0a0a` dark). A unit test recomputes them from `index.css` and requires more than 4.5 for the label and more than 4.3 for the outline. They are computed, not measured on a display.

### Pointer

[pointerTracker.ts](../../apps/web/src/store/canvasPresence/pointerTracker.ts) decides which position is shown as this page's cursor. The events are heard on the window, because the canvas pointer router stops touch and pen events before they reach the canvas element.

| Input  | Reported                                                                                                                                                                                                                                                                 |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Mouse  | Wherever it moves over the canvas, until it leaves the canvas.                                                                                                                                                                                                           |
| Pen    | Wherever it is over the canvas, hovering (where the device reports hover) or in contact; after lifting it stays while the pen remains in range, and clears on `pointerleave` (out of range or off the canvas).                                                           |
| Finger | The contact point of a single touch that began on the canvas, from 80 ms after it lands (`TOUCH_REPORT_DELAY_MS`) and wherever it moves; it stays for 1.5 s after the finger lifts (`TOUCH_LINGER_MS`), then clears. A tap shorter than the delay shows where it landed. |

Two or more fingers are this page's own pan or pinch and are not reported: the delay keeps the first finger of a pinch from flashing, a point already shown is withdrawn when a second finger lands, and nothing is reported until every finger of that gesture has lifted. Touches made while a pen is in range are treated as the resting hand and ignored. The position is reported whatever the input mode, including a mode in which the canvas itself ignores that pointer.

### One editor at a time

Two pages do not edit the same node's body, title or properties at once. `editingNodeIds` is used as an advisory lock ([editLock.ts](../../apps/web/src/store/canvasPresence/editLock.ts)): while another page reports node N as being edited, this page cannot start editing N. Nothing is stored and the server enforces nothing; a page that edits a body anyway is still checked by the content revision, so the worst case is the existing `NODE_CONTENT_CONFLICT` choice. Custom properties are not checked by a revision ([what is versioned](#what-is-versioned-and-what-is-not)): two pages that edit the same property anyway are last-writer-wins, without a notice.

| Surface on the locked-out page                                              | Behaviour while another page edits N                                                                                                                   |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Preview of N (Note editor, raw Markdown, every other preview type)          | Read-only; a notice under the header names the other page (`canvasPresence.editLocked`), and a mouse press in the body shows the same text as a toast. |
| Title in the preview header, and the rename request from the tab (F2, menu) | Does not enter editing; toast.                                                                                                                         |
| Text node edited in place (double-click)                                    | Does not enter editing; toast.                                                                                                                         |
| Frame title, Question title on the card                                     | Does not enter editing; toast.                                                                                                                         |
| Any other rename (layer panel, chat header)                                 | `tryRename('node', …)` refuses when the name is committed and shows the toast; this is the check every rename surface passes through.                  |
| Dropping a block or card onto Note N to append it                           | Not accepted by the Note; the drop falls through to the canvas and creates a node.                                                                     |
| Properties of N in its preview (add, edit, rename, retype, reorder, delete) | Read-only: the rows show their values and the editing controls are not offered. The notice under the header applies.                                   |
| Move, resize, colour, layer order, connect, delete                          | Unchanged. They are structure edits and are not locked.                                                                                                |

The toast is shown at most once per 1.5 s. The outline with `· editing` is drawn as before.

**What holds the lock** ([editingTracker.ts](../../apps/web/src/store/canvasPresence/editingTracker.ts)). A page reports N while a control through which N's saved content can be changed has focus — on the canvas, or in the preview of N — and the page itself has focus and is visible. Focus alone is not editing: one classifier (`writableControl` in [localEditing.ts](../../apps/web/src/store/canvasPresence/localEditing.ts)) decides it for the report, for the page's own exemption below, and for the gates that keep a reload or a remote deletion away from a control in use. It does not count a read-only field (`readOnly`), a read-only editor that keeps its caret for selecting and copying (`aria-readonly`: the raw Markdown source and the file source view while they are read-only), or a control inside the node's preview that edits nothing of the node (`data-not-node-content`: the find field). Opening a Note's preview focuses its editor, so the lock starts there, before the first key press.

**What releases it.**

- The control loses focus or the editor closes. The page first saves N's queued content and reports the release after the server has answered, at most 5 s later (`EDIT_RELEASE_CAP_MS`), so the page that edits next has already been sent that text ([Node content between pages](#node-content-between-pages)).
- The window loses focus or the tab is hidden, even with the caret still in the editor.
- No key press, pointer press or input on the page for 2 minutes (`EDIT_IDLE_RELEASE_MS`). The next input takes the lock again.
- The page closes or navigates away (`leave`), its stream closes, or it stops reporting for 75 s (presence expiry).
- The locked-out page's own stream drops: presence is cleared there, so it is not locked while it cannot know. Its saves are then checked by revision only.

A node another page is editing is never taken. Whenever a page is about to report a node it is not reporting — the caret was put into one of its controls, or the page returned (window focus, tab shown, input after the idle release) to a control of a node another page has started editing meanwhile — and another page reports that node, the control is blurred and the toast is shown instead. So a locked-out page cannot become the editor by focusing something, and its lock stays.

**A page that is itself editing N is never locked out of N.** That is a page whose report of N the rule above let through: if two pages start in the same instant, before either has seen the other's report, both keep their editor and the revision check decides between their saves. This also means a notice cannot remove a caret from under someone who is typing.

Limits: the lock is per node, not per field: a property editor on one page still makes the body read-only on the others and the reverse, although a body and a property can no longer refuse each other. Typing in a Question's chat composer and renaming from the layer panel or the chat header do not report editing, so they hold no lock (they are refused by one). The release can reach another page slightly before the saved content does; a person who starts typing in that gap gets the content-conflict choice.

### Not covered

- Text carets and selections inside a note body, live drag positions and viewport following.
- More than one server process: presence is in the memory of the process that received the report.
- Pen and finger reporting is exercised with synthesized pointer events (unit tests, and Chromium touch and pen events in `apps/web/e2e/space-presence.spec.ts`), not with pen hardware or on a touch device; whether a given pen reports hover, and when it reports leaving range, is the device's and browser's behaviour.
- Two pages in the same browser on the same system have the same label and differ only by colour; with more than six pages colours repeat.
- A sketch stroke selection, an edge selection and a marquee in progress are not presence.

## Stream reliability

The sync route subscribes before reading the initial Canvas version, buffers updates committed during that read, sends the snapshot first, and then flushes the buffered updates. This closes the snapshot/subscribe loss window while preserving snapshot-before-update ordering.

The server emits a heartbeat comment every 15 seconds. Canvas Sync applies a 45-second byte-activity watchdog to the shared SSE reader; every received chunk, including a heartbeat comment that does not produce an application event, resets the timeout. Three missed heartbeat windows terminate a silently stalled or half-open stream so the existing retry loop can recover without a manual page refresh. The timeout is opt-in and does not affect other SSE consumers.

`canvasSyncSubscription` treats inactivity timeouts, non-OK responses, stream read errors and unexpected EOF as failures and reconnects with exponential backoff capped at 10 seconds. Unknown event kinds are ignored. An intentional Canvas switch releases the renderer's subscription; the current request and pending delay are aborted only when no subscribers remain. Successful recognized events reset the backoff. The reconnect snapshot/version handshake remains the convergence mechanism. The server installs disconnect cleanup before reading the baseline, so a view closed during that read cannot leak a subscription or heartbeat; baseline failures are logged and close the transport for retry.

## Known reliability gap

- **Revert-route TOCTOU.** The revert handler reads the record and removes it outside the per-canvas mutex (only `applyDeltasOnServer` is inside), so two concurrent reverts of the same change could double-apply. Negligible on single-user desktop; folded away by P3's unified write path.
