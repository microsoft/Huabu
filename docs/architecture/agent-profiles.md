# Agent Profiles and Harness Discovery

Ordinary external agents use persisted Profiles and the existing ACP runtime. Agentlet owns the supported harness catalogue, detection, capability descriptions, and structured launch compilation; Agenetes owns the generic Profile registry; Huabu owns automatic Profile creation, the application default, and the Settings/API projection.

Profiles describe Agent harness providers, not standalone service APIs. Optional OCR, web search, and image generation integrations retain their own configuration and server-held credentials independently of the Utility Agent or conversational recency preference. Submission-time Ink OCR supplies auxiliary evidence to the chosen Agent; it is not an internal-Agent fallback. A future model-provider or function-provider abstraction is separate from the Profile contract.

## Discovery and provisioning

```text
agentlet control connection / reconnection
  -> capability-gated server/discoverHarnesses through Gateway
  -> local PATH detection and default workspace preparation
  -> Huabu duplicate-safe creation in AgentProfileRegistry
  -> GET /api/acp/profiles
  -> Settings and Agent Node selectors
```

Definitions reside in per-harness modules under `external/agentlet/packages/local/src/harnesses/` and are registered in `registry.ts`. Harness IDs are fixed Definition IDs, such as `copilot`, `claude`, and `codex`, not generated instance IDs. Each Definition owns static identity, boolean capabilities, target-local discovery, and trusted command compilation. Claude and Codex discovery targets their ACP adapters and reports `adapter-missing` when only the corresponding native CLI is present. An optional version probe failing does not make a ready command disappear.

The daemon advertises versioned harness discovery support. The Gateway routes requests to an explicit `agentletId` and validates the reply. Unsupported or unavailable daemons fail explicitly; Huabu never substitutes Server-local PATH observations.

Automatic discovery requests workspace preparation. The daemon resolves its own home and creates or reuses `~/.agentlet/workspace/<harnessId>`, using only identities in its local catalogue. It reports an absolute `workingDirPath`. A workspace failure prevents automatic creation for that entry. Directories are shared by uses of that harness's default Profile, not isolated per Agent Node. Deleting a Profile never deletes its directory. Discovery does not start ACP sessions, install harnesses or skills, copy prompts, or provision credentials.

Huabu subscribes to machine connection events, includes machines already connected at registration, and invalidates stale results on reconnect, disconnect, and shutdown. After each successful response it synchronously checks and creates automatic defaults through the registry. The check and commit contain no asynchronous gap.

The Agentlet CLI owns its default device identity. On first start it atomically creates `~/.agentlet/device.json` containing `{ "version": 1, "deviceId": "<uuid>" }`; later starts reuse that UUID, so identity survives daemon, Huabu, OS-session, binary, upgrade, and worktree restarts while the home directory remains. A malformed or unreadable identity file fails explicitly instead of rotating identity. `--agentlet-id` remains an advanced exact override and does not rewrite the persisted UUID. Hello metadata reports the real hostname, platform, and architecture separately for display; none of those fields participates in identity. Windows and WSL naturally receive distinct identities because they use separate home directories.

The Profile catalogue includes optional `folderPickerAgentletId`: the Server observes its existing local `~/.agentlet/device.json` without creating or rewriting it and reports that UUID only while an exact matching Agentlet is connected. Missing identities and older servers leave folder picking unavailable for Agent paths; malformed or unreadable files produce a warning and a null picker identity without hiding the Profile catalogue. This is filesystem identity, not a supervisor placement default or a hostname/platform heuristic. Custom identity overrides and other local users are conservatively unsupported unless they match the persisted local UUID. Settings and Chat share Common `FolderPickerButton`, which requires both native picker support and a target resolving to this exact device; unique legacy-hostname resolution reuses the normal connected-device resolver. Remote Electron mode remains disabled, and browser pickers remain Server-side with existing localhost restrictions. A target or picker-identity change while the dialog is open discards the result and reports an error. Workspace paths omit the Agentlet target and retain their existing picker behavior. Profile creation and editing both use the same target-aware rule; manual absolute-path entry remains available on every device.

Hostname-era Profiles and frozen workload records remain compatible without rewriting persisted data. Live placement resolution first requires an exact connected `agentletId`; when none exists, it treats the stored target as a legacy hostname and accepts it only when exactly one connected Agentlet reports that hostname. The resolved UUID is used for availability, device projections, Profile operations, and ACP session routing. Zero or multiple hostname matches remain unavailable, so Windows/WSL collisions never route to an arbitrary device.

Multiple Agentlets may share one Huabu connection token and connect concurrently. If an identity is already online, Gateway rejects the second live connection with guidance to retry using `--agentlet-id <unique-id>` instead of evicting the first device; once the prior connection is disconnected, the same identity follows the normal reconnect path. The embedded supervisor is special only as process-lifecycle infrastructure: it resolves, starts, restarts, stops, and diagnoses its child, but it neither assigns that Agentlet's identity nor acts as a placement default.

Device-facing UI defaults to one human-readable `hostname: platform arch` display name, such as `huabu: linux x64`. Connected device rows expose a Rename action with an inline name input, Save/Cancel controls, Enter to save, and Escape to cancel; failed saves retain the draft and show an error. Owner-only `PATCH /api/acp/devices/:agentletId` saves a trimmed 1–120-character name for an exact connected identity in `<HUABU_DATA_DIR>/agentlet-device-names.json`, using atomic writes and strict reads. Saved names survive reconnection and Server restart and are projected through `GET /api/acp/profiles` for device rows and Profile device selectors; polling cannot overwrite an acknowledged rename with an older response. A disconnected, not-yet-connected desktop row retains its runtime-provided name until it rejoins the catalogue. UUID-backed `agentletId` remains a secondary identity detail for disambiguation and routing; renaming never changes it, reported machine metadata, ordering, Profile aliases, or existing execution bindings. New automatic Profile aliases continue to use reported machine metadata, while existing and user-customized aliases are never rewritten.

Gateway sends a WebSocket heartbeat every 15 seconds and terminates connections that do not answer before the next heartbeat. While Agent Settings is mounted and the browser page is visible, its Profile and connected-device snapshot refreshes every 5 seconds; this refresh is scoped to Agent settings and does not reload Space or Workspace data. Disconnected connection records remain available for reconnect but are excluded from connected-device and selectable-Profile projections.

In remote Electron mode, the Connected devices section pins a compact opt-in **Connect this device** row first; permission details remain in the native confirmation. Once connected, the exact matching device occupies that same first position and its name includes a muted **(This device)** suffix. Other devices retain their Server-provided relative order, and browser lists retain their original order without local labels. Steady-state connection labels are omitted because the buttons name the available action; loading, transition, and error statuses remain visible. Once the desktop worker reports its `agentletId`, its controls appear inside the exact matching device list item instead of a separate row. Profile count, version, and device identity share the metadata line below the device name. Missing identities and older desktop bridges never infer a match from hostname, platform, or ordering. When the device is absent from the Server snapshot, standalone controls remain available for reconnection or disconnect. Native confirmation authorizes the exact Server to use local Agents; Electron obtains and protects the existing shared connection token without a user token input or clipboard step, starts one local Agentlet, and restores that origin's saved authorization on later launches. Connection state remains independent of Settings mounting. Disconnect removes local authorization and stops managed local tasks after confirmation; app exit stops the worker but retains authorization. Browser clients keep the existing Add device instructions and local Server desktop mode keeps its existing supervisor. Agentlet discovery, stable device identity, Profile provisioning and placement are unchanged; see [desktop startup](./desktop-startup.md).

## Profile identity and customization

The pinned desktop device row shows the local hostname/platform/architecture, stable Agentlet ID, and runtime-reported version even before authorization, using the canonical runtime identity helper and the same version source as Agentlet hello metadata without starting Agentlet. Profile count is shown only once available from the connected-device snapshot.

A Profile has `id`, `alias`, `agentletId`, `workingDirPath`, a launch configuration, optional `metadata.cliId`, opaque `customData`, and configuration/execution revisions. Launch is either `{ kind: 'acp-command', command }` or a structured `{ kind: 'acp-harness', harnessId, options?: { autoApprove? } }`. Every Profile has exactly one wrapper, derived from this launch union: a command Profile uses the Custom command wrapper; a structured Profile uses its `harnessId`. Neither editable metadata nor command-text inspection determines capabilities. Profile ID, target machine, launch kind, and harness identity are immutable; alias, icon, cwd, and supported launch options are editable. Changing machine or wrapper requires a new Profile.

Structured launches require the target daemon's version 2 discovery and harness-launch capabilities. New automatic Profiles use this form only for discovery entries whose status is `ready`; unavailable known harnesses do not produce compatibility command Profiles. Manual creation and runtime-relevant editing validate the unchanged structured option schema and current discovery capabilities without compiling a preview. Legacy command Profiles, including formerly discovered commands, map to Custom without modifying their stored records. Existing Profiles are not rewritten on discovery, and existing permission defaults are not changed automatically.

New automatic structured Profiles set `options.autoApprove: true` only when discovery reports `capabilities.autoApprove: true`. The Definition compiles the corresponding approval flags; Huabu does not compose them. Users can disable the option through Edit, and later discovery/reconnection preserves that choice, including after a host restart. This creation default does not change manual creation, existing Profiles, or realized execution snapshots.

Discovery is platform-aware and reports `ready`, `adapter-missing`, or `not-found`. On Windows it scans all `where.exe` results and accepts shell-resolvable `.exe`, `.com`, `.cmd`, and `.bat` candidates, so an extensionless npm POSIX shim cannot hide a later `.cmd` wrapper. On Unix it requires an absolute `which` result. Version probing uses `cmd.exe` on Windows and shell-free execution on Unix. This models the target platform shell, not interactive aliases or startup scripts.

Agentlet Definitions expose discovery, boolean `customLaunchCommand` and `autoApprove` capabilities, and launch compilation. Custom supports only `customLaunchCommand`: the user supplies the raw command, and no generic approval or model setting is injected. Known Definitions do not support raw-command editing and compile only trusted static tokens plus bounded options into a terminal-style shell command. Both known and Custom launches execute through the target Agentlet's platform shell; the trust boundary is command provenance, not a shell-free process API. Custom is manually configurable and is never automatically provisioned.

The same capability-driven form handles creation and editing, including automatically created Profiles. Common alias/icon/cwd fields are not wrapper capabilities. Missing or unknown capability support never enables a control. ACP model configuration remains a protocol operation, not a guessed command-line flag; a Custom Agent may still report live ACP model controls without gaining generic Profile-level model injection. A detected binary does not prove authentication, model availability, or an ACP adapter's support for native CLI no-history options. This foundation does not add native print-mode execution or a new background permission policy.

The Agent form labels the device as fixed only when editing; creation offers a device selector without that restriction. Descriptions briefly identify the target-device command and working folder, and state that edits apply to conversations that have not started. Unavailable launch editing explains that name and icon remain editable, without obsolete launch-preview or wrapper terminology. Auto-approval retains a concise confirmation-bypass warning. These presentation changes do not change capability gates or existing execution snapshots.

The frozen execution recipe stores the Profile launch intent and resolved cwd. Runtime and recovery send that frozen intent to the selected Agentlet, whose matching Definition compiles it immediately before spawn. Later Profile edits or deletion do not affect the execution. Historical optional `harnessLaunchPlan` data remains parseable for persisted-data compatibility but is ignored as executable input, and new executions do not write it. This change performs no migration or rewrite of existing Profiles, workloads, or durable state.

The editable Profile is a template, not an execution. A conversation freezes its recipe, cwd, instructions, preferences, and `profileExecutionRevision` at first realization (first prompt, warm-up or first mode/model/config control), not when its tab or Agent Node is created. Unrealized conversations use the latest template; realized executions and resumed/restarted processes keep their persisted snapshot. Both unbound Chat and Agent Node conversations support a conversation-specific cwd override through the shared preparation boundary. Agent Nodes retain `agentLaunchOverrides.workingDirPath`; unbound Chat carries persisted browser intent as `cwd` on every realization entry point. An absent override inherits the selected Profile without copying its value before realization. Both paths apply overrides to the workload cwd and launch recipe, and later requests cannot change the frozen directory. Paths are absolute on the Agentlet machine, not necessarily the Huabu server. A successful non-no-op Profile patch advances `revision`; launch/cwd changes also advance `executionRevision`. Missing legacy revisions mean zero without rewriting the record. HTTP edits require `expectedRevision`; stale saves fail with `409 profile_conflict`, including changes that race asynchronous daemon validation.

The execution snapshot also preserves directory origin as `workingDirectoryOverride`: an explicit path or `null` for Profile inheritance. The ACP driver's spec validator preserves this field across persistence and recovery. Cached metadata returns it separately from the effective frozen cwd, so an inherited directory never gains an override marker and later Profile edits cannot change the displayed execution path. Legacy snapshots without origin remain valid and display their frozen directory without an override marker rather than guessing from the current Profile or browser intent. The compact working-directory presentation and explicit inline-editing interactions are documented in [Preview Workspace](./preview-workspace.md).

Saving Chat as a Question copies only its explicit directory override, never its effective inherited cwd. The existing thread keeps its frozen execution directory; a copied node with a new thread inherits the current Profile unless an explicit override was saved. Draft preparation failures before a control callback starts restore the prior execution lock and skip the unnecessary cache refresh; potentially dispatched requests retain the lock until execution facts are confirmed.

The client records revision-fenced execution facts immediately after a successful cached-metadata lookup, before Profile capability discovery. Discovery errors remain visible but cannot prevent editing a confirmed unrealized draft, and discovery results do not overwrite execution locks.

Runtime-relevant edits invalidate the Profile schema cache. Cache warm-starts and metadata writes are fenced against the frozen execution revision, so an old thread cannot repopulate or consume the new template's cache. Successful model/thought-level choices may update known-harness Profile preferences only from a matching execution revision; Custom keeps such choices session-local. Existing thread metadata remains authoritative for its live controls regardless of Profile edits.

Huabu stores the reserved automatic-source marker in `customData.discoveredAgent`:

```json
{
  "version": 1,
  "agentletId": "machine-a",
  "harnessId": "copilot"
}
```

The tuple deduplicates only automatic defaults. For a ready v2 Definition, an existing automatic Profile suppresses creation only when its actual launch is `acp-harness` for the same harness. A legacy automatic `acp-command` Profile therefore remains untouched while discovery creates a new typed Profile with a distinct ID. Reconnection and restart reuse that typed identity, preserving its edits. Manual Profiles without automatic provenance do not suppress automatic creation.

Profile aliases are display labels, not unique keys: Utility Agent settings, conversational recency, edits, execution snapshots and thread bindings use Profile IDs. When a new automatic typed Profile's standard alias is already occupied, its initial alias adds the harness ID in brackets, such as `GitHub Copilot (huabu) [copilot]`; this is a display hint, not an alias-uniqueness constraint. Existing aliases, commands, launch options, directories, saved settings and conversation bindings are not rewritten or migrated. The create API rejects caller-supplied automatic provenance; patches preserve the original marker even when replacing or clearing other custom data, and reject attempts to change it. The generic Agenetes registry does not interpret this Huabu-owned field.

Deleting an automatic Profile is ordinary deletion. A later discovery may create a new default with a new Profile ID. There is no tombstone, reset endpoint, persisted availability state machine or reconciliation controller. Missing harnesses and failed probes do not delete existing Profiles. Existing ordinary workload snapshots remain independent of subsequent Profile edits or deletion.

## Persistence and retired Team data

The generic registry writes `<HUABU_DATA_DIR>/agent-profiles/registry.json` atomically. On first initialization only, it imports ordinary command Profiles from the former `agent-team/registry.json`, whose records already carry device placement. IDs, directories, metadata and custom data are preserved. Huabu does not import the older `agent-profiles.json` format because those records have no device identity and assigning them to an arbitrary connected or supervised Agentlet would break placement continuity. Initialization is persisted even for an empty list; an existing new registry is authoritative, so a deleted Profile cannot reappear through repeated migration. Invalid command data and conflicting identities fail explicitly.

Old Team registry/config/setup-log files and conversation records are not deleted or rewritten by migration. Manifest Profiles are not imported as active Profiles or converted to executable commands. Agentlet and Agenetes reject retired Team launch recipes instead of silently treating them as ordinary commands.

The repository's `agent-teams/` manifest, prompt and Skill folders remain data assets. There is no bundled Team registration, manifest execution, setup worker, Team CLI, Team API, member Config UI or preparation lifecycle. Space Templates are a separate feature; their implementation is not required for ordinary Profiles. Historical design material is retained in [the archive](../archive/agent-teams-as-extensions.md).

## Settings and APIs

Owner-only `GET /api/agent/defaults` and `PUT /api/agent/defaults` expose the Utility Agent configuration `{ profileId: string | null, functionalModel: string }`, persisted atomically in `<HUABU_DATA_DIR>/agent-defaults.json`. The reserved `huabu` identity selects Built-In Pi explicitly; other identities select external Profiles and `null` means unconfigured. Built-In reads and writes require no external registry or connected Agentlet. Its `available` state means the backend exists, not that provider authentication has been verified; missing credentials are repaired through Built-In settings and never cause a backend fallback.

When no Utility Agent record exists, provisioning chooses a stable ordered external Profile on a connected Agentlet and saves its identity. With no candidate, setup guides the user to connect an external Agent or explicitly choose Built-In Pi. Existing records, including null/deleted/offline selections, remain authoritative. Old provider credentials do not implicitly enable Pi, and switching utility backends does not clear credentials or models. Reads do not discover agents, initialize settings, or create sessions. Deleting or disconnecting the selected Profile does not choose a replacement.

Settings > Agent is the single Agent configuration surface, with peer sections ordered as Connected devices, External agents, Utility tasks, Conversation and changes, Advanced runtime settings, and Built-In Pi, without changing their separate persistence owners. All six overview sections are independently collapsible through the shared SettingSection: Connected devices, External agents, and Utility tasks start expanded; Conversation and changes, Advanced runtime settings, and Built-In Pi start collapsed. Overview sections opt into `keepMounted`, which mounts initially collapsed content only on first expansion and then hides it rather than unmounting it on collapse, preserving local drafts, save feedback, and in-flight requests without making hidden controls keyboard-focusable. Collapse state is local to each mounted section and is not persisted across Settings visits. The Connected devices section contains the device list and an Add device header action, including when no device is connected. Add device opens connection instructions in a focused view using the same navigation, title, Back control, transition animation, and return-trigger focus restoration as Add agent and Profile editing; it does not expand instructions inside the list. Other overview groups are hidden during both device connection and Profile editing. Device connection does not probe Agent harnesses or load runtime limits. External agents lists ordinary Profiles and uses an Add agent header action; neither action repeats a title and description for the same operation. Empty states and missing-device guidance remain visible in expanded list cards. Built-In Pi is de-emphasized at the end of the overview while retaining its chat configuration entry and existing functionality. Focused connection and Profile editor forms remain non-collapsible.

Both Add actions sit outside the list card, to the right of their section heading, using matching compact neutral ghost buttons. SettingSection exposes a shared `action` slot for this header placement without duplicating section markup. List cards contain only entity rows, loading/empty states, and necessary missing-device guidance. Add device remains available with no connected devices; Add agent is disabled until a device is connected and initial catalogue loading completes. Existing focused-view navigation and return-trigger focus restoration are unchanged.

The shared SettingSection uses a 2px heading-to-card gap for plain headings, collapsible headings, and headings with actions. Expanded sections retain 16px bottom spacing, including the outer Profile-management group; collapsed sections use 8px with no empty heading-to-card gap. Collapsible headings are transparent full-row Common Button targets with a 32px minimum height, 13px medium text, a leading chevron pointing right when collapsed and down when expanded, semantic hover feedback, and visible keyboard focus. Header actions remain separate sibling buttons on the right, outside the toggle and card, wrapping to their own right-aligned line when space is insufficient. Long titles wrap within the available width, and chevron transitions honor reduced motion. Collapsed sections have no decorative card border or shadow; SettingRow padding, initial collapse states, lazy mounting, and draft-preserving behavior are unchanged.

The shared Settings content header separates the page title and close/Back controls from the scrollable body using spacing, without a bottom divider. Its 52px height vertically centers the right title on the same centerline as the sidebar title, which uses a 28px title row beneath 12px top padding; both titles remain left-aligned. Its close action reuses Common Button with a 16px icon in a 28px target, subtle foreground at rest, and default foreground on hover with visible keyboard focus. Card borders and row dividers remain unchanged.

Collapsing a SettingSection closes Popovers whose panel or reference belongs to that section through Common Popover's existing registry, including menus portaled outside the hidden card. This also applies to keyboard activation, which does not produce an outside pointer press. Preserved form content stays mounted with its drafts intact, and re-expansion does not reopen the dismissed menus. Popovers belonging to other sections are unaffected.

The shared scrollable content pane starts directly below the header with no top padding, bringing its first section closer to the sidebar's first navigation item. Its 20px horizontal padding and 16px bottom padding remain unchanged across overview and focused settings pages.

The Settings sidebar retains the Agent, Services, General navigation order and existing initial/remembered page behavior. Each text-only entry uses Common Button without an icon, 8px horizontal and zero vertical padding, a 30px minimum target height, 2px inter-row spacing, and an inset rounded full-row neutral selection background instead of a left-edge marker. Its `bg-sidebar` semantic token uses `#FBFAF7` in the light theme and the default background in the dark theme. Selection uses `bg-sidebar-selected` (`#EAE7E0` in light, the hover background in dark) and keeps that background on hover. The Settings title labels the navigation, the selected entry retains `aria-current="page"` and visible keyboard focus, and the application version remains pinned to the bottom. Focused Built-In configuration keeps Agent selected rather than adding another top-level entry.

Utility tasks is the only utility-model configuration entry. Its Agent selector chooses the backend for Huabu-owned auxiliary work. External selections show the existing capability-driven functional-model dropdown; selecting Built-In Pi instead mounts its automatic-cheapest/custom provider, authentication, and model controls inside the same card, without a second Utility model section. Pi utility controls initialize the existing LLM store on demand; switching to an external Agent unmounts them without deleting saved Pi configuration. Automatic selection uses the cheapest eligible model from the built-in chat provider, with the existing chat-model fallback; custom utility provider and model settings remain independent of chat. OAuth login targets the selected utility provider, displays the device-code flow in this card, and refreshes both chat and utility authentication and model catalogues after completion. Credentials remain shared per provider rather than copied between settings surfaces.

The utility explanation sits inside its Agent row and lists only summaries, titles, labels, and keywords; the section heading already establishes the scope. The external model row has no permanent description, while conditional capability, availability, loading, and save feedback remain unchanged. Its status row renders only when it has a warning, error, or save state to display. The Agent selector reuses SettingControl's 240px width with a parent-width cap; Common Select truncates long selected labels without expanding the control or squeezing the description column. Its option menu retains its independent width limits. Changing the Utility Agent never changes a conversation binding or the browser-local recent conversational Agent. Choosing another external Profile clears the old Profile's model override. Conversation and changes owns automatic acceptance of Space edits and the initial conversational history window; its section starts collapsed, mounts its controls on first expansion, and retains their existing immediate-save behavior. Advanced runtime settings starts collapsed and loads idle-timeout and concurrency controls only on first expansion, not again on each collapse/expand cycle. Top-level Agent modules use consistent section spacing.

The focused Built-In Pi view contains only chat provider, authentication, and chat model controls and offers a Back to Agents control. Utility settings are not rendered there, even when Pi is the selected Utility Agent. This view remains available from the Built-In Pi overview entry and a Built-In conversation's configuration button; the latter remains available after binding is locked and does not change Utility Agent settings.

Conversation and changes descriptions state only automatic retention and its post-refresh revert limit, and that older chat history can be expanded. Advanced runtime labels use Agent idle pause time and Agent process limit; their descriptions explicitly identify the Agent as the idle subject, explain automatic resumption, and state that the embedded-runtime limit takes effect after restarting Huabu. These concise localized descriptions omit redundant defaults, ranges, and implementation terms without changing persistence, validation, or process lifecycle behavior.

Settings > Services separately owns Huabu-managed image generation, OCR, Web Search, and YouTube transcript configuration; all services are configured on demand and appear as peer cards with a 12px gap, separate from the 16px spacing between larger Settings sections. The Services container clears section margins so they do not add to its flex gap; card padding and persistence owners are unchanged. An Agent-facing Service Package enables direct external-Agent use but does not imply access to the corresponding Huabu Internal Tool. The larger Image Generation form starts collapsed while retaining its bordered card header and expands on demand.

Services uses field-level persistence instead of a card-wide Save/Discard footer: ordinary text and URL controls commit on blur or Enter, selection controls commit immediately, and secret fields reuse ApiKeyRow with explicit submission and confirmed removal. First-time ordinary edits wait for a missing required key and are submitted with it after validation; errors retain local drafts. Masked responses and key removal never discard unrelated field edits. See [Service Packages](./service-packages.md#owner-settings-api) for the persistence and readiness contract.

Huabu-owned auxiliary tasks outside an Agent Node's bound thread follow the Utility Agent, including summaries, keywords, content/Frame titles, conversation titles, and image labels. The source conversation's backend does not determine its automatic title backend. Each invocation selects its backend once; changing Utility Agent settings does not reroute in-flight work. Built-In tasks reuse `llmComplete` with the existing `contentMeta`, `frameLabel`, and `imageLabel` roles, preserving Utility/Chat model resolution and vision handling. External tasks use independent ACP Jobs. Thread-owned work and its tools retain the thread binding; explicit internal Skill authoring remains available. Legacy background Memory starts only for a Built-In Utility Agent; external Memory and unified Skill authoring remain separate follow-ups.

Image labels reuse chat image resolution and its 4 MB decoded-image cap; unavailable pixels and invalid labels fail explicitly. For external tasks, the trimmed functional-model value inherits the Profile's remembered model when empty, then the harness default. A known wrapper receives the preference only through advertised live ACP model controls. Unsupported or unknown model capability is a warning, not a fabricated guarantee; unavailable values are logged and the harness default remains. Custom commands receive no generic model injection. Functional execution does not modify Profile launch configuration or interactive chat preferences. ACP images require `promptCapabilities.image: true` and a vision-capable harness/model; failures never fall back to Pi.

Utility Profile and model selections save immediately, without a separate Save button. Reselecting the current Profile preserves its functional-model override, including an unavailable saved model ID. The functional-model dropdown uses the same cache-first Profile capability loader as Chat: a cache miss automatically discovers an isolated temporary ACP session without realizing a conversation. Model choices are normalized by `buildAcpSessionSelectors`, including legacy model lists and grouped model config options. The empty selection inherits the remembered Profile model, then the harness default; a probe's current model never changes this configuration. A saved ID absent from the catalogue remains visible with a warning, not silently replaced. Loading, no model list, and discovery failure are distinct, and failures offer retry. Custom command Profiles cannot apply Utility model overrides, so their selector is disabled even if ACP advertises models. The shared Profile store serializes configuration writes across Settings mounts and prevents older responses from overwriting a newer selection. Save errors retain the draft and offer an explicit save retry. Utility settings do not publish or modify a conversational binding.

External functional text tasks reuse Profile snapshot compilation and Agenetes event folding, without creating visible Agent Nodes or storing Agenetes conversations. An unconfigured Utility Agent or unavailable Utility Profile is an explicit failure, never an internal fallback. A background permission request fails the task and forwards cancellation without escalating approval; the task deadline also bounds unresponsive harnesses. Agenetes owns one-shot Job cleanup: normal completion, failure, or early iterator return closes the handle and waits for exact Agentlet process reclamation, while cleanup failure remains observable. Per-workflow overrides and historical conversation migration remain outside this step; both runtimes are retained.

Functional Jobs await the asynchronous Agenetes creation API inside the task deadline. Cancellation or timeout during creation returns promptly, and a handle that arrives afterward cannot dispatch the task. Creation failures propagate without fallback; a process spawned before connection failure is compensatingly stopped, and failure to confirm that stop is reported as cleanup failure.

The client records the most recently explicitly selected conversational Profile under `huabu.recentConversationAgentProfile.v1` through the application preference adapter. Browsers retain `localStorage`; desktop migrates Home's legacy value into main-process preferences and retains only renderer memory, including across independent Space partitions. Incoming preference invalidations reread the current value without echoing a write; deletion clears the remembered identity. Desktop selections persist before changing renderer state, and failures are reported without applying the failed selection. Browsers retain session-local selection when storage is unavailable and report that failure. There is no conversation-preference HTTP endpoint or Server-side preference file. New conversations snapshot that client-local identity after refreshing the Profile catalogue. A missing, deleted, or unavailable cached external identity falls back to the first selectable external Profile without rewriting the cache; an explicit Built-In selection remains client-local and selectable. Existing conversations and restored nodes keep their own persisted binding. Server-created and RFS Agent Nodes do not consume client preference state: callers may supply an explicit Profile, otherwise the Server independently uses the first selectable external Profile without persisting that fallback.

Ink submission without an existing Question target refreshes the Profile catalogue and applies the same browser-local recent selection before creating its Question, using internal `operate` or external `ask` mode. It rejects a changed Space or selection after that await. Failed loading leaves the Ink selection intact and creates no node; an already selected Agent target and a retry of the same created Question keep their binding.

`GET /api/acp/profiles` reads the canonical persisted list, active connected devices, connectivity-filtered selectable IDs, supervised-child health, and saved `agentDefaults` without detecting harnesses, creating Profiles or starting sessions. The active device projection is sorted deterministically and contains the Agentlet UUID, display metadata, Agentlet version, connection time, and associated Profile count; it is not persisted and contains no offline history or last-seen state. A Profile is selectable only while its exact `agentletId` has an active control connection. Settings refreshes the shared Profile store on mount and after mutations; existing selectors refresh that same list when opened. Unavailable Profiles remain visible and editable in Settings but cannot be selected for runtime work. There is no Web discovery store, selector-time materialization, or discovery polling.

`GET /api/acp/agent-cli` requires exactly one explicit target: `agentletId` for creation or `profileId` for editing. It includes launch support and capability observations without preparing workspaces or creating Profiles. Older successful catalogues receive the canonical Custom descriptor; failed detection remains an explicit error, not a misleading successful catalogue. Custom command configuration and display-only edits remain available without successful detection. Manual creation requires an active device and an explicit `workingDirPath`; only automatic defaults get a daemon-prepared directory.

`POST /api/acp/profiles` requires an active `agentletId` and persists that immutable placement; Settings initializes the form with the first deterministically sorted active device only as an unsaved UI convenience. Profile creation and runtime-relevant patches independently validate current discovery readiness, capabilities, and structured options, so client-side controls are not the validation boundary. There is no launch-preview endpoint: compilation remains Agentlet-owned and occurs inside runtime spawn. `PATCH /api/acp/profiles/:id` requires `expectedRevision` and permits mutable template fields only; display-only edits do not require a connected Agentlet.

The Agent Settings surface presents active Connected Devices first, followed by ordinary Profiles, their existing edit/delete actions, and the supervised-child health banner alongside Utility Agent and backend-specific configuration. The create editor requires a device selection before harness selection; editing displays the immutable device identity read-only. Opening a Profile editor temporarily focuses that nested view without duplicating or rewriting Profile state. Template/member Config/setup controls are removed. Catalogue, Profile, Utility Agent, and conversational preference endpoints remain owner-only. Shared HTTP contracts remain under `packages/shared/src/types/api/`, with type-only imports in the Web app.

Workload placement is always explicit. New workloads snapshot the Profile's `agentletId`; existing snapshots continue to use their stored placement. A missing Profile or a legacy workload without placement is treated as invalid data and fails clearly. Runtime code never falls back to the supervised child, hostname, or first connected device.

Owner-only `GET/PUT /api/acp/runtime-config` persists the external-agent idle timeout and supervised-daemon process limit in `<HUABU_DATA_DIR>/external-agent-runtime-config.json`; both controls appear under Settings > Agent > External Agent runtime. `maxAgents` defaults to `10` and accepts any positive JavaScript safe integer without a product-defined maximum. Both numeric inputs save on blur or Enter, not each keystroke, without permanent Save buttons. Custom idle minutes accept whole numbers from 1 through 1440 and retain Custom mode even when the saved duration matches a preset. Invalid input and save failures render below each field through a shared local feedback composition; failures retain drafts and offer explicit retry. Unchanged values do not write, and a shared synchronous in-flight guard prevents Enter/blur duplicates and overlap between runtime saves. Each full-configuration write preserves the other field from the latest acknowledged configuration, and controls stay disabled until configuration has loaded successfully. Idle-timeout presets still save immediately and restore the prior selection if a save fails. Huabu passes the process limit as `--max-agents` whenever the supervised daemon starts; saving does not hot-update or automatically restart the daemon, and manually launched remote daemons continue to use their own CLI argument without a configuration handshake.

The focused Add device view presents three ordered steps: prepare a matching Huabu source checkout with Node.js 24.16+ and pnpm, choose the target terminal and copy/run the connection command, then keep the terminal running and check Connected devices. It reuses Common Button and Select; feature-specific instructions use 13px text, readable line spacing, and inset code blocks rather than a long SettingRow description. Private connection env-file copying and stable-token guidance live under a collapsed Other connection options disclosure. A short, always-visible notice states that connection commands and files contain a Huabu access key and must remain private. Loopback guidance appears inline only after an explicit successful copy supplies that fact; the legacy `generated` source warning remains compatible with older responses, while current managed tokens survive restarts. Insecure-transport warning codes remain in the API response but are omitted from both inline notices and copy-result toasts; when no other guidance applies, successful command and env-file copying use their ordinary success messages. Owner-only no-store `POST /api/acp/connection-command` derives the public origin from effective environment-over-setup deployment settings, falling back to the validated browser origin only for unconfigured loopback development. Copy text uses `pnpm start:daemon` with token-only env transport, and the Web app never renders or retains returned credential content. Token editing/configuration endpoints remain removed; the Server fixes an environment or automatically persisted managed token and ignores but retains historical Settings token records.

Add device copy describes connecting Agents running on another computer or server to Huabu, rather than installing or moving Agents there. Both locales explicitly place setup and connection commands on the Agent device and confirmation in Huabu, and instruct users to select their actual shell to copy its matching command. Loopback warnings identify the Huabu server's device, not the browser's device; credential handling and connection behavior are unchanged.

The preparation step separates the Node.js 24.16+/pnpm requirements from the instruction to download matching Huabu source and install dependencies. It omits the redundant existing-checkout exception and post-command paragraph; shell commands and version compatibility requirements are unchanged.

Other connection options keeps only the file-saving instruction, launch command, and fixed-key environment variable guidance, without file-content or process-parameter explanations. Copy actions and launcher configuration are unchanged.
