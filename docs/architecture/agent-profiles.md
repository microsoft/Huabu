# Agent Profiles and Harness Discovery

Ordinary external agents use persisted Profiles and the existing ACP runtime. Agentlet owns the supported harness catalogue, detection, capability descriptions, and structured launch compilation; Agenetes owns the generic Profile registry; Huabu owns automatic Profile creation, the application default, and the Settings/API projection.

Profiles describe Agent harness providers, not standalone service APIs. Optional OCR, web search, and image generation integrations retain their own configuration and server-held credentials independently of the Utility Agent or conversational recency preference. Submission-time Ink OCR supplies auxiliary evidence to the chosen Agent; it is not an internal-Agent fallback. A future model-provider or function-provider abstraction is separate from the Profile contract.

## Discovery and provisioning

```text
agentlet control connection / reconnection
  -> capability-gated server/discoverHarnesses through Gateway
  -> local PATH detection and default workspace preparation
  -> Huabu duplicate-safe creation in AgentProfileRegistry
  -> GET /api/acp/profiles
  -> Settings and Agent Node selectors
```

Definitions reside in per-harness modules under `external/agentlet/packages/local/src/harnesses/` and are registered in `registry.ts`. Harness IDs are fixed Definition IDs, such as `copilot`, `claude`, and `codex`, not generated instance IDs. Each Definition owns static identity, boolean capabilities, target-local discovery, and trusted command compilation. Claude and Codex discovery targets their ACP adapters and reports `adapter-missing` when only the corresponding native CLI is present. An optional version probe failing does not make a ready command disappear.

The daemon advertises versioned harness discovery support. The Gateway routes requests to an explicit `agentletId` and validates the reply. Unsupported or unavailable daemons fail explicitly; Huabu never substitutes Server-local PATH observations.

Automatic discovery requests workspace preparation. The daemon resolves its own home and creates or reuses `~/.agentlet/workspace/<harnessId>`, using only identities in its local catalogue. It reports an absolute `workingDirPath`. A workspace failure prevents automatic creation for that entry. Directories are shared by uses of that harness's default Profile, not isolated per Agent Node. Deleting a Profile never deletes its directory. Discovery does not start ACP sessions, install harnesses or skills, copy prompts, or provision credentials.

Huabu subscribes to machine connection events, includes machines already connected at registration, and invalidates stale results on reconnect, disconnect, and shutdown. After each successful response it synchronously checks and creates automatic defaults through the registry. The check and commit contain no asynchronous gap.

The Agentlet CLI owns its default device identity. On first start it atomically creates `~/.agentlet/device.json` containing `{ "version": 1, "deviceId": "<uuid>" }`; later starts reuse that UUID, so identity survives daemon, Huabu, OS-session, binary, upgrade, and worktree restarts while the home directory remains. A malformed or unreadable identity file fails explicitly instead of rotating identity. `--agentlet-id` remains an advanced exact override and does not rewrite the persisted UUID. Hello metadata reports the real hostname, platform, and architecture separately for display; none of those fields participates in identity. Windows and WSL naturally receive distinct identities because they use separate home directories.

The Profile catalogue includes optional `folderPickerAgentletId`: the Server observes its existing local `~/.agentlet/device.json` without creating or rewriting it and reports that UUID only while an exact matching Agentlet is connected. Missing identities and older servers leave folder picking unavailable for Agent paths; malformed or unreadable files produce a warning and a null picker identity without hiding the Profile catalogue. This is filesystem identity, not a supervisor placement default or a hostname/platform heuristic. Custom identity overrides and other local users are conservatively unsupported unless they match the persisted local UUID. Settings and Chat share Common `FolderPickerButton`, which requires both native picker support and a target resolving to this exact device; unique legacy-hostname resolution reuses the normal connected-device resolver. Remote Electron mode remains disabled, and browser pickers remain Server-side with existing localhost restrictions. A target or picker-identity change while the dialog is open discards the result and reports an error. Workspace paths omit the Agentlet target and retain their existing picker behavior. Profile creation and editing both use the same target-aware rule; manual absolute-path entry remains available on every device.

Hostname-era Profiles and frozen workload records remain compatible without rewriting persisted data. Live placement resolution first requires an exact connected `agentletId`; when none exists, it treats the stored target as a legacy hostname and accepts it only when exactly one connected Agentlet reports that hostname. The resolved UUID is used for availability, device projections, Profile operations, and ACP session routing. Zero or multiple hostname matches remain unavailable, so Windows/WSL collisions never route to an arbitrary device.

Multiple Agentlets may share one Huabu connection token and connect concurrently. If an identity is already online, Gateway rejects the second live connection with guidance to retry using `--agentlet-id <unique-id>` instead of evicting the first device; once the prior connection is disconnected, the same identity follows the normal reconnect path. The embedded supervisor is special only as process-lifecycle infrastructure: it resolves, starts, restarts, stops, and diagnoses its child, but it neither assigns that Agentlet's identity nor acts as a placement default.

Device-facing UI defaults to one human-readable `hostname: platform arch` display name, such as `huabu: linux x64`. Connected device rows expose a Rename action with an inline name input, Save/Cancel controls, Enter to save, and Escape to cancel; failed saves retain the draft and show an error. Owner-only `PATCH /api/acp/devices/:agentletId` saves a trimmed 1–120-character name for an exact connected identity in `<HUABU_DATA_DIR>/agentlet-device-names.json`, using atomic writes and strict reads. Saved names survive reconnection and Server restart and are projected through `GET /api/acp/profiles` for device rows and Profile device selectors; polling cannot overwrite an acknowledged rename with an older response. A disconnected desktop row uses known Server metadata when available and otherwise its runtime-provided name. UUID-backed `agentletId` remains a secondary identity detail for disambiguation and routing; renaming never changes it, reported machine metadata, ordering, Profile aliases, or existing execution bindings. New automatic Profile aliases continue to use reported machine metadata, while existing and user-customized aliases are never rewritten.

Gateway sends a WebSocket heartbeat every 15 seconds and terminates connections that do not answer before the next heartbeat. While Settings > Devices and Agents is mounted and the browser page is visible, its Profile and connected-device snapshot refreshes every 5 seconds; this refresh does not reload Space or Workspace data or probe harnesses. Disconnected connection records remain available for reconnect but are excluded from connected-device and selectable-Profile projections. The optional `knownDevices` field in `GET /api/acp/profiles` projects display-only metadata from all Gateway records, including disconnected devices, plus persisted device names. It is not a placement or availability source. Gateway metadata survives browser reloads, not Server restarts; persisted names remain available after restart, and otherwise unknown Profile targets display their saved target identifier without guessing a hostname or version. Missing versions are omitted from device menus. Older servers without `knownDevices` still show offline Profiles grouped by their stored target.

In remote Electron mode, Devices and Agents pins the exact local device first, using the worker's `agentletId` or pre-authorization `device.agentletId`; its name includes a muted **This device** suffix without parentheses. Once identity is known, the same card and its Profiles remain mounted across connection transitions. Disconnected local devices show only a Connect button in the header, without a redundant Not connected label; enabled local workers expose Disconnect in the device menu rather than an extra control row. Loading, connecting, reconnecting, stopping, and error statuses remain visible in the header; authorization failures retain Reconnect, and connection errors remain visible below the header. Disconnect stays available in the menu during recovery and is disabled during an in-flight action or shutdown. Dismissing native confirmation leaves the connection state unchanged. Older bridges without an identity retain a compact standalone row and the same controls; they never infer a match from hostname, platform, or ordering. Local-server Electron uses the exact native folder-picker identity for the local label and keeps its existing supervisor. Other online devices retain Server order, followed by offline device groups; browser lists have no local labels or connection actions. Offline non-local devices show only Not connected, not Connect or Add agent. Profile count appears only while collapsed; known version and copyable identity appear at the bottom of the device menu. Native confirmation authorizes the exact Server to use local Agents; Electron obtains and protects the existing shared connection token without a user token input or clipboard step, starts one local Agentlet, and restores that origin's saved authorization on later launches. Connection state remains independent of Settings mounting. Disconnect removes local authorization and stops managed local tasks after confirmation; app exit stops the worker but retains authorization. Agentlet discovery, stable device identity, Profile provisioning and placement are unchanged; see [desktop startup](./desktop-startup.md).

Disconnect closes the device menu through its controlled open state, preserving the shared DropdownMenu focus-restoration behavior after cancellation, failure, or success. If an older bridge has no local identity and its standalone menu disappears after disconnect, focus returns to Connect once the action settles, but only when focus would otherwise remain on the document body. Collapsing content continues to use ancestor-hide dismissal without restoring focus into hidden rows.

## Profile identity and customization

The pinned desktop device row shows the local hostname/platform/architecture, stable Agentlet ID, and runtime-reported version even before authorization, using the canonical runtime identity helper and the same version source as Agentlet hello metadata without starting Agentlet. Known Server display names and versions take precedence over runtime values; runtime metadata fills missing local fields even when the Server retains only a saved device name after restart. This is a display-only merge: it does not write back to the Server, mark the device connected, or enable offline Profiles. Profile counts are derived from the complete saved Profile list, including offline Profiles.

A Profile has `id`, `alias`, `agentletId`, `workingDirPath`, a launch configuration, optional `metadata.cliId`, opaque `customData`, and configuration/execution revisions. Launch is either `{ kind: 'acp-command', command }` or a structured `{ kind: 'acp-harness', harnessId, options?: { autoApprove? } }`. Every Profile has exactly one wrapper, derived from this launch union: a command Profile uses the Custom command wrapper; a structured Profile uses its `harnessId`. Neither editable metadata nor command-text inspection determines capabilities. Profile ID, target machine, launch kind, and harness identity are immutable; alias, icon, cwd, and supported launch options are editable. Changing machine or wrapper requires a new Profile.

Structured launches require the target daemon's version 2 discovery and harness-launch capabilities. New automatic Profiles use this form only for discovery entries whose status is `ready`; unavailable known harnesses do not produce compatibility command Profiles. Manual creation and runtime-relevant editing validate the unchanged structured option schema and current discovery capabilities without compiling a preview. Legacy command Profiles, including formerly discovered commands, map to Custom without modifying their stored records. Existing Profiles are not rewritten on discovery, and existing permission defaults are not changed automatically.

New automatic structured Profiles set `options.autoApprove: true` only when discovery reports `capabilities.autoApprove: true`. The Definition compiles the corresponding approval flags; Huabu does not compose them. Users can disable the option through Edit, and later discovery/reconnection preserves that choice, including after a host restart. This creation default does not change manual creation, existing Profiles, or realized execution snapshots.

Discovery is platform-aware and reports `ready`, `adapter-missing`, or `not-found`. On Windows it scans all `where.exe` results and accepts shell-resolvable `.exe`, `.com`, `.cmd`, and `.bat` candidates, so an extensionless npm POSIX shim cannot hide a later `.cmd` wrapper. On Unix it requires an absolute `which` result. Version probing uses `cmd.exe` on Windows and shell-free execution on Unix. This models the target platform shell, not interactive aliases or startup scripts.

Agentlet Definitions expose discovery, boolean `customLaunchCommand` and `autoApprove` capabilities, and launch compilation. Custom supports only `customLaunchCommand`: the user supplies the raw command, and no generic approval or model setting is injected. Known Definitions do not support raw-command editing and compile only trusted static tokens plus bounded options into a terminal-style shell command. Both known and Custom launches execute through the target Agentlet's platform shell; the trust boundary is command provenance, not a shell-free process API. Custom is manually configurable and is never automatically provisioned.

The same capability-driven form handles creation and editing, including automatically created Profiles. Common alias/icon/cwd fields are not wrapper capabilities. Missing or unknown capability support never enables a control. ACP model configuration remains a protocol operation, not a guessed command-line flag; a Custom Agent may still report live ACP model controls without gaining generic Profile-level model injection. A detected binary does not prove authentication, model availability, or an ACP adapter's support for native CLI no-history options. This foundation does not add native print-mode execution or a new background permission policy.

Creation is entered from a specific device group and keeps that exact target fixed throughout the flow; editing also retains its immutable target. Descriptions identify the target-device command and state that edits apply to conversations that have not started. Unavailable launch editing explains that name and icon remain editable, without obsolete launch-preview or wrapper terminology. Auto-approval uses the shared Toggle and retains its confirmation-bypass warning. These presentation changes do not change capability gates or existing execution snapshots.

The frozen execution recipe stores the Profile launch intent and resolved cwd. Runtime and recovery send that frozen intent to the selected Agentlet, whose matching Definition compiles it immediately before spawn. Later Profile edits or deletion do not affect the execution. Historical optional `harnessLaunchPlan` data remains parseable for persisted-data compatibility but is ignored as executable input, and new executions do not write it. This change performs no migration or rewrite of existing Profiles, workloads, or durable state.

The editable Profile is a template, not an execution. A conversation freezes its recipe, cwd, instructions, preferences, and `profileExecutionRevision` at first realization (first prompt, warm-up or first mode/model/config control), not when its tab or Agent Node is created. Unrealized conversations use the latest template; realized executions and resumed/restarted processes keep their persisted snapshot. Both unbound Chat and Agent Node conversations support a conversation-specific cwd override through the shared preparation boundary. Agent Nodes retain `agentLaunchOverrides.workingDirPath`; unbound Chat carries persisted browser intent as `cwd` on every realization entry point. An absent override inherits the selected Profile without copying its value before realization. Both paths apply overrides to the workload cwd and launch recipe, and later requests cannot change the frozen directory. Paths are absolute on the Agentlet machine, not necessarily the Huabu server. A successful non-no-op Profile patch advances `revision`; launch/cwd changes also advance `executionRevision`. Missing legacy revisions mean zero without rewriting the record. HTTP edits require `expectedRevision`; stale saves fail with `409 profile_conflict`, including changes that race asynchronous daemon validation.

The execution snapshot also preserves directory origin as `workingDirectoryOverride`: an explicit path or `null` for Profile inheritance. The ACP driver's spec validator preserves this field across persistence and recovery. Cached metadata returns it separately from the effective frozen cwd, so an inherited directory never gains an override marker and later Profile edits cannot change the displayed execution path. Legacy snapshots without origin remain valid and display their frozen directory without an override marker rather than guessing from the current Profile or browser intent. The compact working-directory presentation and explicit inline-editing interactions are documented in [Preview Workspace](./preview-workspace.md).

Saving Chat as a Question copies only its explicit directory override, never its effective inherited cwd. The existing thread keeps its frozen execution directory; a copied node with a new thread inherits the current Profile unless an explicit override was saved. Draft preparation failures before a control callback starts restore the prior execution lock and skip the unnecessary cache refresh; potentially dispatched requests retain the lock until execution facts are confirmed.

The client records revision-fenced execution facts immediately after a successful cached-metadata lookup, before Profile capability discovery. Discovery errors remain visible but cannot prevent editing a confirmed unrealized draft, and discovery results do not overwrite execution locks.

Runtime-relevant edits invalidate the Profile schema cache. Cache warm-starts and metadata writes are fenced against the frozen execution revision, so an old thread cannot repopulate or consume the new template's cache. Successful model/thought-level choices may update known-harness Profile preferences only from a matching execution revision; Custom keeps such choices session-local. Existing thread metadata remains authoritative for its live controls regardless of Profile edits.

Huabu stores the reserved automatic-source marker in `customData.discoveredAgent`:

```json
{
  "version": 1,
  "agentletId": "machine-a",
  "harnessId": "copilot"
}
```

The tuple deduplicates only automatic defaults. For a ready v2 Definition, an existing automatic Profile suppresses creation only when its actual launch is `acp-harness` for the same harness. A legacy automatic `acp-command` Profile therefore remains untouched while discovery creates a new typed Profile with a distinct ID. Reconnection and restart reuse that typed identity, preserving its edits. Manual Profiles without automatic provenance do not suppress automatic creation.

Profile aliases are display labels, not unique keys: Utility Agent settings, conversational recency, edits, execution snapshots and thread bindings use Profile IDs. When a new automatic typed Profile's standard alias is already occupied, its initial alias adds the harness ID in brackets, such as `GitHub Copilot (huabu) [copilot]`; this is a display hint, not an alias-uniqueness constraint. Existing aliases, commands, launch options, directories, saved settings and conversation bindings are not rewritten or migrated. The create API rejects caller-supplied automatic provenance; patches preserve the original marker even when replacing or clearing other custom data, and reject attempts to change it. The generic Agenetes registry does not interpret this Huabu-owned field.

Deleting an automatic Profile is ordinary deletion. A later discovery may create a new default with a new Profile ID. There is no tombstone, reset endpoint, persisted availability state machine or reconciliation controller. Missing harnesses and failed probes do not delete existing Profiles. Existing ordinary workload snapshots remain independent of subsequent Profile edits or deletion.

## Persistence and retired Team data

The generic registry writes `<HUABU_DATA_DIR>/agent-profiles/registry.json` atomically. On first initialization only, it imports ordinary command Profiles from the former `agent-team/registry.json`, whose records already carry device placement. IDs, directories, metadata and custom data are preserved. Huabu does not import the older `agent-profiles.json` format because those records have no device identity and assigning them to an arbitrary connected or supervised Agentlet would break placement continuity. Initialization is persisted even for an empty list; an existing new registry is authoritative, so a deleted Profile cannot reappear through repeated migration. Invalid command data and conflicting identities fail explicitly.

Old Team registry/config/setup-log files and conversation records are not deleted or rewritten by migration. Manifest Profiles are not imported as active Profiles or converted to executable commands. Agentlet and Agenetes reject retired Team launch recipes instead of silently treating them as ordinary commands.

The repository's `agent-teams/` manifest, prompt and Skill folders remain data assets. There is no bundled Team registration, manifest execution, setup worker, Team CLI, Team API, member Config UI or preparation lifecycle. Space Templates are a separate feature; their implementation is not required for ordinary Profiles. Historical design material is retained in [the archive](../archive/agent-teams-as-extensions.md).

## Settings and APIs

Owner-only `GET /api/agent/defaults` and `PUT /api/agent/defaults` expose the Utility Agent configuration `{ profileId: string | null, functionalModel: string }`, persisted atomically in `<HUABU_DATA_DIR>/agent-defaults.json`. The reserved `huabu` identity selects Built-In Pi explicitly; other identities select external Profiles and `null` means unconfigured. Built-In reads and writes require no external registry or connected Agentlet. Its `available` state means the backend exists, not that provider authentication has been verified; missing credentials are repaired through Built-In settings and never cause a backend fallback.

When no Utility Agent record exists, provisioning chooses a stable ordered external Profile on a connected Agentlet and saves its identity. With no candidate, setup guides the user to connect an external Agent or explicitly choose Built-In Pi. Existing records, including null/deleted/offline selections, remain authoritative. Old provider credentials do not implicitly enable Pi, and switching utility backends does not clear credentials or models. Reads do not discover agents, initialize settings, or create sessions. Deleting or disconnecting the selected Profile does not choose a replacement.

Settings separates **Devices and Agents** from **Agent settings** without changing their persistence owners. Devices and Agents derives one bordered, initially expanded group per device from the complete Profile list, connected devices, display-only known devices, and exact desktop identity. Profiles resolve against the connected list first using `resolveConnectedDevice`, then against known metadata with the same exact-ID/unique-hostname rule for display only. Unresolved targets receive their own identifier-labelled group; ambiguous legacy hostnames never select an arbitrary machine. There is no separate Device unavailable Profile section. Only the device group folds; polling and connection transitions preserve its mounted state, and collapse hides rather than unmounts its Profile rows and dismisses their open popovers. Multiple Profiles with the same harness or alias are retained. Profile rows show the saved avatar, alias, and canonical harness identifier (or localized Custom command), omitting an exactly equal duplicate label. Device-level offline state is not repeated beneath every Profile. The overview does not probe devices merely to resolve cosmetic harness names. Edit and Delete remain available offline as always-visible pencil and trash icon buttons; deletion retains confirmation and existing launch-editing capability gates remain unchanged. Device menus remain visible and contain Rename for online devices, local Disconnect when enabled, and inline device information, without a second information popup. Rename remains connected-only under the existing API contract. The copy-ID action participates in menu keyboard navigation and reports clipboard errors. Settings has no batch detection/provisioning action: users inspect availability and installation instructions in Add agent and explicitly save individual Profiles. Connection-time provisioning remains unchanged.

Each online device header has its own Add agent action independent of folding. Device cards have a consistent 12px gap, without an additional offline section or spacer. Connect device is a left-aligned outline button after the list and remains available when the list is empty. Connection instructions, creation, and editing reuse the focused-view header, Back action, reduced-motion-aware transitions, and return-trigger focus restoration. Connection instructions do not probe harnesses or load runtime settings.

Device and Profile names stay on one line with ellipsis rather than expanding the rows; their full stored names remain available on hover and in the existing accessible action labels and editors. Profile harness labels stay inline and truncate independently when needed. Profile action buttons remain muted at rest on pointer and touch devices. Edit uses the default foreground on hover/focus; Delete uses the danger foreground. Both show short localized tooltips and include the full Profile name in their accessible labels. Individual controls retain keyboard-focus outlines without adding a whole-row background. Profile rows keep their avatar, identity, and actions side by side even in narrow Settings layouts. Device headers use 6px vertical padding, Profile rows use 4px vertical padding around their 32px action controls, and the Profile list has 6px top and bottom padding. The trailing Delete button and device menu share a right edge, while the Profile avatar column is indented beneath the device heading. Device names and the smaller This device label share a text baseline with a 6px gap, including in the standalone local-device row.

Profile avatars, aliases, and harness labels share a vertical center rather than a text baseline; the avatar tooltip wrapper uses flex layout to avoid inline baseline spacing. Device-name fold controls remain transparent on hover and retain their pointer cursor and visible keyboard-focus outline.

Add agent uses the target device's read-only catalogue, listing every supported harness plus Custom command without a dropdown or an additional detection/manual choice. Names remain the primary content; only Custom command has a leading terminal icon. Each harness has one persistent status label: Ready to configure in `text-success-fg`, Connection component required or Check failed in `text-warning-fg`, and Not detected in muted text. Status is expressed in words, not color alone. Catalogue and form status text use the existing semantic foreground tokens to meet normal-text contrast in both themes without changing global colors. Rows have no status icons, secondary action labels, or tooltips; pointer and touch layouts are identical. Pending discovery retains its reduced-motion-aware spinner. Each whole-row button has a divider, hover/focus feedback, and a persistent muted right chevron aligned to the same trailing edge, including unready harnesses and Custom command. The decorative chevron indicates progression to configuration or installation guidance, not an external link. Missing commands remain clickable, not disabled, and not-found does not imply the device or harness is permanently unavailable. The current selection uses a neutral background without a checkmark. Selecting a row keeps the page title and device fixed and replaces the list with a selected-name summary and Change action. Unready harnesses show their actual target-local installation hint and diagnostics; Check again performs only `GET /api/acp/agent-cli`, never provisioning or installation. Pending, request failure, lookup failure, missing adapter, and not-found states remain distinct, and manual Custom configuration remains available when discovery fails. Requests are fenced by target, observed connection identity/time, and request generation; explicit rechecks do not poll. Readiness is command availability, not login or successful session startup.

The device menu footer uses two compact muted rows labelled ID and Version, with both values aligned to the same right edge. Long IDs display their first eight and last four characters on one line; hovering or keyboard-focusing the copy control exposes the complete ID, and copying always uses the original value. The copy icon appears over the right end of the ID when its row is hovered or keyboard-focused and remains visible on non-hover devices. The surface-backed icon is absolutely positioned without reserved space or layout shifts. Version refers to the device connection program, not the Huabu desktop version.

Creation and editing share `CommandProfileForm`, its capability gates, target-aware folder picker, custom-command field, and icon/permission persistence. Each visited harness retains a mounted, hidden draft during this creation visit; only the selected form publishes footer actions. Change dismisses draft-owned popovers before hiding the form and focuses the selected catalogue option, or the first available option if detection no longer includes that harness. Changing the selection never saves a Profile. The Add action submits explicitly, blocks same-tick duplicate submissions, and retains drafts after failure. After a successful write followed by failed snapshot refresh, the form offers refresh-only retry instead of creating another Profile. Refresh failure feedback appears only after rejection, never while the initial refresh or a retry is pending, and clears after a successful retry. Drafts are scoped to the fixed device and discarded on leaving the flow.

While edit-time capability discovery is pending, the form and draft remain mounted and capability-dependent controls stay disabled. Unsupported approval and execution-editing warnings appear only after discovery settles, not while its result is unknown; successful detection therefore does not remove transient warning rows or shift the form. Confirmed unsupported states and discovery failures remain visible, and alias/icon editing keeps its existing availability.

Agent settings contains Utility tasks, Conversation and changes, Advanced runtime settings, and Built-In Pi. Utility tasks starts expanded; the remaining sections start collapsed and retain existing `keepMounted` behavior and save semantics. Built-In chat configuration remains a focused subview of Agent settings. Existing `open('agent')` deep links continue to reach device/Profile management; `builtIn` reaches Pi configuration directly. Huabu-owned auxiliary tasks outside an Agent Node's bound thread follow the Utility Agent, including summaries, keywords, content/Frame titles, conversation titles, and image labels. For external tasks, the trimmed functional-model value inherits the Profile's remembered model when empty, then the harness default. External functional text tasks reuse Profile snapshot compilation and Agenetes event folding, without creating visible Agent Nodes or storing Agenetes conversations. An unconfigured Utility Agent or unavailable Utility Profile is an explicit failure, never an internal fallback. A background permission request fails the task and forwards cancellation without escalating approval; the task deadline also bounds unresponsive harnesses. Agenetes owns one-shot Job cleanup: normal completion, failure, or early iterator return closes the handle and waits for exact Agentlet process reclamation, while cleanup failure remains observable. Functional Jobs await the asynchronous Agenetes creation API inside the task deadline. Cancellation or timeout during creation returns promptly, and a handle that arrives afterward cannot dispatch the task. The client records the most recently explicitly selected conversational Profile under `huabu.recentConversationAgentProfile.v1` through the application preference adapter. `GET /api/acp/profiles` reads the canonical persisted list, active connected devices, connectivity-filtered selectable IDs, supervised-child health, and saved `agentDefaults` without detecting harnesses, creating Profiles or starting sessions. The active device projection is sorted deterministically and contains the Agentlet UUID, display metadata, Agentlet version, connection time, and associated Profile count; it is not persisted and contains no offline history or last-seen state. Devices and Agents groups ordinary Profiles under their devices and includes the supervised-child health banner; Utility Agent and backend-specific configuration live in Agent settings. The shared Profile store's `refresh({ afterMutation: true })` waits for any older in-flight snapshot, then obtains a post-mutation snapshot instead of joining the pre-mutation GET. Workload placement is always explicit. New workloads snapshot the Profile's `agentletId`; existing snapshots continue to use their stored placement. Owner-only `GET/PUT /api/acp/runtime-config` persists the external-agent idle timeout and supervised-daemon process limit in `<HUABU_DATA_DIR>/external-agent-runtime-config.json`; both controls appear under Settings > Agent > External Agent runtime. `maxAgents` defaults to `10` and accepts any positive JavaScript safe integer without a product-defined maximum. Both numeric inputs save on blur or Enter, not each keystroke, without permanent Save buttons. Invalid input and save failures render below each field through a shared local feedback composition; failures retain drafts and offer explicit retry. Unchanged values do not write, and a shared synchronous in-flight guard prevents Enter/blur duplicates and overlap between runtime saves. Each full-configuration write preserves the other field from the latest acknowledged configuration, and controls stay disabled until configuration has loaded successfully. Idle-timeout presets still save immediately and restore the prior selection if a save fails. Huabu passes the process limit as `--max-agents` whenever the supervised daemon starts; saving does not hot-update or automatically restart the daemon, and manually launched remote daemons continue to use their own CLI argument without a configuration handshake.

The focused Add device view presents three ordered steps: prepare a matching Huabu source checkout with Node.js 24.16+ and pnpm, choose the target terminal and copy/run the connection command, then keep the terminal running and check Connected devices.
