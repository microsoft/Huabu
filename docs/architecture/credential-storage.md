# Credential Storage

> Credential persistence for Electron and standalone server deployments. Last updated: 2026-10-19

## Runtime backends

All server modules use a single synchronous-read, asynchronous-write `SecretStore` facade. Runtime selection happens before the HTTP server binds, so agent tools can read an initialized in-memory credential view without synchronous disk access.

| Runtime                                       | Credential backend                                           | At-rest behavior                                                                                                                                                                                                          |
| --------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Electron-managed server                       | `ElectronSecretStore` over Electron `safeStorage`            | The main process writes OS-protected ciphertext to `<userData>/data/secure-secrets.json`; decrypted values are sent once to the trusted server utility process and retained in server memory for synchronous tool access. |
| Standalone web/server with `HUABU_SECRET_KEY` | `EncryptedFileSecretStore` with AES-256-GCM                  | UI-saved credentials are independently encrypted with random 96-bit IVs and authenticated metadata in `<dataDir>/encrypted-secrets.json`; the Base64 32-byte master key remains outside the data directory.               |
| Standalone web/server without an explicit key | `EncryptedFileSecretStore` with an automatically managed key | A random 32-byte master key is published once in the private instance configuration directory; credentials remain AES-256-GCM encrypted in the data directory.                                                            |
| Electron with an external or remote server    | External server's own backend                                | Electron does not migrate or expose its local secure store because it does not own the external process. Remote HTTP Basic Auth credentials remain only in Chromium's current network session.                            |

Electron enables the bridge with `HUABU_SECRET_BRIDGE=1`; the server waits for a `secret:init` snapshot over `utilityProcess` messaging before binding its HTTP port, and settings mutations are acknowledged only after Electron has encrypted and atomically persisted the new value.

The main process validates every bridged mutation before touching `safeStorage`, rejecting anything malformed with `Invalid secure credential mutation`. That validation matches the secret id by **shape** (`llm` / `integration` / `oauth` namespace, one to three `:`-separated segments, bounded length) rather than against a copy of the server's `SECRET_IDS`. The distinction matters: the server process already receives every decrypted secret in the `secret:init` snapshot, so enumerating ids in Electron buys no confidentiality — it only keeps junk out of the vault. An exact list bought that marginal hygiene at the price of a recurring outage class, because a server-side id the desktop package forgot to mirror was rejected and the credential silently never persisted ([microsoft/Huabu#40](https://github.com/microsoft/Huabu/issues/40)). Shape validation keeps the hygiene and removes the hand-synced duplication, so adding a server secret that follows the naming scheme needs no desktop change. The server's `llmProviderApiKeySecretId` generator enforces the provider segment's character and 64-character length invariant before producing an id; Electron retains the same bounded shape as defense at the IPC boundary. The accepted and rejected shapes are pinned in [`apps/desktop/src/secure-secrets.test.ts`](../../apps/desktop/src/secure-secrets.test.ts), and the generator boundary is pinned in [`apps/server/src/security/secret-ids.test.ts`](../../apps/server/src/security/secret-ids.test.ts).

The `pi-ai` credential adapter preserves the `CredentialStore.modify` contract during concurrent OAuth refresh: a returned credential replaces the stored value, while `undefined` leaves the current value unchanged because another locked caller may already have refreshed it. Credential removal is performed only through `delete`; treating a no-op `modify` as deletion would erase a freshly rotated Copilot credential when several requests observe expiry together.

OAuth API errors expose the deepest message in an `Error.cause` chain so a persistence rejection remains actionable after `pi-ai` wraps it. The response includes only the selected message, never the error object or stack. In Settings, a device code remains visible and copyable while polling, and the provider verification page opens only after an explicit user action.

The source workflows `pnpm dev` and `pnpm dev:desktop` run the server as an external development process, so they use the standalone backend rather than Electron `safeStorage`. They automatically initialize a writable encrypted backend without requiring `.env` or setup. Existing externally keyed stores continue to require their original `HUABU_SECRET_KEY`.

For standalone deployments, the encrypted primary backend wins over the environment fallback. Writes target only the primary backend, and the application never writes to `.env`. The one deliberate `process.env` mutation is at startup: `initializeSecretStore()` reads `HUABU_SECRET_KEY` once, parses it into the in-memory `EncryptedFileSecretStore` master key, then deletes `process.env.HUABU_SECRET_KEY` so the raw key can never be inherited by a forked child process (the agentlet daemon and the external agents it spawns). This is defense in depth alongside the agentlet transport's `HUABU_` namespace strip — see [`agent-reachback.md`](./agent-reachback.md) ("Environment injection and isolation"). A `.env` file is merely one way `dotenv` can populate `process.env` during startup.

The renderer never receives plaintext credentials. Existing HTTP read models continue to return only authentication/status booleans.

Settings credential editors remain open and disable duplicate submissions while a mutation is pending. LLM (chat, utility, and image) and legacy integration stores return an explicit boolean acknowledgement while retaining their existing error state; credential callbacks forward that result to the shared `ApiKeyRow`. Failed saves or removals retain the draft or removal confirmation and display an inline error for retry. Only an acknowledged mutation clears the draft and closes the editor; explicitly cancelling also clears it. Model catalogues refresh only after a successful key save, and a subsequent catalogue-read failure does not turn an acknowledged credential write into a failed save.

Remote-client Basic Auth credentials are separate from the client's `SecretStore`. Electron accepts credentials only through a sandboxed prompt for the exact configured Server origin, submits them directly to Chromium's authentication callback, and does not write them to its own `safeStorage`, server data, process arguments, or renderer state. On the hosting Server, setup stores a newly entered server-side password encrypted as `integration:server:access-password` and the non-secret username in `deployment.json`. The username defaults to its saved value or `owner`, including legacy configurations without a username; explicit Basic Auth environment values still override the complete pair. With a complete environment-owned pair, setup skips both credential inputs, displays only the username and configured status, and preserves any saved credentials without copying environment passwords into SecretStore.

An explicitly enabled remote desktop local-Agent connection has a separate device credential, not a persisted Basic Auth password. Main obtains the existing shared connection token through an owner-authenticated, no-store HTTPS request and encrypts it with `safeStorage` in `<userData>/remote-agent/secure-secrets.json`, keyed by the configured Server origin hash. This vault is never included in a local Server's `secret:init` snapshot. Linux `basic_text` encryption is rejected. Disconnect removes the origin's entry; normal app exit retains it for automatic reconnection. HTTP requires an explicit native warning and is only suitable for a trusted network. The shared-token privilege and global rotation semantics remain unchanged.

Settings API updates for optional service credentials use an explicit three-state patch contract: omitting a key preserves the persisted value, a non-empty string sets or replaces it, and `null` removes the value stored by Huabu. Removing a persisted key preserves non-secret provider configuration and does not alter deployment-owned environment variables; an environment fallback may therefore keep the service available at runtime.

Settings > Services is rendered from bundled `huabu-service/v1` manifests and writes through `ServiceProvisioner`. Each manifest names a code-registered opaque storage namespace whose adapter delegates to the existing owner and SecretStore IDs. This compatibility layer performs no read-time migration and creates no generic duplicate record: Image, Tavily, RapidAPI, and Ink OCR retain their existing storage, fallback, masking, and update semantics. See [`service-packages.md`](./service-packages.md).

### Agentlet connection token

Setup uses the asynchronous `readPersistedSecret()` facade to inspect existing credentials without creating storage for a new instance. On repeat setup, a saved password is kept by default and never displayed or rewritten; changing it is an explicit choice. Automation without `--password-stdin` likewise reuses a saved password, while an explicit replacement must pass validation. Missing first-time passwords and unreadable stored credentials fail explicitly.

Setup may explicitly disable browser login for trusted-network or externally authenticated deployments. It then skips username/password collection, retains inactive saved credentials, and does not inject them into the effective deployment environment. Legacy configurations continue to require Basic Auth. Re-enabling login can reuse a retained password or a complete environment-owned pair; the login opt-out does not disable Agentlet/RFS tokens or credential encryption.

The Agentlet/RFS connection token has no Settings editor. Before serving requests, the Server captures a non-empty trimmed `HUABU_CONNECTION_TOKEN`, or reads `integration:agentlet:managed-token` from the initialized SecretStore. When absent, it generates and acknowledges persistence of a random 256-bit hexadecimal token before attachment. The managed token survives Server restart and is reported as source `managed`; environment values remain deployment-owned. Historical `integration:agentlet:connection-token` records remain untouched and ignored. `pnpm run setup --reset-connection-token` replaces the managed token for the next boot and rejects an active environment override. It requires restart, invalidates previous copied commands/files after restart, and does not hot-switch or disconnect the running Server.

Settings > Agent > External Agent runtime provides How to connect for a compatible source checkout, with an explicit POSIX/PowerShell selection. The owner-only no-store copy action returns either invocation-scoped source-daemon commands or a private connection dotenv file, plus source/transport warnings. It places copy text directly on the clipboard without rendering the token. POSIX uses scoped env assignments; PowerShell restores previous process env in `finally`. The token necessarily exists transiently in the explicit HTTP response, renderer memory, clipboard, and shell history (or the intentionally saved private env file), but never in the Agentlet process argv. An env file whose credential cannot be represented losslessly fails explicitly and directs the owner to command format; it never silently changes a token.

### Azure AI Vision handwriting OCR

Settings > Services exposes optional handwriting recognition as a compact Azure AI Vision row alongside other Huabu-managed services, matching the key icon and Set API Key / Update Key interaction used by those services. One click opens visibly labeled Endpoint and API Key inputs in spaced, full-width field groups below the title and description, followed by Save and Cancel, without configuration-source paragraphs or instructional text. The row identifies Azure AI Vision and briefly discloses selected-stroke processing; the endpoint and key must belong to the same Azure resource. Errors and read-only restrictions remain explicit. There is no provider selector, connectivity probe, or generic OCR compatibility claim.

Owner-only `GET` and `PUT /api/integrations/ink-ocr/config` use the shared OCR configuration schemas. Endpoint and API key overrides are stored together as one versioned JSON record under `integration:azure-vision:config` in the existing `SecretStore`. Serialized read-modify-write updates replace that single encrypted record, so recognition observes a complete old or new configuration rather than a partially written pair. This uses the existing standalone encrypted-file and Electron safeStorage backends; it does not depend on multi-secret desktop batching or a rollback across two files.

Each field independently prefers its UI-saved override over `VISION_KEY` / `VISION_ENDPOINT`. Omission preserves an override, and `null` removes it to restore the corresponding environment fallback. Before the first successful record write, the legacy `<dataDir>/ink-ocr-config.json` endpoint and `integration:azure-vision:api-key` secret remain readable. The first successful update captures both overrides in the new record. Once that record exists, legacy values are never consulted, including when either override is explicitly null; legacy files and keys are left untouched rather than making cleanup a second required write. A malformed canonical record fails closed instead of restoring legacy credentials. Reads return only the validated effective endpoint, per-field source (`stored`, `environment`, or `none`), `hasStoredKey`, and `configured`; this last flag describes local configuration completeness, not tested provider connectivity. Invalid environment endpoints are not reflected back into the UI. Damaged stored configuration produces an explicit settings error and disables optional OCR with a redacted warning.

Endpoint validation permits only HTTPS resource-root URLs at a single resource label under `cognitiveservices.azure.com` or a single regional label under `api.cognitive.microsoft.com`, with the default HTTPS port and no embedded credentials, query, or fragment. These are [Azure public-cloud endpoint forms](https://learn.microsoft.com/en-us/azure/ai-services/cognitive-services-custom-subdomains). Custom gateways, IP literals, unrelated hosts, sovereign-cloud endpoints, and API-path URLs are rejected both at settings validation and before recognition. A permitted Azure resource hostname may resolve through private networking; this policy restricts the host name, not Azure private-link DNS resolution.

The UI saves changed fields together: an unchanged endpoint and a blank key are omitted, so endpoint-only edits never erase a saved credential. Saved keys are never prefilled; removing a stored key is an explicit separate action, not a side effect of saving a blank password field. Read-only secret stores reject all configuration updates, including endpoint-only changes, with `credential_store_read_only`; environment-only recognition remains available. Errors remain explicit, validation messages identify invalid inputs, and a failed acknowledgement triggers a status refresh without discarding the user's drafts. A persistence acknowledgement can be uncertain after the complete record is written, but no partial pair is published. Clearing a saved key does not disable OCR if a deployment-owned environment key remains. Saved settings take effect on the next submission without restarting and never rewrite `.env`; OCR already in flight keeps its captured request configuration.

## Electron encrypted store

The encrypted file is versioned JSON whose values are Base64 representations of buffers returned by `safeStorage.encryptString()`; Base64 is transport encoding, while the security comes from the platform backend used by Electron.

Windows uses DPAPI, macOS uses Keychain, and Linux requires Secret Service or KWallet. Electron startup fails closed when encryption is unavailable or Linux reports the insecure `basic_text` backend.

Non-secret provider configuration remains in `llm-config.json` and integration status is derived from the secure in-memory snapshot. Environment-variable fallbacks remain supported and are not migrated because they are deployment-owned configuration rather than UI-owned persisted values.

Key resolution reads the secret store only; there is no caller-supplied or on-disk plaintext fallback.

## Standalone encrypted store

`HUABU_SECRET_KEY` must be canonical Base64 encoding of exactly 32 random bytes. It is used directly as the AES-256 key; each credential entry receives a new random 12-byte IV and uses its stable secret ID as additional authenticated data. The file records its version, algorithm, non-secret key fingerprint, IV, authentication tag, and ciphertext for each entry.

Every mutation constructs a new encrypted snapshot, atomically replaces the file, reads it back, authenticates and decrypts every entry, and only then publishes the new in-memory snapshot. A wrong key, malformed file, modified ciphertext, or authentication failure aborts startup or rejects the write.

The standalone backend does not coordinate writes between processes. Stop all Huabu servers and Vite development servers sharing an instance's credential storage before running setup or resetting its connection token, then start them afterward. Otherwise, a service's stale in-memory snapshot can overwrite the setup process's changes on its next credential write. Setup reports this prerequisite but does not enforce it; see [deployment security](./deployment-security.md).

Without `HUABU_SECRET_KEY`, standalone startup resolves `HUABU_CONFIG_DIR` or `~/.huabu/servers/<first-24-hex-of-SHA256-of-absolute-data-directory>/`. The shared client-runtime resolver anchors both the default `apps/server/data` and relative `HUABU_DATA_DIR` overrides to the repository root, independent of startup cwd; setup, Server, Vite, and the standalone launcher therefore share the same instance identity. Absolute overrides, including Electron's injected data directory, remain unchanged. The private directory stores `master-key` separately from business data. POSIX requires current-user ownership, directory mode 0700, and key mode 0600; symlinks and non-regular key files are rejected. Windows creates the directory with a restricted user ACL. A fully written random key is published with a no-replace hard link so concurrent initializers reuse the winner, never a partial file. An existing encrypted store without its original private key or explicit environment key fails rather than generating a replacement.

The automatically managed key is a private file, not an OS-encrypted credential. It separates keys from business-data-only backups but cannot defend against an attacker who can read files as the same OS user. Back up and restore the private directory together with the matching data directory; persist both for containers. Moving data changes the default instance hash, so preserve the private directory and set `HUABU_CONFIG_DIR` explicitly when relocating an instance. File/permission errors are fatal, not a fallback to read-only storage or ephemeral tokens.

The deployment readiness endpoint exposes only whether credential storage is writable. Its existing `secret-key-required` read-only reason remains wire-compatible, but normal standalone startup now initializes writable storage or fails explicitly. Backend kind, key material, credential values, and environment fallbacks remain private. See [`deployment-security.md`](./deployment-security.md).
