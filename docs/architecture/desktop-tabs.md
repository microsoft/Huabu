# Desktop Space Tabs

The Electron desktop window hosts a persistent Home page and one independent `WebContentsView` per opened Space. They share one Server and one active Workspace. Browser deployments retain the existing single-page router behavior.

## 1. Ownership

```text
Electron main
  ├─ shared Server
  ├─ DesktopTabs: identities, activation, save coordination, recovery
  └─ BrowserWindow
       ├─ Shell renderer: window chrome and Space Tab strip
       └─ WebContentsView × N: Home and independent Space applications
```

The main process is authoritative for Tab order, the active identity, loading/error state, background activity, and session restoration. The Shell and loaded content pages subscribe to snapshots and send validated operations through preload. A Space page retains its existing single-instance canvas, chat, history, preview, selection, and gesture Stores; no Store is shared between content pages.

Home cannot be closed and remains the only renderer allowed to coordinate Workspace activation. Space identities are deduplicated within the active Workspace. Opening an existing Space activates its page instead of navigating or reloading another Space.

The content views are sandboxed, use context isolation, and disable Node integration. Each Space uses a persistent Chromium session partition keyed by Server, Workspace and Space identity. Independent connection pools prevent several Spaces' SSE streams from exhausting Chromium's six HTTP/1.1 connections per origin and blocking further Spaces or saves. Home and Shell keep the default session. Every partition receives the same external-preview response-header policy, and the existing remote Basic-auth handler reuses in-memory credentials once per new renderer while still prompting on a rejected credential. Hidden views remain alive with background throttling disabled; v1 does not automatically discard, suspend, split, or detach Tabs.

## 2. Navigation and chrome

The Shell owns the 36px window title/Tab strip: Home, Space Tabs, the optional blank Tab and the new-Tab button, with icon-only application actions anchored at the far right. Settings and the separate Workspace button immediately to its right remain visible in both Home and Space Tabs. All Tab-strip icon controls reuse Common Button's medium sizing for 16px glyphs and at least 28px click targets; the strip height remains 36px and Tab titles use 13px regular-weight text with a 20px line height. Content views occupy the area below it; their `WindowChrome` is suppressed. Desktop Home does not repeat the standalone logo/application-name header. Its content header contains only the Spaces heading and existing Space import/create actions, with neither Workspace selection nor Settings mixed into page actions. The browser keeps its original standalone header and list heading. Existing Settings, menus, Chat, previews and other popovers remain inside the content renderer; ordinary Shell DOM cannot overlay a native content view.

Home is pure navigation and does not open a menu. Clicking the persistent Workspace button, or pressing ArrowDown on it, activates Home and opens the Workspace menu, including when invoked from a Space. The Shell sends its measured button anchor through the existing validated Home-menu command; main owns the menu state and relays the position to Home and Shell. The menu is rendered by the persistent Home router root using Common Popover and menu items, directly below the title strip rather than behind a native content view. It lists recent Workspaces with a check on the active identity and truncates secondary paths inside a viewport-bounded 320px panel, with no path/count hover tooltip. Escape and selections return focus to the Shell's Workspace button; outside clicks dismiss without stealing focus, and Tab activation, Settings, saves and reload close the menu. Recent selections reuse the Workspace Store activation/save barrier. Open Workspace always links to the existing Home switch page at `/setup`, regardless of native picker support; visiting that page does not itself activate a Workspace or close existing Space Tabs. Folder picking and manual path entry remain owned by that page. During activation, Home shows the existing Workspace loading screen; failures use the Store's localized error via a toast. Read-only connections can inspect the current Workspace but cannot switch it.

Home is an icon-only navigation Tab with an accessible name and no visible label. Its glyph is centered in a symmetric control without close-button padding; its inactive background matches the window-control gutter, while selected Home uses the same default-background highlight as other Tabs. Space Tabs show only the title and close button, with a neutral active highlight. Loading, running tasks, completion and task errors do not add icons, change the title color, or add status text to the accessible name. Task state remains inside the Space. Operation failures still use the existing Shell error feedback; renderer crashes and page-load failures produce a separate native error dialog rather than decorating the Tab.

Tabs form continuous full-height segments separated by thin vertical borders, not rounded pills. The strip uses the semantic surface color (white in light mode), distinguishing it from the default page background. The selected segment uses the default background color, including Home; its title and close control share the same surface. Both colors follow the existing dark-mode tokens rather than hard-coded white. Close controls appear when their Tab is hovered or contains keyboard-visible focus, and remain visible on devices without hover. Their layout space and 28px target remain reserved while hidden, preventing title movement. Activation and closing remain sibling buttons rather than nested interactive elements; closing does not activate the Tab. On macOS the native traffic-light controls are explicitly positioned inside the title strip and shown without requiring hover, with reserved space before Home; fullscreen retains native macOS behavior.

The plus button and `Cmd/Ctrl+T` open a single closable `new-tab` entry; repeated requests activate that entry rather than adding more. Home and the blank entry render the same `CanvasListPage`, including search, remembered top-level/all scope, canonical parent paths, card layout, and create/import/export/delete actions; there is no separate picker presentation or filtering implementation. Opening a Space from Home adds or activates its Tab while retaining Home. Selecting, creating, or importing a Space from the blank entry replaces it in place. If that Space is already open, its existing Tab is activated and the blank entry is removed. Closing the blank entry returns to the Tab active when it was created, or Home if that Tab has closed. Blank entries are not restored after restart.

The blank entry reuses the retained Home content view instead of allocating another renderer. Main maps its active content, visibility, reload and Settings commands to Home, while the published active identity remains `new-tab`. Activation navigates that view to `/spaces`; the shared list clears its search when the active identity changes and retains the scope selection across both entries. The Tab manager, not the list presentation, owns the different opening behavior. Workspace coordination and save acknowledgements remain owned by the single Home renderer. Space renderers remain independently retained and unchanged.

The never-unmounting router-root navigation blocker diverts cross-Space navigation into `DesktopTabs.open`, preserving the destination query, fragment and one-shot router state. Same-Space node links remain local. Native application links and new-window requests also route through the Tab manager instead of replacing a Space renderer's immutable identity or opening another application window. Returning to the list or Workspace setup activates Home. Home's `/` landing stays `/spaces`, even when World is enabled; World still opens through its existing navigation entries as a Space Tab.

The retained Home list refreshes after local Space creation/import and when Home becomes active again, including after changes made in another content renderer. Ordinary status snapshots do not repeatedly fetch the list. Refreshes retain existing cards and fence responses by request generation and Workspace identity, so an older request cannot replace a newer list or publish another Workspace's count.

Native macOS menu commands and diagnostics target the active content renderer. Editing roles continue to use Electron's focused WebContents. Folder pickers remain parented to the owning window. Fullscreen and update status are broadcast to the Shell and all loaded content pages. The Tab strip's Settings button routes through the existing command bridge to open the modal inside the active content page, not inside the Shell or a cross-view overlay. Home has no duplicate Settings trigger; a Space's existing App menu remains available.

DevTools open in a detached window for startup development tools, diagnostic requests, and keyboard shortcuts. Docking Shell DevTools inside the main window would leave them behind the native Home/Space content views; detached tools preserve the existing content layout. Shortcuts still toggle the active content page's tools.

`Cmd/Ctrl+T` opens or selects the blank Tab, `Cmd/Ctrl+W` closes the active closable Tab, and `Ctrl+Tab` / `Ctrl+Shift+Tab` cycle Tabs. Reload shortcuts drain saves before reloading the active page. DevTools shortcuts target the active content page. The Tab strip also supports arrow, Home and End keyboard navigation. Keyboard-driven strip activation explicitly targets Shell focus through the validated activation request and refocuses the selected Tab after acknowledgement; ordinary clicks continue to focus the content page.

## 3. Saving and lifetime

The native macOS Close menu action closes the active closable Tab only when the main window is focused. A focused auxiliary window, including the remote sign-in prompt, closes normally without touching the main window's Tabs; without a focused window the action does nothing.

Closing a Tab is an acknowledged operation, not a fire-and-forget renderer destruction. Main sends an identity-fenced preparation request to the owning page. The renderer freezes input, blurs the focused editor and invokes its single `pageLifecycle` boundary: settle registered editors, await local mutations through their final state insertion, then flush registered persistence owners. Mutation registration covers shared file import (toolbar, paste and drop), delayed clipboard reads, cross-Space artifact cloning, dropped-image sizing, Note sizing changes, Space creation/import/migration, conversation draft patches, attachment/capture uploads, recordings and Agent submission up to durable acceptance. File batches await every upload, insert successful results and report failures; an operation that fails during preparation rejects the close. Home participates even without a loaded Canvas. Creation/import that finishes while closing retains the created Space in the catalogue without issuing navigation against main's operation lock. Closing the blank Tab prepares its retained Home renderer before removing the logical entry and resumes Home afterward.

Persistence stays owned by its subsystem rather than a checklist in the desktop hook. The Canvas participant calls `saveCanvasForSubmission`, promotes and drains preprocessing, verifies saves again after projections, and persists viewport/Preview Workspace state. The preview participant settles every active Note/Text editor across split groups without closing inner tabs; recording participants stop active capture and await upload. Conversation participants drain title and draft writes, including blur-triggered work. Preparation rechecks operation generations after flushing and repeats if an owned continuation created more local work. A current title/draft failure or blocked restored-content barrier rejects preparation; preprocessing retains its existing per-node ingestion error reporting. Superseded title failures cannot override newer successful intent, and safely persisted pre-send title intent/recognized missing-thread creation races remain locally queued without blocking. Destruction requires a successful acknowledgement or an explicit discard confirmation in the recovery cases below. Close, reload, Workspace changes, quit and update installation reuse this boundary.

After a 150 ms grace period, an unfinished preparation displays an opaque, full-viewport progress overlay, including on Home. It shows only “Saving…” and “Cancel”, without a separate heading, explanatory paragraph or internal operation names. It continues automatically when ready and remains cancellable when this page finishes before another page during a window-wide preparation. Main announces when all pages are prepared so the overlay can disappear before Workspace activation uses its existing loading UI. Cancellation cancels only the pending desktop action: uploads, saves and server execution are not aborted. Main rejects the entire preparation batch and resumes every surviving page; generation/abort fencing prevents obsolete preparation callbacks from acknowledging a later action. Opening or activating a Tab still does not initiate preparation.

Input freezes synchronously before blur and stays frozen until main resumes or destroys the renderer. The document body remains inert, including React portals, and a capture-phase guard installed before React blocks shortcuts and input. The progress surface uses a native modal dialog because its top-layer inert exemption is necessary to keep the cancel button accessible without unfreezing background content; it reuses Common Button/Loading and semantic colors. Only events inside that open control dialog bypass the input guard, and Canvas shortcuts exclude it. Native menu callbacks retain the same freeze check. The underlying page stays mounted throughout preparation.

A rejected preparation retains the page unless the user explicitly confirms discarding unsaved changes for a single-Tab close or reload. These two actions reuse one native warning after save failure or timeout, with Cancel as the default and escape action; cancellation of the preparation itself never opens a discard prompt. The warning includes the save error and data-loss risk, releases the obsolete preparation overlay while keeping input and the main operation lock frozen, and only the destructive choice permits close or reload. Declining resumes the unchanged page so saving can be retried after connectivity returns. Workspace changes and healthy-page shutdown failures retain their stricter save requirement.

The 15-second timeout detects an unresponsive renderer, not slow local work: a preparing page sends a request-scoped heartbeat every five seconds, allowing a responsive upload/save to finish without a fixed duration limit. Heartbeats and acknowledgements validate exact renderer ownership for live requests; replies for retired requests are ignored and cannot settle or extend a newer request. Repeated close requests share one pending operation. An aborted renderer preparation can be replaced immediately, even before its asynchronous cleanup runs; the old cleanup cannot release the replacement's lock. An unavailable renderer still requires explicit discard confirmation; reload remains available through existing keyboard shortcuts rather than an extra Tab button.

Title-save rejection adds a localized “Retry title save” action to the existing persistent danger toast. It retries all current failed title intents through the title Store, including intents whose inner Chat tabs have closed, without reopening Chat or discarding a rename. Another failure produces fresh feedback with the same action; successful recovery does not resume the rejected desktop operation automatically, so the user can close, reload, switch Workspace, or quit again. Dismissing the toast never clears failed intent; a later save attempt exposes recovery again.

Title preparation distinguishes read errors, failed server writes, and failed local draft persistence. Read-only query failures never block an already persisted draft. LocalStorage write failures block acknowledgement even if Zustand already holds the pending title in memory; the same retry action first persists the latest pending snapshot. Identical successfully persisted snapshots are not rewritten for runtime-only cache updates. Server-write failures remain blocking independently of later query success or failure.

Window close, application quit, and explicit update installation coordinate saves across every loaded content page through the same pending preparation. A quit in progress is not approval to destroy the window: repeated quit and window-close events remain prevented until saves succeed. Closing a window without quitting clears its prepared state so a later window must save independently. All acknowledgements settle before a failed operation resumes the pages. If healthy pages save successfully but a renderer is unavailable, including Home, shutdown requires explicit confirmation before discarding the unavailable pages; cancelling keeps the pages and resumes healthy input. Healthy save failures still block shutdown, and Workspace changes never offer this discard escape hatch. The existing cooperative Server shutdown starts only after saving succeeds or the unavailable-page discard is confirmed. Remote mode also performs the save barrier even though Electron owns no local Server. An install failure cancels and resumes only a successfully prepared quit; a rejected competing quit/update request must not release another Tab close, reload or Workspace-change operation's lock.

Closing or switching a Tab never invokes Agent Stop. Server-owned accepted invocations continue until settlement or explicit cancellation; reopening uses the existing history/stream attachment paths. Quitting the local application still shuts down its Server: restoring Tabs is not a promise to recover in-flight Agent execution after process exit.

Workspace changes are initiated from Home, save all content pages, retain the old Workspace's Tab session, and destroy its Space views before activating a new Workspace. No page from the previous Workspace is left able to issue writes. Home clears its ready identity during activation and commits the authoritative Workspace information before refreshing the recent registry. A registry-refresh failure still reports an error but cannot revert the active identity. A rejected activation or information response triggers a Server identity check; only a confirmed active Workspace can restore a Tab session, including the old session if the Server confirms it remains active. Main rejects identity registration until the change has ended instead of queuing potentially stale identities. If confirmation also fails, Home remains unconfigured with an error and restores no Space pages.

If the initial Workspace save barrier fails, the Store retains the current Workspace identity and records the failure for inline feedback. Both path selection and recent-Workspace selection on `/setup` also show the existing danger toast, matching the Home Workspace menu.

If Home fails after the Workspace save barrier has completed, main releases only the abandoned Workspace transition's lock and keeps the Workspace identity unset. Reload and confirmed shutdown remain available. Home must become ready and confirm the active Workspace through Server initialization before registering an identity and restoring its session; main never guesses the previous identity. A Home failure during the save barrier does not release that barrier early, and readiness is rechecked before destroying Space views. Home failures never unlock an unrelated Tab close, reload or shutdown operation.

Successful Space deletion invalidates pending list requests before removing the card and starts a background refresh. Responses captured before deletion cannot restore the deleted card or overwrite the updated count.

Home refuses to delete a Space that still has a desktop Tab, including a lazy restored Tab, and shows a localized instruction to close that Tab first. The current main-process snapshot is checked both before showing confirmation and again on confirmation. Deletion reuses the shared Space-tree confirmation dialog. Before sending the tree deletion request, it checks every ID in the server preview, including descendants, against open and lazy Tabs. For a closed Space tree, Home acquires the existing main-process operation lock with the complete preview identity set; main rechecks that none has a Tab and blocks opening Tabs or changing Workspaces until the request settles. Home releases the lock on success or failure, and a Home failure releases an abandoned deletion lock. Deletion never closes or discards an open Space automatically. Browser deletion retains its existing behavior.

## 4. Persistence and status

The main process atomically replaces a fixed `desktop-tabs.json` file under Electron `userData`. Session records are keyed by Server identity and Workspace identity; local Server identity deliberately excludes the ephemeral loopback port. Session records contain ordered Space identities, the active Space and a validated title snapshot for opened Spaces; application preferences have a separate top-level record. Title snapshots are captured by the existing atomic session writes and restored before loading content, so lazy Tabs do not expose raw Space IDs. Legacy records without titles remain readable. Home synchronizes its existing Space catalogue through a Workspace-fenced command to refresh names for unloaded entries, including legacy sessions, without allocating Space renderers; loaded pages retain authority over their live titles so an older catalogue response cannot overwrite a rename. Until a name is available, Shell uses the localized untitled-Space label rather than an internal ID. Activation and closing persist the intended session before committing destructive runtime changes, so a filesystem error keeps the original Tab and surfaces the failure. Restoration follows successful Home Workspace initialization and creates lazy entries; only the active Space view is loaded until another Tab is selected.

Space-local chat binding/model metadata, conversation directory/title intent and panel state use Workspace/Space-scoped localStorage records inside the Space's partition. Before Stores initialize, Home supplies a validated legacy-storage snapshot through identity-fenced synchronous IPC. New Space partitions copy only missing legacy records; existing scoped records are never replaced. Viewport and Preview Workspace layouts also use scoped keys. This prevents independent pages from replacing a sibling's whole persisted Store snapshot.

Chat messages, unsent drafts, pending attachments, selection and undo caches remain page-local runtime state. They survive Tab switching because the page remains alive; they are not promised to survive closing/reloading a page or restarting the application. Saved Space content and conversation execution/history remain Server-authoritative. Application preferences such as language, input tools, recent-history count, World visibility and MiniMap visibility use a fixed-key main-process IPC bus. Desktop renderers read the authoritative synchronous snapshot and retain preferences only in their in-memory Stores or i18next; they neither persist global preference replicas in localStorage nor generate synthetic storage events. The canonical preference writer persists through main before changing local UI state. Recipients treat IPC notifications as invalidations and reread the current value without supplying legacy data, rather than trusting the notification payload. A queued old notification therefore cannot replace an acknowledged newer write. Snapshot failures are logged and thrown. Incoming World and MiniMap visibility updates set Store state directly, and incoming language changes update i18next without invoking the outbound writer or localStorage caching. Explicit language selection in Settings persists before changing the local interface. This one-way hydration prevents IPC feedback loops. The same preference adapter preserves localStorage persistence and native storage-event subscriptions in browser deployments.

Only Home supplies legacy global preferences. Main atomically persists previously missing preferences before acknowledging migration, then notifies already loaded renderers, including Shell. Home removes obsolete global localStorage keys only after successful acknowledgement; failed migration leaves them available for retry. Shell never cleans the shared legacy storage, so migration is independent of Shell/Home startup order. Space bootstrap copies only missing legacy metadata and removes obsolete global replicas without using them as preference input. Initial Store and language hydration reads main directly, so a reopened partition cannot restore a deleted preference.

The entry point loads the content application lazily, so Shell does not initialize content Stores or attempt persisted-version migrations through the content-only writer. Incoming tool or chat preference deletion resets only persisted fields to defaults without resetting transient tool selection or writing those defaults back to main.

On Home and Space mount, the content hook installs preference subscriptions before rereading World and MiniMap visibility and rehydrating tool and chat preferences. This reconciles changes or deletions made after module initialization but before React effects mount, without outbound writes or resetting transient tool state. Read failures are reported while keeping the subscription available for later recovery; browser startup is unchanged.

Tool and chat preferences reuse Zustand persistence for hydration, version migration, and browser storage. Desktop mutations use a shared write-before-notify boundary: read and migrate the current main-process value, apply the requested update to that authoritative state, persist changed preference fields, and only then notify local Store subscribers. Writes include the previously read serialized value; main atomically rejects a conflicting replacement with explicit retry feedback instead of overwriting a concurrent edit. No revision counter or additional persistent metadata is needed. Transient tool selection is applied locally without persisting a preference record. A pending invalidation therefore cannot let an unrelated tool action overwrite newer settings, and failed writes preserve the previous renderer state and show an error toast. MiniMap write failures likewise preserve desktop visibility; browsers retain their existing in-memory fallback when localStorage is unavailable.

The shared tool/chat persistence boundary logs failures without depending on UI components. Before importing App and initializing content Stores, the lazy content entry injects the existing danger-toast reporter for both initial hydration and later mutation errors. Shell does not initialize this content-only boundary.

The recent conversational Agent identity is also an application preference: Home migrates `huabu.recentConversationAgentProfile.v1`, new Space partitions hydrate it from main, and incoming invalidations update only the remembered identity without changing existing conversation bindings. Routine preference reads use validated synchronous single-key IPC and never transfer legacy chat, layout, or viewport records; the full legacy snapshot is reserved for renderer bootstrap. Once a pen has been observed, subsequent pen input returns before reading or writing preferences.

Content reports still carry internal activity/error metadata and keep Space titles synchronized, but the Shell does not present those summaries as Tab status. Existing Question nodes and Chat views own task progress, completion and error presentation. Lifecycle errors remain available to the main process for safe close/reload handling; they are not conflated with task errors in the Tab strip.

Content renderers compare computed report fields before sending, so dragging, panning, or streamed message updates that do not change title, running state, completion identity, or error do not produce duplicate reports. Main also skips unchanged reports before broadcasting snapshots. Opening Settings from Shell or the native macOS Settings menu (`Cmd+,`) explicitly focuses the active content WebContents before dispatching the modal command, handing native keyboard input to the content view.

## 5. Verification

The content root tracks Space activation from the existing main-process Tab snapshots in a renderer-local Store. Both reactive and imperative question-view predicates require this activation in addition to an expanded Preview panel and matching inner tab. Background completion remains unread until the Space is activated, without unmounting retained previews; browser behavior is unchanged. Activation starts unconfirmed and an older initial snapshot cannot override a newer subscription event.

Desktop save failures retain the original error in logging and show an Error cause's message in both the toast and main-process acknowledgement, falling back to the outer message when no Error cause exists. Preference tests cover both startup orders, durable migration, migration failure, no desktop localStorage caching, authoritative reads after stale notifications, and browser compatibility; Space-scoped metadata is preserved.

Desktop IPC notifications hydrate World visibility, MiniMap visibility and language from main; native storage events are not a desktop preference source, even between Home and Shell. Browser subscriptions read current localStorage rather than historical event payloads. Missing toggle values are disabled, and missing or unsupported language values do not replace the active language.

Explicit desktop language choices must persist through main before i18next changes the interface. Browser choices use i18next's existing best-effort localStorage cache rather than the mandatory desktop preference writer, so unavailable storage does not prevent an in-memory language change.

`pnpm --filter @huabu/desktop test` covers identity deduplication, lazy recovery, save failure/timeout handling, Workspace transitions, completion signals, and IPC ownership. The web tests cover navigation-state preservation, scoped persistence, and existing save/Store compatibility.

After the normal workspace dependency builds, `pnpm --filter @huabu/desktop test:tabs` starts an isolated Server and Vite instance and drives real Electron content views through Playwright. It creates temporary Workspaces, verifies draft/document isolation, retained selection and viewport, usable undo/redo after switching, cross-partition preference and language synchronization, save refusal and persisted content on close, five simultaneous Spaces, lazy restart recovery and Workspace switching, and cleans up its temporary processes and data. It prints warm-switch timing and process memory samples; these samples are observations, not fixed product limits. `HUABU_TABS_SCREENSHOT` optionally names a Shell screenshot output file; a sibling `-content.png` captures the active native content view separately because Shell page capture does not composite child views.
