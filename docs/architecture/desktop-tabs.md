# Desktop Space Tabs

The Electron desktop window hosts a persistent Home page and one independent `WebContentsView` per opened Space. They share one Server and one active Workspace. Browser deployments retain the existing single-page router behavior.

## 1. Ownership

```text
Electron main
  ├─ shared Server
  ├─ DesktopTabs: identities, activation, save coordination, recovery
  └─ BrowserWindow
       ├─ Shell renderer: window chrome and Space Tab strip
       └─ WebContentsView × N: Home and independent Space applications
```

The main process is authoritative for Tab order, the active identity, loading/error state, background activity, and session restoration. The Shell and loaded content pages subscribe to snapshots and send validated operations through preload. A Space page retains its existing single-instance canvas, chat, history, preview, selection, and gesture Stores; no Store is shared between content pages.

Home cannot be closed and remains the only renderer allowed to coordinate Workspace activation. Space identities are deduplicated within the active Workspace. Opening an existing Space activates its page instead of navigating or reloading another Space.

The content views are sandboxed, use context isolation, and disable Node integration. Each Space uses a persistent Chromium session partition keyed by Server, Workspace and Space identity. Independent connection pools prevent several Spaces' SSE streams from exhausting Chromium's six HTTP/1.1 connections per origin and blocking further Spaces or saves. Home and Shell keep the default session. Every partition receives the same external-preview response-header policy, and the existing remote Basic-auth handler reuses in-memory credentials once per new renderer while still prompting on a rejected credential. Hidden views remain alive with background throttling disabled; v1 does not automatically discard, suspend, split, or detach Tabs.

## 2. Navigation and chrome

The Shell owns the 36px window title/Tab strip: Home, Space Tabs and the open-Space button, with icon-only application actions anchored at the far right. Settings and the separate Workspace button immediately to its right remain visible in both Home and Space Tabs. All Tab-strip icon controls reuse Common Button's medium sizing for 16px glyphs and at least 28px click targets; the strip height remains 36px and Space title text retains its existing compact sizing. Content views occupy the area below it; their `WindowChrome` is suppressed. Desktop Home does not repeat the standalone logo/application-name header. Its content header contains only the Spaces heading and existing Space import/create actions, with neither Workspace selection nor Settings mixed into page actions. The browser keeps its original standalone header and list heading. Existing Settings, menus, Chat, previews and other popovers remain inside the content renderer; ordinary Shell DOM cannot overlay a native content view.

Home is pure navigation and does not open a menu. Clicking the persistent Workspace button, or pressing ArrowDown on it, activates Home and opens the Workspace menu, including when invoked from a Space. The Shell sends its measured button anchor through the existing validated Home-menu command; main owns the menu state and relays the position to Home and Shell. The menu is rendered by the persistent Home router root using Common Popover and menu items, directly below the title strip rather than behind a native content view. It lists recent Workspaces with a check on the active identity and truncates secondary paths inside a viewport-bounded 320px panel, with no path/count hover tooltip. Escape and selections return focus to the Shell's Workspace button; outside clicks dismiss without stealing focus, and Tab activation, Settings, saves and reload close the menu. Recent selections reuse the Workspace Store activation/save barrier. Open Workspace always links to the existing Home switch page at `/setup`, regardless of native picker support; visiting that page does not itself activate a Workspace or close existing Space Tabs. Folder picking and manual path entry remain owned by that page. During activation, Home shows the existing Workspace loading screen; failures use the Store's localized error via a toast. Read-only connections can inspect the current Workspace but cannot switch it.

Home is an icon-only navigation Tab with an accessible name and no visible label. Space Tabs show only the title and close button, with a neutral active highlight. Loading, running tasks, completion and task errors do not add icons, change the title color, or add status text to the accessible name. Task state remains inside the Space. Operation failures still use the existing Shell error feedback; renderer crashes and page-load failures produce a separate native error dialog rather than decorating the Tab.

The never-unmounting router-root navigation blocker diverts cross-Space navigation into `DesktopTabs.open`, preserving the destination query, fragment and one-shot router state. Same-Space node links remain local. Native application links and new-window requests also route through the Tab manager instead of replacing a Space renderer's immutable identity or opening another application window. Returning to the list or Workspace setup activates Home. Home's `/` landing stays `/spaces`, even when World is enabled; World still opens through its existing navigation entries as a Space Tab.

The retained Home list refreshes after local Space creation/import and when Home becomes active again, including after changes made in another content renderer. Ordinary status snapshots do not repeatedly fetch the list. Refreshes retain existing cards and fence responses by request generation and Workspace identity, so an older request cannot replace a newer list or publish another Workspace's count.

Native macOS menu commands and diagnostics target the active content renderer. Editing roles continue to use Electron's focused WebContents. Folder pickers remain parented to the owning window. Fullscreen and update status are broadcast to the Shell and all loaded content pages. The Tab strip's Settings button routes through the existing command bridge to open the modal inside the active content page, not inside the Shell or a cross-view overlay. Home has no duplicate Settings trigger; a Space's existing App menu remains available.

`Cmd/Ctrl+T` selects Home, `Cmd/Ctrl+W` closes the active Space Tab, and `Ctrl+Tab` / `Ctrl+Shift+Tab` cycle Tabs. Reload shortcuts drain saves before reloading the active page. DevTools shortcuts target the active content page. The Tab strip also supports arrow, Home and End keyboard navigation. Keyboard-driven strip activation explicitly targets Shell focus through the validated activation request and refocuses the selected Tab after acknowledgement; ordinary clicks continue to focus the content page.

## 3. Saving and lifetime

The native macOS Close menu action closes the active Space Tab only when the main window is focused. A focused auxiliary window, including the remote sign-in prompt, closes normally without touching the main window's Tabs; without a focused window the action does nothing.

Closing a Tab is an acknowledged operation, not a fire-and-forget renderer destruction. The main process sends an identity-fenced save request to the owning page. The page freezes user input, blurs the active editor, uses `saveCanvasForSubmission` to flush and verify structural/content writes, and flushes viewport and Preview Workspace state. Only a successful acknowledgement permits destroying the view. This reuses the existing save pipeline and its version-conflict and restored-content checks.

The saving overlay is shown only while a Space's save is pending for more than 150 ms, and disappears as soon as that save settles. Home has no Space to save and never shows this overlay. Opening or activating a Tab does not initiate a save. Input freezes synchronously before editor blur and remains frozen independently until the main process resumes or destroys the page, so hiding the overlay does not reopen an editing window after acknowledgement. A capture-phase guard installed before React's global shortcuts blocks user input, the entire document body is inert to include portals, and native menu callbacks consult the same freeze flag. Workspace activation after the save barrier uses its existing loading UI rather than retaining a misleading saving message. When visible, the overlay is opaque and covers the content viewport, so an underlying Workspace/Space loading screen cannot show a second overlapping progress message. The underlying page stays mounted and retains its runtime state.

Save rejection or a 15-second acknowledgement timeout retains the page and resumes input. Repeated close requests share one pending operation. A save acknowledgement from another page or subframe is rejected. An unavailable renderer requires an explicit warning confirmation before its Tab is discarded; reload remains available through the existing keyboard shortcuts, not an extra Tab button.

Window close, application quit, and explicit update installation coordinate saves across every loaded content page through the same pending preparation. A quit in progress is not approval to destroy the window: repeated quit and window-close events remain prevented until saves succeed. Closing a window without quitting clears its prepared state so a later window must save independently. All acknowledgements settle before a failed operation resumes the pages. If healthy pages save successfully but a renderer is unavailable, including Home, shutdown requires explicit confirmation before discarding the unavailable pages; cancelling keeps the pages and resumes healthy input. Healthy save failures still block shutdown, and Workspace changes never offer this discard escape hatch. The existing cooperative Server shutdown starts only after saving succeeds or the unavailable-page discard is confirmed. Remote mode also performs the save barrier even though Electron owns no local Server. An install failure cancels and resumes only a successfully prepared quit; a rejected competing quit/update request must not release another Tab close, reload or Workspace-change operation's lock.

Closing or switching a Tab never invokes Agent Stop. Server-owned accepted invocations continue until settlement or explicit cancellation; reopening uses the existing history/stream attachment paths. Quitting the local application still shuts down its Server: restoring Tabs is not a promise to recover in-flight Agent execution after process exit.

Workspace changes are initiated from Home, save all content pages, retain the old Workspace's Tab session, and destroy its Space views before activating a new Workspace. No page from the previous Workspace is left able to issue writes. Home clears its ready identity during activation and commits the authoritative Workspace information before refreshing the recent registry. A registry-refresh failure still reports an error but cannot revert the active identity. A rejected activation or information response triggers a Server identity check; only a confirmed active Workspace can restore a Tab session, including the old session if the Server confirms it remains active. Main rejects identity registration until the change has ended instead of queuing potentially stale identities. If confirmation also fails, Home remains unconfigured with an error and restores no Space pages.

If the initial Workspace save barrier fails, the Store retains the current Workspace identity and records the failure for inline feedback. Both path selection and recent-Workspace selection on `/setup` also show the existing danger toast, matching the Home Workspace menu.

If Home fails after the Workspace save barrier has completed, main releases only the abandoned Workspace transition's lock and keeps the Workspace identity unset. Reload and confirmed shutdown remain available. Home must become ready and confirm the active Workspace through Server initialization before registering an identity and restoring its session; main never guesses the previous identity. A Home failure during the save barrier does not release that barrier early, and readiness is rechecked before destroying Space views. Home failures never unlock an unrelated Tab close, reload or shutdown operation.

Successful Space deletion invalidates pending list requests before removing the card and starts a background refresh. Responses captured before deletion cannot restore the deleted card or overwrite the updated count.

## 4. Persistence and status

The main process atomically replaces a fixed `desktop-tabs.json` file under Electron `userData`. Session records are keyed by Server identity and Workspace identity; local Server identity deliberately excludes the ephemeral loopback port. Session records contain only ordered Space identities and the active Space; application preferences have a separate top-level record. Activation and closing persist the intended session before committing destructive runtime changes, so a filesystem error keeps the original Tab and surfaces the failure. Restoration follows successful Home Workspace initialization and creates lazy entries; only the active Space view is loaded until another Tab is selected.

Space-local chat binding/model metadata, conversation directory/title intent and panel state use Workspace/Space-scoped localStorage records inside the Space's partition. Before Stores initialize, Home supplies a validated legacy-storage snapshot through identity-fenced synchronous IPC. New Space partitions copy only missing legacy records; existing scoped records are never replaced. Viewport and Preview Workspace layouts also use scoped keys. This prevents independent pages from replacing a sibling's whole persisted Store snapshot.

Chat messages, unsent drafts, pending attachments, selection and undo caches remain page-local runtime state. They survive Tab switching because the page remains alive; they are not promised to survive closing/reloading a page or restarting the application. Saved Space content and conversation execution/history remain Server-authoritative. Application preferences such as language, input tools, recent-history count, World visibility and MiniMap visibility use a fixed-key main-process IPC bus. Desktop renderers read the authoritative synchronous snapshot and retain preferences only in their in-memory Stores or i18next; they neither persist global preference replicas in localStorage nor generate synthetic storage events. The canonical preference writer persists through main before changing local UI state. Recipients treat IPC notifications as invalidations and reread the current value without supplying legacy data, rather than trusting the notification payload. A queued old notification therefore cannot replace an acknowledged newer write. Snapshot failures are logged and thrown. Incoming World and MiniMap visibility updates set Store state directly, and incoming language changes update i18next without invoking the outbound writer or localStorage caching. Explicit language selection in Settings persists before changing the local interface. This one-way hydration prevents IPC feedback loops. The same preference adapter preserves localStorage persistence and native storage-event subscriptions in browser deployments.

Only Home supplies legacy global preferences. Main atomically persists previously missing preferences before acknowledging migration, then notifies already loaded renderers, including Shell. Home removes obsolete global localStorage keys only after successful acknowledgement; failed migration leaves them available for retry. Shell never cleans the shared legacy storage, so migration is independent of Shell/Home startup order. Space bootstrap copies only missing legacy metadata and removes obsolete global replicas without using them as preference input. Initial Store and language hydration reads main directly, so a reopened partition cannot restore a deleted preference.

The entry point loads the content application lazily, so Shell does not initialize content Stores or attempt persisted-version migrations through the content-only writer. Incoming tool or chat preference deletion resets only persisted fields to defaults without resetting transient tool selection or writing those defaults back to main.

Tool and chat preferences reuse Zustand persistence for hydration, version migration, and browser storage. Desktop mutations use a shared write-before-notify boundary: read and migrate the current main-process value, apply the requested update to that authoritative state, persist changed preference fields, and only then notify local Store subscribers. Writes include the previously read serialized value; main atomically rejects a conflicting replacement with explicit retry feedback instead of overwriting a concurrent edit. No revision counter or additional persistent metadata is needed. Transient tool selection is applied locally without persisting a preference record. A pending invalidation therefore cannot let an unrelated tool action overwrite newer settings, and failed writes preserve the previous renderer state and show an error toast. MiniMap write failures likewise preserve desktop visibility; browsers retain their existing in-memory fallback when localStorage is unavailable.

Content reports still carry internal activity/error metadata and keep Space titles synchronized, but the Shell does not present those summaries as Tab status. Existing Question nodes and Chat views own task progress, completion and error presentation. Lifecycle errors remain available to the main process for safe close/reload handling; they are not conflated with task errors in the Tab strip.

Content renderers compare computed report fields before sending, so dragging, panning, or streamed message updates that do not change title, running state, completion identity, or error do not produce duplicate reports. Main also skips unchanged reports before broadcasting snapshots. Opening Settings from Shell explicitly focuses the active content WebContents before dispatching the modal command, handing native keyboard input to the content view.

## 5. Verification

The content root tracks Space activation from the existing main-process Tab snapshots in a renderer-local Store. Both reactive and imperative question-view predicates require this activation in addition to an expanded Preview panel and matching inner tab. Background completion remains unread until the Space is activated, without unmounting retained previews; browser behavior is unchanged. Activation starts unconfirmed and an older initial snapshot cannot override a newer subscription event.

Desktop save failures retain the original error in logging and show an Error cause's message in both the toast and main-process acknowledgement, falling back to the outer message when no Error cause exists. Preference tests cover both startup orders, durable migration, migration failure, no desktop localStorage caching, authoritative reads after stale notifications, and browser compatibility; Space-scoped metadata is preserved.

Desktop IPC notifications hydrate World visibility, MiniMap visibility and language from main; native storage events are not a desktop preference source, even between Home and Shell. Browser subscriptions read current localStorage rather than historical event payloads. Missing toggle values are disabled, and missing or unsupported language values do not replace the active language.

`pnpm --filter @huabu/desktop test` covers identity deduplication, lazy recovery, save failure/timeout handling, Workspace transitions, completion signals, and IPC ownership. The web tests cover navigation-state preservation, scoped persistence, and existing save/Store compatibility.

After the normal workspace dependency builds, `pnpm --filter @huabu/desktop test:tabs` starts an isolated Server and Vite instance and drives real Electron content views through Playwright. It creates temporary Workspaces, verifies draft/document isolation, retained selection and viewport, usable undo/redo after switching, cross-partition preference and language synchronization, save refusal and persisted content on close, five simultaneous Spaces, lazy restart recovery and Workspace switching, and cleans up its temporary processes and data. It prints warm-switch timing and process memory samples; these samples are observations, not fixed product limits. `HUABU_TABS_SCREENSHOT` optionally names a Shell screenshot output file; a sibling `-content.png` captures the active native content view separately because Shell page capture does not composite child views.
