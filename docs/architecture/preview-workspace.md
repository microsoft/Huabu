# Preview Workspace

Preview Workspace is the only right-side presentation surface on a Canvas page. It hosts node previews, webpage URL tabs, and unbound Chat conversations in one or two tab groups while the Canvas remains mounted in the centre.

The implementation originated in the [Unified Preview Workspace proposal](../proposals/unified-preview-workspace.md). This document is authoritative for the shipped system; the proposal is retained as design and migration history.

## 1. Ownership boundaries

Large canvas Note, PDF, and Web nodes also support an inline reading layer, independently of Preview Workspace tabs. The activation thresholds and selection rules live in [canvas-zoom-rendering.md](./canvas-zoom-rendering.md). Canvas PDF reading reuses the virtualized page pipeline without preview search/capture/header controls; canvas Web reading uses an isolated original-site iframe rather than the expanded preview's extracted reader. Inline reading never opens a tab or claims Preview Workspace keyboard shortcuts.

Preview Workspace owns presentation topology: open tabs, tab order, active tabs, groups, split ratio, transient inspection state, and runtime requests addressed to a tab.

`canvasStore` owns Canvas document state and the command pipeline. Preview renderers read live nodes from that store rather than copying node content or labels into tabs.

`chatStore` owns conversation state keyed by `threadId`: messages, drafts, paged display-history state, streaming state, binding, model settings, compose mode, and pending attachments. It persists thread identity metadata (binding, built-in settings, and compose mode) without an entry limit so every independent Chat tab rehydrates with the same agent after reload; messages, history pages and cursors, drafts, streaming state, and attachments remain runtime-only. Preview Workspace stores only the target needed to select a renderer.

New Chat and New Agent Node both use `conversationPreparation.createConversation` to initialize a known-empty, loaded thread. Node creation adds the spatial owner without changing the conversation initialization contract. Restored, duplicated and existing conversations still hydrate their actual history; empty authored content alone is never proof of empty history.

`conversationPreparation` is the shared preparation boundary for both presentations: Agent selection, working-directory intent, control admission and execution locking. Node-bound drafts retain their server-owned node configuration; unbound Chat directory intent is persisted locally by Canvas/thread address until canonical external realization captures it. This adapter preserves existing storage ownership instead of maintaining two authoritative copies. Send, warm-up and mode/model/config controls all resolve the same preparation. A read-only cached-meta response includes frozen execution binding and cwd even when live metadata or the original Profile is unavailable. Existing external conversations wait for those facts before allowing preparation edits; pre-realization cache reads are revision-fenced against a newer realization. Failed realization stays locked when its outcome is ambiguous, and a successful no-record cache read permits retrying preparation. Runtime-capability changes remain distinct from immutable launch identity.

The working-directory popover shows the complete effective path as its primary content without truncation, a duplicate Profile summary, or a copy button. A separated, subdued Runs on row identifies the Agentlet using the same canonical `displayName` as Settings, without substituting the hostname or stripping platform details; missing device information is explicit. Visual hierarchy comes from the labeled row and typography, not a different device name. It reuses Common Button, TextArea, Popover and Tooltip plus `useAutoSizeTextArea`: read-only and editing modes share one path field, which occupies one rendered line unless the path wraps, and header actions reserve their geometry so entering or cancelling editing does not shift the field. Narrow popovers place the reserved action group on a second header line in both modes rather than squeezing the title or switching text actions to icons. Change enters inline editing; Done or Enter explicitly saves, Cancel or Escape discards the edit, and Default clears only the conversation override. Blur and outside dismissal never save. Enter during IME composition does not commit, save failures retain the draft with an inline error, and pending saves block duplicate writes and dismissal. Non-editable conversations show a lock tooltip rather than edit controls; only a confirmed realized execution is described as having a fixed directory, and its persisted path remains authoritative. The folder tooltip contains only the localized Working directory label; complete paths and device information remain in the click-open popover rather than being duplicated on hover. The shared connected-device resolver preserves exact-ID and unambiguous legacy-hostname matching used by Settings. Runs on names the machine that owns the path without guessing whether it is local or remote to the browser.

The working-directory popover uses consistent 12px typography for its title, path, actions and device metadata. The title is a normal-weight muted label; the full path retains the default foreground color in both read-only and editing modes.

During editing, the popover offers the shared Common `FolderPickerButton` only when the selected Agentlet is confirmed to own the native picker's filesystem; the identity contract is documented in [Agent Profiles](./agent-profiles.md). Selecting a folder updates the draft only, and Done still commits it. The picker slot reserves width and height in read-only mode to prevent edit-mode reflow. Picking blocks dismissal and save actions; cancellation preserves the draft, and failures appear inline. Settings `PathInput` reuses this same button and target validation while retaining its single-line form layout.

Warm-up and runtime controls are queued FIFO per Canvas/thread address, including their cache refreshes. A failed operation reports its error without discarding later choices, and different conversations proceed independently. Queued work keeps launch edits and sends gated until it drains, while controls remain available during streaming. Selector optimism starts with its queued RPC; failure rollback occurs before its cache refresh so it cannot overwrite a later choice.

The composer stays editable while initial history loads or fails, but button, keyboard and panel submission paths remain gated until history is ready. Initial-load failures expose an explicit retry without pretending the history is loaded or discarding a draft. Saving Chat as a Question retains its thread identity and working directory.

Chat history hydration requests the newest configurable number of complete display turns, three by default, from the paginated agent-history endpoint. An active user-started tail counts as a display turn, while continuation records attach to their preceding turn. `Recent chat turns` also sizes the initial presentation window: ordinary opening or reactivating a Chat selects the latest complete turns before message cards mount or Activity Effects reconnect, even when the runtime cache contains the entire conversation. Server display-turn identities keep continuation messages together; live user inputs establish boundaries until history reconciliation supplies server identities. The active turn is never split or discarded.

The explicit Show earlier turns action first reveals another batch of cached-but-hidden turns; only after reaching the cache boundary does it retrieve and prepend the preceding server page. Cached hidden history and the server cursor/has-more state are separate. The client does not retrieve the entire server conversation merely to hide it, and narrowing the presentation window does not discard loaded pages, reset history hydration, or modify drafts, attachments, permissions or streams. The global preference is persisted separately from thread state and applies to future hydration, expansion and recent-window selection.

While a Chat remains visible, new turns extend its presentation window. A genuine stream `done` event records a thread-owned completion identity; it is not inferred from loading becoming false, tool completion, a permission wait or transport termination. At completion, a list following latest compacts to the latest configured turns and stays at the bottom. Compaction pauses while reading older content or following explicit history/search/reading-return navigation. The explicit bottom action may compact and resume following; ordinary activation also resets the window. Background completion never scrolls a hidden or unrelated view. This bounds displayed turn count at safe completion points, not the size of an individual turn or retained cache.

Newest-page refreshes after reconnect or stream completion merge from stable server turn identities so previously fetched older pages remain available while active-tail messages converge with their persisted form. A stale pagination cursor causes a newest-page reload because the server generation changed; ordinary expansion failures leave visible history intact and expose a retry action.

Within a mounted Chat renderer, the thread-scoped composer owns the draft subscription. Draft updates therefore rerender the composer without invalidating `MessageList`; unchanged historical message cards are memoized, while message-array updates and streaming changes continue through the history tree normally.

Chat prose uses the shared Milkdown factory for both streaming updates and completed messages. Explicit `latex` fences (case-insensitive) behave like `tex`: highlighted source only, including formulas, custom macros and math delimiters inside the fence. They are not document previews or an alternative spelling of display math. Outside code, `$...$`, `$$...$$`, `\(...\)` and `\[...\]` retain mathematical rendering and the existing KaTeX/sanitization boundary. The factory redirects original code AST nodes before Crepe converts explicit display math into its internal LaTeX block representation; drag editability does not choose the syntax's meaning. Original fence language/body survive Markdown serialization for fragment extraction, dragging and Add as note; whole-response Copy still uses the original assistant Markdown, and block Copy uses the source body. See [the shared Note factory](./note-node.md#4-two-surfaces-one-factory).

The main chat textarea grows with its rendered content from a minimum of two text lines to a maximum of ten, including soft-wrapped lines. Content beyond ten lines scrolls inside the textarea without chaining scroll to the conversation. Content changes, restored or cleared drafts, and composer width changes remeasure its height; shrinking or clearing the draft reduces it back toward the two-line minimum. Main Chat and fragment-comment input share `useAutoSizeTextArea`, which measures content including field borders and observes parent width changes; each surface retains its own CSS height limits. Quoted-comment editors retain their separate sizing policy.

After history hydration, a conversation with no messages displays a single subdued, localized AI-content accuracy disclaimer centered in the otherwise empty message area. The disclaimer disappears as soon as loading starts or any message exists, and the composer retains no persistent disclaimer text or icon.

Rendered assistant text supports fragment comments in the active Chat, including during streaming, permission waits, and initial history hydration when text is already visible. Comment availability is independent of the completed-response action buttons; hidden or collapsed Chat panels still disable it. A native text selection may span lines or paragraphs within one Milkdown text segment, but never separate messages or tool/thinking surfaces. While a mouse selection is in progress or a native text selection remains inside the preview, incoming Markdown updates are deferred for that preview only; the latest content is applied when the selection clears or selection reporting is disabled, without pausing generation. Comment opens an editor with a capture-time quotation that remains unchanged by subsequent source updates; its sole confirmation is **Add to input**, with empty-comment prevention. Escape or an outside pointer press dismisses the editor without changing the composer; there is no separate Cancel button. Selection, comment editing and insertion never invoke generation. Add to input stages a structured quoted comment in the owning thread's composer, preserves its ordinary text draft, closes the editor and requests that thread's composer focus. Several quoted comments and free-form instructions can be combined before ordinary Send.

The selection popover offers **Copy**, **Add as note**, and **Comment** as icon buttons with localized tooltips and accessible names. The selection toolbar and the comment editor's Add to input action use the shared Button's compact `sm` size. The editor places a neutral ghost upward-arrow icon button matching the Chat composer's send icon inside the bottom-right edge of its Common TextArea, with text padding reserved for the control and a localized Add to input tooltip and accessible name rather than a Send label. The button is disabled for empty or whitespace-only comments; Enter submits the form without sending a message, Shift+Enter inserts a newline, and Enter during IME composition does not submit. Copy writes only the selected plain text and reports clipboard failures with retry available. Add as note serializes only the selected ProseMirror slice as Markdown, retaining marks, links and enclosing block/list/code structure, then uses the same `canvasStore.addNode` path and `user-from-chat` thread origin as the whole-response action. Neither action adds neighboring context or comments, modifies the source, changes the input draft, or invokes generation. Successful copy or note creation dismisses the popover. The existing response-bottom Copy and Add as note buttons remain unchanged and still act on the entire visible response.

Mouse selections anchor the popover at the release coordinates with a 4px horizontal and 8px vertical offset, including releases outside the preview after a drag begins inside it. The popover does not follow subsequent mouse movement; scrolling repositions the anchor with the selected content. Keyboard selections anchor at the native selection's focus endpoint, including backward selections. The shared Popover retains viewport clamping.

Native drag completion or cancellation clears the mouse-selection gesture hold even when the browser omits `mouseup`. The preview then rechecks the actual text selection: a genuine range keeps deferred Markdown intact, while no selection releases the latest pending content.

The comment editor separates the selected passage from the input with a subdued neutral inset background (`bg-hover/60`) and a 2px left quotation rule using `border-edge-default`, with 8px between the rule and muted text instead of a quotation icon. The same quotation rule appears in composer and sent-message cards. The editor retains 12px outer padding, uses an 8px gap between the quotation and input, and reduces quotation vertical padding to 6px. The quotation and shared TextArea use matching medium-radius corners, with a circular ghost add button using the Chat composer's `sm` pill sizing and a larger-radius outer panel. The add button has a transparent background and muted arrow at rest, with a neutral background on enabled hover. It is inset 4px from the input's right and bottom edges, with 36px right text padding to prevent overlap; its minimum 24px square hit area is unchanged. The input overrides only its local focus styling to use a single semantic info-colored border without an additional ring; Common field defaults remain unchanged. There is no separate icon header. The localized Quoted passage caption is screen-reader-only rather than visible text. The editor and inserted quotation trim whitespace only at the boundaries of the entire selected text, preserving internal spaces, indentation and blank lines; Copy and Add as note retain the original selection content. Quoted text uses compact 12px typography, wraps long tokens, and scrolls within a 96px maximum height without chaining scroll to the conversation. The comment TextArea grows from two to six rendered text lines, including soft wraps, with padding and borders added to those limits; larger comments scroll inside the field without scroll chaining, and shortening or clearing content shrinks it again. The input uses a concise localized Add a comment placeholder and preserves internal line breaks when staged.

The composer and user messages share `QuotedCommentCard`: a quotation and its associated comment grouped within one shallow neutral background, with no outer border. The quotation is a single-line ellipsis preview within a width-constrained, shrinkable wrapper, including in right-aligned sent messages. The full original text remains in its accessible content and the shared Common Tooltip, available on hover or keyboard focus. Quote tooltips are constrained to the viewport, remain open while the pointer enters their scrollable content, and support wheel scrolling; Arrow/Page/Home/End keys scroll the quote while its trigger is focused. The comment wraps in full without truncation. Neighboring context remains in the structured snapshot for agent rendering but is not shown in either UI surface. Composer comments display as wrapping text by default; clicking or keyboard-activating the comment opens a Common TextArea only for that edit, preserving existing line breaks. Blur or Enter finishes editing, Shift+Enter inserts a newline, and Escape restores the pre-edit value; Enter never sends and respects IME composition. An empty edit stays open with an inline validation message and blocks submission. Each composer quote has a circular neutral remove button overlaid at the top-right without taking layout space, revealed on card hover or keyboard focus and always visible on devices without hover; sent comments are read-only. Ordinary draft text stays in the textarea and quote-only messages can be sent. Prompt history navigation recalls both text and quoted comments and restores the unsent pair with its original local draft identities when navigating back.

The optional `quotedComments` wire field contains quote, contextBefore, contextAfter and comment strings, plus optional Note `source` metadata (`kind`, `canvasId`, `nodeId`, `snapshotRevision`). The shared zod schema trims outer quotation/comment whitespace and rejects empty values. The server preserves this field in `ChatEnvelope.user` and renders an escaped `<quoted_comments>` section through the canonical prompt builder shared by built-in and ACP agents; Chat quotes use assistant-passage wording, while Note quotes use Note-specific wording and source metadata. Quoted slash tokens never become invoked commands, and external commands typed in the ordinary textarea retain their lead-with-task path. The server history projection and browser hydration retain the same field, so reloaded user messages keep their cards without parsing generated template strings. Existing records without the field continue displaying their original text, including previously inserted plain-text comment templates; no backfill or new storage table is required.

Expanded Note rich text shares the Comment editor and selection actions, with an existing-conversation picker rather than Chat's fixed current thread. The picker reads the accepted recent-Canvas-conversation endpoint without updating it: a remembered owner is retained even when unavailable, a sole available owner defaults when no pointer exists, and ambiguous/empty choices require explicit resolution. Lookup errors expose retry and manual choice, never New. Internal Ask/Operate and existing external conversations are eligible regardless of streaming or removed Profile; missing/rebound owners and pending forks block staging. A Note Comment never creates or realizes an Agent. When the destination composer is already visible in an expanded Preview group, staging requests its focus without changing topology. Otherwise it leaves the source Note, tabs/groups, viewport and collapse state intact and shows a persistent dismissible notification naming the destination with **View input**. Only this explicit action opens/promotes the captured owner and focuses its composer. Notifications coalesce per Space/thread and retire when their pending draft entries are consumed/removed or the owner/Space becomes invalid. No hidden focus request is queued.

Original quotations and comments are never translated. The source message/segment and ProseMirror range remain transient capture data, not permanent annotation identities or raw Markdown offsets. Source changes and live/history ID reconciliation never rewrite staged or sent quotations. Unsent quoted comments are thread-local runtime draft state and disappear on reload; pending quote threads are pinned against inactive-thread cache eviction so hidden Note drafts remain available. Send captures a submission snapshot and immediately clears its text and quoted comments before asynchronous dispatch preparation, allowing the user to compose the next message. Durable turn acceptance never clears the composer again. A definitively rejected, busy or stopped submission before acceptance restores the snapshot only if both the current text and quoted-comment draft are empty; newer drafts are never overwritten. When restoration is blocked by a newer draft, the original submission remains a retryable local user message, including when preparation failed before the controller appended a user message; both paths share the same message projection so attachments, source selections and invoked skills remain intact. An ambiguous transport failure keeps the snapshot pending until acceptance reconciliation confirms acceptance or rejection, rather than restoring it and risking duplicate submission. Uploads and selection excerpts retain their existing acceptance-time consumption. Local quoted-comment draft identities are preserved on restoration but omitted from agent requests and history. Sent comments travel in the existing durable envelope and canonical rendered submission, with no separate annotation sidecar or two-way synchronization. Conversation titles and search use human-readable quotations/comments rather than model-only context.

`panelStore` owns and persists the outer right-column collapse state, owns the transient Preview fullscreen state, and owns thread-addressed composer focus requests. Opening a Preview target expands the right column; closing a tab does not delete its underlying node or conversation history. `MainLayout` treats the persisted collapse state as authoritative whenever no panel motion is active. A settled collapsed slot is zero-width and clips overflow, while an active open/close motion temporarily releases that clipping; interrupted startup hydration therefore cannot leave translated panel content visible over the Canvas in either persisted state. Fullscreen is intentionally not persisted across reloads.

```text
Canvas command -> canvasStore document -> Preview target resolves live node
User open     -> Preview Workspace  -> active tab/group
Chat renderer -> chatStore thread   -> messages, binding, stream state
Outer layout  -> panelStore         -> collapsed/open and composer focus
```

## 2. Persisted model

A workspace is scoped to one Canvas and contains semantic targets rather than renderer snapshots.

```ts
type PreviewTarget =
  | { kind: 'node'; canvasId: string; nodeId: string }
  | { kind: 'chat'; canvasId: string; threadId: string }
  | { kind: 'url'; canvasId: string; url: string };

type PreviewTab = {
  id: string;
  target: PreviewTarget;
  transient: boolean;
  lastActiveSeq: number;
};

type PreviewGroup = {
  id: string;
  tabIds: string[];
  activeTabId: string | null;
};

type CanvasPreviewWorkspace = {
  tabs: Record<string, PreviewTab>;
  groups: PreviewGroup[];
  activeGroupId: string;
  splitRatio: number;
  activationSeq: number;
};
```

`tab.id` is presentation identity. `isSamePreviewTarget` is the only authority for resource identity: node targets compare `{ canvasId, nodeId }`, Chat targets compare `{ canvasId, threadId }`, and URL targets compare `{ canvasId, url }` after HTTP(S)-only validation and normalization with `URL.href`. Paths, queries, and fragments remain part of URL identity. Open, replacement, and persistence parsing use the same normalization boundary; invalid URL targets do not mutate topology.

The first shipped model allows at most one tab for a semantic target across the workspace. Reopening a target activates its existing tab even when it belongs to the other group.

Titles are derived at render time. Node tabs use the current node label; Chat tabs derive their conversation label. URL tabs show the URL host with the full URL as their accessible name and tooltip, without fetching title metadata. Renaming a node therefore updates its tab without mutating workspace state.

Unbound Chat titles are durable thread host metadata, not tab properties. `ThreadRecord.hostMetadata.huabuConversationTitle`, written through `Agenetes.updateHostMetadata`, persists one current `{ title, source }`, with priority `user > generated > acp > fallback`; lower-priority updates are rejected rather than saved. When no higher-priority host title exists, reads may use the driver's current valid ACP session title; the last valid ACP title is persisted only as the current title with source `acp`, never as a separate candidate. Empty conversations display “New conversation”. Initialization attempts Huabu naming even when ACP is available, using the first user prompt and canonical utility/global-model routing. No usable model or generation failure retains ACP or the first-user fallback and permits a later turn/initialize to retry; title queries never perform paid generation. ACP validation accepts only nonblank, single-line strings whose normalized value is at most 120 characters, with no prompt-text or fixed-prefix filtering. Invalid raw or persisted ACP titles are ignored on query without mutation; invalid updates leave the current host title unchanged. There is no migration for the old unmerged candidate-field shape, and raw driver metadata is untouched. The same backend `ConversationTitleService` names Questions through their canonical node label and protected `conversationTitleSource` provenance instead of thread metadata; current node ownership takes precedence, without two competing title authorities. No hidden automatic title is retained after manual naming. The zod-free policy is available as `normalizeAcpConversationTitle` from `@huabu/shared/conversation-title`; manual title semantics and visual overflow handling are unchanged. The panel header and tab strip read the same Canvas/thread-scoped title cache; clicking the header enables inline rename, with Enter/blur to save and Escape to cancel. Renames before the first send are persisted locally as pending user intent and flushed once the server creates the thread; established names are server-owned.

One workspace-level coordinator batch-loads titles for all open Chat tabs, including unmounted tabs, without loading conversation history on initial hydration, target changes, and browser focus. The backend title service alone normalizes, filters, generates, ranks, and persists titles. The frontend caches the exact backend projection, including an empty or lower-priority result, without reapplying source arbitration or ACP filtering. Stream start/completion and title-bearing `session_info_update` events invalidate only the affected thread's cache; raw ACP titles never become display values directly. An invalidation during a query fences that response and queues one coalesced follow-up query after it settles; ordinary overlapping queries only deduplicate. The stream epoch restarts the bounded retry window for unresolved titles because generation can finish after the answer stream. Untitled realized conversations and pending manual edits can retry; untouched empty tabs do not poll. Stream events do not trigger an immediate all-tabs refresh. Queries started during a manual rename cannot overwrite its optimistic title or settled result; successful saves and rollbacks advance the local revision, while subsequent queries accept newer server facts. A rename during the first send that receives `404 thread_not_found` becomes locally persisted pending intent, just like a pre-send rename, and the existing refresh/stream path flushes it after durable creation. Other failed title requests expose a retry action.

Saving Chat as a Question transfers naming authority through canonical node creation: manual titles become user labels, nonmanual titles become automatic labels, and `conversationTitleSource` preserves provenance without a second title value. The server uses the latest effective backend title when the incoming label is not user/agent-protected. Without a current title, the existing node-creation fallback is unchanged. Thereafter the Canvas node, Preview tab, and Question chat header use only the node label; eligible late generation and ACP updates continue through the shared service's node writer, while manual or agent-owned labels remain protected. See [Question conversion](./question-node.md#3-node-lifecycle). Closing a tab remains non-destructive and does not add a conversation-history browser.

The zod-free shared title utility owns fallback extraction for the server and preprocessing: first Markdown heading, otherwise first nonempty line, with inline formatting removed and a 50-character cap, followed by common whitespace normalization. The frontend does not derive titles from submitted messages or loaded history; it displays “New conversation” until a backend title or local manual edit is available. Manual and ACP title limits remain unchanged. A successful title query attempts pending manual saves even when the response has no title: title absence is not proof that the thread is absent. `404` keeps pending intent without an error banner, and the workspace's finite retry window includes these pending entries; focus/reopen or a later stream can try again. No title operation creates an Agent session solely to name it.

## 3. Opening and target conversion

`openPreviewTarget` is the topology action. It opens or activates a target in the focused group, supports transient inspection, and delegates all ordering and group repair to the pure model.

`openPreviewNode` is the user-facing node adapter. It settles the previously active editable Note or Text when necessary, expands the right panel, opens the node target, and requests editor focus for an explicitly opened Note. Node opens are transient by default, including when options are omitted or empty; callers must pass `{ transient: false }` to request a permanent open. Browsing an existing permanent tab never demotes it. The lower-level `openPreviewTarget` topology action retains its permanent default for independent Chat, URL, and creation workflows.

After `CanvasPage` consumes a canonical Node deep link, nodes registered in `NodePreviews` open permanently through `openPreviewNode` with `{ transient: false }`; the semantic-target model activates an existing target across groups and promotes an existing transient target instead of duplicating it. Text, Audio, Frame, Space Preview, and other nodes without an expanded renderer remain Canvas-only. The retained URL query is independent from per-Canvas workspace persistence, so a restored tab is activated through the same deduplication and promotion path.

An existing Question conversation opens only when its live node already has a nonempty persisted `threadId`. The deep-link coordinator opens that node target and sends the tab-addressed one-shot `bottom` positioning request; `PreviewRenderer` then derives the conversation owner from the live Canvas node and ordinary Chat mounting hydrates existing history and Profiles. Deep-link handling never calls Question compose or thread-creation helpers, focuses the composer, acknowledges a result as viewed, realizes an ACP workload, spawns an Agent, binds or rebinds a Profile, or sends input. A Question without an existing thread is selected and focused on the Canvas without opening Chat.

Layers primary activation uses transient semantic node targets and the passive existing-Question contract. It opens or activates nodes registered by `hasNodePreview` regardless of whether Canvas is mounted, and it opens an existing Question target followed by the same tab-addressed `bottom` request. It does not reopen a node already active in any visible group, because `openPreviewNode` intentionally emits a fresh Note editor-focus request for explicit opens. Inactive and restored targets pass through `openPreviewNode` with `transient: true`, so browsing replaces the focused group's transient slot, revisiting a transient target does not promote it, and existing permanent targets remain permanent. Frame, legacy Group, idle Question, Agent-without-thread, and other unsupported rows remain Canvas-only; Frame disclosure is owned by Layers rather than Preview Workspace.

`openPreviewUrl` is the desktop document-link adapter. Expanded `NotePreview` and Chat's `MilkdownMessageCard` both explicitly select `linkActivation="plain"` and use `openDocumentLink`, which chooses desktop preview or external browser navigation through the existing Electron detection. Note supplies its source node ID and Chat supplies its source thread ID. In the web app, plain clicks open a browser tab without changing the workspace. On desktop, the adapter validates the URL, finds the matching source node or unbound Chat tab, promotes it, and opens a permanent URL tab in its group even when the other group is focused; a source Note is also settled before navigation. The source inspection slot is not replaced. Without a matching source tab, opening falls back to the focused group. Existing URLs are activated wherever their tab already lives. URL tabs use the ordinary move, split, merge, close, Canvas-switch, and unload persistence paths; they create no Canvas nodes or Chat threads.

Note and Chat links share the pointer cursor through `data-link-activation="plain"`. Activation is not inferred from callback presence: canvas `NoteNode` uses `modifier`, suppressing native plain-click navigation while allowing the event to bubble for node selection. Platform-modifier clicks open externally on both Note and Chat rather than invoking their host callback. All Milkdown link handlers suppress drag and repeated-click navigation, including surfaces without a callback; the first eligible stationary click opens synchronously and cannot be cancelled by a later double-click. See [Note link activation](./note-node.md#6-link-activation) for the shared gesture contract and single editable-editor link panel used by toolbar, shortcut, and hover. Expanded Note supports creating links from selected text and editing existing links; Chat remains read-only and has no link-edit form.

`openChat` activates the most recently used unbound Chat target or creates a new thread and tab when none exists. A new conversation always creates an independent `threadId` and snapshots the browser-local recent conversational Agent unless supplied another binding; a missing, deleted, or unavailable cached external identity uses the first selectable external Profile. Existing threads retain their persisted selection; Utility Agent changes and legacy Canvas-thread initialization do not alter conversational bindings.

Open to Side moves the existing semantic target into the other group instead of duplicating it and preserves whether the tab is transient or permanent. Saving an unbound Chat as a Question replaces that tab's target in place, preserving tab identity, position, messages, and draft continuity.

Canvas node double-clicks, Question toolbar compose or replay actions, search results, and connected-node navigation open transiently. New Chat opens are permanent.

After durable acceptance of a Lasso request, the destination Agent Node opens permanently in Preview Workspace and receives a tab-addressed `bottom` positioning request. This applies to continued and newly created conversations, with Ink or node-only selections. The previous tab stays in the background, including a transient inspection tab; an already-open destination is activated in its existing group and promoted instead of duplicated. No split or composer-focus request is created. Rejected, superseded, or cross-Canvas submissions do not reveal a tab, and a removed or rebound destination is not opened by a late acceptance.

## 4. Rendering and Chat sessions

Each group mounts its active tab plus at most one warm inactive tab selected by the greatest `lastActiveSeq`. The warm slot is a bounded runtime optimization rather than persisted topology: React 19 `Activity` keeps that tab's DOM and component state with `mode="hidden"`, cleans up its Effects while hidden, and restarts those Effects when the tab becomes visible again. Activity cleanup and closing a tab do not mark the page as unloading or terminate a thread-owned stream; only the browser page lifecycle suppresses unload-time transport errors.

PDF tabs retain view state in the warm slot, but discard the loaded pdf.js document proxy during Activity cleanup because `react-pdf` destroys that proxy's worker transport while hidden. Page rendering and text indexing remain suspended until the visible tab loads a fresh proxy.

Chat, Question, Note, Text, PDF, and Office tabs are eligible for the warm slot. Node eligibility follows the live node type, without a World-reference projection. Web, Audio, Video, and other node types are not retained because hidden native media or iframe work can outlive React Effect cleanup. Closing or replacing a warm tab, deleting its node, or advancing the slot to a more recently active eligible tab unmounts the old tree. Ordinary node previews retain the shared runtime scroll cache as their cold-restore fallback; Chat uses explicit best-effort reading return instead of automatic cold restoration.

`PreviewRenderer` resolves node targets against the current Canvas nodes. Ordinary nodes render through `ExpandedNodePanel`; Question nodes and unbound Chat targets render through `ChatPanel`. An ordinary node's summary and keywords are accessed through an icon-only AI Summary button in the existing content toolbar, next to connected-node navigation. It opens an anchored, height-bounded Common Popover without inserting a banner or moving the document. Closing the popover preserves the metadata and leaves its entry available to reopen; empty metadata reserves no entry. Node-specific controls continue to portal into the trailing header slot, so Web reload/external opening and PDF capture/highlight share the same toolbar as summary access.

Preview tabs own the primary display title. In Preview Workspace, Chat, Question, and ordinary node renderers suppress their duplicate static header title without adding a rename icon. Tab context menus use Common `DropdownMenu` and `DropdownMenuItem`, anchored below the tab, with text-only Rename, Close, and Keep Open for transient tabs. F2 requests editing directly; Shift+F10 or the context-menu key opens the same menu. Arrow keys navigate menu items and Escape restores tab focus. URL and deleted-node tabs omit Rename but retain Close. A rename request activates the addressed tab and passes a runtime-only nonce to its existing editor; the request is scoped to the group, tab, and semantic target, is discarded if group focus, activation, or the target changes, and is never persisted. It supersedes a deferred content-focus request for that tab. Chat waits for history hydration and its existing ownership/save guards before accepting a request. Double-click still pins transient tabs; an accepted rename still promotes them through the existing mutation callback.

Chat, Question, and ordinary node renderers share [`InlineEditableTitle`](../../apps/web/src/components/Common/InlineEditableTitle.tsx), composed from the common `Button` and `TextInput`. PreviewGroup provides a DOM slot in the active tab; the renderer portals its existing input into that slot with the full current title selected. While editing, the tab expands to a readable input width and hides its display label and Close control, without adding a content-header row. The portal keeps persistence and state ownership in the renderer and does not create a second rename implementation. The component owns focus/select, IME-safe Enter submission, blur submission, and Escape cancellation without duplicate blur commits. Enter and Escape restore focus to the initiating tab; blur submission does not steal focus from the clicked control. Callers retain draft state, identity resets, permissions, validation, and their existing node or conversation persistence paths, including conversation failure feedback and retry. Standalone panels retain their normal display title and click-to-edit interaction.

An active external Chat or Question reports its existing capability-cache status to its group's tab, scoped by tab ID and semantic target identity. The status is a 6px dot at the icon's bottom-right corner, with a background-colored ring; it occupies no extra title width. The existing Common tab Tooltip adds only a short localized status (Normal, Loading, or Load failed) on hover or keyboard focus, without an Agent name, technical explanation, error detail, or nested tooltip. Agent identity remains in the existing composer area. Status reflects capability-cache loading, not a live connection check; moving it adds no requests or workload realization. Internal Chat has no dot. Activity cleanup, switching targets, and closing clear the runtime report rather than displaying stale status on inactive tabs. A failed cache read without a usable snapshot shows its detail and a Common Retry button in Chat content, so recovery does not depend on hover. Standalone Chat retains its header badge using the same dot and short descriptions, with failure details and retry in content.

Save-as-Agent actions, connected-node navigation, and node-specific header portals remain in their existing content headers. An embedded ordinary-node header takes no space when it has no navigation or leading/trailing portal actions; both portal hosts remain mounted so controls can appear after content loads. A Preview Chat header is hidden when it has no save action or collapse control; its tab editor remains mounted independently. The node header retains its 10px leading inset (`px-2.5`), 14px navigation icon column with a 24px hit target, and `gap-1.5`, independently of the tab strip's spacing and width cap. Content tools, search, document scroll, and tab-strip scrolling remain independent.

Content-header icon actions share `PreviewHeaderButton`, a thin wrapper over Common `Button`: neutral ghost styling, `sm` sizing (13px icons and a minimum 24px square hit target), default corners, and bottom-positioned tooltips. The wrapper requires a localized title and does not expose size, icon-only, variant, tone, shape, or tooltip-placement overrides. Chat save, node tools, summary triggers, connected-node navigation, standalone node close, and URL external-open actions all use it. Callers retain refs, accessibility attributes, handlers, disabled state, and semantic selected-state classes, but should not override geometry. Header layout, portals, tab-strip controls, form buttons, and popup-content controls remain separate.

URL targets render through `UrlPreview`: a direct remote iframe with `sandbox="allow-scripts allow-forms"`, `referrerPolicy="no-referrer"`, and an always-visible external-open button. It has no same-origin, popup, top-navigation, preload, or interactive-view bridge privileges, even for a URL that redirects to the app origin. It does not use node ingestion, server fetch/extraction endpoints, reader artifacts, metadata requests, or iframe load/timeout failure detection. Sites can refuse framing or require storage, cookies, popups, or other unavailable capabilities; the external-open action remains usable regardless. Unlike node-backed `WebPreview`, this renderer intentionally has no reader fallback.

The URL toolbar uses a compact address surface with an emphasized host, subdued path, and truncation for narrow groups; the full destination remains available on hover. External opening uses `PreviewHeaderButton` with a localized tooltip and accessible name rather than a wide text action.

URL tabs are not eligible for the warm slot, and their cross-origin iframe scroll state cannot be read or restored. Switching away unmounts the iframe; reopening starts from the target URL rather than retaining hidden page activity or in-frame navigation history. Source Note and Chat tabs remain eligible for ordinary warm retention and scroll restoration.

Every mounted `ChatPanel` receives an explicit `ChatSession` and owning preview tab ID. There is no globally current Chat thread or Question replay pointer, so two groups can render independent conversations without sharing messages, drafts, bindings, attachments, settings, loading state, or stream control.

Chat and Canvas Ink submissions delegate to the same component-independent `agentTurnController`, which owns captured sources, save barriers, per-thread stream claims, event reduction, lifecycle settlement, typed retry, and durable acceptance. Closing or unmounting Chat does not own the stream; any mounted view of the same thread can stop it. A confirmed Stop applies its acceptance before releasing the local claim; when it confirms that no durable turn started, it instead rejects the pending acceptance observer so an Ink reservation becomes retryable. A transport-unknown or `stopped: false` result keeps the original stream and loading state alive as the reconciliation channel instead of making resubmission appear safe.

Dragging a Chat or Note block into an editable Note uses Milkdown's geometric drop position, while its fixed-position indicator is portalled to `document.body` so the Preview panel's compositor transform cannot rebase viewport coordinates in either split group.

PDF area capture routes directly to a Chat or Question conversation that is active in the group beside the PDF. When no conversation is visible beside it, the Canvas's canonical unbound Chat opens to the side and the capture is staged immediately as that thread's pending attachment. The explicit Send to Chat action always produces a thread-owned attachment; passive browser text selection remains a shared, temporary excerpt until sent, removed, or pinned to a Chat.

The composer unifies explicitly chosen context above its textarea, without a separate visible heading: a temporary excerpt first, thread-owned attachments next, an optional adjacent-node candidate next, and the Canvas selected-node count always last in both DOM and visual order. Excerpts and attachments retain an accessible "Included with your message" group; the unconfirmed candidate stays outside it, and the final count has its own accessible source label. Chips are 24px high and at most 160px wide, and wrap naturally instead of forcing horizontal scrolling. The source row has a 12px top inset and a 10px gap before the textarea. Included chips share a borderless, soft neutral background and muted text at rest; focus anywhere within the composer gives its border a blue highlight and subtle ring and changes included chips together to the same soft blue background and blue text. The unconfirmed candidate instead has a dashed border and transparent background at rest, on hover, and during focus; its text and border follow the composer's focus color. Chips have no decorative type icons or "Plus" prefix; long labels truncate, images retain a small thumbnail, and tooltips retain content previews. Chips use one leading action slot: a temporary excerpt has a Pin action, and a thread-owned attachment has a remove action in the same left-side position; there are no trailing actions. The temporary excerpt is included automatically even before pinning. Clicking or keyboard-activating its Pin/text area pins it to the current thread and replaces Pin with the remove action, so removing a temporary excerpt from the composer is a pin-then-remove flow. Pinning preserves the excerpt in the current thread while later browser selections can replace the shared temporary excerpt. Selected-node counts and hover labels come from the same `getAgentChatContext` tree used for submission, including Frame descendants and partial Sketch selections, deduplicated by node id and excluding the conversation's anchor recursively. This replaces the separate source count beside Send; it does not enumerate implicit history, memory, instructions, or spatial neighbourhoods, and does not change submission ownership or collection rules.

When a conversation is visible beside an ordinary node, its composer offers a compact source chip after the included-source group and before the Canvas selected-node count in the same wrapping flow. The chip displays a plus action icon and the truncated node title, without repeated Add text, and uses a dashed outline with no background to distinguish an unconfirmed candidate from included sources; its leading plus, tooltip, and accessible name describe the Add action. Confirming it replaces the plus action with the included attachment's remove action and the dashed outline with the shared filled surface. The attachment retains the candidate's display name, including the localized "Untitled" fallback for empty, missing, or non-string node labels. The composer uses equal horizontal padding so the source area and textarea share the same content edges. Confirming the chip stages a thread-owned source attachment that the prompt renderer emits as a structured node reference; switching the node in the adjacent group updates the unconfirmed candidate, while an already confirmed source remains attached to the thread. Nodes already included through Canvas selection or a confirmed node-reference attachment are not offered again.

Typing `@` at the start of the draft or after whitespace or opening punctuation opens a compact node picker above the composer. It searches titles on the current Canvas, with case-insensitive prefix matches before substring matches; an empty query lists all nodes. Email addresses and URL paths do not activate the picker. Rows reuse the canonical node icons and localized type labels. Arrow keys navigate, Enter or Tab confirms, and Escape dismisses without changing the draft; an empty result never causes Enter to submit accidentally. IME composition and non-collapsed text selections suppress the picker. Selecting a result completes the active token to plain `@Node title` text in place, preserving the surrounding sentence, and stages the same thread-owned node-reference attachment used by adjacent-node chips. Repeating a reference does not duplicate an existing node-reference attachment, while excerpts and uploads remain distinct. The text and attachment are deliberately independent: deleting or editing the plain mention does not remove its chip, and removing the chip leaves the sentence intact. Plain typed mentions without picker confirmation do not create attachments. This adds no full-content fetch, wire syntax, or new submission path; Canvas switching never offers nodes from a different Canvas.

Ordinary Question sessions retain `AgentConversationView`: presentation and owner identify the same active Canvas/node, and the owner carries the Question's `threadId`. History, reconnect, Agent turns, tools, lifecycle writes, binding, mode, and change records use that owner scope. Legacy World `nodeRef` sessions and source-reference resolution are removed. Space Preview scenes do not mount source Question conversations; the user enters the source Space to open one.

An authored Question node remains authoritative for persisted agent mode and fixed binding. A new selectable Question snapshots the browser-local recent conversational Agent unless the caller supplies an explicit binding; a missing or stale local external identity falls back to the first selectable external Profile. Existing Questions do not inherit later conversational, Utility Agent, or Canvas selection changes.

Attachment preview text is keyboard-focusable independently of its remove action, so pinned excerpts and uploads expose the same content tooltip on focus as on hover. Adding, pinning, or removing a source hands focus synchronously to that composer's retained textarea before the triggering control is removed, preserving the draft and native selection without scrolling. `ChatInput` owns this handoff through a source-action callback separate from `onCommit`; other internal controls retain their own focus, and the existing `focus-within` styles remain active only while focus is inside the composer.

The node mention picker preserves every match without a result cap. Matching partitions prefix and substring results in a single pass, preserving Canvas order within each tier. Its 28px rows use a fixed-height virtual window with eight visible rows and three overscan rows on either side; the active option remains mounted for `aria-activedescendant` even when scrolled out of view. Arrow navigation scrolls the selected result into view, and option position and total-count ARIA metadata describe the full result set.

## 5. Groups, tabs, and bounds

The workspace contains one or two horizontal groups. Each nonempty group owns one active tab, and only the active group receives group-scoped keyboard actions. The Split control is available with zero, one, or many tabs: it creates and activates an empty right group without moving or redistributing existing tabs. Both empty groups retain their tab strips and New Chat controls, with the localized message "No preview open in this group" regardless of group focus or fullscreen state; the message does not direct users to a Canvas that is unavailable in fullscreen. Empty groups survive persistence and routine validation. The panel host retains its lazy Chat seed for an empty single group but does not populate a restored empty split.

Pointer or keyboard focus inside a group's tab strip, content, or empty area makes it the active group, without adding a visual group-focus marker. Returning to the Canvas does not reset that destination. Double-clicking a node that is not already open uses the active group's transient slot; double-clicking an already-open node activates its existing tab and owning group, without moving or duplicating it. Other permanent tabs and the other group's transient slot are unchanged. A group's New Chat control explicitly opens in that group.

Tabs can be reordered within a group or moved across groups with pointer or keyboard drag sensors. Every drop delegates to the pure `moveTab` model action, which repairs ordering and active tabs while retaining an empty source group. Moving a tab activates its destination. The tab strip has no Move to other group or Merge groups controls.

Pointer dragging keeps a faded source placeholder in the tab strip, portals a labelled tab overlay to `document.body` so transformed panel ancestors cannot offset it from the pointer, and marks the resolved insertion edge of the hovered tab or the end of a group. Pointer hit testing first resolves the group tab-strip viewport under the pointer, then considers only that group's tabs; clipped, overflowing tab rectangles cannot steal a drop from another group or accept a drop outside their strip. Blank strip space, including an empty group's strip, remains a group-end drop target. Keyboard collision detection is unchanged. The visual marker follows the same destination semantics used by `resolveTabDropDestination`. Window blur and document hiding dispatch `pointercancel` through the pointer sensor's registered handler rather than calling only its completion callback, so pending and activated gestures both detach their movement and release listeners and clear click suppression through the sensor's normal cleanup. Releasing outside the Electron window cannot leave a tab in a stale dragging state or consume the next ordinary click after cleanup. The pointer activation distance remains 5px.

Closing an active tab selects the nearest remaining tab in the same group. Closing the final tab in either group removes that group and automatically returns to a single group; closing a non-final tab does not remove an intentionally empty neighbor. In split mode, an empty group's header exposes Close empty group, which removes only that group, preserves the surviving group's identity and tabs, and returns focus ownership to the surviving group. It does not collapse the outer panel. The sole remaining group cannot be closed this way, even when empty. Deleting the last live node in a group follows the same removal rule as closing its final tab. Closing the workspace's final tab still collapses the outer panel.

A transient tab is one reusable inspection slot per group. Opening another transient target replaces that slot; using its Pin action, double-clicking the tab, or committing a persistent mutation through its renderer promotes it in place. Moving a transient tab into a side group does not promote the moved tab; if that group already has a transient slot, the moved tab replaces the existing disposable slot. The model's internal merge action keeps the most recently active transient slot and drops older transient slots; it is not exposed as a UI control. Runtime topology changes report every implicitly removed tab before committing the new workspace so mounted authored editors can settle through the same lifecycle boundary as an explicit close; the store then clears tab-addressed focus and opening requests atomically with the topology update. Persistence repair has no mounted editor and only repairs the stored topology.

The tab context menu offers Close other tabs, Close tabs to the right, and Close all tabs in this group. Each command is anchored to the clicked tab's current group, even when that tab is inactive; right-side targets follow the current tab order and never include another group. Empty batches are disabled and skipped by menu keyboard navigation. The store resolves and closes the entire batch in one state update, settling removed authored tabs against the original workspace before clearing their runtime focus/opening requests. Empty-group cleanup follows ordinary close behavior, and closing the final workspace tabs collapses the outer panel once. These commands only close presentation tabs, not their underlying nodes or conversations.

When a close action removes the focused tab, menu item, or empty-group control, DOM focus returns to the repaired active tab, or to New Chat when the surviving group is empty. Focus already retained in another control is not moved. Closing the final workspace tabs hands portal-menu focus back to the panel before the host performs its normal Canvas focus handoff and collapse.

Permanent tabs are never closed automatically. A group may retain any number of permanent tabs; users close them explicitly, while transient browsing continues to reuse the group's inspection slot.

The activation sequence is an integer stored with the workspace rather than a wall-clock timestamp, making recent-target ordering deterministic in tests and persistence. Rendering also uses this sequence as the per-group LRU order for the single inactive warm slot; it does not add a second recency model.

Single and batch tab closing share one removal primitive: resolve the removed IDs, copy the tab record once, filter the affected group once, and repair its active tab and empty-group topology once. Batch computation is linear in the workspace's tab count; editor settlement and runtime-request cleanup still run before the single store commit.

## 6. Focus and opening position

Editor focus is a runtime-only `{ tabId, nonce }` request. Only the addressed active tab receives it, and its renderer consumes it after focus succeeds so remounting cannot replay stale intent.

Question conversation positioning is a runtime-only `{ tabId, position, nonce }` request where `position` is `last-user` or `bottom`. `MessageList` consumes an explicit request after history hydration and successful positioning. Ordinary Chat activation (warm switch, cold mount, close/reopen or opening after reload) defaults to the latest content in the recent-turn window, not an older saved offset. Each group supplies an activation identity that changes only when its active tab changes; repeated clicks on the active tab, other-group focus and ordinary rerenders do not reset the window. Explicit positioning and conversation-search navigation take precedence over the ordinary default. Search addresses the destination thread, reveals its cached turns, and suspends following/compaction. An explicit jump also pages older server history before resolving its source address; a recent-only match must not stand in for an older result. Paging stops on completion, cancellation, timeout, page error, or tab deactivation. Unavailable matches retain the localized failure hint instead of silently jumping to the first occurrence.

Activating a Canvas content match opens the node's transient preview and hands its normalized query and source address to the preview-local search store through a nonce-addressed navigation request. The input retains its raw spelling, but the streamed request, highlights, and handoff use the same trimmed query. Changing the effective query or filters invalidates old rows synchronously, before debounce, so an old row cannot activate under new input. Search opens previews with `focusEditor: false`, suppressing both a new Note editor-focus request and a stale request for the destination tab; ordinary Note opening retains its editor-focus behavior. This opens the find bar without focusing its input or stealing keyboard ownership from the Canvas search results. Canvas and preview queries remain independent after this initial handoff.

Preview search registers individual renderer owners rather than disposing by node ID alone. Only the current owner processes a handoff; registration release settles at a microtask checkpoint so StrictMode effect replay can renew the same registration without destroying a cold request. Disposing an old renderer cannot close a newer same-node owner, while final real disposal and node changes still close abandoned sessions. Completion consumes only the matching nonce.

Manual Next/Previous navigation also owns its adapter cancellation function. A replacement jump, query/session/renderer change, adapter replacement, or unmount cancels the old work; delayed completions must still match the active navigation identity, query, session sequence, renderer owner, and adapter registration before updating counters, highlights, or notifications.

Streaming result updates preserve the active row by its stable match key, including field regrouping that changes row indices. Query, scope, and node-type filter changes reset selection; appended results do not move keyboard focus to the first header. Renderer-local document boundaries exclude editor chrome without excluding searchable sibling surfaces in the Canvas or conversation root.

Content and conversation matches retain their raw-source ordinals for result ordering, but navigation uses `{ hash, offset, length? }`: a SHA-256 identity of the exact source segment and its original UTF-16 match span, including case-folding length changes. Server, DOM, and PDF scanners reuse the same literal matcher rather than treating lowercased-string offsets as original-source offsets. User prompts, quoted passages/comments, and assistant Markdown register their own sources; conversation navigation never treats a raw whole-thread ordinal as a rendered DOM ordinal. Markdown mapping reuses the shared GFM parser and projects visible leaf text. Milkdown verifies that projection against its ProseMirror document, maps text offsets through model positions into DOM positions, and verifies the resulting Range without changing the editor selection; node-view chrome cannot shift the address of a later paragraph. Other registered text surfaces require an exact DOM projection. Hidden link destinations, syntax, changed sources, ambiguous identical segments, and unsupported rendering transformations report unavailable rather than choosing another occurrence or switching to source mode. Note and Office Markdown use the same registration path. Sandboxed Web and media previews have no source-position bridge and therefore report unavailable for exact content navigation.

The scheduler waits for both asynchronous content and a laid-out Range. Scrolling uses the actual Range coordinates in each nested scrollable or clipping ancestor, not the height of its parent paragraph, and rechecks the viewport intersection before reporting success. Zero-size or still-clipped targets remain pending until layout is ready or the localized timeout notification fires.

Source hashing uses Web Crypto when available and a lazy-loaded SHA-256 implementation otherwise, preserving the server digest on supported ordinary-HTTP deployments. Original-span validation uses the shared whole-source lowercase matcher, including contextual Unicode mappings and complete-character expansion boundaries. Bounded Space `SEARCH` responses reuse the canonical Canvas match schema instead of duplicating the wire shape.

The literal matcher advances by the full folded query length only after accepting a complete-source-boundary match. Rejected expansion-boundary candidates advance by one folded UTF-16 unit so a later valid candidate is not skipped; accepted matches remain non-overlapping.

When a Note is already in raw Markdown mode, CodeMirror registers the unprojected source and a preview-local indexed adapter. Matching and counters use the complete editor document, including virtualized content. Navigation requests the exact source position through CodeMirror's scroll effect, then resolves and verifies the rendered Range without changing selection, content, focus, or editing mode. Markdown syntax and link URLs are visible matches in this mode; their unavailable behavior in rendered Markdown does not apply.

PDF search handoff waits for its indexed adapter to register with the current query identity rather than treating a pending or previous-query adapter as a DOM-only renderer. The adapter remains non-navigable until the document has loaded and text indexing has settled. Extracted pages and processed-page progress publish atomically, so readiness cannot expose a partial match list and consume a pending ordinal too early. Canvas source addresses are accepted only when their source hash and the complete whitespace-normalized Markdown projection agree with the PDF text index; otherwise exact navigation reports unavailable. Indexed page offsets map across text-layer spans, including inferred whitespace, and the adapter acknowledges completion only after the actual Range is visible. Out-of-range requests never clamp, and missing page occurrences never fall back to the first match.

Terminal PDF source/load errors settle the matching handoff immediately with the localized unavailable notification. Failures belong to their source, so a replacement source does not inherit an old terminal error. Adapter registrations expose a current-registration check; retired snapshots cannot process or complete a handoff while a replacement registration is propagating through React context. Waiting for adapter registration or indexing is also bounded by an eight-second readiness watchdog; unregistered or indefinitely loading adapters cannot leave the request pending forever.

Question `content` matches carry ordinals local to the plain-text node body, not the complete conversation. After revealing history, navigation scopes these ordinals to the unique user prompt whose complete trimmed content equals that body; prompt text has a dedicated DOM marker excluding quoted comments, skills, interpretation text, and attachments. Missing or ambiguous source prompts use the existing unavailable-match notification rather than selecting a different message. Conversation-tier matches use source identities and offsets instead.

DOM search handoffs wait for the requested occurrence instead of accepting the first match while asynchronous Markdown is still mounting. A missing requested occurrence uses the existing timeout notification rather than silently navigating to a different occurrence.

Preview find counters and Next/Previous use the complete searchable occurrence count. The shared text walker counts matches without allocating a Range for each one; the highlight layer independently caps painted ranges at 500 per preview surface. A result beyond that cap still shows its correct ordinal and navigates across the full result set; its active range replaces the last painted range so the destination remains highlighted without increasing the cap.

The shared CSS Custom Highlight registration merges ranges owned by all active search surfaces. Clearing or unmounting an inactive find bar removes only its own ranges, so a Canvas search or another preview cannot accidentally erase the current document's highlights.

Every scrollable Preview renderer uses a runtime cache: Chat keys by conversation-owner Canvas plus `threadId`, while ordinary nodes key by target Canvas plus `nodeId`. Chat remembers an intentional reading message and viewport offset without overwriting them on programmatic bottom navigation. When available on activation, Return to previous reading position reveals the cached target and restores it best effort, outside the activation path. An unavailable target is reported explicitly; this action does not fetch history solely for recovery or persist across reload. Live-to-history ID replacement can make an old bookmark unavailable. Prepending earlier content anchors the first visible message and compensates for bounded late resizing unless user input takes control. Note, PDF, Office, and Web reader renderers keep automatic offset restoration through the shared hook because the outer panel is intentionally non-scrolling. Hidden retained tabs ignore Activity-driven scroll events and Effect cleanup. The cache removes an offset after the final target is closed, replaced, or invalidated, and clears unreferenced offsets when a Canvas layout is deleted or evicted from the persisted MRU index.

Chat shows a localized Back to bottom action whenever the viewport is more than 50px from the bottom, independently of unread detection. The same action reads New message when new messages or an updated streaming tail arrive while reading above the bottom; prepending older history does not count as new output. Clicking the action and automatic bottom-follow use instant container-local scrolling, not smooth animation. The action is hidden only after measuring the viewport within the 50px bottom tolerance. Content and viewport ResizeObservers maintain bottom-follow through asynchronous Markdown, tool, attachment, font, and panel-size changes. Upward wheel/touch gestures and native scrolling pause following; returning near the bottom or clicking the action resumes it. Resize compensation does not pull a paused reader to the bottom or compete with older-page prepend anchoring. Inactive retained tabs do not perform this scrolling, and observers disconnect on effect cleanup. Native wheel and touch scrolling remain unchanged.

Inactive tabs never count as actively viewed, including a tab retained in hidden Activity. A Question is actively viewed only when its tab is the active tab of a rendered group and the outer right panel is expanded; this rule controls the Canvas open indicator and whether stream completion marks a result as viewed.

Composer focus is addressed by `threadId` through `panelStore`, so opening one Chat cannot steal focus through a request intended for another mounted Chat.

## 7. Persistence and validation

Workspace topology is local UI state stored under one versioned local-storage record per Canvas. Content, messages, drafts, stream handles, and resolved node data are not duplicated into that record.

The current Canvas layout is written synchronously before switching Canvas and by the consolidated `beforeunload` handler. Tab switching and ordinary topology mutations do not write storage immediately.

A capped MRU index retains workspace records for at most 50 Canvases. Evicting an old layout is non-destructive because the record contains presentation topology only.

Persisted input is parsed defensively. Invalid targets, dangling tab IDs, duplicate group references, invalid active IDs, excess groups, duplicate transient slots within one group, and malformed split values are dropped or repaired without preventing the remaining layout from loading. Duplicate transient slots keep the most recently active slot and drop the older disposable slots.

URL targets extend the existing version-1 record; no separate runtime overlay or storage namespace is introduced. URL strings are validated and canonicalized on restore, and malformed or cross-Canvas targets are rejected. Only the destination URL is persisted, not fetched content or in-frame history. Node deletion validation leaves URL and Chat tabs intact because neither target depends on a Canvas node.

After a command deletes nodes, the web post-effect validates the workspace against the committed live node IDs. Tabs targeting deleted nodes are removed and active IDs or empty groups are repaired by `validateWorkspace`.

Closing a Preview tab does not delete the Canvas node, stop a running turn, or remove server-side Chat history. Successful Canvas deletion calls `deleteWorkspace(canvasId)` to remove its layout and runtime scroll-memory ownership; unreachable layout records are also reclaimed when they fall out of the capped Canvas MRU index.

For repeatable Chat activation measurements, explicitly enable the test-only production playground with `VITE_CHAT_PERFORMANCE_FIXTURE=true pnpm --filter @huabu/web build`, then run `pnpm --filter @huabu/web exec playwright test --config e2e/chat-activation.config.ts`. The fixture feeds full cached rich-turn arrays into the real MessageList, uses Activity and the workspace retention selector, and distinguishes retained activation from cold remount. It checks mounted rows, cache-first expansion and conditional completion compaction. The same-build full-list/windowed comparison times the captured tab click through destination rows and Milkdown headings becoming ready, followed by one animation frame for a paint opportunity. Reports include raw samples and median/p95; this is not a compositor trace, composer-input measurement, real-user measurement or universal latency guarantee. Normal unflagged production builds do not expose this playground.

## 8. Layout and accessibility

PDF previews place compact zoom out / percentage menu / zoom in controls in the existing node-action header slot beside capture and highlight controls; zoom adds no separate toolbar row or document divider. The percentage opens the shared Common DropdownMenu with Fit width, Fit page and Reset to 100% actions, marks the active fit mode, supports keyboard navigation, and returns focus after a choice. Percentages are relative to the first page's natural PDF viewport width; Fit width is the default, while Fit page fits the first page's aspect ratio to the available viewport. Manual zoom is bounded to 25–400%. Enlarged pages support horizontal scrolling; reduced pages are centred. Each page shell reserves its final scaled dimensions, independently of the debounced canvas resolution, so virtualization, search navigation, text selection, normalized highlights and region capture share the same geometry. Canvas resolution increases after 400ms when enlargement exceeds 15%, and decreases when the displayed width falls below 75% of the rendered width.

In Chromium-based web and desktop surfaces, macOS trackpad pinch arrives as Ctrl+wheel and is consumed only inside the PDF preview, with the pointer as the zoom anchor. Ordinary two-finger scrolling remains native. Toolbar zoom anchors the viewport centre. Canvas-embedded PDF readers retain their existing fit-width behavior and pass modifier gestures through to Canvas. Zoom mode, custom scale and horizontal position use the existing runtime target-owned scroll-memory record alongside vertical position, survive tab unmount/remount, and are reclaimed with that record; they are not persisted across reloads. Saved PDF zoom is source-specific and is not applied to a replacement source.

The tab-strip fullscreen control uses Lucide `Maximize` / `Minimize` icons with concise localized tooltips and accessible labels: "Fullscreen" / "Exit fullscreen".

Tab tooltips use three visual levels within the existing Common Tooltip: a full, wrapping 13px semibold title; an 11px subdued metadata row combining content type and optional short status with a decorative separator; and an optional 11px lower-emphasis temporary-preview hint with extra spacing above it. Agent names and technical details are not repeated. The hierarchy does not alter other Common tooltips or the tab's accessible label.

Ordinary Chat tabs and Send to Chat controls use Lucide `MessageCircle`, matching the conversation glyphs in the playground studies. Question node-type icons retain the canonical `MessageCircleQuestionMark` from `nodeIcons.ts`; the custom Chat/Agent mode icons remain separate.

Before a focused side panel becomes inert on collapse, `MainLayout` transfers focus without scrolling to the Canvas container. In fullscreen, collapsing Layers transfers focus to the visible Preview container; collapsing Preview transfers focus to the persistent layout container while Canvas remounts. Collapsing a panel that does not contain focus leaves focus unchanged. This applies to both header controls and programmatic collapse requests.

`MainLayout` owns the resizable right overlay and mounts `PreviewWorkspace`; Canvas remains full-size beneath both side panels. The outer width may grow beyond half the layout for wide document browsing and is capped by the expanded Layers width plus a minimum 100px uncovered area; narrow layouts clamp the rendered panel widths. Both panels share a 220ms slide without resizing Canvas. Panel toggles and node preview opening never move Canvas, including when the target becomes obscured; explicit search and focus actions retain their own viewport behavior. The bottom Canvas toolbar is horizontally centred on the uncovered Canvas area above both panels, retaining its existing dimensions and bottom offset, but slides out and becomes inert only while a side panel owns focus or pointer interaction and overlaps the toolbar's expanded footprint. It returns when interaction leaves the panels or resizing clears the overlap. Panel surfaces isolate pointer, scroll, and Canvas keyboard handling, including during exit motion. Native scroll chaining remains enabled between descendants inside a panel so vertical wheel input over truncated or horizontal-overflow content can reach the renderer's outer scroller; overscroll containment applies at the panel root, where it prevents an exhausted internal scroll chain from reaching Canvas. The internal split ratio is clamped so both groups remain usable.

Preview fullscreen replaces the visible centre area with Preview Workspace and unmounts the Canvas subtree entirely. Canvas document and selection remain in `canvasStore`, while its locally persisted viewport is restored by `useInitialCanvasViewport` when Canvas remounts after fullscreen; unmounting also guarantees that React Flow portals and compositor layers cannot leak stale Canvas pixels into Preview. Exiting fullscreen is deliberately two-phase: `MainLayout` first paints the ordinary split layout with a Canvas loading placeholder, then remounts Canvas after that feedback has reached one frame, preventing synchronous React Flow construction from making the restore control appear unresponsive. The fullscreen Preview slot clips renderer overflow so content cannot cover the Layer List when that list expands and narrows Preview. The existing Layer List remains available at the left with its normal resize, search, rename, lock, reorder, disclosure, and accessible tree behaviour; unmodified primary activation opens supported node targets in both ordinary and fullscreen layouts, skips Canvas reveal while React Flow is unmounted, and expands Frame hierarchy without invoking Preview. Modifier clicks retain Layer List multi-selection semantics. When the list is collapsed, `MainLayout` renders the existing Canvas header as a narrow vertical rail containing only the Layer List expansion control. The last Preview group exposes fullscreen and restore controls, `Escape` restores the ordinary layout unless an inner control consumes it, and collapsing Preview also exits fullscreen.

The outer Preview resize handle and internal split separator each expose an 8px pointer target spanning both sides of a 1px idle rule. Both use a centred 4px blue highlight at 30% opacity on hover and 50% during resizing, without changing the hit target or content geometry. Preview content is clipped inside its wrapper so the outer handle's Canvas-side half remains hit-testable without allowing renderer overflow. Both controls capture the pointer and track movement on `window`; their blue feedback follows the actual resize gesture, including while the pointer leaves the handle, rather than relying on touch hover or CSS `:active`. Release, cancellation, lost pointer capture, or window blur ends the resize and clears its active feedback. The internal separator also supports keyboard resizing.

Each group uses the WAI-ARIA tabs pattern with a tablist, selected tab, labelled tabpanel, and roving keyboard focus. Only the focused group responds to group-level shortcuts; editable controls, search, menus, and media viewers keep ownership of their own keys.

Tabs use lightweight rounded pills: only the selected tab has a persistent subdued background, with no tab dividers or selected top rule. Width follows content up to 320px; inactive tabs shrink first, retaining at least four em of title space, while the active tab shrinks more slowly and retains six em. Icon, padding, gaps, and the Close control are budgeted separately. Transient tabs use the same width budget as permanent tabs; Keep Open lives in the text-only context menu rather than a separate Pin button. Titles truncate by available width rather than character count, and tabs never automatically collapse to icons. Once these minimum widths no longer fit, the strip scrolls horizontally. Activation, opening a new tab, and resizing the strip or active tab reveal the active item without replacing native scrolling.

Tabs retain full accessible labels. The common Tooltip wraps each tab so hovering its title or focusing the tab with the keyboard reveals the complete title and localized content type, including specific Office formats; URL tabs show the full URL, including its domain. Temporary previews additionally explain how to keep the tab. The active tab always shows Close; no tab shows a Pin button. On fine-pointer devices with hover, inactive tabs use the full title width instead of reserving an empty action rail. Close is positioned over the trailing title area and revealed only while hovered or containing keyboard-visible focus; a matching title fade prevents text from overlapping the control without resizing the tab or moving neighboring tabs. Hidden Close controls retain keyboard accessibility but do not receive pointer events. Active tabs and touch or other non-hover devices keep Close visible in the normal layout. Transient tabs remain italicized; their context-menu Keep Open action and double-click/double-tap promotion remain available.

The tab strip keeps native horizontal scrolling with a compact scrollbar rather than navigation arrows. Chromium, Electron, and WebKit use a 4px track with no scrollbar buttons; Firefox uses its native thin scrollbar. The track and thumb are transparent at rest; hovering the strip or keyboard-visible focus reveals the thumb, while pointer focus alone does not keep it visible after the pointer leaves. Only color changes on interaction, not scrollbar dimensions. The outer strip and expanded compact Canvas header are both 44px tall; only the Preview header has a subtle bottom rule, while the left header flows into the Layers controls without a divider. Preview pills are 28px tall, centered between 8px top and bottom margins, with an 8px corner radius and 8px inner horizontal padding; the strip's outer horizontal padding is also 8px. The compact native lane occupies the bottom margin rather than shifting the pills or their controls upward. Toolbar controls stay centered outside the scrolling area. In fullscreen, the 48px-wide left rail uses the same 28px control height and 8px top inset, aligning its Layers toggle with the Preview header controls at a 22px vertical center. The collapsed floating Canvas header retains its own dimensions; Layers search rows and Preview content headers are not part of this top-level alignment.

## 9. Integration rules

New user-visible node, URL, and Chat open paths must use the Preview Workspace actions rather than independently mutating panel, Canvas, and Chat presentation state.

Renderer code must treat targets as references and resolve mutable data at render time. Adding labels, node snapshots, conversation state, or derived resource keys to persisted tabs creates a second source of truth and is not allowed.

Code that determines visibility must inspect each group's active tab, not every tab in `workspace.tabs` or every mounted renderer, because one inactive renderer may remain mounted in hidden Activity.

Runtime intents such as editor focus, composer focus, and initial message position must stay outside the persisted workspace model and must be addressed to a tab or thread.

Document mutations remain in the Canvas command path. Preview Workspace may request settling or validation at lifecycle boundaries, but it does not directly author Canvas node content or topology.
