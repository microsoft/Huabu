# Canvas Zoom Rendering

> Authoritative rendering policy for nodes, frames, edges, labels, and interaction chrome while the canvas viewport zoom changes.
> Last updated: 2026-07-23

## 1. Scope and coordinate spaces

The canvas supports zoom values from `0.05` through `5`, with the shared bounds in [`apps/web/src/config/canvas.ts`](../../apps/web/src/config/canvas.ts) applied to React Flow and the custom pinch handlers.

Zoom-sensitive rendering uses two coordinate spaces deliberately. Canvas-space content participates in the viewport transform and therefore grows or shrinks with the canvas; screen-space overlays are positioned from transformed coordinates but retain stable physical size for controls or labels that must remain operable.

The governing rule is semantic priority rather than uniform scaling: structural geometry stays in canvas space, expensive content may switch level of detail, relationship and container labels defend readability, and interaction chrome remains usable.

## 2. Policy matrix

| Surface                                  | Coordinate/scale policy                  | Visibility policy                                                      |
| ---------------------------------------- | ---------------------------------------- | ---------------------------------------------------------------------- |
| Note, PDF, web node body                 | Canvas space                             | Switches between `full` and `minimal` LOD from screen-space width      |
| Other node bodies                        | Canvas space                             | Always full rendering unless explicitly added to the LOD configuration |
| Minimal node label                       | Canvas-space tiered typography           | Wraps and clamps inside the node; naturally scales with the viewport   |
| Frame body                               | Canvas space                             | Always full rendering                                                  |
| Frame label                              | Screen-space overlay                     | Collision-aware for nested frames; interaction can force reveal        |
| Edge path and markers                    | Canvas/SVG space                         | Always rendered; no zoom visibility threshold                          |
| Non-empty edge label                     | Canvas portal with bounded inverse scale | Always rendered; idle text clamps to three lines                       |
| Empty edge label                         | Canvas portal with bounded inverse scale | Mounted only while the edge is selected or the label is being edited   |
| Floating toolbars and selection controls | Screen-space interaction chrome          | Driven by selection/input state rather than a semantic zoom threshold  |

## 3. Node level of detail

[`SEMANTIC_ZOOM_CONFIG`](../../apps/web/src/config/semanticZoom.ts) opts `note`, `pdf`, and `web` into the two-level `full → minimal` pipeline. Unlisted node types remain `full` at every zoom. The `question` node deliberately does **not** use this binary boundary — it uses the continuous zoom takeover described in §3.1.

Participating binary types render the generic tier-sized title label in `minimal`.

PDF rendering has a second cost boundary in the expanded preview. The canvas node lazy-loads pdf.js only when it needs an uncached first-page thumbnail, while the expanded preview keeps a lightweight aspect-ratio placeholder for every page and mounts the expensive canvas and text layer only within one scroll viewport of the visible area. A six-page LRU retains recently visited renders to avoid churn during short reverse scrolls; older pages are unmounted so canvas memory remains bounded.

PDF in-preview search is independent of both the render window and canvas-wide search. Cmd+F inside an expanded PDF opens preview-local state; a two-worker background index extracts text and the true aspect ratio from every page without mounting its canvas. The result count becomes final when indexing completes; Next/Previous is held until then so concurrently indexed pages cannot renumber an active result. Navigation forces the target page into the render window, scrolls its stable placeholder into view, and then resolves the page-local occurrence after the text layer mounts. Its query, lifecycle, highlights, and navigation never open or mutate the Canvas Layers panel. Canvas-wide search can still find and open a PDF node, but it does not inject its query into the PDF preview, build the PDF page index, paint preview highlights, or navigate to an in-document occurrence.

[`useNodeLOD`](../../apps/web/src/hooks/useNodeLOD.ts) compares `nodeWidth × zoom` with a 150 px screen-width boundary. A 10 px hysteresis buffer means a full node must shrink below 140 px to collapse, while a minimal node must grow to at least 160 px to expand; retaining the previous mode prevents rapid switching near the boundary.

[`NodeWrapper`](../../apps/web/src/components/Nodes/NodeWrapper.tsx) keeps the full body and [`SemanticPlaceholder`](../../apps/web/src/components/Nodes/SemanticPlaceholder.tsx) in the same node shell so CSS can cross-fade the two render modes without changing geometry.

The minimal placeholder expresses hierarchy from node geometry, not title length. [`selectTypographyTier`](../../apps/web/src/config/semanticZoom.ts) uses the canvas-space representative size $\sqrt{width \times height}$ to select 32 px, 52 px, or 76 px typography; the resulting text still participates in viewport scaling.

Minimal labels wrap at word boundaries, break only an otherwise unbreakable token, and clamp to the smaller of six lines or the number of lines that physically fit the padded node height. They never continuously shrink to fit content.

AI provenance chrome is independently hidden when a node's screen width falls below 150 px. This threshold reduces non-essential detail but does not determine the node body's LOD mode.

### 3.1 Continuous zoom takeover (question node)

The `question` node uses a **continuous** zoom takeover instead of the binary boundary. The agent mark's SIZE is a continuous function of the node's on-screen width, so across a zoom the badge shrinks smoothly with the card it is pinned to — no discrete size swap, no one-shot tween, and every frame is the exact size for that zoom. A single `collapseProgress` value $t \in [0, 1]$ (smoothstep-eased) drives it:

The policy can be summarized as **zoom-driven mark size + fade-driven mark position + size-driven glyph detail**. These signals are deliberately independent: zoom width drives $t$ and therefore the diameter, the hysteretic stage hides or restores the card and carries the mark's corner → centre glide with it, and the final rendered mark size alone decides avatar versus dot.

Status chrome follows the same geometry: the structural Running, Approval, and Error outer-ring width and outward inset scale from the rendered mark size with crisp minimums and restrained maximums, while attention halos remain fixed screen-space emphasis rather than part of the ring geometry.

| $t$     | When (node on-screen width)           | What renders                                                                                                                                                 |
| ------- | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| $t = 0$ | width ≥ `TAKEOVER_START_WIDTH` (64px) | the sticky card **plus** the agent badge at the top-left corner; the badge scales together with the card (`BADGE_FRACTION` of the shorter on-screen side)    |
| $0<t<1$ | transition band                       | the badge continuously resizes badge → mark as the node shrinks                                                                                              |
| $t = 1$ | width ≤ `TAKEOVER_END_WIDTH` (24px)   | the card is gone and a centred agent mark stands in for it; the mark's **glyph** is size-driven — a full agent avatar down to `MARK_FACE_MIN` px, then a dot |

The readable endpoint diameter is $\operatorname{clamp}(0.28 \times \min(w,h), 30, 84)$ screen px. The collapsed endpoint is a gamma-$0.7$ curve of the shorter screen side bounded to 6–30 px, and the live diameter linearly interpolates between those endpoints by $t$. The final scope deliberately renders no collapsed title caption: the Agent mark is the complete minimal representation.

The mark's POSITION does **not** follow $t$. It is tied to the card's visibility and glides corner → centre over the same 200 ms the card takes to fade (`TAKEOVER_GLIDE_MS`, `useGlideProgress`). The reason is that edges are not part of this system at all: every edge terminates on React Flow's handle points, on the node's own border box, exactly as it does for every other node type at every zoom. The card is the only thing that makes that box visible — so the mark has to hang off the card's corner for precisely as long as the card is drawn, and stand at the centre those edges converge on for precisely as long as it is representing the whole node. A zoom-driven glide is out of step with the card on both counts: it strands the mark mid-flight over a card that is still there, and parks it at the corner of nothing once the card has gone, which is what made edges appear to point at empty canvas mid-zoom.

Making the mark meet the edges rather than the edges chase the mark is also what keeps this cheap: no edge component reads takeover state, so a collapsing node re-renders its own overlay and its own ports, and nothing else. The last of the gap — edges stop on the border box, the mark is a small disc at its centre — closes from the other side, in §6: the connect handles are laid out against the same blended rect the ports are, and re-measuring them walks React Flow's own endpoints in with the mark.

The card-body fade is the only discrete signal: a binary `data-lod-body` attribute derived from the same width via `resolveQuestionStage` (a two-value `readable` \| `collapsed` stage with hysteresis so it never flickers at the edge). It fades the node shell to zero opacity over 200 ms while intentionally retaining the invisible React Flow node footprint for canvas selection and double-click activation. The sticky's darker depth board hides immediately on collapse and returns only after the pale body finishes fading in, so it cannot flash by itself beneath the portal-rendered mark. That stage decides card-body visibility + chrome, and carries the mark's corner → centre glide with it; it never drives the mark's size, which comes purely from `collapseProgress`. The face ↔ dot fallback is likewise NOT a stage — it is size-driven inside the mark. A small, mostly type-agnostic engine drives it:

Because the geometry is exact every frame, the overlay simply re-renders at the new left/top/size as the canvas zooms — the badge glides and resizes smoothly with the gesture, with no discrete stage swap and no one-shot animation to feel abrupt. The engine's only interaction of its own is pointer-drag of the node (the collapsed mark hides the node's tiny footprint, so native React Flow node-drag can't reach it): a press that stays within the activation distance falls through as a plain click and the mark opens the conversation, while a press that exceeds it becomes a node-drag and its trailing click is swallowed so the two never conflict. ## 4. Frame and frame-label policy

Frame geometry always remains full canvas-space content. A frame does not use `SemanticPlaceholder` because its border and containment boundary are structural information even when zoomed out.

The editable frame name is different: [`FrameNode`](../../apps/web/src/components/Nodes/frame/FrameNode.tsx) sends it through the screen-space overlay owned by [`NodeWrapper`](../../apps/web/src/components/Nodes/NodeWrapper.tsx), positioned 24 px above the transformed frame top. Its `text-xs` typography therefore remains readable instead of shrinking with the frame.

Fixed screen-space labels can overlap when nested frame top edges converge during zoom-out. `FrameNode` compares the vertical screen-space gap to the nearest frame ancestor and hides the nested label below 22 px, with a 4 px hysteresis buffer around subsequent hide/reveal transitions.

The default collision priority preserves the outer frame as the zoomed-out structural summary. Selecting, hovering, or editing an inner frame force-reveals its label; when a selected descendant would collide, the conflicting ancestor label is suppressed rather than merely painted underneath it.

### Display priority

When frame labels collide, the higher-priority label wins:

1. Label currently being edited.
2. Label of a selected frame.
3. Label of a hovered frame.
4. Label of the outer frame.
5. Label of the inner frame.

The first three interaction states force the affected label to remain visible and use matching overlay layers in descending order. With no interaction, the outer frame wins because zoomed-out views prioritize structural context over nested detail; the inner label returns after sufficient screen-space separation.

Frame label width is capped to the transformed frame width with a 48 px usability floor. Overflowing names truncate visually while the input title retains access to the complete name.

`FrameNode` owns the hierarchy and collision policy because it is frame-specific. `NodeWrapper` remains generic: it converts node coordinates to screen coordinates, applies owner-provided semantic visibility and width, handles interaction reveal, and performs opacity/FLIP transitions.

## 5. Edge and edge-label policy

Edge paths, markers, and hit areas remain in the React Flow SVG layer and have no semantic zoom visibility threshold. Endpoints are React Flow's handle points for every node type at every zoom, including a node collapsed to its takeover mark — no edge component reads collapse state. What moves under a collapsing node is the handle, not the edge (§6).

[`LabelledEdge`](../../apps/web/src/components/Panels/Canvas/edges/LabelledEdge.tsx) renders editable relationship labels at the edge midpoint through `EdgeLabelRenderer`. Because this portal remains inside the zoomed viewport, the label pill applies a bounded inverse scale `min(max(1 / zoom, 1), 2.5)` so text defends readability while zooming out but neither shrinks on zoom-in nor grows without bound at extreme zoom-out.

Only the label pill is counter-scaled; its midpoint positioning wrapper is not transformed, so its anchor remains stable. Horizontal padding is divided by the same scale to avoid visually inflated whitespace.

A non-empty edge label is always mounted. Idle labels clamp to three lines, while hover, selection, or editing reveals the complete relationship. An empty edge label is omitted until its edge is selected, at which point the placeholder becomes available for editing.

The edge-label portal uses [`getEdgeLabelRenderZ`](../../apps/web/src/components/Panels/Canvas/edges/edgeZ.ts) to paint one layer above its SVG edge and both connected nodes. This lift applies only to the HTML label; unrelated nodes on higher layers and the SVG edge's normal stacking contract remain unchanged.

Inside a structured Frame, relationship labels also participate in layout through the shared edge-aware gutter plan. A label expands only the track boundary crossed by its edge; the solver reserves its bounded 120 px label extent plus 32 px of visual clearance at the same maximum `2.5×` inverse scale used by the renderer, so even the minimum viewport zoom retains roughly 16 screen px on each side. Unlabelled edges retain a smaller routing channel. Edges between two children of a **structured** Frame use mutually facing handles on the dominant endpoint axis rather than obstacle-avoidance handles that would route outside their containing Frame — the solver owns those positions and guarantees the children do not overlap. A `free` Frame makes no such guarantee, so edges between its children keep the general obstacle-aware router, as do edges between different containers.

## 6. Interaction chrome

Floating toolbars, resize controls, and similar interaction affordances use screen-oriented sizing so they remain operable across the zoom range. Their visibility follows selection, hover, editing, and input-mode state rather than node semantic LOD.

Structured Frame drop feedback answers "where will this land" with the layout itself rather than with a stack of explanatory overlays. While the dragged node hovers a `column`, `row`, or `grid` Frame, that Frame's existing children are moved live to the positions the solver projects for the pending drop, so the peers open a gap under the cursor exactly where the node will sit. This transient reflow is written onto the real nodes (see [`canvas-command-architecture.md`](./canvas-command-architecture.md#live-structured-drop-preview)), which keeps edges, handles, and the selection HUD in agreement with what is on screen — a purely visual CSS transform would desync all three. Peers animate with a short `transform` transition scoped to a `structured-reflow` class on the React Flow root, so the transition exists only while a structured drop is being previewed and is dropped entirely under `prefers-reduced-motion`.

With the reflow carrying the explanation, [`StructuredDropOverlay`](../../apps/web/src/components/Panels/Canvas/StructuredDropOverlay.tsx) is reduced to what the reflow structurally cannot say. First, a single mark on the spot the dragged node will occupy — the solver's projected position at the dragged node's own size, in every layout mode — because the node itself is glued to the cursor and so is absent from the peer motion. The masonry modes used to substitute a hand-computed insertion caret, which meant re-deriving the solver's intra-track spacing beside the solver: two implementations of one layout, free to drift, and a weaker answer than the footprint `grid` was already able to show. `kind` now only selects the treatment: a plain outline for `into-existing`, a dashed `+` plate for `insert-new`, which needs its own mark because a brand-new track displaces nothing and is therefore invisible in the reflow. Second, the Frame's track structure (`context.tracks`, plus `context.rows` for `grid`), drawn as one hairline per track boundary, a numbered chip per track in the Frame's margin, and a borderless wash over the targeted track. Peers only ever _imply_ the track grid: a column holding one short card and an empty column look alike, and a `grid` row that no peer happens to occupy is invisible, so "how many rows and columns are there, and which cell am I over" stays guesswork right when the user is aiming. Boundaries rather than per-track outlines because `n` tracks need only `n - 1` of them, and boxing each track — on both axes for `grid` — would stack a rectangle over every node, over the drop mark, and over the Frame's own border until the one rect the user is steering is lost in the thicket. The bands are drawn from the **simulated** layout, so they show the structure the drop produces rather than the one it replaces, and they are suppressed below two tracks, where there is no ambiguity to resolve. Peer boxes and swap-destination rects are gone entirely — each was a second geometry competing with the one the user is actually steering, and describing them cost a whole extra solver pass per drag tick. The overlay still projects the shared helper's canvas-space geometry into the screen-space HUD and never re-derives layout from DOM geometry, and the helper still delegates its decision to the same picker and solver used at commit, so preview and final placement cannot disagree.

Selection is necessary but not sufficient for chrome to appear. Two suppression layers sit above it, split by what they know about:

Node-level suppression lives in the [`NodeWrapper`](../../apps/web/src/components/Nodes/NodeWrapper.tsx) mount gate and answers "should _this_ node show chrome". A node's floating toolbar requires sole selection and additionally stands down while the node is being dragged, while a stroke-level (sketch) selection owns the surface, and while a create-connected gesture is pending. The last case covers the whole canvas, not just the source node: the connected-node picker asks what type of node terminates the new edge, which is a different question from what the selected node looks like, and answering both at once puts two unrelated control clusters on screen for one gesture.

Surface-level suppression lives in [`CanvasFloatingPopover`](../../apps/web/src/components/Common/CanvasFloatingPopover.tsx) and answers "should _any_ canvas floating surface show". Every floating canvas surface funnels through that component, so all of them inherit the same rules: hidden behind an app-wide modal backdrop, hidden when an expanded node or preview replaces the canvas, and hidden when the user is working in another surface entirely (chat panel, split-mode expanded node, layer panel).
A node collapsed to its takeover mark is the one case where chrome must not use the node's own rect. The footprint survives collapse — it stays selectable and keeps receiving pointer events — but it has faded to zero opacity, so a selection outline, floating toolbar, or port drawn against it frames empty canvas beside a mark it appears unrelated to. Everything therefore anchors to the mark's canvas-space bounding square, published per node by [`nodeCollapseStore`](../../apps/web/src/store/nodeCollapseStore.ts).

What chrome reads is `blendedMarkRect`, not the mark's raw rect: the mark is published as soon as it leaves the corner, while it is still gliding toward the centre, so adopting its geometry outright would drop every port, outline, and toolbar onto a circle parked at the card's corner. The published mark therefore carries both the glide `progress` and the node's own border box, and `blendedMarkRect` eases one into the other, arriving exactly as the card finishes fading and easing symmetrically back on the way in.

Both the mark's radius and its corner offset are a screen-px constant divided by `zoom`, and the glide `progress` multiplies them. That makes `progress` the one input in this system whose range is load-bearing: it is not merely an easing value but a multiplier on lengths that are already inversely proportional to a number as small as 0.02, and its product is written straight into a CSS offset. `useGlideProgress` therefore clamps at both ends, and `localMarkRect` clamps again at the point of use. It has to. The tween originally measured elapsed time by subtracting `performance.now()` from the timestamp React hands a `requestAnimationFrame` callback — two clocks with no guaranteed shared origin — and clamped only the upper end, so a negative elapsed time evaluated smoothstep outside its domain, where it diverges rather than saturating. The result fed the next run's starting value and never re-converged: `progress` climbed into the thousands, the handles were laid out $10^8$ units from the node, and React Flow faithfully measured committed edge endpoints there. The visible symptom was an edge leaving a collapsed question node for a point far outside the viewport, flickering back whenever a re-measure happened to catch a sane frame.

For the same reason the connect handles recompute their rect from the live zoom rather than reading the published one. HUD layers (`SelectionOutlines`, the floating toolbar, the hot-port overlay) paint in canvas space and can take `blendedMarkRect` directly, where a frame of lag costs a frame of lag. The handles cannot: React Flow measures committed edge endpoints from their DOM box, so a rect computed at a stale zoom would be wrong by the ratio of the two zooms rather than by a frame's worth of movement.

At the end of that ease the selection outline is a circle around the mark, the floating toolbar anchors above it, and the four connect ports sit on the square's edge midpoints — which are also the mark circle's cardinal points, so one rectangular formula serves both the readable card and the collapsed mark. The outline ends circular rather than following the rectangular convention the readable card uses, because `collapsedRadius` makes that square exactly as wide as the mark's disc: a circle hugs it with no gap, whereas any squarer corner exposes bare canvas that reads as a plate behind the mark. Resize handles are dropped entirely while collapsed — there is no visible card whose size they would describe.

Moving the ports is also what brings the **edges** in, and it is the only mechanism that does. A committed edge endpoint is React Flow's cached bounds for the handle it starts from, so laying the handles out against `blendedMarkRect` is already half the job — the missing half is that React Flow re-measures handle bounds only on demand. `NodeConnectionHandles` therefore calls `useUpdateNodeInternals` whenever the published mark changes, and the endpoints walk in with the ports onto the icon. This is deliberately the whole of it: no edge component reads collapse state, and no endpoint is ever computed anywhere but inside React Flow. Earlier attempts inverted it — having the edge lerp its own endpoint toward the mark, then project it onto a morphing footprint → mark boundary — and both put endpoints in places no drawn shape passed through, because the endpoint's target was moving on a different clock from the card the user was actually looking at. The re-measure is scoped to nodes that have ever published a mark, so a canvas of ordinary nodes pays nothing.

Collapsed port dots are painted through the same screen-space HUD as the aimed-at port's `+` rather than in the node. Opacity is inherited through compositing, so a dot inside the faded card cannot opt out of the fade: it would be correctly positioned on the mark and still invisible, leaving only the `+` to appear from nowhere as the pointer crossed a port. The split follows the rule the `+` overlay already established — the in-flow handle keeps hit-testing and edge geometry, the HUD copy is paint only.
That last rule resolves attention from the last deliberate interaction — a pointer press or a focus change — rather than from pointer position. The generic mechanism lives in [`useTrackAttention`](../../apps/web/src/hooks/useTrackAttention.ts); the canvas verdict is published through [`canvasAttentionStore`](../../apps/web/src/store/canvasAttentionStore.ts) so consumers far from the canvas page can read it without prop drilling. Hover is the obvious signal and the wrong one: sweeping the cursor across a panel en route somewhere else would blink chrome out and back, and defending against that needs grace timers that make the chrome feel laggy in return. Press/focus is discrete and sticky — chrome disappears exactly once, when the user commits to another surface, and returns as soon as they click into the canvas again. Selection itself is never cleared by this, so returning resumes where they left off.

Surface ownership is expressed in the DOM. The React Flow wrapper carries `data-canvas-root`. Chrome that portals to `document.body` is outside every surface subtree, so it carries `FLOATING_CHROME_PROPS` ([`floatingChrome.ts`](../../apps/web/src/components/Common/floatingChrome.ts)) and interactions inside it are **neutral** — they leave the current verdict untouched instead of counting as a move. Marking such chrome as belonging to one specific surface would be wrong twice over: a toolbar would vanish under its own pointer if unmarked, and a chat-side popover marked as canvas would drag attention back to the canvas. Neutrality gets both right, and it means a colour picker portalled out of a toolbar (`FloatingToolbar.ColorPicker`) has to be marked too, not just the toolbar root.

The same arbitration governs the note editor's selection toolbar ([`MilkdownFloatingToolbar`](../../apps/web/src/components/Milkdown/MilkdownFloatingToolbar.tsx)), which does not go through `CanvasFloatingPopover` because it is anchored to a text selection inside one editor rather than to a canvas rect. A ProseMirror selection survives blur, so "there is a selection" would otherwise keep the toolbar floating over the chat panel or an app-wide modal long after the user left the note. Its boundary arrives as a `surfaceRef` prop rather than being read off the editor: the surface is the whole note preview, including sibling overlays such as the provenance accept/reject controls, so scoping it to the editor mount alone would make accepting an AI edit dismiss the toolbar.

The bottom-left viewport controls display the current canvas zoom as a compact multiplier rounded to one decimal (`1×`, `0.8×`, `1.9×`) for orientation across wheel, pinch, shortcut, and button-driven zoom. Its tooltip and accessible label retain the exact integer percentage. Clicking the multiplier animates the viewport back to 100%; this value describes viewport scale only and does not report a selected node's dimensions. The multiplier sits after fit-view and before the interactivity lock; the custom-positioned lock mirrors React Flow's native toggle by changing node dragging, connection, and element-selection state together.

Viewport restoration is local and keyed by canvas ID. When no local or legacy viewport exists, the first mount fits all nodes through bounds computed from React Flow absolute positions with persisted `style.width` / `style.height` fallbacks. This avoids the native `fitView` failure mode where `onlyRenderVisibleElements` leaves every offscreen node unmeasured and the initial fit silently resolves to an empty rectangle. During this asynchronous first fit, the React Flow surface remains hidden behind the standard loading overlay and is revealed only after `fitBounds` settles, preventing a transient paint at the default viewport. Cached viewport restoration and genuinely empty canvases skip this overlay.

Ctrl-modified wheel events use the custom cursor-anchored path in [`useCanvasGestures`](../../apps/web/src/hooks/useCanvasGestures.ts). Small trackpad deltas retain a `0.02` exponential sensitivity for responsive pinch gestures, while the effective absolute delta per event is capped at `10`; this keeps a discrete mouse-wheel notch near a 13% zoom change instead of allowing a multi-fold jump. Two-finger touch pinch remains distance-based and is unaffected by this cap.

Selection outlines are rendered as canvas-level HUD overlays instead of changing node order. The HUD outlines nodes that are selected or actively dragging, so a Ctrl/Cmd press before pointer-down may retain its normal toggle-selection semantics without making the dragged node lose its blue movement feedback; once the drag ends, an unselected node's outline disappears. During a Frame transaction the HUD builds the same transient future node tree as React Flow before resolving nested absolute coordinates and sizes, so a selected child stays aligned when its source Frame fits or its structured ancestors reflow. Zoom never promotes a selected node in the content stack; node and edge stacking remains governed by the policy in [`web-architecture.md`](./web-architecture.md#6-node--edge-stacking-z-order).

Zoom-invariant and counter-scaled chrome should be bounded. New overlays must not use unbounded `1 / zoom` scaling at the minimum zoom, and non-essential chrome should prefer a screen-space visibility threshold when it would obscure semantic content.

## 7. Extension rules

Add a node type to `SEMANTIC_ZOOM_CONFIG.nodeLOD` only when its full renderer is expensive or unreadable at small screen size and a meaningful minimal representation exists. Node geometry and persisted data must not change when LOD changes.

Use screen-space overlays for controls and short labels that must remain readable or clickable. Use canvas-space typography for content whose size should communicate hierarchy and naturally recede during zoom-out.

Every new fixed-size label needs an explicit collision policy, width bound, and interaction priority. Raising `z-index` alone is not a collision policy because it only chooses which overlapping text paints last.

Route every new floating canvas surface through `CanvasFloatingPopover` rather than portalling it directly, so it inherits the surface-level suppression rules instead of growing a parallel set. Add a new app-wide suppression reason there (or, for modals, to `useAnyGlobalModalOpen`); keep reasons that depend on which node is involved in the `NodeWrapper` gate. Chrome that legitimately cannot go through it — anchored to a text selection rather than a canvas rect, say — should still reuse `useTrackAttention` and mark its portalled roots with `FLOATING_CHROME_PROPS`.

Use hysteresis for any visibility or render-mode threshold that can be crossed continuously during wheel or pinch zoom. Keep threshold ownership with the feature that defines the semantic policy; generic portal components should accept resolved visibility rather than infer feature hierarchy.

## 8. Space Preview rendering

`spacePreview` keeps its outer node in host Canvas space but renders the target through a bounded static SVG and an independent local viewBox. Preview-local zoom never changes host React Flow zoom. Distant previews suspend their SVG renderer through `IntersectionObserver`; nested preview sources render only an inert placeholder. See [space-preview.md](./space-preview.md).
